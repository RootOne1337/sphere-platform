Это конечный canary одного устройства, а не приёмка VPN для всего парка.

## Область и защита

PH030 имеет только Android user 0. Новый guard plan 5 охватывает UID
`10000–10059` и `10061–99999`; точный UID Sphere `10060` исключён.
Проверены IPv4/IPv6 UID routing rules, обе FILTER-цепочки, blackhole default
и соответствие session ID. При активном туннеле IPv4 разрешён только через
его TUN; IPv6 приложений блокируется, поскольку исходный WG1-конфиг IPv4-only.

При паузе отсутствует обход через обычный default route: запросы диагностического
процесса с UID игры по HTTPS IPv4, HTTPS с DNS и HTTPS IPv6 не проходят.
Запрос с UID Sphere проходит. Это подтверждение проверенных правил и конечных
проб, а не доказательство защиты системных сетевых служб или поведения после reboot.

На установленном сайте проверены авторизованные события, свежий отчёт PH030,
версия `1.2.86-dev`, область «Все приложения, кроме Sphere» и состояние
«Пауза · трафик заблокирован». Интернет и внешний IP этим экраном не объявляются
подтверждёнными.

## Что не заработало

Обычный WG1 на Android получил начальный handshake, но HTTPS по IP и имени
не прошёл. Native RX в сохранённом активном замере составлял только 92 байта;
в дальнейшем журнал содержит повторные handshake initiation без завершения.
Явная привязка curl к правильному TUN-адресу также не помогла. Chrome был открыт
на `https://2ip.ru/`, но загрузка страницы и внешний IP не подтверждены.

Тот же клиент ранее проходил независимые HTTPS/DNS-пробы с ПК, чей underlying
path проходит через существующий VPN. Это разные сетевые пути. Фильтрация
обычного WG — возможное объяснение, но проверка не установила точную причину.

Выполнен один клиентский compatibility A/B без изменения сервера, ключей и
области: `Jc=4`, `Jmin=40`, `Jmax=70`, `S1=S2=0`, стандартные `H1/H2/H3/H4=1/2/3/4`.
Он не дал успешного HTTPS на PH030. Это не AWG 3.1 сервер и не доказательство
полноценной маскировки. Описания такого клиентского режима есть у
[WG Tunnel](https://www.wgtunnel.com/docs/android/tunnels/);
[Amnezia](https://docs.amnezia.org/documentation/amnezia-wg/) отдельно описывает
необходимость согласованных параметров и отличия обычного WG от AWG.

## Ограничение дальнейшего теста

В выданном API обнаружены уже работающие `awg1` и `awg2`; `awg1` при чтении
не имел peers. Для переноса единственного тестового клиента сначала была
отправлена адресная DELETE только собственного `sphere-ph030-20261022` из `wg1`.
API вернул HTTP 403 / `FORBIDDEN_DELETE`: выданному ключу запрещено удаление.
Удаление не выполнено. AWG peer после отказа **не создавался**; серверы,
их параметры и upstream-привязки не менялись.

Пользователю предложен выбор: разрешить один дополнительный AWG-клиент для той
же PH030 с выключенным прежним WG либо самостоятельно удалить прежний peer.
До ответа зависимая операция создания остановлена. Ошибка доступа не обходится
другим endpoint или транспортом.

PH030 оставлена `PAUSED_GUARD_HELD` для широкого режима. Sphere доступна;
приложения не получают автоматический выход через исходный IP. Временный
Android diagnostic binary удалён, временный nginx relay восстановлен.

Открыты: рабочий Android egress, проверка IP в браузере, системный DNS и
делегированные network services, reboot, дополнительные Android users/profiles,
длительная работа и production executor/leases. Общая production-приёмка не закрыта.
