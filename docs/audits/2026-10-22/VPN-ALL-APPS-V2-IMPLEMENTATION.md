# VPN всех приложений, кроме Sphere: кандидат v2

22 октября 2026. Исходники основного изменения: `f5b2b1d608341ad97279a88a34cb69c5e77a93c9`.
Это **не квитанция установки APK86 и не приёмка внешнего VPN**.
Установлены APK85 на четырёх online устройствах, UI `46dd02ff`, API `cd2431e2`.
[Машинная квитанция этапа](VPN-ALL-APPS-V2-IMPLEMENTATION.json).

## Реализовано

- Раздельные закрытые профили: v1 `selected_apps`, v2 `all_apps_except_control`.
  v2 не допускает списков включения, произвольных исключений и переключения на
  legacy-root. Зашифрованная команда сохраняет v2; downgrade отклоняется до
  изменения сети. Вход v1 с ранее необязательным `mode` сохранён.
- Android Builder использует либо allowed packages v1, либо точное исключение
  собственного package v2. Повторная проверка UID/shared UID предшествует TUN.
  Основной процесс, `:vpn`, media/control и native UDP принадлежат UID Sphere;
  транспорт дополнительно проходит `protect()`. Общая настройка proxy в ОС не
  используется. `allowBypass()` не включается.
- Guard plan 5 хранит точные UID-диапазоны с исключением owner UID. Это покрывает
  приложения, установленные позже, без перечисления текущего каталога пакетов.
  Обе IP-семьи блокируются до TUN; pause сохраняет защиту. Plan 3/4 читаются по
  прежнему контракту, их нельзя переинтерпретировать как диапазоны.
- Ротация не меняет область, IPv6 или исключённое приложение. Для смены scope
  нужен отдельный переход; нельзя назвать такую смену обычной ротацией peer.
- Веб предлагает одинаковый выбор области для одного файла и пакета до 100
  профилей. Скрытые package ID не попадают в v2. Изменение области аннулирует
  предыдущую проверку; каталог не придумывает количество «всех приложений».
- `trafficMode` добавлен к runtime-отчёту Android/backend/веба. Отчёт старого APK
  без поля остаётся неизвестной областью. Это не вывод из имени игры или профиля.

## Точные границы

Первый кандидат: Android API 26–32, основной user 0, обычный owner UID 10000–19999.
Другие users, shared UID самого Sphere и Android 13+ отклоняются. Guard покрывает
UID 10000–99999 кроме Sphere. Системные службы UID 0–9999 не блокируются этим
guard: защита DNS/DownloadManager, делегированный system traffic, SDK sandbox и
reboot требуют отдельной физической приёмки. Нельзя обещать защиту каждого
пакета буквально всего Android при такой границе.

`disconnect` по-прежнему означает явное снятие защиты после точного подтверждения
закрытия TUN. Остановка с сохранением блокировки — `pause`. Публичный apply и
production capability остаются выключенными; исходники не являются основанием
запускать не принятый режим на всём парке. Переход старого guard PH030 не выполнен.

## Документация и опыт других проектов

Android штатно поддерживает исключение приложения из VpnService; allowed и
disallowed списки одного Builder несовместимы. Это основа маршрутизации, но само
исключение не доказывает kill switch после смерти сервиса.
[VpnService.Builder](https://developer.android.com/reference/android/net/VpnService.Builder)
и [Android VPN](https://developer.android.com/develop/connectivity/vpn).

В upstream Amnezia есть отдельное обсуждение обхода per-app VPN через привязку
сокета к TUN. Авторы тестовых исправлений также описывают задержки при lookup
владельца потока в reader thread, ошибки кеширования verdict и UDP-потери.
Это полезные сценарии приёмки; сторонний тестовый форк не внедрён и не считается
доказательством причины нашего зависания.
[Issue 2457](https://github.com/amnezia-vpn/amnezia-client/issues/2457).

Есть сообщения о застывшем туннеле после сна при продолжающемся статусе Connected.
Наш PH030 зависает в активном ограниченном HTTP-тесте; переносить эту причину на
него нельзя. Правило интерфейса остаётся прежним: handshake, данные, HTTP/DNS и
egress IP имеют разные подтверждения.
[Issue 3255](https://github.com/amnezia-vpn/amnezia-client/issues/3255).

Проверен официальный релиз SDK `v3.1.20260814`; именно этот pin уже используется.
Описание релиза не является исправлением наблюдаемого plain WireGuard профиля
пользователя и не превращает его в конфигурацию AWG 3.1.
[Upstream release](https://github.com/amnezia-vpn/amneziawg-android/releases/tag/v3.1.20260814).

## Следующая физическая проверка

Независимый `tools/vpn-netstack-probe` собирается в CI без VPN-конфига. Он создаёт
WG/AWG и gVisor только в памяти, без Windows adapter, routes и firewall. Приватный
вход подаётся через stdin; вывод ограничен результатами трёх HTTP/HTTPS/DNS
проверок, egress IP и native counters. Программа не запускается одновременно с
другим клиентом того же ключа. Даже успех host probe не доказывает готовность
Android v2: физический путь хоста и Android могут различаться.

После получения настроенного APK86 отдельная ограниченная проверка должна
подтвердить работающий HTTPS/DNS/UDP, прямой Sphere, новую установку приложения,
pause/crash/revoke и отсутствие прямого egress. Текущая блокировка PH030 при этом
не снимается ради неподтверждённого повторного применения.

## Один внешний peer WG1: выполнено

По прямому указанию пользователя прочитаны список серверов и публичная
[OpenAPI провайдера](https://wg1-api.leetproxy.com/openapi.json). Создан ровно
один peer на существующем сервере `wg1`: `sphere-ph030-20261022`. Сохранён один
профиль в зашифрованном каталоге Sphere; на Android он ещё не применён.
Конфиг обычного WireGuard содержит IPv4, без AWG-параметров. Дополнительные
серверы, туннели и аккаунты не создавались. Identity/port/subnet/tunnel `wg1`
после теста совпадают с исходным состоянием; API-key и конфиг в Git не попали.

Независимый probe собран и проверен в GitHub run `39807557326`, исходник
`a7011ed0`, SHA исполняемого файла связан с artifact digest. Он выполнен локально
сначала с прежним пользовательским конфигом, затем с одним новым peer. Между
опытами движок закрыт; параллельного использования одного клиентского ключа нет.

| Проверка в in-memory netstack | Прежний профиль | Новый WG1 peer |
| --- | --- | --- |
| HTTP по IP | Ответ 301 за 236 мс | Ответ 301 за 264 мс |
| HTTPS по IP | Таймаут 8000 мс | HTTP 200 за 304 мс |
| HTTPS с DNS | Таймаут 8000 мс | HTTP 200 за 381 мс |

301 — полученный HTTP redirect, а не подтверждение содержимого trace endpoint.
HTTPS использует штатную проверку сертификата. В обоих опытах Windows routes,
Android guard и Sphere control session сохранились. Процесс завершился; исключение
Windows Firewall оператором теста не создавалось. Windows показал стандартный
запрос для UDP-listener; пользователю предложено отменить входящее разрешение.

Это локализует различие профиля/peer/внешнего пути: TLS-сбой старого профиля
воспроизводится без Android и без игры, а новый peer проходит те же запросы.
Опыт не доказывает конкретную серверную ошибку и не заменяет Android/Game test.
Хост при этом остаётся в своей существующей сетевой среде, включая VPN пользователя.

### Границы будущего адаптера провайдера

- API `POST peers` не объявляет idempotency key. После неопределённого ответа
  нельзя повторять создание; нужна сверка по единственному сохранённому имени.
- `rotate` или смена `server/tunnel` меняет выход **всего WG-сервера**, следовательно
  может затронуть других peers. Эти операции для теста не вызывались. Нельзя
  выдавать их за независимую ротацию одного Android-устройства.
- Выдача конфига возвращает private key: только backend secret storage и sealed
  delivery, без browser storage, URL query, логов и массового повторного экспорта.
- Один peer должен иметь одну активную аренду на устройство. Конфиг нельзя
  копировать на весь парк: WireGuard endpoint roaming будет менять получателя.
- OpenAPI использует общий `APIResponse`; будущий адаптер должен проверять
  `success` и фактическую форму `data`, а не трактовать любой HTTP 200 как успех.
- WG/AWG, назначение выхода, leases, rollback и статистика — разные capability.
  Существование AWG endpoints не доказывает версию протокола или его приёмку.
