# AUD-99: автоматическое восстановление сети станции

**13 сентября 2026 · High / operational availability · исправление подтверждено
для двух LDPlayer 9 на текущем Windows-стенде.**

[Исходный инцидент](LDPLAYER-NAT-INCIDENT.md) ·
[Установка и диагностика](../../operations/LDPLAYER-NETWORK-RECOVERY.md) ·
[Готовность](../../operations/READINESS.md)

## Root cause и исходное доказательство

Второй APK не подключался при запущенной VM: у её `LdNatNetwork1` отсутствовал
`VBoxNetNAT.exe`, а `VBoxNetDHCP.exe` продолжал работать. Start NAT завершался
`DHCP server already running`. APK не может исправить процесс Windows изнутри VM;
обновление приложения и смена адреса сервера этого состояния не устраняли.
Исходная причина завершения NAT пока неизвестна.

Первый адресный repair из AUD-99 восстановил две APK, но требовал оператора.
Автоматического host supervisor на станции не было: проверка планировщика перед
установкой показывала только `Sphere-Publisher-pilot-20260911`. Этот follow-up
автоматизирует **подтверждённый** путь ремонта, сохраняя его ограничения.

## Fix и affected files

- [ldplayer_network.py](../../../scripts/ldplayer_network.py): общий thread/OS lock
  для manual/automatic repair, проверка других running VM перед вмешательством,
  отказ при неполной process identity и распознавание timeout. PID, creation time,
  command line, executable и отсутствие NAT проверяются перед остановкой DHCP.
- [ldplayer_watchdog.py](../../../scripts/ldplayer_watchdog.py): один ограниченный
  цикл, явный allowlist, две последовательные missing-NAT observations, cooldown,
  атомарная запись попытки до ремонта, 50 последних событий и отказ при повреждении
  состояния. Максимум один ремонт за цикл; отсутствующая/выключенная VM не запускается.
- [Install-LDPlayerWatchdog.ps1](../../../scripts/Install-LDPlayerWatchdog.ps1) и
  [runner](../../../scripts/Invoke-LDPlayerWatchdog.ps1): задача Windows текущего
  пользователя, скрытая, Limited, раз в минуту и при входе. Встроенная проверка
  конфигурации перед установкой; чужая задача не перезаписывается.

На этом ПК установлена **`Sphere-LDPlayer-pilot-20260911`**, только indices **0, 1**.
Локальные конфигурация/состояние: `.local-pilot/station-network/config.json` и
`status.json`. PC-agent сейчас не является условием работы этого восстановления;
его backend credentials не создавались. APK, серверные образы и Docker topology
не изменялись этим исправлением.

## Native reproduction → automatic repair → verification

Контрольный сценарий 12 сентября 2026, 22:17–22:19 UTC (13 сентября по времени ПК):

1. Проверены актуальные task status и настоящие команды обеих APK; сохранены PID.
2. По точным executable/command line/creation time выбран и остановлен **только**
   NAT второго LDPlayer. DHCP оставлен живым, `missing_nat` воспроизведён.
3. Первый APK продолжает отвечать; его первый echo во время отказа — **0.609 s**.
4. Без ручного запуска repair планировщик записывает первую missing observation.
   Следующий штатный минутный запуск восстанавливает выбранную сеть.
5. NAT обнаружен через **106.91 s после fault**. Первая проверенная команда второй
   APK проходит через **108.12 s после fault** / **1.22 s после обнаружения NAT**.
   Интервалы измерены внешними probes, это не точная длительность внутреннего reconnect.
6. **12/12 команд**, по 6 на устройство с различными IDs и markers, проходят.
   PID обоих APK и NAT первой сети неизменны. Safety fallback в `finally` не
   понадобился; APK не перезапускались и их данные не сбрасывались.

[Структурированное native evidence](evidence/ldplayer-automatic-recovery-20260913.json).
Готовность нового стека после drill: **9 healthy services**, HTTP readiness 200;
старый Compose project этим сценарием не изменялся.

## Regression tests и стоимость проверки

**56 passed** на Windows, включая actual OS locks между потоками/процессами,
долговечный cooldown после аварийного выхода, неисправный диск, повреждённый state,
CIM timeout, stopped/shared VM, PID reuse, конкурентный repair, неполные identities,
очередность ремонта и проверку PowerShell installer с подменой scheduler cmdlets.
53 переносимых случая выполняются в Linux backend CI; 3 installer cases требуют Windows.

Во время разработки тесты выявили и предотвратили два дефекта кандидата:
сброс grace при длительном непрерывном наблюдении и скрытие degraded соседа после
успешного ремонта. Оба исправлены до включения автоматизации.

Три здоровых цикла на двух VM: **0.688 / 0.968 / 0.719 s**, без ремонтов.
Выборочный peak RSS дерева Python/дочерних команд: **123.48–124.25 MiB**.
Постоянного процесса нет; запуск раз в 60 s. Замер с шагом 25 ms может пропустить
короткий пик и не учитывает общий Windows WMI provider, VM и OS. Это не benchmark
нагрузки сотен устройств. Отдельный тест 100 здоровых fake instances подтверждает
один CIM snapshot и отсутствие per-VM detail queries, но не runtime capacity.
[Методика и замеры](evidence/ldplayer-watchdog-resources-20260913.json).

## Residual risk

- Реальный интернет/DNS/серверный отказ или зависший **живой** NAT не запускает
  этот repair. Не исправлена первопричина первоначального завершения NAT.
- Требуется вход Windows-пользователя; reboot/logoff и массовый старт не приняты.
  Компонент установлен на текущем ПК, не автоматически на удалённых станциях.
- На пилоте один ремонт за минутный цикл. При массовом отказе нужно измерить
  допустимую параллельность и приёмку 10/64/100 устройств; текущие два не доказывают её.
- Статус пока локальный, интеграция свежих событий в PC-agent/backend/UI открыта.
  Старый `status: ok` без свежего `checked_at` не считается подтверждением работы.
- Проверка topology отражает наблюдаемое состояние. Не перенастраивайте сеть VM
  одновременно с ремонтом; сторонние VBox-инструменты не используют наш lock.
- Независимый ingress/discovery source, сквозной DAG из UI, VPN и физические
  телефоны остаются отдельными критериями общей приёмки.
