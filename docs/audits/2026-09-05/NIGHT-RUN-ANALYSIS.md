## Что фактически исполнялось

Успешный маршрут содержит 13 шагов: start, переменная, HOME, 500 ms ожидания,
открытие шторки, 1,500 ms ожидания, закрытие, инкремент, Lua-условие, echo,
проверка значения, Android SDK, end. Вторая ветка условия предусмотрена, но
ночью не исполнялась. Сам DAG занимал **2.422–2.915 s**, p50 2.620 / p95 2.796 s.
Остальное время двухминутного цикла — просмотр, диагностика и ожидание.

Проверено **9 из 32 типов действий**, включая технические start/end/sleep.
Это перечень задействованных типов, не процент покрытия кода. Tap, swipe, scroll,
поиск элементов, ввод текста, screenshot, HTTP action, launch/stop app и остальные
неисполненные типы перечислены в JSON evidence. Ошибочные ветки, retry, timeout,
конкурентная отмена Android-узла и отказы сети/БД в этом профиле не проверялись.

Шторка видна лишь около полутора секунд раз в две минуты, поэтому её легко
пропустить. **Отдельный контроль 17:14** выполнил ещё два задания через Sphere,
а read-only ADB сохранил 28 PNG. На обоих просмотрены HOME → открытая шторка →
HOME; действия видимы. Игры не запускались. Эти два задания и кадры отделены от
ночных counters и не доказывают визуальное состояние каждого ночного цикла.

## Реальные дефекты по приоритету

### AUD-119 — High / P1: журнал APK блокирует длительную работу даже после ACK

**Root cause:** [CommandJournal.kt](../../../android/app/src/main/kotlin/com/sphereplatform/agent/commands/CommandJournal.kt)
хранит подтверждённые receipts семь дней и допускает максимум 512 entries.
`acknowledge` сокращает payload, но не освобождает entry. Следующий `claim`
удаляет лишь достаточно старые подтверждённые записи, поэтому 513-е свежее
задание блокируется `command_journal_capacity_exhausted`.

**Reproduction:** настоящий CommandJournal с in-memory adapter для prefs:
512 × claim→complete→acknowledge, затем новый экземпляр класса и следующий claim.
[Сохранённый probe](probes/AuditAcknowledgedCapacityProbeTest.kt) падает именно
с capacity_exhausted; JUnit 1 failure, ошибок setup нет. Probe лежит вне обычного
passing suite до реализации исправления. Это воспроизведение класса, не перегрузка
живых APK 513 заданиями. На текущей нагрузке около 30–33 задач в час порог
достижим примерно за 15.5–17 часов с пустого журнала; при более частых задачах — раньше.

**Fix: открыт.** Простое удаление старейшего ACK или очистка данных APK сократит
dedup guarantee и может повторить действие. Следующий шаг — отделить durable
pending results от компактного индексированного хранения receipts, сохранить
явную политику retention и учесть миграцию существующих APK. Приёмка: больше 512
подтверждённых задач, replay старого ID без исполнения, pending без потерь,
restart/миграция/ошибка записи, bounded memory. До этого continuous farm не принят.

### AUD-120 — High / P1: Task Engine скрывает задачи и выдаёт неполные показатели

**Root cause:** [tasks/page.tsx](../../../frontend/app/%28dashboard%29/tasks/page.tsx)
вызывает `useTasks({per_page:100})` без серверной страницы. Поиск, статус, сортировка,
Total Tasks, Success Rate и страницы по 25 вычисляются только на полученной сотне.

**Evidence:** API до отдельного visual control вернул total **174**, на странице 1
100, на странице 2 ещё 74, без пересечения IDs. В браузере deployed frontend
показал Total Tasks **100** и 1/4 страницы. После двух visual tasks вырос фактический
набор, но UI всё ещё 100. Более ранние failures могут исчезнуть из поиска/статистики;
это механизм дефекта, не утверждение, что конкретные скрытые 74 были ошибочными.

На этой же странице подтверждены другие неверные представления:

- `priority > 0` отображается как `CRON`; наши ручные priority-5 задания подписаны CRON.
- Active Pipeline — постоянный текст `No active pipeline running`, запрос pipelines отсутствует.
- New Workflow не имеет обработчика; реальный click не дал диалога или перехода.
- Next 60s — график от времени создания задач, а не прогноз планировщика.
- List polling каждые 10 s обычно может не застать running у DAG длительностью 2.6 s.
  Это ограничение наблюдения, а не отсутствие выполнения.

**Fix: открыт.** Нужны серверные pagination/filter/search и честные агрегаты по
выбранному набору; отдельные реальные источники статуса pipeline/очереди. Для
неизвестного происхождения задач нельзя угадывать CRON. Regression: >100 задач,
ранняя failed-задача, server page 2, фильтр по всей истории, loading/error вместо
ложных нулей, функциональная кнопка workflow. Бэкенд уже отдаёт page/total;
нужна согласованная реализация, а не увеличение лимита до новой случайной цифры.

### AUD-118 — Medium / P2: краткий reader lock прерывает harness

Настоящая Windows file-sharing проверка воспроизвела отказ `Path.replace`.
Исправлено **`b8e0d0b`**: ограниченный повтор только local replace, шесть попыток /
310 ms; постоянные ошибки остаются ошибками. **2 failures → 18 passing tests**,
включая native reader close. [Root cause, evidence, residual risk](SOAK-WINDOWS-SNAPSHOT.md).
Это не доказывает, что исходный ночной PermissionError возник именно здесь.

### AUD-121 — Medium / P2: интерактивные ответы загрязняют журнал SQL-задач

Во всём ночном окне **1,555 `task.result.not_found`**, ровно по числу интерактивных
команд. UUID предупреждений не пересекаются со 164 завершёнными native task IDs.
Остальные warning/error/critical в структурированных строках не найдены.

Причина: `_request_interactive_command` в
[devices/router.py](../../../backend/api/v1/devices/router.py) выдаёт UUID без SQL
Task; [handle_command_result](../../../backend/api/ws/android/router.py) после
публикации ответа пытается сохранить любой terminal UUID как Task. Нужен явный
контракт интерактивных ID и durable task IDs, сохраняя сигнал для настоящих
неизвестных task results. **Fix открыт**, blanket suppression не выполняется.
Приёмка: shell/logcat без SQL task lookup, обычный task/ACK и его replay работают,
действительно неизвестный task не исчезает из диагностики.

## Что ограничено или ещё не доказано в самом Engine

- `AdbActionExecutor` для key/tap/swipe пишет в persistent root stdin и возвращает
  после flush, без чтения exit code. Для этих примитивов success означает delivery,
  а не доказанное UI-действие. Shell action имеет другой путь выполнения.
  Нужен отдельный exit/visual acceptance; нулевой `duration_ms` HOME не означает
  физическое выполнение за 0 ms.
- Один node output обрезается после 2,048 символов; whole terminal receipt более
  64 KiB заменяется коротким `result_truncated=true`, без прежних node logs.
  Ночные results около 1.3 KiB и не проверяют этот порог. Large-result retention
  и предупреждение в UI остаются отдельной приёмкой; это не потеря текущих 13 шагов.
- Live log UI оставляет последние 100 entries, final logs приходят из Task.result.
  Журнал не является полным event trace всех попыток. `nodes_executed` отражает
  сохранённые logs, а не универсальный счётчик внутренних действий вложенных loop.
- Android допускает максимум 500 nodes, 500 routing hops, nesting depth 10;
  у loop logs отдельный cap 200. Backend разрешает циклы с timeout, поэтому
  «будет крутиться пока не истечёт timeout» не гарантируется: раньше может
  сработать hop limit. Граничные циклы/large output этим soak не принимались.
- Pause/cancel pipeline на границе delay не доказывает остановку исполняющегося
  root subprocess. GET stream status остаётся worker-local (ранее открытый риск).

## Исправление прежней трактовки waves

Волна размера 1 ограничивает **подачу задач**, не число одновременно исполняемых.
31 из 39 wave-size-1 пар пересекались; медиана разницы started_at — 2 ms.
При wave-size 2 пересекались все 39. `BatchService` ждёт между публикациями,
но `TaskService` забирает очередь периодически (5 s), и обе задачи могут попасть
в один dispatch tick. Даже идеальная задержка 1 s меньше длительности DAG 2.6 s.
Поэтому прежнее описание «последовательное и параллельное выполнение» неверно:
проверено чередование **размеров подачи**, не strict serial concurrency. Само
по себе это не доказательство дефекта waves; для max-in-flight=1 нужен отдельный
контракт и тест. Задержка queue/dispatch влияет на старт задания, а не на ping APK.
