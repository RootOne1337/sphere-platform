## Инцидент и причина

Цикл 107 остановился **до создания нового batch** на 20-секундном ожидании
SPS/PPS/IDR в `Runner.open_viewer`. Первый viewer успел пройти готовность;
таймаут относится ко второму устройству.

В 01:37:11 UTC backend зарегистрировал второго зрителя и доставил
`viewer_connected`, но доставки `start_stream` в этом интервале нет.
В Android-журнале также есть только запрос ключевого кадра. Предыдущий захват
был остановлен после цикла 106. Перезапуска APK или нового native crash нет.

Анализ выявил два воспроизводимых дефекта одного пути:

1. `PubSubRouter._listen_loop` использовал блокирующий `listen()` с общим
   Redis `socket_timeout=5`. При обычном отсутствии команд redis-py пересоздавал
   здоровое соединение. Между disconnect и resubscribe live-команда могла попасть
   в канал без подписчика. Это не обязательно создаёт исключение в приложении.
2. `VideoStreamBridge.register_viewer` игнорировал `False` от отправки
   `start_stream`. Зритель оставался зарегистрированным; следующий запрос
   ключевого кадра не запускает уже остановленный encoder.

На изолированном Redis с production-настройками соединение сменилось с ID 118
на 120 за 6,3 секунды простоя. Отдельный тест с настоящим нулём подписчиков
подтвердил незакрытый viewer. **Оба regression tests упали до изменения кода.**
Эта цепочка согласуется с ночными журналами; точный Redis connection ID и
число подписчиков в момент ночной отправки прежний код не сохранял. Поэтому
автоматический Redis reconnect как причина именно той отправки — обоснованная
гипотеза, а два дефекта кода подтверждены независимым воспроизведением.

## Исправление и проверка

- Командный reader использует `get_message(timeout=1.0)`: истечение времени
  ожидания Pub/Sub возвращает управление, не уничтожая здоровую подписку.
  Обработка настоящего разрыва, backoff и восстановление всех каналов сохранены.
- Отказ первоначальной отправки захвата вызывает cleanup viewer и закрытие
  WebSocket с **1013**, которое существующий web-клиент обрабатывает восстановлением.
  Добавлен `stream_start_unavailable` с device/session для расследования.
- Нет слепого повтора команды и отложенного запуска захвата через offline queue.

**105 связанных тестов прошли** на изолированных PostgreSQL/Redis: idle connection,
нулевой subscriber count, частичное/повторное восстановление подписок, доставка
между workers, tenant boundaries, RPC, video routing и освобождение viewer.
Тестовые receivers для дополнительных устройств теперь действительно подписаны
на командные каналы; offline viewer больше не используется как успешная фикстура.

Затронуты `backend/websocket/pubsub_router.py`, `stream_bridge.py`, новый
`tests/production/test_stream_start_delivery.py` и связанные recovery/video fixtures.
[Regression evidence](evidence/stream-start-regression.json).

Повторить две регрессии можно командой
`pytest tests/production/test_stream_start_delivery.py -q --no-cov` с
`SPHERE_RUN_INTEGRATION=1` и `POSTGRES_URL`/`REDIS_URL`, направленными на отдельные
тестовые сервисы. Эти production-тесты используют disposable fixtures;
адреса рабочего стенда для них не подходят.

## Границы результата

Изменение кода и 105 тестов не являются новой восьмичасовой приёмкой.
Установленный backend прошёл ограниченную проверку выше. Требуется новый конечный прогон.
Старую ночь нельзя продолжить или переименовать в passed.

Redis Pub/Sub остаётся недолговечным: subscriber count не подтверждает выполнение
на APK. Отказ после PUBLISH и до Android требует клиентского восстановления;
delivery ACK для capture controls здесь не добавлен. Прогон не доказывает
готовность сотен устройств, физических телефонов, VPN или независимого ingress.
