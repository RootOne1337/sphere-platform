# AUD-126 · Один просмотр вытесняет другой на том же backend worker

**20 сентября 2026 · High / P1 · исправление установлено и принято на двух APK.**

## Эксплуатационный дефект

При открытии нескольких окон одного устройства backend сохранял только последнего
зрителя на каждом worker. Первый WebSocket продолжал отвечать на ping, но его
задача отправки видео отменялась. Закрытие последнего окна удаляло подписку worker,
хотя прежние окна оставались открыты. Они не получали последующие кадры.

Это потеря живого изображения без падения APK. Она воспроизводится независимо от
AUD-125 и не объявляется установленной причиной таймаута второго устройства в
ночном прогоне. Восьмичасовая приёмка по-прежнему не пройдена.

## Доказательства до исправления

- На изолированных PostgreSQL/Redis **три теста упали**: оба порядка закрытия двух
  зрителей и подключение медленного зрителя после быстрого. Первый зритель не
  получил единственный опубликованный кадр за две секунды.
- На установленном backend `8a6b30e` открыты три последовательных WSS-просмотра
  каждого из двух APK **1.2.7 / 10207**. Каждый сначала получил SPS/PPS/IDR.
- После подключения всех трёх открытие и закрытие шторки Android дало прирост
  кадров **0 / 0 / 11** на первом устройстве и **0 / 0 / 7** на втором.
- После закрытия новейшего зрителя оба оставшихся получили **0 / 0** новых кадров;
  после закрытия старейшего — **0** у оставшегося. Все шесть этапов не прошли.
- Обе контрольные echo-команды успешны, API показывает online, PID **2182 / 2187**
  и crash buffers не изменились. Это не обрыв связи с APK и не новый native crash.

Действия выполнялись через проверенный signed discovery route и API/WSS нового
стенда. ADB использовался только для чтения PID/crash/projection. Игры, APK,
backend и старый стенд во время исходного воспроизведения не менялись.
Сырые журналы и credentials остаются приватными.

## Root cause и fix

В `backend/websocket/stream_bridge.py` четыре реестра были индексированы только
по `device_id`: socket, session, queue, send task. `register_viewer` отменял
прежнюю задачу и перезаписывал реестр, не закрывая прежний browser socket.
Старое session fencing защищало новый просмотр от cleanup старого, но не
обеспечивало одновременную доставку обоим.

Теперь устройство содержит отдельные `ViewerSession` по session ID:

- У каждой сессии своя ограниченная очередь и задача отправки. Неизменяемые байты
  кадра используются совместно. Лимиты **50 кадров / 8 MiB** и write timeout
  **5 секунд** сохраняются для каждого зрителя.
- Redis-подписка открывается для первого локального зрителя и снимается после
  последнего. Проверка наличия зрителей на других workers и grace stop сохранены.
- Открытие и закрытие сериализованы отдельным lock устройства: запоздавший
  unsubscribe не удаляет подписку нового зрителя. Ожидание сети одного устройства
  не блокирует регистрацию другого. Неиспользуемые locks не накапливаются.
- Ошибка записи, отмена/отказ регистрации и cleanup сессии затрагивают только её.
  Отказ первоначального capture control по-прежнему не принимается как успех.
- Shutdown закрывает все локальные сессии и запрещает новые. Drop ratio считается
  по сумме полученных/отброшенных кадров оставшихся локальных viewers.

## Regression

**112 связанных tests passed** на изолированных сервисах. Семь новых сценариев
в `tests/production/test_stream_multi_viewer.py` проверяют независимое закрытие,
медленного/оборванного зрителя, отказ второго start, конкурентное закрытие/открытие,
шесть зрителей на одной подписке, восстановление Redis и shutdown.
Существующий тест настоящего WS handler теперь требует кадры в обоих окнах до
закрытия одного; прежняя проверка только сохранности нового окна была недостаточна.

Затронуты bridge и fixtures/assertions в `test_stream_video_routing.py`,
`test_stream_start_delivery.py`, `tests/test_ws/test_stream_bridge.py`.
Повторить новые случаи: `pytest tests/production/test_stream_multi_viewer.py -q --no-cov`
с `SPHERE_RUN_INTEGRATION=1` и отдельными disposable PostgreSQL/Redis.
Не направлять этот harness на рабочие базы.

[Машиночитаемая регрессия](evidence/stream-multi-viewer-regression.json).
Локальный mypy с установленными runtime dependencies сообщил две существующие
ошибки `Redis | None` в неизменённом `redis_client.py:50–51`; это не зелёная
локальная проверка типов. Статус source CI и установленной приёмки фиксируется отдельно.

## Остаточный риск и следующая проверка

Сама передача H.264 не доказывает декодирование браузером, качество изображения
или fleet capacity. Ни один из этих коротких сценариев не является новой ночью.

Память ограничена на viewer, но общий admission limit зрителей не введён.
Redis Pub/Sub не подтверждает выполнение capture control на Android.
REST stream status/drop ratio остаётся локальным для worker. Независимый ingress,
полный новый восьмичасовой прогон, физические телефоны, VPN и сотни устройств
требуют отдельной приёмки.
