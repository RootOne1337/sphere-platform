# AUD-97: после отказа Redis переставали доставляться команды и события

**Severity: High · эксплуатационная доступность · 12 сентября 2026.**

Исправлены повторные подписки в backend. На новом стенде после 30-секундной
недоступности Redis первая команда дошла до установленного APK через **9.47 s**
после возврата Redis; затем прошли ещё **12/12** команд. Сохранились процесс APK,
его identity и WebSocket-сессия. Во время восстановления backend не перезапускался.
Это единичное измерение на одном эмуляторе, без гарантии времени восстановления парка.

## Причина и затронутые файлы

- [PubSubRouter](../../../backend/websocket/pubsub_router.py) переносит команды
  из Redis в WebSocket устройства, которым владеет другой backend worker.
- [EventsManager](../../../backend/api/ws/events/router.py) переносит события
  организации из Redis в уже открытые WebSocket-соединения браузера.

Оба listener при сетевой ошибке создавали новый PubSub и один раз пытались
восстановить подписки. Если Redis ещё недоступен, `subscribe()` выбрасывает ошибку.
Вложенный обработчик её записывал, но возвращал управление в обычный listener:

1. При сбое первой подписки `subscribed == False`: listener бесконечно ждёт
   появления подписок, не пытаясь восстановить существующие каналы.
2. При сбое второй подписки `subscribed == True`: listener может бессрочно
   получать сообщения только первого канала. Остальные устройства/организации
   теряют доставку, хотя процесс и его подключение остаются живыми.

Наличие здорового Redis или HTTP readiness 200 поэтому не доказывало работу команд.
При нескольких Gunicorn workers HTTP shell возвращал 503 из-за отсутствующего
подписчика, а веб мог перестать получать новые события.

## Воспроизведение до исправления

Baseline backend `a22fb54` совпадает с backend на `b76d225`.
На новом project `sphere-pilot-20260911` Redis приостановлен на **30.3 s**, затем
восстановлен. Логи фиксируют `PubSub reconnect failed` и `EventsManager reconnect
failed`, после чего успешной повторной подписки нет. Первые **5** настоящих shell
запросов после возврата Redis получили 503.

Ограничение исходного harness: последующие попытки каждый раз повторяли login и
получали ошибки авторизации после достижения лимита. Они **не используются** как
доказательство длительности отказа командного канала. Повторный harness получает
access token один раз до fault injection.

[Детерминированные regressions](../../../tests/test_ws/test_pubsub_recovery.py)
дали **6 failed / 2 passed** до fix. Сценарии первой, частичной и многократно
неуспешной подписки падают для обоих listener; два контрольных случая ошибки close
работали и до изменения.

## Минимальное исправление

Listener сохраняет признак незавершённого восстановления. Повторное создание
соединения и **всех** сохранённых подписок выполняется в основном защищённом цикле.
Любая ошибка оставляет восстановление незавершённым; listener не переходит к
обычному чтению сообщений или ожиданию пустого набора каналов.

Прежняя задержка повторов сохранена: 1, 2, 4, 8, 16, максимум 30 секунд; успешная
обработка сообщения сбрасывает задержку. Частично восстановленное соединение
закрывается перед следующей попыткой. Формат команд, токены и данные APK не менялись.

## Проверки после исправления

**77 passed / 7.39 s / 1 существующее deprecation warning**:

- 8 случаев восстановления: первая/частичная подписка, ошибка close, повторный
  отказ с достижением максимальной задержки; доставка и маршрутизация по организации.
- [2 интеграционных случая](../../../tests/production/test_pubsub_recovery.py):
  после инъекции ошибок реальные Redis subscribe ACK и publish возвращают доставку
  существующему получателю команд и событий, без его повторной регистрации.
- Соседние PubSub/events, cross-worker interactive commands и presence recovery.

Команда из подготовленного isolated test environment:

```text
python -m pytest tests/test_ws/test_pubsub_recovery.py tests/test_ws/test_pubsub.py tests/test_ws/test_events.py tests/production/test_pubsub_recovery.py tests/production/test_interactive_command_routing.py tests/production/test_presence_recovery.py -q --no-cov
```

Production-directory fixtures требуют `SPHERE_RUN_INTEGRATION=1`, loopback Redis
и отдельную PostgreSQL БД с `audit` в имени; [настройка](../../../tests/production/README.md).
Ruff затронутых файлов прошёл. Локальный Windows mypy с полным набором установленных
зависимостей сообщает 13 ошибок в 7 других, неизменённых файлах; это не объявляется
успешной проверкой. Проверка нового PR head в Linux CI учитывается отдельно.

## Runtime после исправления

Новый backend image установлен только в `sphere-pilot-20260911`. Установка образа
завершена **до** повторного fault injection. Затем:

1. Получен один операторский token и успешно выполнен baseline echo.
2. Проверены Compose project/service и ID нового Redis; только он paused на **30.22 s**.
3. Реальная scheduled publisher task отклонила нездоровый route и сохранила signed
   mirror/journal. Redis гарантированно unpaused в `finally`.
4. Первая команда после возврата Redis прошла за **9.47 s**; четыре предыдущих
   попытки получили честный 503. Ещё 12 команд завершились с ожидаемым выводом.
5. PID APK, device identity, подписанный cache v8 и WebSocket session остались
   прежними; новых регистраций — 0. Backend ID/start time не менялись внутри drill.
6. Scheduled publisher вернулся к unchanged v8. Все 9 сервисов — healthy.

[JSON evidence: before, after, состояние сервисов](evidence/pubsub-redis-recovery-20260912.json).
APK: `0f1410e`, SHA-256
`3fea6b1be345bec99a71e1926a386dd070c361887d875d5b46a7c18d83d0d36b`,
`com.sphereplatform.agent.pilot.debug`, один Android 9/API 28 emulator.

Чтобы повторить native drill, подключите именно тестовый APK, сохраните его PID,
device ID, signed cache и Redis presence `ws_session_id`, выполните baseline shell.
После проверки labels приостановите **только выбранный тестовый Redis** на 30 s
с обязательным `unpause` в `finally`. Тем же token повторяйте безопасный `echo`
через `/api/v1/devices/{id}/shell`, затем сверяйте identity/session и отсутствие
backend restart. Не используйте `FLUSHALL`, старую установку или production Redis.

## Остаточные риски

Redis Pub/Sub не хранит потерянные сообщения: события во время отказа не
воспроизводятся этим fix. Задания требуют своего durable journal/receipt пути.
UI snapshot/resync после пропуска событий — отдельная приёмка; здесь доказано
возобновление событий через реальный Redis, но не полный browser UI сценарий.
Redis restart с потерей памяти, длительный partition, сотни клиентов и failover
между Redis nodes этим 30-секундным pause не покрыты. Многопроцессная доставка
зависит от Redis, а [независимый внешний ingress](DISCOVERY-CDN-FRESHNESS.md) остаётся открыт.

Старый Sphere не выбирался ни одной изменяющей командой. При сравнении общей
инвентаризации отдельно сохранён ранее наблюдавшийся restart старого tunnel
16:42:38 UTC с неизвестной причиной; это произошло до обоих Redis drills.
