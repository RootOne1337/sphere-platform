# AUD-99: второй LDPlayer работал без процесса выхода в сеть

**Severity: High · локальный эксплуатационный инцидент · 13 сентября 2026 (UTC+5).**

Пользователь сообщил, что одна свежая APK подключается, а вторая не подключается
после перезапуска приложения и эмулятора. После восстановления сети оба устройства
работают одновременно. Причина наблюдавшегося отказа — отсутствующий NAT process
второго LDPlayer при продолжающем работать DHCP. Дефект discovery/auth APK этим
инцидентом не установлен; исходная причина завершения host NAT process неизвестна.

## Evidence / reproduction

Первичный осмотр 12 сентября с 18:34 UTC:

- `ldconsole list2` и `VBoxManage list runningvms`: running `leidian0` и `leidian1`.
- ADB видит только `emulator-5554`; `ldconsole adb --index 1` сообщает отсутствие
  `emulator-5556`. Это диагностический симптом, а не транспорт Sphere.
- `showvminfo leidian1 --machinereadable`: VM running, `nic1=natnetwork`,
  `nat-network1=LdNatNetwork1`, cable on.
- Процесс NAT существует только для `LdNatNetwork0`. DHCP существует для обеих
  сетей; вторая имеет lease `172.16.1.4`.
- `natnetwork start --netname LdNatNetwork1` не исправляет состояние:
  `Cannot start DHCP server because it is already running`, PID 35376.
  Попытка штатного stop/start также оставила этот DHCP и не запустила NAT.

После адресного завершения **только** подтверждённого DHCP второй сети повторный
`natnetwork start` запустил её NAT. Эмуляторы не выключались, APK не менялись,
дополнительные публичные порты не открывались. LDPlayer сам восстановил свой ADB
forwarding; это не настройка внешнего канала Sphere.

Последующий осмотр обоих APK подтвердил одинаковый актуальный SHA-256:
`3fea6b1be345bec99a71e1926a386dd070c361887d875d5b46a7c18d83d0d36b`, package
`com.sphereplatform.agent.pilot.debug`, сборка `0f1410e`, подписанный cache **v8**.

| Эмулятор | Model, проверенная командой на устройстве | Device ID | Первая параллельная команда |
| --- | --- | --- | --- |
| 0 / emulator-5554 | V2266A | `85f2f935-7739-400e-9389-0d71227e8f0a` | 200, верный marker, 0.672 s |
| 1 / emulator-5556 | HD1910 | `ba1346c1-1581-452f-adee-451d36622aaf` | 200, верный marker, 0.719 s |

Переустановка, сброс credentials, ручной ввод endpoint или UI reconnect для этого
ремонта не выполнялись. Время первичного восстановления не объявляется SLA:
между первым ремонтом и итоговой проверкой была пауза в работе задачи.

## Fix и сохранённый regression

[scripts/ldplayer_network.py](../../../scripts/ldplayer_network.py) добавляет
read-only проверку и явный `--repair` для одного running экземпляра. Exact
VM/network/executable/process identity checks ограничивают исправление; здоровый
NAT не перезапускается. Успех означает только наличие NAT, а не работу приложения.

[15 tests](../../../tests/test_ldplayer_network.py) прошли: чужие сети и сходный
индекс `10` не выбираются при `1`, сменившийся DHCP и конкурирующий NAT не
останавливаются, stopped VM/иная сеть/неверный binary отклоняются. Ошибка старта
не превращается в сообщение об успешном восстановлении. Ruff включён в backend CI.

Повторный native drill 12 сентября 21:53 UTC:

1. Сначала подтверждены рабочие команды на обоих APK и сохранены их PID.
2. Для воспроизведения остановлен только NAT второй сети; её DHCP оставлен живым.
   Новая read-only утилита правильно сообщает `missing_nat`, `dhcp_running=true`.
3. Первый APK во время отказа второго выполняет echo за **0.500 s**.
4. После 15 s паузы новая утилита в `finally` восстанавливает выбранную сеть.
   Первый запрос второму APK получает честный 503; следующий проходит через
   **6.08 s после возврата из repair**, с правильным marker.
5. Ещё **12 параллельных команд**, по 6 на каждый APK, проходят. PID обоих APK и
   процесс NAT первой сети сохранились. Повторный `--repair` здоровой сети — no-op.

## Residual risk

Это подтверждение двух работающих эмуляторов и одного способа восстановления
конкретного сетевого сбоя. Не доказана нагрузка в сотни устройств, совместимость
всех LDPlayer версий или других эмуляторов. На момент первоначального repair
автоматический host watchdog отсутствовал. [Следующий этап AUD-99](LDPLAYER-AUTOMATIC-RECOVERY.md)
добавил его, проверил по расписанию и включил для двух экземпляров; первоначальная
причина завершения NAT и доставка состояния станции в backend/UI ещё открыты.
NAT-процесс может существовать при недоступном интернете/DNS — утилита этого не скрывает.

Первоначальные host действия не изменяли Sphere source. Новый инструмент сохраняет
воспроизводимый ремонт внешнего runtime, не маскируя его под исправление Android-кода.
В APK остаётся необходимость понятного сообщения «сеть недоступна» вместо общей
ошибки подключения; независимый серверный ingress остаётся отдельным открытым риском.
