# PH030: VPN работает, телефонный стрим и ввод не приняты

[Машинная квитанция](PH030-STREAM-VPN-INCIDENT.json).
Установка: UI `a239baa2`, API `1afdc529`, PH030 APK86. Это дополнительное
расследование после [сетевого canary](PH030-AWG2-LAN-GATEWAY-CANARY.md).

## Разделение результатов

| Проверка | Факт |
| --- | --- |
| VPN приложений | Ранее прошли IP/HTTPS/DNS и 901,8 с сетевого наблюдения; Sphere вне VPN |
| Телефон → PH030 | Пользователь подтвердил ту же LAN и отсутствие VPN на ноутбуке; видео ушло в server fallback, управления нет |
| ICE телефона и Android | `checking`, ответы проверок отсутствуют, DTLS `new`; это не доказательство конкретной причины потери UDP |
| Независимый headless на ПК → PH030 | Прямой UDP: 780 декодированных кадров за 15,014 с; 0 потерянных RTP в счётчике; 75 RGB-наблюдений, 4,995 Гц |
| Ввод | `root_handoff_unknown`, затем `cleanup_unknown`; не работает и через fallback |

Headless-клиент не запрашивал native input, не отправлял касания/клавиши,
не запускал модель и не сохранял непрерывное видео. Выбранный pair — UDP,
host/prflx, оба адреса частные. Сам тип pair не объявляется доказательством
физической LAN; путь телефона этим тестом не принимается. SCTP smoothed RTT
3,52 мс относится к этому конечному PC-опыту, не к задержке действия в игре.

## Почему заблокирован ввод

Собственная packet-observation команда диагностики через общий `SHELL`
в 18:24:36 UTC вернула `Root command result unavailable: execution_read_timeout`.
Лимит исполнителя — 5 с. В текущем APK любой неопределённый результат общего
shell сохраняется в `rootInputOutcomeUnknown`: текст команды может содержать
мутацию или запускать дочерний процесс, поэтому произвольно считать её
безвредной нельзя. Следующий `prepareContinuousInput` отвергает такое состояние.
`OwnedTouchPipeFactory` сохраняет ограждение владельца, SharedInput —
`cleanup_unknown`; последующие shell-запросы получают `device_input_busy`.

Это эффект нашей диагностической операции. Он не доказывает, что на Android
остался зажатый палец, и не означает, что guard нужно автоматически снимать.
В текущей поставке нет принятого адресного восстановления такой неопределённости
без перезапуска управляющего процесса. Длинную внешнюю packet-пробу нельзя
пропускать через общий input-capable shell и считать read-only по намерению.

## Кандидат и допуск

APK87 source `001fd1a306ff342e94ef172bb9ec5c5f9d01dafb`:

- Явно исключает VPN и loopback из ICE adapter mask; Wi-Fi/Ethernet/cellular
  и NetworkMonitor остаются включены. Шифрование не отключается.
- Не отправляет лишний FIFO-маркер, когда root-shell не имеет незавершённого
  input write. Реальный `rootInputOutcomeUnknown` этим не снимается.
- Тестирует политику на API используемого WebRTC SDK и случай shell без input;
  прежние тесты запрета обхода неизвестного handoff сохранены.

Это исходный кандидат, **не установленное исправление**. Один полный
[GitHub Android CI](https://github.com/RootOne1337/sphere-platform/actions/runs/39841457086)
поставлен в очередь; на момент квитанции jobs ещё не выделены. Локальная сборка
не допущена штатным guard по RAM/commit. Ограничения не ослаблялись.

Перед установкой необходимо завершить CI, собрать настроенный зашифрованный
пакет, сверить payload и подписать прежним сертификатом. Затем — адресная OTA
только PH030, проверка версии/SHA и сохранения guard. Возможное закрытие TUN
при обновлении требует явного восстановления запечатанной ревизии; открывать
приложения через исходный IP ради удобства нельзя.

После обновления нужны настоящий READY и native receipt ввода на свежем кадре,
браузерный ICE при активном VPN и повторная проверка телефона в той же LAN.
Успех headless или один лишь номер новой APK этого не заменяют.
Три собственных diagnostic fixtures ожидают уборки после восстановления.

## Следующая доработка диагностики

Для постоянной эксплуатации нужны типизированные ограниченные запросы состояния,
которые не разделяют injector ownership с произвольным `SHELL`: состояние
интерфейсов/UID, installed package hash, свежий native snapshot. Нельзя разрешать
произвольную команду по клиентскому флагу `read_only`. Неизвестные мутации
должны сохранять строгую защиту и иметь отдельное подтверждаемое восстановление.

Политика WebRTC проверена по [официальному Options API](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/api/org/webrtc/PeerConnectionFactory.java).
Фильтр адаптера — кандидат для явного исключения VPN, а не аттестация причины
телефонного ICE-сбоя. Android лог перечислял VPN и Wi-Fi; PC headless показал,
что VPN не уничтожил все возможные прямые пути.
