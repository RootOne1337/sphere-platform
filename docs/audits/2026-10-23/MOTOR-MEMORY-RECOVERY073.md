# Возврат памяти WSL и настоящие neural shadow-прогоны PH011

**23 октября 2026 · worker0.7.3 · конечная проверка, не приёмка автономной навигации.**
[Машинная квитанция](MOTOR-MEMORY-RECOVERY073.json).
Предыдущий [срез APK88/GPS](PH011-APK88-MOTOR-CALIBRATION.md) сохраняет результаты
своего времени: тогда model inference блокировал guard. В этом новом срезе
ресурсный допуск восстановлен и предсказания действительно получены.

## Что освободилось

В существующей WSL VM измерено13,09GiB файлового кеша при малом объёме Dirty.
Выполнена **одна** диагностическая запись `1` в `/proc/sys/vm/drop_caches`.
Она освобождает чистый page cache; dirty pages не сбрасываются принудительно.
Это диагностический инструмент с возможным временным ростом IO при повторном
чтении, не штатный memory manager приложения. [Документация ядра Linux](https://kernel.org/doc/html/latest/admin-guide/sysctl/vm.html#drop-caches).

| Показатель | До операции | Позднее чтение |
| --- | ---: | ---: |
| Cached внутри WSL |13,09GiB |1,06GiB после25с |
| Windows commit |80,00GiB |65,82GiB |
| Доступная физическая RAM |9,40GiB |11,14GiB |
| vmmemWSL private bytes | около21GiB в предыдущем чтении |7,00GiB |

Первые25с значимого уменьшения commit не было. Позднее чтение15:07:51 UTC,
после начала проверки15:03:54 UTC, подтвердило возврат около14,18GiB **commit**.
Это не14GiB дополнительной физической RAM. WSL возвращает кеш хосту через свой
механизм reclaim; его устройство описано [Microsoft](https://devblogs.microsoft.com/commandline/windows-subsystem-for-linux-september-2023-update/).

WSL boot ID, все14 контейнеров, их start times/restart counts и health сохранены;
API health/ready прошли до и после. Процессы пользователя не завершались,
Windows/WSL/Docker не перезагружались. `.wslconfig`, pagefile и порог85% не менялись.
Повтор операции и автоматический cache clearing не настроены. Не выполнялись
`sync`, очистка slab, принудительный reclaim anonymous pages или сброс compression.

Расход Windows kernel pool остаётся высоким: это не доказательство устранения
утечки драйвера или атрибуции всех выделений WSL. Этот опыт вернул достаточный
резерв для измерений модели, но не заменяет длительную диагностику роста памяти.

## P2P150M: быстрый моторный контур подтверждён в shadow

Модель получает реальные новые RGB через отдельный headless Sphere client.
Исходный кадр960×540 преобразуется model wrapper в192×192. Eager SDPA port и
checkpoint сохранены; bounded BF16-кандидат из предыдущего опыта здесь не используется.
SHA checkpoint повторно проверен после прогонов по pinned HF artifact:
`2a3b43121144ca2d9c2b8aa605e313184c98ac5ef6d2c3b530c2d353d886c5bc`.
HF repo перенаправляет старое имя в `elefantai/open-p2p`; revision
`de18b62bc8f9722bda64497600c38c8f7634d86b` сохранена. Проверка выполнена отдельно:
сам stdio bridge не аттестует веса.

| Сцена | Принято ответов | Средняя частота | Минимум в полном секундном окне | Возраст кадра к ответу,p95 | Максимальная пауза |
| --- | ---: | ---: | ---: | ---: | ---: |
| Выбор персонажа |125 |5,029Гц |5 из24 окон |176,715мс |242,149мс |
| Активный игровой мир |124 |4,999Гц |5 из24 окон |232,931мс |250,254мс |

Небольшое отличие среднего4,999 от5 связано с границами конечного измерения;
каждое полное окно выдержало5. В игровом прогоне параллельно шло скачивание
весов Qwen2B; это не idle/dedicated-GPU benchmark. Direct UDP `host/prflx`, private
адреса,0 server bytes после handover; физический shortest LAN этим не доказан.

Временная шкала — worker receiver clock. Возраст включает ожидание и обработку
после получения кадра worker, но **не даёт полной Android capture→action latency**.
Ответ модели не равен применённой Android-команде. В обоих прогонах native input0,
goal/text conditioning выключены, arrival не проверялся; cleanup подтверждён.
Декодирование шло примерно33FPS: sampling5Гц не уменьшает автоматически encode/decode
стоимость источника. Нагрузка десятков агентов на1–2 GPU этим не принята.

## Qwen: отдельная медленная оценка сцены, не мотор5Гц

Оба кандидата запускались локально на RX9070 через официальный llama.cpp b11836
Vulkan, с matching vision projector и1024 image tokens. Quantization repo —
`unsloth`, pinned revision и SHA каждого файла записаны в JSON. Размеры файлов
не являются обещанием VRAM или общей системной памяти.

| Кандидат | Вес модели + projector | Результат |
| --- | ---: | --- |
| Qwen3.5-0.8B Q4_K_M |737,5MB | На launcher3 противоречивых отказа с координатами. На игровом кадре7/7 `unknown` для opposite-goal/marker задач. |
| Qwen3.5-2B Q4_K_M |1,949GB | Корректно описала деревянное строение с полосатым навесом, но7/7 координатных ответов `unknown`. |

На0.8B cold request занял8,979с; последующие0,368–2,083с. Самые быстрые запросы
использовали тот же кадр и prefix cache, поэтому не являются свежим inference5Гц.
2B дала caption за2,503с, координатные ответы0,690–2,779с с тем же ограничением кеша.
Модели не допущены к физическому управлению.

Отдельная2B scene-калибровка использовала явно помеченные старые fixtures launcher,
ограды и строения, затем свежий кадр и negative case без изображения. Она различила
launcher/gameplay, но назвала центральный объект на кадре с оградой `ground`.
Без изображения выдала `android_launcher/ground/left` вместо запрошенных `unknown`.
Это отрицательные результаты, не достаточная квалификация obstacle detector.
Одна удачная свободная caption не доказывает координатное grounding или clearance.

## Что добавлено в worker0.7.3

`visual_waypoint.py` разбирает bounded JSON и проверяет смысл полей: отказ или
`not_gameplay` не может одновременно нести координатную цель. Extra fields,
duplicate keys, bool вместо integer и усечённый ответ отклоняются. `VisualReply`
связывает ответ с request/frame/epoch/active goal; cleared/replaced goal, просроченный
deadline или слишком старый кадр не дают вернуть точку для моторного контура.

На сохранённых ответах0.8B parser отклонил3 противоречивых результата; все остальные
были отказами. Никакой координатной цели для ввода не принято. Модуль не является
калибровкой camera→stick, collision detector, planner executor или выдачей native
lease. Даже syntactically valid fresh point требует независимой проверки сцены
и прохода. Медленный planner proposal нуждается в новом подтверждении по свежему
восприятию; его нельзя переименовать в200-мс motor correction.

Source `3f57b3d9`,231 motor tests и Ruff прошли. APK88/API/UI не пересобирались:
изменён headless worker. Все принадлежащие этим опытам model processes закрыты.
Регистрация, очистка игры и смена VPN не выполнялись. Существующий guest character
открыт одним Play tap после свежей проверки меню;2/2 APPLIED и CLOSED.

## Следующие условия

Ресурсная блокировка текущего опыта снята; теперь ограничение — качество и
согласование целей/восприятия/исполнения. P2P не получила goal только потому,
что рядом запущена Qwen. Нужны квалифицированный perception adapter, устойчивая
привязка подцели, камера/стик, finite recovery и arrival evidence. Проверять
препятствия на отдельном размеченном наборе и live сценариях; при неизвестности
останавливаться. До их проверки соединять медленный VLM-ответ с мотором опасно
для корректности результата даже при хорошем FPS.

Крупные модели не оставлены resident, новые public PNG не опубликованы.
Старые кадры использовались только как подписанные read-only fixtures; старого
frame→input replay и непрерывного server frame archive не включалось.
