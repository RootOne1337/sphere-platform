# Расход памяти рабочего ПК после остановки эмуляторов

Квитанция: [HOST-MEMORY-DIAGNOSIS.json](HOST-MEMORY-DIAGNOSIS.json).
Замер 23 октября 2026, 01:20 по Екатеринбургу (22 октября, 20:20 UTC).
Это диагностика текущего хоста, а не приёмка производительности Sphere.

## Что измерено

| Показатель | Значение | Как читать |
| --- | ---: | --- |
| Физическая память, видимая Windows | 47,19 GiB | Комплект памяти пользователя — 48 ГБ |
| Доступно Windows | 9,96 GiB | Включает доступную standby-память |
| Commit / предел commit | 73,56 / 94,38 GiB | Обязательства по памяти, не фактически занятая RAM |
| Рабочий набор Memory Compression | 10,03 GiB | Сжатые страницы других потребителей; владелец исходных страниц этим замером не установлен |
| Paged pool ядра | 9,34 GiB | Из них резидентно около 5,17 GiB |
| Nonpaged pool ядра | 5,28 GiB | Невыгружаемая память ядра |
| Рабочий набор vmmemWSL | 2,39 GiB | Private bytes того же процесса — 20,97 GiB; это разные показатели |
| 14 Docker-контейнеров, сумма reported used | Около 1,99 GiB | Входит в ресурсы VM, не добавлять повторно к WSL |

В Linux VM отдельно видны 13,05 GiB файлового кеша, 2,20 GiB buffers,
2,97 GiB anonymous pages и 19,06 GiB MemAvailable. Эти гостевые значения
не являются дополнительным независимым объёмом физической RAM Windows.
Суммировать их с vmmem private bytes, compression и host working sets нельзя.

Нельзя заключать, что backend занимает 21 ГБ, только по private bytes vmmem.
Но и объявлять весь расход «нормальным кешем» оснований нет: отдельно наблюдается
большой объём резидентной памяти ядра. Остановка эмуляторов не закрывает
WSL, Windows-фильтры, службы и остальные приложения.

## Куда распределён pool

Ограниченный read-only запрос `SystemPoolTagInformation` дал следующие
крупные теги. Сумма тегов не обязана совпадать с полными pool counters:
это разные уровни учёта, включая служебные накладные расходы.

| Тег | Объём | Назначение по справочнику |
| --- | ---: | --- |
| FMfn | 3,20 GiB paged | Filter Manager, кеш имён файлов |
| Toke | 1,43 GiB paged | Объекты токенов безопасности ядра |
| AleS | 1,16 GiB nonpaged | TCP/IP ALE token information |
| File | 0,95 GiB nonpaged | Файловые объекты |

Назначения проверены по [справочнику Microsoft pool tags в System Informer](https://github.com/winsiderss/systeminformer/blob/master/SystemInformer/resources/pooltag.txt).
Тег указывает место выделения памяти, а не приложение или фильтр, который
удерживает ссылку. Наличие Amnezia, Defender, WSL или драйверов LDPlayer
не доказывает причинную связь с этими выделениями.

В трёх снимках за 80 секунд FMfn изменился всего на +365600 байт,
Toke — на +160320 байт, AleS — на +57600 байт. В более ранних двух снимках
FMfn также уменьшался. Короткий интервал не подтверждает неограниченную утечку
и не исключает накопление за предыдущие восемь дней работы Windows.
Для атрибуции Microsoft рекомендует сопоставлять [динамику тегов и нагрузку](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/using-poolmon-to-find-a-kernel-mode-memory-leak).

Есть похожий [upstream-инцидент WSL/DrvFS и Windows 26200](https://github.com/microsoft/WSL/issues/41296).
Это рабочая гипотеза для дальнейшего сравнения, не установленная причина
на этом ПК: версии WSL и набор доминирующих тегов отличаются.
Не запускать рекурсивный обход миллионов файлов через границу Windows/WSL
специально для воспроизведения при текущем запасе RAM.

## Что изменено и что сохранено

`scripts/pilot/resource_guard.py` теперь возвращает `kernelPagedBytes`,
`kernelNonpagedBytes`, `processCount` и `handleCount` из того же
[GetPerformanceInfo](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-performance_information).
Новых тяжёлых сборщиков для штатной проверки не добавлено. Эти поля объясняют
состояние, но не дают разрешение на сборку и не меняют её пороги.
49 изолированных unit tests и Ruff прошли.

В замере локальная Android-сборка не допущена: доступно около 10 GiB
при требовании 12 GiB. Порог commit 85% сохранён. Облачный полный CI
[39844420660](https://github.com/RootOne1337/sphere-platform/actions/runs/39844420660)
для Android-кандидата APK87 выполнялся; установленным APK остаётся 86.
Его Android-дерево совпадает с кандидатом `001fd1a3`, исходник запуска — `a238c480`.
Старый dispatch 39841457086 продолжал показывать queued без jobs; попытка
отмены получила ответ GitHub о невозможности отмены завершённого run.
Отмена не подтверждена, новый dispatch не создавался.

Процессы пользователя, Docker и WSL не останавливались. Кеши не сбрасывались,
compression не отключалась, pagefile, `.wslconfig`, firewall и маршруты не менялись.
Эмуляторы не запускались. Сырые списки процессов и командные строки в репозиторий
не опубликованы. Изменение настройки WSL потребовало бы отдельного применения
при остановке VM; [документация WSL](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
не даёт основания обещать исправление этим уже удерживаемого kernel pool.

## Сопутствующее восстановление VPN

При чтении состояния обнаружено отсутствие собственного временного gateway:
PID уже не существовал, UDP-порт был свободен, прежний state.json устарел.
Причина завершения процесса неизвестна. Перезапущен только этот конечный
вспомогательный процесс с прежним исходником и примерно прежним сроком аренды
(округление запуска +1 секунда, автоматического продления нет).
Новых peer, профилей и правил сети не создавалось.

Свежие пакеты в обе стороны, `HANDSHAKE_CONFIRMED`, прежний native PID и та же
управляющая сессия PH030 подтверждены [отдельной квитанцией](PH030-AWG2-GATEWAY-RECOVERY.json).
Свежая проверка HTTPS и браузерного управления в этот ресурсный замер не входит.
Статический файл `running` без проверки времени обновления, PID и listener
не является доказательством работающего шлюза.
