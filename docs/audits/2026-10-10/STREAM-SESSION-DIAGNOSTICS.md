# Последние десять сеансов и автоматическая диагностика браузера

Состояние: **установлено UI a32854e6 / API c14c3235**; история проверена в реальном браузере основного ПК и через API.
[Фактическая установка и пределы](STREAM-SESSION-DIAGNOSTICS-INSTALLED.md).

Пользователь запросил автоматическую диагностику реального клиента ноутбука вместо
ручного выбора профилей и сохранение последних10сеансов на эмулятор. Это отдельная
функция наблюдения; она не превращает текущий WebSocket stream в основной WebRTC.

## Запись и пределы ресурсов

- Сервер назначает ID после авторизации stream viewer. Каждая вкладка — отдельный
  сеанс. Организация и устройство берутся из проверенной server identity.
- На устройство сохраняются последние10сеансов. Атомарный Redis Lua удаляет
  одиннадцатую запись и исключает её восстановление запоздалым report/end.
- Максимум32KiB сохранённого JSON на сеанс,15последних browser samples,
  15APK samples,8событий отказа управления и3результата прямой проверки.
  При достижении лимита байтов удаляется самая старая детализация; последний
  срез каждого вида и завершение сеанса сохраняются. Число срезов — верхний предел.
- Browser samples отправляются раз10с по существующему viewer WS. Серверные
  срезы APK используют существующий10с keepalive. Дополнительного медиапотока
  для сбора счётчиков нет. Пиковые ошибки/RTT и число отчётов сохраняются отдельно.
- Неактивная запись истекает через7дней независимо от обновлений других viewers.
  Хранение в Redis disposable: eviction/restart могут удалить историю раньше;
  это не долговечный архив и не видео DVR.
- Отдельный worker на viewer имеет очередь4малых записей. Запись Redis не
  блокирует приём касаний; переполнение пропускает диагностический report.
  Все операции ограничены0,5с; отключение очищает worker и ограничивает flush.

## Какие данные сохраняются

Browser: входящие пакеты/байты/FPS, decoded/rendered frames, decode/render errors,
queue depths/recoveries/drops, возраст последнего пакета и canvas frame, состояние
управления, классифицированная причина отказа, последний RTT native ACK и число
попыток восстановления. Источник явно `client_reported`, время приёма назначает сервер.

APK: версия/heartbeat/status, исходное время telemetry snapshot, соответствие
текущей agent session, capture/render/encoder и локальные WS queue counters.
Старый snapshot сохраняет исходное время; повторное чтение не делает его свежим.

Отказы сервера: операция, фиксированный код/причина, retryable и наличие владельца.
Не сохраняются координаты, текст ввода, APK command payload, screenshot/video,
SDP, IP/candidate addresses, ICE credentials, JWT и текст исключений декодера.

## Автоматическая проверка прямого видео

В одиночном открытом stream автоматически запускается только server-admitted
readonly-video renderer после получения кадра, при видимой странице. Фокус окна не
требуется: оставленный видимым viewer может собирать результаты без оператора.
Скрытая вкладка, запись сценария, инспекция и task handoff исключают автотест.
Допуск читается для текущего viewer после первого кадра; один временный HTTP
отказ разрешает один повтор чтения, permission/schema отказ не повторяется.
На один viewer: один finite host attempt≤30с, при неуспехе максимум один admitted
public-STUN attempt≤30с. Автоматического расходования TURN grant нет.

Проверка использует реальный video element и requestVideoFrameCallback. Только
действительно представленные кадры с размерами подтверждённого capture binding
увеличивают счётчик. SDP, connected ICE/DTLS и20echo сами по себе не подтверждают
изображение. Первый кадр ограничен8с после binding; hidden/смена страницы/устройства
останавливают peer. Ни проверка, ни её результат не разрешают Android input.

Результат сохраняется автоматически: профиль, выбранный путь host/nat/relay/unknown,
UDP/TCP, причина остановки, число echoes/RTT p95, представленные кадры и размеры,
ICE/DTLS состояния. IP и session keys не входят в report. Старый renderer не может
записать результат в новый viewer. Ручная проверка остаётся дополнительной.

## Чтение без действий пользователя

`GET /api/v1/devices/{device_id}/stream-sessions`, permission `stream:read`,
tenant/device active check до Redis, `Cache-Control: private, no-store`.
Последние записи доступны оператору/assistant через авторизованный API после
того, как реальный браузер загрузил новую сборку. Нельзя измерить сеть ноутбука
браузером основного ПК с VPN. Открытый старый JavaScript обновляется после F5;
установка APK или API сама по себе не обновляет код чужой вкладки.

UI показывает историю в диагностике стрима; отсутствие данных и Redis outage
отличаются от нуля и здорового сервиса. Worker loss даёт `stale`, явный disconnect —
`closed`. Контрольные RTT не называются video glass-to-glass latency.

## Приёмка

Fixtures: атомарное11→10, concurrent viewers, bounded samples/bytes/TTL,
tenant rejection, late/closed write fencing, invalid/private field rejection,
unknown latency, independent diagnostic writer, automatic host→NAT limit,
renderer frame/binding проверка, stale callback и WS backpressure.
Отмена незавершённого video.play() при cleanup не заменяет исходный сетевой
отказ ошибкой renderer; активный отказ воспроизведения остаётся отдельным сбоем.

Установленные образы, история на обоих адресах и автоматический outcome ноутбука
с 223 RTP-кадрами проверены. Следующий gate: основной транспорт видео/управления. Успешная конечная диагностика
не закрывает primary direct media/input, reconnect/multi-viewer/NAT/TURN matrix,
native ресурсы и длительную стабильность. Эти задачи остаются открытыми.
