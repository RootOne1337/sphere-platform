### WEB-01 — «Создать Pipeline» запускает pipeline на ранее выбранных устройствах

- **Условие и ожидание.** В `/orchestration` открыть «Новый Pipeline», заполнить форму, открыть «Создать и запустить», выбрать устройство, затем нажать отдельную кнопку «Создать Pipeline». Оператор выбрал создание определения.
- **Причина.** Обычная кнопка меняет видимость селектора, сохраняя `targetDeviceIds`. Обе кнопки вызывают одну mutation без параметра намерения. После успешного `POST /pipelines` callback проверяет сохранённый массив и отправляет `POST /pipelines/{id}/run` для одного устройства либо `/run-batch` для нескольких.
- **Последствие.** Действия pipeline могут уйти на парк без выбора режима запуска на последнем шаге. Для воздействия требуется успешное создание, принятие запроса запуска и доступность соответствующего исполнителя.
- **Доказательство.** В jsdom после обычного создания за запросом `POST /pipelines` последовал `POST /pipelines/created-pipeline/run` с `device_id=fixture-device`. Запросы записаны через подменённый HTTP-клиент. [Кнопка](../../../frontend/app/%28dashboard%29/orchestration/page.tsx#L1381), [callback](../../../frontend/app/%28dashboard%29/orchestration/page.tsx#L1077), [историческая запись F-16](../2026-11-01/FINDINGS-REGISTER.md#f-16).

### WEB-02 — снятие последнего устройства в расписании оставляет прежнюю цель

- **Условие и ожидание.** В `/orchestration → Schedules → Редактировать` убрать последнее выбранное устройство и нажать «Сохранить изменения». Интерфейс должен либо явно отказать в пустом выборе, либо передать серверу намерение очистить список.
- **Причина.** Форма разрешает сохранить расписание без проверки числа выбранных устройств. Поле `device_ids` получает `undefined` и исчезает при JSON-сериализации. Серверный `PATCH` применяет переданные поля, поэтому прежнее значение сохраняется. Поведение формы создания отличается, она требует хотя бы одно устройство.
- **Последствие.** После commit расписание сохраняет старую цель. Запуск на ней возможен при следующем срабатывании. Обычный успешный HTTP-ответ вызвал бы сообщение об обновлении, а фактическая проба текущего API показала `500` после commit, поэтому оператор может увидеть сообщение об ошибке при частично применённом редактировании. Влияние групп и тегов требует отдельной проверки. [BE-02](BACKEND-DATA.md#be-02)
- **Доказательство.** В jsdom кнопка осталась активна после снятия единственной цели, а в сериализованном PATCH поле `device_ids` отсутствовало. [Обработчик формы и `canSubmit`](../../../frontend/app/%28dashboard%29/orchestration/page.tsx#L1787), [PATCH](../../../backend/api/v1/schedules/router.py#L153), [service](../../../backend/services/scheduler/schedule_service.py#L121). Историческая запись [F-04](../2026-11-01/FINDINGS-REGISTER.md#f-04).

### WEB-03 — «Завершить» присваивает нули и null ранее записанным показателям сессии

- **Условие и ожидание.** В `/sessions` вручную завершить активную запись, в которой ранее сохранились счётчики либо диагностические поля. Команда содержит только причину ручного завершения.
- **Причина.** Клиент передаёт `end_reason=manual`. Схема подставляет `0` для `nodes_executed` и `errors_count`, `null` для `error_message`, `level_after` и `balance_after`. Backend присваивает эти значения записи без проверки наличия полей в исходном запросе.
- **Последствие.** В PostgreSQL сброс полей наблюдался внутри транзакции до rollback. Текущий API вернул `500` при формировании ответа, а контрольный GET сохранил прежние значения и активное состояние. При успешном commit этого обновления значения будут потеряны, что повлияет на суммарную статистику. Фактическая остановка игры или задания по этому запросу не доказана. [BE-01](BACKEND-DATA.md#be-01) · [BE-13](BACKEND-DATA.md#be-13)
- **Доказательство.** В jsdom после подтверждения запрос для сессии с `7` узлами и `2` ошибками содержал только `{end_reason: "manual"}`. [UI](../../../frontend/app/%28dashboard%29/sessions/page.tsx#L225), [схема](../../../backend/schemas/account_sessions.py#L22), [запись](../../../backend/services/account_session_service.py#L160) и [агрегация](../../../backend/services/account_session_service.py#L346). Историческая запись [F-06](../2026-11-01/FINDINGS-REGISTER.md#f-06).

### WEB-04 — изменение логина перезаписывает отдельный ник персонажа

- **Условие и ожидание.** В `/accounts → Редактировать` открыть аккаунт с разными `login` и `nickname` и поменять значение поля «Логин / Ник». При необходимости изменить только логин UI должен позволять сохранить существующий ник.
- **Причина.** У формы одно видимое поле, заполненное логином. Его обработчик записывает введённое значение сразу в `login` и `nickname`. При сохранении PATCH содержит оба поля. Backend принимает и присваивает их отдельно.
- **Последствие.** Старый ник исчезает после успешного PATCH. При сверке аккаунта по имени персонажа появляется расхождение с игрой.
- **Доказательство.** Синтетическая запись `login=fixture_login`, `nickname=SeparateNick` после ввода `changed_login` отправила PATCH с `login` и `nickname`, оба равны `changed_login`. [Поле ввода](../../../frontend/app/%28dashboard%29/accounts/page.tsx#L938), [сборка PATCH](../../../frontend/app/%28dashboard%29/accounts/page.tsx#L1070), [схема](../../../backend/schemas/game_accounts.py#L123), [service](../../../backend/services/game_account_service.py#L297).

### WEB-05 — форма аккаунта принимает изменение пола, которое PATCH игнорирует

- **Условие и ожидание.** В `/accounts → Редактировать` изменить «Пол» и сохранить. После успешного ответа ожидается сохранение выбранного значения.
- **Причина.** Поле присутствует в форме и включается в payload как `gender`. `UpdateGameAccountRequest` его не объявляет, а `update_account` не записывает. При успешном HTTP-ответе UI закрывает диалог. Пол поддерживается отдельной схемой создания и читается в ответе.
- **Последствие.** Исправить ошибочное значение с этой формы нельзя, хотя она предлагает выбор и выполняет запрос сохранения.
- **Доказательство.** В изолированном Python-вызове `UpdateGameAccountRequest.model_validate(dict(gender="female")).model_dump(exclude_unset=True)` вернул `{}`. [Клиент](../../../frontend/app/%28dashboard%29/accounts/page.tsx#L1077), [закрытие при успехе](../../../frontend/app/%28dashboard%29/accounts/page.tsx#L602), [PATCH schema](../../../backend/schemas/game_accounts.py#L120), [запись](../../../backend/services/game_account_service.py#L273).

### WEB-06 — неверные метаданные аккаунта пропускаются при сохранении

- **Условие и ожидание.** В `/accounts → Редактировать` ввести незавершённый JSON в «Метаданные (JSON)» и изменить другое поле. Сохранение должно показать ошибку ввода либо явно запросить подтверждение частичного результата.
- **Причина.** `JSON.parse(meta)` обёрнут пустым `catch`. Далее форма вызывает `onSave` и при успехе закрывает диалог. Об ошибке синтаксиса форма не сообщает.
- **Последствие.** Другие поля могут сохраниться, введённые метаданные не попадают в PATCH, после закрытия введённый текст теряется.
- **Доказательство.** В jsdom ввод `{` в метаданные и смена уровня с `5` на `6` дали PATCH `{level: 6}`. После фикстурного успешного ответа диалог закрылся без ошибки. [Метаданные и обработчик](../../../frontend/app/%28dashboard%29/accounts/page.tsx#L1055), [закрытие диалога](../../../frontend/app/%28dashboard%29/accounts/page.tsx#L602).

### WEB-08 — поиск сессии на текущей странице сбрасывает страницу при вводе

- **Условие и ожидание.** В `/sessions` открыть вторую или следующую страницу, ввести значение, видимое в одной из её записей, в поле «Поиск сессий на текущей странице». Оператор ожидает фильтрацию строк текущей страницы.
- **Причина.** В `onChange` одновременно сохраняется строка поиска и вызывается `setPage(1)`. Query меняется на первую страницу, а фильтр применяется только к её `items`.
- **Последствие.** Видимая перед вводом запись исчезает, если её нет на первой странице. Случай отличается от серверного поиска по всему каталогу, где сброс страницы допустим.
- **Доказательство.** В jsdom строка `only_page_two` отображалась на второй странице. Ввод этого же текста вызвал `GET /account-sessions` с `page=1`, строка исчезла. Существующий `sessions/page` проверяет сам сброс страницы и проходит, но использует одинаковые `items` для обеих страниц. [Параметры запроса и локальная фильтрация](../../../frontend/app/%28dashboard%29/sessions/page.tsx#L173), [обработчик поля поиска](../../../frontend/app/%28dashboard%29/sessions/page.tsx#L303), [существующий тест](../../../frontend/__tests__/sessions/page.test.tsx#L58).

### WEB-09 — селектор pipeline для триггера ограничен первой страницей

- **Условие и ожидание.** В `/event-triggers` создать триггер и выбрать конвейер, который API возвращает со второй или следующей страницы каталога. Существующий активный конвейер должен быть доступен для выбора.
- **Причина.** `usePipelineOptions` запрашивает `GET /pipelines?per_page=200` без `page` и возвращает только `data.items`. API отдаёт первую страницу по умолчанию и сообщает `pages`, UI игнорирует это поле. Селектор рендерит только полученные элементы. Уже связанный pipeline за пределами первой страницы отображается в таблице как первые восемь символов ID.
- **Последствие.** При каталоге больше 200 определений оператор не может назначить pipeline за пределами первой страницы через этот диалог. Пагинация каталога триггеров не меняет список целей.
- **Доказательство.** Статическое сопоставление [запроса каталога](../../../frontend/app/%28dashboard%29/event-triggers/page.tsx#L62), [селекта](../../../frontend/app/%28dashboard%29/event-triggers/page.tsx#L516), [подписи в таблице](../../../frontend/app/%28dashboard%29/event-triggers/page.tsx#L248) и [пагинации API](../../../backend/api/v1/pipelines/router.py#L85). Лимит срабатывания события рассмотрен отдельно. [BE-05](BACKEND-DATA.md#be-05)

### WEB-10 — «Вперёд» возвращает список потоков на первую страницу

- **Условие и ожидание.** В `/stream` каталог содержит больше устройств, чем помещается на странице. Нажатие «Вперёд» должно показать вторую страницу после ответа сервера. В кэше ещё нет второй страницы с этим набором фильтров и размером сетки.
- **Причина.** `useDevices` создаёт отдельный React Query key для каждой страницы и во время первой загрузки нового ключа не предоставляет `data`. Компонент вычисляет `totalPages=1` из отсутствующего ответа. Эффект воспринимает это временное значение как подтверждённую последнюю страницу, делает `setListPage(1)` и снимает подписку со страницы 2. Сигнал запроса страницы 2 отменяется.
- **Последствие.** Оператор возвращается на первую страницу и не может открыть поток устройства на следующей. Предел особенно заметен при начальной сетке на четыре устройства. Другие маршруты к карточке устройства доступны отдельно.
- **Доказательство.** В jsdom реальный `useDevices` получил страницу 1 из 2. После нажатия появился `GET /devices` с `page=2`, его `AbortSignal` стал `aborted=true` до ответа, на экране осталось `1 / 2`. Поздний фикстурный ответ с пятым устройством не отобразился. Существующий тест пагинации возвращает данные синхронно через подмену всего хука, поэтому переход без `data` там отсутствует. [Пагинация и эффект](../../../frontend/app/%28dashboard%29/stream/page.tsx#L124) · [Ключ и сигнал запроса](../../../frontend/lib/hooks/useDevices.ts#L75) · [Существующий тест](../../../frontend/__tests__/stream/device-presence.test.tsx#L235) · [Наблюдение](evidence/web-second-pass.test.cjs).

### WEB-11 — после потери ответа «Повторить выполнение» разрешает создать ещё одно задание

- **Условие и ожидание.** На `/tasks/[id]` нажать «Повторить выполнение» для завершённого задания. Сервер успел создать новое задание, но клиент потерял ответ. Интерфейс должен сообщить, что исход неизвестен, и дать способ сверить результат до следующего запуска.
- **Причина.** UI использует одинаковый текст ошибки для отклонённого запроса и отсутствующего ответа. После ошибки блокировка `writesPending` снимается, обычное чтение исходного задания по-прежнему считается успешным. При повторном нажатии `useRetryTask` отправляет ещё один `POST /tasks/{id}/rerun`. В запросе и обработчике нет идентификатора попытки. Сервер создаёт независимое задание и фиксирует его до отправки HTTP-ответа.
- **Последствие.** Повтор во время активного первого запуска ограничен серверной проверкой конфликта по устройству и версии скрипта. Если первый запуск уже завершился к моменту повторного нажатия, тот же сценарий и входные параметры могут выполниться ещё раз.
- **Доказательство.** В jsdom после имитации потерянного ответа интерфейс показал «Команда не выполнена… затем повторите действие», кнопка снова стала доступна. Второе нажатие сформировало идентичный POST и открыло ссылку на второй ID фикстуры. Две записи на реальном сервере или устройстве в этой проверке не создавались. [Статус ошибки](../../../frontend/app/%28dashboard%29/tasks/%5Bid%5D/page.tsx#L156) · [Кнопка](../../../frontend/app/%28dashboard%29/tasks/%5Bid%5D/page.tsx#L199) · [Mutation](../../../frontend/lib/hooks/useTasks.ts#L202) · [Commit до ответа](../../../backend/api/v1/tasks/router.py#L182) · [Конфликт только активных заданий](../../../backend/services/task_service.py#L223) · [Наблюдение](evidence/web-second-pass.test.cjs).

### WEB-12 — повторное открытие назначения VPN снимает блокировку неизвестного исхода

- **Условие и ожидание.** В `/vpn → Инфраструктура` отправить «Назначить адрес» и потерять ответ. Страница обещает блокировать новые операции для устройства с неизвестным исходом до сверки состояния.
- **Причина.** После ошибки диалог устанавливает `provisionDone=true`, а устройство попадает в `unresolved`. Новый диалог сбрасывает `provisionDone`, а выбор и отправка смотрят только на устройства с peer в последнем прочитанном каталоге. `unresolved` применяется к ротации, перезапуску и kill switch, но не к назначению.
- **Последствие.** Если каталог ещё не отражает предыдущую попытку, оператор может вновь отправить назначение для того же устройства, хотя в фоне остаётся предупреждение о блокировке. При существующем `assigned` peer сервер возвращает его, а для промежуточного статуса отвечает `409`. Создание дубликата peer этой проверкой не установлено.
- **Доказательство.** В jsdom кнопка заблокировалась после первой ошибки. После закрытия диалога предупреждение осталось, но повторное открытие позволило выбрать то же устройство и сформировало второй `POST /vpn/assign` с тем же `device_id`. Использованы реальный хук назначения, подмена API и тестовый выбор устройства. [Набор неизвестных исходов](../../../frontend/src/features/vpn/VpnRouterInfrastructure.tsx#L48) · [Сброс диалога](../../../frontend/src/features/vpn/VpnRouterInfrastructure.tsx#L160) · [Условия отправки](../../../frontend/src/features/vpn/VpnRouterInfrastructure.tsx#L357) · [Серверная сверка](../../../backend/services/vpn/pool_service.py#L95) · [Наблюдение](evidence/web-second-pass.test.cjs).

### WEB-13 — журнал подтверждает очистку, хотя лог остался на сервере

- **Условие и ожидание.** Уполномоченный оператор подтверждает «Удалить логи» в `/logs`, а удаление файла завершается ошибкой ввода-вывода. Сообщение об очистке должно отражать реальное состояние архива.
- **Причина.** Сервер вызывает `shutil.rmtree(device_dir, ignore_errors=True)` и возвращает `204` без проверки результата. Веб после принятого HTTP-ответа очищает локальные строки и показывает уведомление «Логи устройства … удалены». Обработчик не перечитывает архив после ответа.
- **Последствие.** Оператор может считать, что архив больше недоступен. На повторном чтении прежние строки снова видны. Фактическое наличие проблемного архива или разрешения на удаление файлов в рабочей установке не проверялись.
- **Доказательство.** Вызов реального handler с временным архивом и подставным `PermissionError` в `unlink` вернул `204`, файл остался на месте. В отдельном jsdom-наблюдении такой ответ дал успешное уведомление и пустой список, а ручное «Обновить логи» вновь показало исходную строку. ### WEB-14 — в разделах чтения активны действия, которые текущая роль не может выполнить

- **Условие и ожидание.** `viewer` с разрешениями чтения открывает журнал, карточку работающего задания и оркестрацию. Кнопки административного действия должны быть недоступны либо объяснять, какое разрешение требуется.
- **Причина.** Маршруты допускают `device:read`, `script:read` и `pipeline:read`. Кнопка очистки журнала проверяет состояние загрузки, а API требует `device:delete`. Карточка задания проверяет состояние запроса и статус задачи, а остановка требует `script:execute`. Кнопка «Новый Pipeline» показывается всем допущенным к маршруту, тогда как создание требует `pipeline:write`.
- **Последствие.** Оператору доступны действия, которые сервер отклонит. В журнале он может дойти до необратимого подтверждения, а в оркестрации заполнить форму до отказа. Защита записи на сервере сохраняется.
- **Доказательство.** Три jsdom-сценария прошли через настоящие `CapabilitiesProvider` и `RouteAccessBoundary` с ответом прав для `viewer`. Кнопки «Очистить логи», «Остановить задание» и «Новый Pipeline» были активны. Команды в этих трёх проверках не отправлялись.
