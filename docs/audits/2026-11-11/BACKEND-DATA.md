Срез от 11 ноября 2026 года, `94cf7c3a2a50bbc8197737f5cf666e0e2c8ddec3`. У `backend`, `alembic` и `infrastructure/postgres` рабочее дерево совпадало с HEAD. Код и выводы реестра от 1 ноября сверены с текущим деревом. [Предыдущий реестр](../2026-11-01/FINDINGS-REGISTER.md).

<a id="be-01"></a>
### BE-01. API игровых сессий падает при формировании ответа

Нормальный запрос на создание дал `500`, контрольное чтение ранее созданной строки дало `200`, число открытых сессий осталось равным `1`. Ручное завершение существующей строки тоже дало `500`, чтение после запроса показало `ended_at=null` и прежние значения. В журналах обоих запросов `MissingGreenlet`. Сервисы выполняют `flush`, затем `_to_response` синхронно обращается к ORM relationships и `updated_at`. Новая запись не загружает relationship устройства до формирования ответа. После UPDATE `updated_at` рассчитывается SQL-выражением и требует загрузки. Handler начинает `commit` только после возврата сервиса, а зависимость БД откатывает при исключении. Действия через эти API в проверенном сценарии не изменили данные. Критерий исправления для последующей задачи — ответ о завершении операции и повторное чтение совпадают, тест использует реальный PostgreSQL и свежую сессию на запрос. [Преобразование ответа и создание](../../../backend/services/account_session_service.py#L36) · [завершение](../../../backend/services/account_session_service.py#L144) · [handlers](../../../backend/api/v1/account_sessions/router.py#L87) · [ORM timestamps](../../../backend/models/base_model.py#L9) · [rollback](../../../backend/database/engine.py#L31) · [наблюдения](evidence/backend-functional-observations.json).

<a id="be-02"></a>
### BE-02. Расписания отвечают ошибкой после сохранения изменения

`POST /schedules` вернул `201`. `PATCH /schedules/{id}`, `POST /schedules/{id}/toggle` и `POST /schedules/{id}/fire-now` вернули `500`. Pydantic зафиксировал `get_attribute_error` на `ScheduleResponse.updated_at` из-за `MissingGreenlet`. При повторном `GET` изменённые поля уже находились в PostgreSQL, включение поменяло видимость для scheduler discovery. Handler сначала вызывает `commit`, затем `model_validate` читает SQL-generated `updated_at`, который `flush` оставил требующим обновления ORM. Оператор получает ошибку в ответ на уже сохранённое изменение и может повторить действие с неверным представлением о его результате. Критерий исправления — каждый успешный commit сопровождается сериализуемым актуальным ответом, отдельно проверяется неизвестный исход при потере ответа. [PATCH](../../../backend/api/v1/schedules/router.py#L146) · [toggle и fire-now](../../../backend/api/v1/schedules/router.py#L180) · [timestamp](../../../backend/models/base_model.py#L13) · [наблюдения](evidence/backend-functional-observations.json).

<a id="be-03"></a>
### BE-03. Принудительный запуск отключённого расписания не попадёт к исполнителю

В пробе `fire-now` сохранил `next_fire_at` при `is_active=false`. Реальная `sphere_auth.schedule_work` вернула активный контрольный schedule после `fire-now` и пропустила отключённый с уже наступившим временем. Сервис меняет только дату, SQL discovery и `_fire_schedule` независимо требуют `is_active`. Сопутствующий 500 относится к BE-02. После устранения ошибки сериализации семантика выключенного расписания останется неоднозначной без явного отказа или отдельного one-off запуска. Критерий проверки — запрос к выключенному расписанию даёт однозначный отказ или оставляет проверяемый execution receipt без неявного включения. [fire_now](../../../backend/services/scheduler/schedule_service.py#L172) · [discovery SQL](../../../alembic/versions/20260921_schedule_work.py#L13) · [worker](../../../backend/services/scheduler/scheduler_engine.py#L70) · [наблюдения](evidence/backend-functional-observations.json).

<a id="be-04"></a>
### BE-04. Расписания допускают некорректную комбинацию триггеров

На создании `cron_expression="invalid cron"` прошёл проверку формы и вызвал ошибку `croniter` с HTTP `500`. На PATCH переданы валидный cron и интервал 120 секунд, последующее чтение подтвердило сохранение обоих. `CreateScheduleRequest` проверяет число заполненных значений, но не синтаксис cron. `UpdateScheduleRequest` не проверяет итоговую комбинацию, `ScheduleService.update` оставляет оба явно заданных поля, SQL `ck_schedules_has_trigger` требует хотя бы одно поле через `OR`. В расчёте cron идёт первым, поэтому сохранённый интервал может быть проигнорирован. Критерий проверки — ошибка ввода до записи, инвариант «ровно один» сохраняется при создании и частичном обновлении. [Схемы](../../../backend/schemas/schedule.py#L31) · [update](../../../backend/services/scheduler/schedule_service.py#L115) · [расчёт cron](../../../backend/services/scheduler/schedule_service.py#L224) · [CHECK](../../../alembic/versions/20260224_tz12_orchestrator.py#L174) · [наблюдения](evidence/backend-functional-observations.json).

<a id="be-05"></a>
### BE-05. Часовой лимит запуска по событиям не применяется

Синтетический trigger с `max_triggers_per_hour=1`, `cooldown_seconds=0` обработал два последовательных однотипных события. После двух отдельных commit счётчик trigger был `2`, в PostgreSQL существовали два `PipelineRun`. Схема разрешает настройку часового лимита и документирует `0` как безлимитный режим. Reactor читает cooldown, место часовой проверки оставлено как TODO. Поток повторяющихся событий может создавать больше запусков, чем задал оператор. Тест не включает выполнение этих pipeline на устройствах или проверку конкурентных событий. Критерий исправления — атомарное применение часового окна, включая конкурентные workers, откаты и отключённый лимит. [API-схема](../../../backend/schemas/event_trigger.py#L23) · [реактор](../../../backend/services/event_reactor.py#L325) · [наблюдения](evidence/backend-functional-observations.json) · [история F-09](../2026-11-01/FINDINGS-REGISTER.md#f-09).

### BE-06. Активная сессия аккаунта не уникальна

PostgreSQL принял три открытые строки для одного аккаунта после исходной фикстуры и двух внутренних вызовов `start_session_internal`. На этих данных `EventReactor._end_active_session` завершился `MultipleResultsFound`. Миграция создаёт обычный partial index, а реактор вызывает `scalar_one_or_none` на всех открытых строках. Другие пути записи открывают сессию при assign и ротации. Публичный `POST` из BE-01 на текущем стенде откатывается. Доказательство относится к целостности данных и обработке уже существующих дублей, конкретный конкурентный путь образования дублей на устройствах остаётся для проверки. Критерий — согласованный инвариант открытых сессий, обработка накопленных дублей до ограничения и тесты реакций на событие с конкурентными writers. ### BE-07. Два readiness endpoint расходятся при отсутствии Redis-клиента

С реальным `SELECT 1` в PostgreSQL и без запуска Redis lifespan `/api/v1/health/ready` вернул `200` с `redis=ok`, `/api/v1/health/readyz` вернул `503`. Старый код выставляет `ok` после условного `ping`, даже если `redis is None`. Новый `HealthService` явно считает отсутствие клиента состоянием `down`. Preview workflow обращается к старому пути. Успех старого probe при этом условии не проверяет Redis-зависимые возможности. Проба воспроизводит отсутствие клиента, а не сценарий обхода штатного startup на действующем сервере. Критерий — одинаковая семантика отсутствующей зависимости на используемых readiness путях. ### BE-08. Сохранённый OpenAPI не совпадает с зарегистрированным API

`app.openapi()` вернул `201` операцию на `160` путях и полностью совпал по JSON с `docs/openapi.json`. Корневой `openapi.json` описывает `161` операцию и отличается наборами статусов `auth/logout`, `logs/upload` и `tasks/{task_id}/stop`. Клиент, использующий корневой файл, пропустит, например, device refresh, чтение содержимого screenshot и управление VPN-профилями. Документация и штатный генератор frontend используют `docs/openapi.json` или runtime соответственно. [Полный перечень](evidence/backend-routes.md) · [корневой snapshot](../../../openapi.json) · [документация API](../../README.md#разработка-и-интеграция) · [генератор типов](../../../frontend/package.json#L15).

На совпадающей runtime/docs схеме дополнительно подтверждены девять явных `return Response(status_code=204)`, для которых статус не объявлен. Для `/logs/upload` это условная ветка. AST сопоставил 197 из 201 операций и служит указателем на конкретные `return`. Критерий исправления — единый актуальный экспорт и проверка документированных кодов по результатам HTTP. [Явные ответы 204](evidence/backend-routes.md#явные-ответы-204) · [история F-13](../2026-11-01/FINDINGS-REGISTER.md#f-13).

<a id="be-09"></a>
### BE-09. Discovery сообщает завершённое сканирование после ошибки RPC

Сервис получает `PubSubRouter` и вызывает `send_command_wait_result`, который принадлежит `PubSubPublisher`. Исключение превращается в пустой список. Затем `scanned` рассчитывается по размеру сети и диапазону портов, включая ветки без вызова агента. У PC Agent отдельно отсутствует обработчик `discover_adb`. В интерфейсе отсутствие результата может выглядеть как пустая сеть при фактически невыполненной операции. Текущий проход подтверждает пути исходников, сетевое сканирование и агент не запускались. Критерий — совместимый RPC-контракт, явный статус невозможности выполнить запрос и счётчик подтверждённых попыток. Эту же проблему описывает INT-01 со стороны интеграции. [Расчёт ответа](../../../backend/services/discovery_service.py#L81) · [вызов](../../../backend/services/discovery_service.py#L106) · [RPC publisher](../../../backend/websocket/pubsub_router.py#L167) · [PC dispatcher](../../../pc-agent/agent/dispatcher.py#L17) · [INT-01](INTEGRATIONS.md#int-01-запрос-discovery-завершается-до-вызова-pc-agent) · [история F-07](../2026-11-01/FINDINGS-REGISTER.md#f-07).

<a id="be-10"></a>
### BE-10. MinIO/S3 не имеет подключённого потока публикации screenshot задачи

Manifest извлекает ключи только из `node_logs[*].screenshot_key` и `final_screenshot_key`. API чтения обращается к S3 по зарегистрированному ключу и явно отвечает `503` при отсутствующих настройках. Поиск вызовов `upload_screenshot` в backend, Android и PC Agent нашёл определение метода без вызывающего пути. История эксплуатации отдельно фиксирует пустой manifest для задачи и незакрытый writer.
