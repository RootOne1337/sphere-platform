# Управление вебхуками и подтверждение результата до отправки

**14 ноября 2026.** Продолжение OPWEB-01 и BE-20. Проверка использовала
изолированный PostgreSQL, Redis, тесты интерфейса и HTTP-получатель внутри
теста.

## Что изменилось

- API реестра возвращает записи текущей организации, включая выключенные.
  Оператор может снова включить запись после обновления списка. Внутренний
  отбор получателей сохраняет фильтр активности.
- Веб показывает состояние подписки и отдельные доступные признаки
  доставки. Отсутствие времени подтверждения видно независимо от состояния
  переключателя. Ошибки записи отображаются рядом с действием.
- Callback отдельной задачи запускается после успешного commit результата
  и пакетных счётчиков. Транзакционный отказ оставляет задачу доступной для
  повторной квитанции агента. Повтор уже принятой квитанции подтверждается
  повторно, а callback второй раз не планируется. Формат callback сохранён.

## Как проверено

- До исправления сценарий «создать → выключить → перечитать» терял запись
  при GET. После исправления реальная runtime-роль PostgreSQL увидела
  сохранённое выключенное состояние, затем включила запись. Другая организация
  получила пустой список и 404 при записи. Секрет в списке отсутствовал.
- Проверка Android WebSocket прервала настоящую транзакцию PostgreSQL после
  `flush`. Получатель не увидел callback и агент не получил ACK. При повторе
  независимая сессия получателя прочитала уже сохранённый `completed`.
  Повтор квитанции оставил одну доставку и один итог пакета.
- Набор тестов API реестра и отправщика прошёл 63 проверки, отдельный тест
  runtime-роли проверил RLS. Доставка на внешние адреса в ходе проверок
  не выполнялась.
- В повторном наборе обработки Android-квитанций, изоляции аккаунтов и
  отправщика прошли 62 проверки, включая отказ commit и повтор квитанции.
- Семь Jest-проверок страницы покрыли раздельные состояния подписки и
  доставки, повторное включение, ошибки и состояние после неудачного чтения.
  TypeScript прошёл.

## Остаток EP-025

Обычные продуктовые события ещё не подключены к отправщику реестра n8n.
Задача callback после commit пока живёт в процессе. Потеря процесса после
commit может потерять отправку. Для полного закрытия нужны транзакционный
outbox с устойчивым ID доставки, подтверждённый контракт подписи и тела,
история попыток, повтор и проверка совместимости с n8n. [OPWEB-01](../2026-11-13/OPERATOR-WORKFLOWS.md#opweb-01) · [BE-20](../2026-11-11/BACKEND-DATA.md#be-20).
