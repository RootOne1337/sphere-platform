# AUD-172 · 401 при повторной регистрации клонированного Android

## Наблюдение

В приватном `adb logcat` emulator-5556 зафиксированы 13 повторов
`RegistrationException: Ошибка регистрации: HTTP 401`. В том же выборочном
журнале не обнаружены DNS-, TLS-, timeout- или connection-refused ошибки. Сырой
журнал остаётся в локальном ignored evidence и в этот документ не копируется.

Установленный APK на emulator-5556 — `1.2.19-dev / 10219`; на emulator-5554 —
`1.2.20-dev / 10220`. На обоих эмуляторах присутствует
`/sdcard/sphere-agent-config.json`; его credential fingerprint совпадает между
устройствами. Значения ключей и URL в evidence не записываются. Текущий
`/api/v1/config/agent` из изолированного pilot не совпадает с URL и ключом этих
файлов. Это доказывает, что данный локальный bootstrap не соответствует
конфигурации pilot; само по себе это не доказывает, какой production endpoint
ответил на сохранённый 401.

## Подтверждённая причина и граница вывода

`DeviceRegistrationClient.requestRegistration()` отправляет enrollment
credential в `X-API-Key` на `POST /api/v1/devices/register` и создаёт
`RegistrationException` с HTTP-кодом при неуспешном ответе. Endpoint
`register_device()` возвращает HTTP 401, если ключ неизвестен, отключён или
истёк; для известного ключа без `device:register` предусмотрен отдельный 403.
Следовательно, непосредственная причина этих повторов — сервер отвергает
enrollment credential. Это не доказательство неисправности видеотуннеля.

Код discovery сначала принимает managed config, затем локальный JSON-файл и
только потом запрашивает config endpoint. Поэтому общий файл мастер-инстанса
может продолжать перекрывать более свежую удалённую конфигурацию. Совпадающий
fingerprint файла на двух локальных эмуляторах подтверждает общий bootstrap
материал, но не объясняет, был ли ключ отозван, истёк, неверно опубликован или
устройство обратилось к другому окружению. Эти варианты остаются открытыми.

## Воспроизведение

1. На исходном клоне оставить локальный `sphere-agent-config.json`.
2. Запустить APK, которому требуется новая instance binding.
3. Наблюдать HTTP 401 от регистрации; в серверном обработчике это ветка
   `APIKeyService.authenticate()` с результатом `None`.
4. Убедиться, что `403` означал бы отдельную проблему permission, а сетевые
   отказы классифицируются как `IOException`, а не `RegistrationException`.

Из-за отсутствия route provenance в APK того запуска журнал не связывает эти
401 с конкретным host/config source. Публичный pilot API и удалённые серверы не
опрашивались для дополнительной проверки; запуск устройства не менялся.

## Исправление и приёмка

Исправление пока не отмечается выполненным. Повторять запрос регистрации с тем
же отвергнутым ключом или пробовать alternate host автоматически небезопасно:
это не лечит неверный ключ и может отправить credential не тому серверу.
Следующее безопасное изменение должно добавить структурированный, очищенный от
секретов контекст (`config_source`, `route_role`, `http_status`) и тестировать
обновление локального bootstrap только из доверенного, route-bound discovery.
До этого сервис должен показывать состояние `registration_rejected`, а не
бесконечно выглядеть как обычный сетевой reconnect.

Удалённая массовая раскатка APK не выполнялась. Для пилота нужны совпадающие
bootstrap и серверный environment, отдельная регистрационная квитанция каждого
устройства, затем фактический heartbeat и подтверждённая версия APK.
