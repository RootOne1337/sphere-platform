# Совместное управление на прямом media peer

13 октября 2026. Кандидат APK69 / новый веб / новый бэкенд. Этот документ описывает
реализацию и проверки исходников; установка APK69 и приёмка десяти живых браузеров пока не подтверждены.
Работающая установка APK68 сохранена в [протоколе доставки](DIRECT-SOURCE-QUALITY-DELIVERY.md).

У прежней версии три независимых ограничения: Redis-резервация одного peer на устройство,
один encoded viewer в APK и эксклюзивный continuous input owner. Исправление одного слоя
не устраняет ограничения остальных.

## Новый контракт

- До десяти прямых peers на одном APK; каждый имеет собственный ICE/DTLS, срок действия,
  ресурсы и точное завершение. Видеозахват и аппаратное кодирование остаются общими.
- Redis-clock admission атомарно ограничивает число peers между процессами бэкенда.
  У каждого peer свой nonce и ключ; закрытие одной вкладки не удаляет соседнюю резервацию.
- `sphere-control-v2` находится на том же `RTCPeerConnection`, что и основное видео.
  Сервер отдельно проверяет `stream:control` перед выдачей этого права и при продлении.
  `touch_open`, DOWN/MOVE/UP и завершение участника идут по его прямому DataChannel.
- Один bounded actor и один root pipe принимают ввод всех участников. Порядок определяется
  приходом в APK. Новый DOWN другого участника требует подтверждённого native CANCEL старого
  жеста; его поздние MOVE/UP не присваивают управление обратно.
- Прерывание жеста не разрывает участникам видеопоток или соединение. Участник может
  начать новый жест с новым nonce. Чужое закрытие отменяет только собственный удерживаемый жест.
- Между готовностью, actor liveness, native применением, отменой участника и неизвестным
  результатом есть явные различия. Неизвестная native доставка не повторяется по серверу.
  Неизвестная очистка root pipe блокирует новый pipe до подтверждённого освобождения.
- Настройка качества общая для устройства. Свежая наименьшая WebRTC bitrate allocation
  среди текущих зрителей ограничивает единственный кодек; отдельное качество каждому зрителю
  в этой версии не объявлено.

Старые APK используют прежний v1. Новая capability выдаётся только при APK10269 или новее
и включённом серверном input gate. Серверный grant привязан к authenticated peer, устройству,
пользователю, capture epoch и текущей Android-сессии.

## Выполненные проверки

Frontend: 2345 тестов, 162 набора и проверка типов прошли. Проверены прямой OPEN/CLOSE,
прерывание уже отпущенного, но ещё ожидающего ACK жеста, запоздалое сообщение старого жеста,
чужой owner, невозможность принять v2 readiness в v1 и запрет fallback неизвестного клика.

Бэкенд: 226 scoped tests прошли. Два процесса конкурентно запрашивают двадцать резерваций:
допускаются десять. Exact release/renew, чужой пользователь, старый APK, отдельное control RBAC,
disabled/offline capability и старый v1 проверены. Сорок проверок установщика прошли.

Native actor cases добавлены для десяти участников с одним pipe, CANCEL перед takeover,
старого MOVE/UP, чужого close, потери peer и неизвестного CANCEL. Компиляция Android production
кода прошла; тестовый ACK-адаптер исправлен после отдельной ошибки компиляции. Подписанная
сборка, native прогоны и живая многопользовательская приёмка ещё выполняются.

## Границы

Этот этап не отменяет серверное продление авторизации. Сохранение localhost/LAN peer при
потере Интернета требует следующего negotiated grant и отдельного lifecycle. Прямые системные
кнопки, keyboard/IME, audio, реальный телефон, WAN/TURN и физическая смена сети остаются
отдельными проверками. Лимит десять не является обещанием 60 FPS при любой нагрузке или
одинаковой задержки на десяти разных сетях.

RTP-видео и SCTP DataChannel используют разные потоки внутри одного защищённого peer:
одинаковый `RTCPeerConnection` не превращает управление в видеопакеты и не доказывает
одинаковую задержку. [W3C WebRTC](https://www.w3.org/TR/webrtc/),
[RFC8831](https://www.rfc-editor.org/rfc/rfc8831) описывают этот транспортный контракт.
