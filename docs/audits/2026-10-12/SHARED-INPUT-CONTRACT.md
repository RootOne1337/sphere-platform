# Общий ввод нескольких зрителей: контракт следующей доработки

Дата сверки: 12 октября 2026 года. **Статус: OPEN, проектирование по текущему коду.**

Пользователь подтвердил требование: несколько вкладок и компьютеров могут
одновременно управлять одним Android, рядом остаётся доступен физический ввод
эмулятора. Новое действие может прерывать прежний жест. Просмотр и разрешение
ввода должны учитываться отдельно для каждой вкладки.

Это дополнение к CHAT-18 в [реестре состояния](../../operations/STATUS-REGISTRY.json).
Исправление одного отказа STARTUP и успешный жест одного зрителя не закрывают
этот контракт. Установленный APK1.2.63-dev не объявляет поддержку общего ввода.

## Что ограничивает текущую реализацию

| Участок | Ограничение | Следствие |
| --- | --- | --- |
| `backend/websocket/continuous_lease.py` | Один Redis-ключ владельца на устройство | Второй допуск получает `controller_busy` |
| `ContinuousInputController.kt` | Один `AtomicReference<Owner?>` | Второй нативный владелец не допускается |
| `DeviceInputOwnership.kt` | Непрерывный владелец исключает дискретные команды | Home/Back из другого клиента могут отклоняться |
| `DirectProbeTransport.kt`, source set `directProbe` | Один `Probe` | Несколько независимых прямых peers не реализованы |
| `ContinuousPointer` | Один жест и подтверждения одного владельца | Нужен отдельный сигнал прерывания жеста другим клиентом |

## Требуемое поведение

1. Подключение зрителя не захватывает исключительное управление устройством.
2. Каждый клиент получает собственный допуск, последовательность сообщений,
   срок действия и канал подтверждений. Роль read-only остаётся read-only.
3. Android принимает события в одном локальном порядке. Этот порядок определяет
   результат одновременных поступлений; часы разных компьютеров не сравниваются.
4. Новый DOWN другого клиента завершает прежний виртуальный жест и начинает новый.
   MOVE/UP прежнего жеста после прерывания не возобновляют его.
5. Прерванный клиент получает явный результат `interrupted`; это не потеря видео,
   не неизвестное выполнение и не повод пересоздавать весь WebRTC peer.
6. После прерывания клиент может отправить новый самостоятельный DOWN. Старые
   движения не накопляются и не воспроизводятся после восстановления сети.
7. Физическое управление эмулятором не отключает видимую вкладку браузера.
   Удерживаемый браузерный жест при потере фокуса освобождается отдельно.
8. Home/Back/Recents/Menu и клавиатура согласуются тем же арбитром Android.
   Клавиша может отменить текущий виртуальный жест; другим зрителям не требуется
   сначала закрыть видеопоток.
9. Закрытие одной вкладки отзывает её допуск и освобождает только её удерживаемые
   действия. Другие подключения продолжаются.
10. Зависший канал одного зрителя имеет отдельный ограниченный буфер и не
    блокирует остальные каналы или общий захват экрана.

## Границы реализации

- Общая сессия ввода требует новой явно согласованной версии протокола.
  Установленные APK с одним владельцем не должны ошибочно объявляться готовыми
  к нескольким независимым владельцам.
- Сервер сохраняет проверку пользователя, tenant, RBAC, устройство, поколение
  подключения агента и отзываемые допуски. Полезные события и их подтверждения
  идут по прямому DataChannel при доступном прямом peer.
- APK должен иметь один арбитр и один ограниченный нативный обработчик для
  устройства, а не отдельный привилегированный процесс для каждого зрителя.
- Несколько медиаподключений требуют fan-out общего захвата и кодированных
  кадров. Память, число peers и суммарный трафик ограничиваются отдельно.
- Недоступный peer освобождается самостоятельно. Отзыв всей группы применяется
  только при общем изменении захвата, прав, поколения агента или остановке службы.
- Исход неизвестной отправки не превращается в успех. Автоматическое
  восстановление допуска не повторяет старое действие.
- TTL, метрики и журналы не должны расти пропорционально числу MOVE за всё время
  работы. Нужны небольшие счётчики, ограниченная очередь и последние десять
  записей сеансов, а не бессрочный журнал каждого движения.

## Обязательная проверка перед закрытием CHAT-18

| Проверка | Что наблюдать |
| --- | --- |
| 2 и 10 клиентов, включая несколько вкладок одного аккаунта | Каждый клиент получает допуск; подключения не вытесняют друг друга |
| Два одновременных DOWN | Один локальный порядок, завершение предыдущего жеста и отдельные результаты |
| MOVE/UP прерванного клиента | Нет повторного захвата и ложного подтверждения применения |
| Home другого клиента во время жеста | Известное завершение жеста и одно подтверждённое выполнение клавиши |
| Физический клик рядом с видимым вебом | Просмотр продолжается, видимый idle-клиент остаётся доступен |
| Закрытие, blur, hidden и авария одной вкладки | Освобождение её действий; другие peers сохраняются |
| Удаление прав, смена tenant и новое поколение APK | Старые допуски не принимают новые события |
| Низкая пропускная способность одного клиента | Ограничение его буфера без задержки остальных зрителей |
| Потеря ACK, повтор пакета и перестановка | Нет двойного ввода и воспроизведения устаревшей траектории |
| Десять прямых медиазрителей | CPU, RAM, FPS, суммарный битрейт и очереди измерены на слабом эмуляторе |

Нужны нативные тесты арбитра, проверки нескольких backend workers с настоящим
Redis и реальные браузерные сеансы. Один успешный ввод с ноутбука не заменяет
эту матрицу. Нулевой сетевой RTT не означает нулевую задержку изображения.
