# Неподвижный экран, цепочка H.264 и повторное согласование: APK56–59

**12 октября — дополнительная проверка обычного Chrome.** Найден конкретный
отказ разрешения mDNS имени между Windows и виртуальной сетью Android.
С действительным Windows lookup обычный Chrome без numeric flag получил
30672 decoded frames при 29 FPS, без drops/freezes/packet loss; 14 native
input ACK и UP подтверждены, серверных touches ноль. Первоначально это был
прототип с SDP adapter. Теперь UI/API `cac67643` установлены; обычный Chrome
без этого adapter подтвердил direct video/input на 3015 и Tuna.
[Текущий срез](DIRECT-MDNS-INSTALLED-OBSERVATION.json) оставляет OPEN legacy
uplink, WAN/VPS discovery, shared input и полный latency/soak.
[Исследование и исправление discovery](DIRECT-MDNS-DISCOVERY-RESEARCH.md),
[неизменяемый срез прототипа](DIRECT-MDNS-PROTOTYPE-OBSERVATION.json).

Продолжение [анализа смены сети и частоты кадров](STREAM-NETWORK-CADENCE-FOLLOWUP.md).
Время измерений — UTC. Этот документ фиксирует новые проверки; прежний JSON-срез

## Дефект, обнаруженный на одной машине

подтверждена завершённой командой и SHA-256 установленного `base.apk`:

Остальные 14 доступных совместимых эмуляторов в этом срезе сохраняют APK55.
Шесть offline-записей не имеют подтверждённого текущего пакета и queued grant.

Проверка APK56 выявила нарушение восстановления декодера. Повтор неподвижного
изображения на целевой частоте обновлял тот же таймер, который ограничивает
запросы ключевого кадра. При 30 FPS таймер сдвигался каждые 34 мс; новый SYNC
подавлялся до истечения 250 мс, которых уже не наступало. Метод возвращал успешное
принятие запроса, хотя `MediaCodec.setParameters(REQUEST_SYNC_FRAME)` не вызывался.
Поэтому после сброса очереди поток мог продолжать получать delta-кадры и не
восстановить изображение. Успешные ICE/DTLS и сетевой RTT около 1 мс этого не
исключали: выбранный путь, полученные пакеты и отрисованные кадры — разные сигналы.

Распространение APK56 остановлено. В адресном диспетчере действует hold, который
запрещает дополнительные публикации и команды установки отвергнутого кандидата.
Обычный канал Android этим canary не заменён; данные приложения не очищались.

## Исправление

В [H264Encoder](../../../android/app/src/main/kotlin/com/sphereplatform/agent/streaming/H264Encoder.kt)
используются два независимых времени: последняя подача кадра для ограничения
частоты и последний фактический SYNC-запрос для ограничения ключевых кадров.
Подача idle-кадра больше не сдвигает время SYNC-запроса. Сохраняются одна ожидающая
RAW-подача, ограничения очереди, возрастающее PTS, владение codec и отказ от
повторения операции с неизвестным результатом.

[Регрессионный тест](../../../android/app/src/test/kotlin/com/sphereplatform/agent/streaming/PlanarKeyFrameRefreshTest.kt)
сначала подаёт десять idle-кадров через 33 333 334 нс, затем запрашивает SYNC и
проверяет реальный вызов codec. Следующие восемь запросов проверяют, что лимит
250 мс продолжает работать независимо от idle-частоты. До исправления тест упал
на первом ожидаемом вызове `setParameters`; это воспроизведение исходного дефекта.
После исправления прошли все 42 теста `PlanarKeyFrameRefreshTest`,
`StreamingCaptureLifecycleTest` и `H264EncoderConfigTest`: 0 failures/errors/skips.
Сборка выполнялась без build cache и повторно сгенерировала KSP-артефакты.

APK имеет новую монотонную версию `1.2.57-dev / 10257`; APK56 с тем же
versionCode другим содержимым не подменяется. Полная локальная сборка без build
cache прошла lint, подпись и по 1041 тесту dev/enterprise: 0 failures/errors,
3 skips на вариант. Точная Android CI-сборка исходника `52d3e58a` также прошла
[все обычные и экспериментальные профили](https://github.com/RootOne1337/sphere-platform/actions/runs/38169292540).
SHA-256 установленного PH010 подтверждён:
`4e47ed861c9ce161ec3b7144f817395aff6fd74277261dfb2c1e8fb2ba57f588`.

## Следующий кандидат: сохранение цепочки закодированных кадров

Регрессия `DirectEncodedVideoSourceTest` подаёт корректный IDR, два последовательных
delta и новый IDR. Запрос нового ключевого кадра во время первой delta не должен
уничтожать действующую цепочку. До исправления получен `expected 3, actual 1`:
адаптер сам выбрасывал исправную delta, а затем блокировал её продолжение.
Исправление запрашивает IDR асинхронно и пропускает непрерывную цепочку; второй
тест подтверждает, что настоящая пропущенная reference всё ещё блокирует delta.

Для общей MediaCodec-цепочки отключён внутренний raw-frame dropper WebRTC;
это отдельный механизм от Java budget. Его режим описан в
[исходнике WebRTC](https://webrtc.googlesource.com/src/+/refs/heads/main/video/video_stream_encoder.cc).
Уже закодированные H.264 pictures нельзя отбрасывать как независимые RAW-кадры.
Сохраняются ограничения памяти и запрет передачи delta после действительного
разрыва. Добавлены агрегаты encodeCalls, keyframeWaitDrops, pausedFrames,
keyframeHints, syncRequests, forwardedBytes и предложенных WebRTC bitrate/FPS.
В снимки не попадают SDP, IP, ключи, изображения или события по каждому кадру.

Кандидат `1.2.58-dev / 10258` требует полной подписанной сборки, адресной установки,
сравнения received/encode/forwarded/decoded и повторной проверки native UP.
Координированное изменение source bitrate по congestion control остаётся отдельным
непройденным gate: запись предложенного bitrate не означает его применение.

Это короткое наблюдение конкретного контекста, а не полная задержка отображения
и не приёмка обычного Chrome, ноутбука или смены Wi-Fi на мобильную сеть.

Проверка ввода затем обнаружила `fenced` без восстановленного управления;
конечный жест не отправил ни одного события, native UP не подтверждён.
Такой результат не принимается за рабочий прямой ввод APK58.
Две регрессии веба воспроизведены тестами до исправления:

1. Read-only → управление оставлял peer без отдельного control channel.
   При возврате в просмотр новый render терял callback отзыва старого handle.
   Переговоры теперь зависят от наличия разрешённого callback, а не его identity;
   отзыв принадлежит прежней сессии. Запоздалый callback не возвращает управление.
2. Отзыв STARTUP до ответа `touch_session` игнорировал позднюю identity и поэтому
   не мог сопоставить настоящее RELEASE. Теперь identity может использоваться
   только для завершения уже отозванного owner; STARTUP/касания его не оживляют.
   Чужая identity, неизвестное освобождение и таймер не дают права на новую команду.

После исправления проходят 595 тестов 29 наборов stream/probe/metrics и TypeScript.
Эти изменения веба ещё требуют отдельной установки и повторной аппаратной проверки
DOWN/MOVE/UP, переключения режима и переподключения; массовая рассылка APK58 удержана.

## APK59: политика каждой новой фабрики и аппаратный canary

В APK58 field trials задавались при глобальной инициализации SDK. В современной
фабрике используется собственный Environment; deprecated global initialization
не является договором для каждого нового peer factory. APK59 задаёт ту же
политику через `PeerConnectionFactory.Builder.setFieldTrials` при **каждом**
создании фабрики. Наличие этого метода проверено в фактически закреплённом
`io.getstream:stream-video-webrtc-android:146.7.0`, а связь builder с Environment —
в [первичном исходнике WebRTC](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/api/org/webrtc/PeerConnectionFactory.java).
Режим не отменяет memory budget, проверки access units и разрыва действительной
reference-цепочки; предложенный congestion bitrate всё ещё не считается
применённым source bitrate.

APK59 `1.2.59-dev / 10259`, исходник `bb7f315d`, собран заново без производных
build caches: lint, подпись, по 1043 теста dev/enterprise, 0 failures/errors,
3 skips в каждом варианте. SHA-256:
`a33dc8e7e7bfffdb24001ab733a58839228f4eb01d9ec60e3278ed7ec120796b`.
PH010 обновлён штатной адресной OTA-командой; подтверждены её результат и SHA
установленного `base.apk`. Данные приложения не очищались.

В отдельном Chrome-контексте с числовыми ICE-кандидатами подтверждены:

1. Управление → просмотр → управление: прежний owner освобождён, новый канал ready.
2. Жест после смены режима: 13 событий, 13 успешных native input receipts,
   terminal UP подтверждён, серверных touch events — 0.
3. Один синтетический `online`: старый video peer закрыт, новый подключён,
   управление снова ready. Физическая сеть при этом не менялась.
4. Жест после reconnect: 14 событий, 14 успешных native input receipts,
   terminal UP подтверждён, серверных touch events — 0.
5. Следующие 741,425 секунды наблюдения: 21 530 декодированных кадров,
   28 FPS в последнем секундном окне, 960×540; freezes/pauses/drops и
   packet loss/NACK/PLI/FIR — 0. Сам закрытый предыдущий peer не включён
   в эти счётчики.

После закрытия только тестового viewer получен агрегат **текущего процесса APK59**:
received = encodeCalls = forwarded = 22 985; keyframeWaitDrops, budgetRejected,
invalidAccessUnits, failed и retained input/output frames/bytes — 0.
Отбор по текущему process identity исключил старые logcat-строки APK58;
PID, исходные логи, SDP, IP и ICE keys в публичное свидетельство не сохраняются.

## Корневой адрес review gateway

Найдена отдельная реальная ошибка входа в веб: GET `/` на 3015 возвращал
`Location: http://127.0.0.1:8080/dashboard`. Пользовательский браузер переходил
на внутренний порт gateway и получал отказ соединения. `absolute_redirect off`
оставляет относительный `/dashboard`, сохраняя внешний host, HTTPS и порт.
Регрессия запускает настоящий изолированный nginx: до исправления неверный
Location воспроизведён, после него проходят 15 gateway checks.

Проверенный шаблон установлен reload без замены контейнеров; сохранены IDs всех
46 контейнеров. На 3015 и Tuna root возвращает относительный redirect,
а конечный dashboard — HTTP 200. Этот фикс входного адреса не является
исправлением ICE-маршрута или Android latency.
