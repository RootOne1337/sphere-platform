## Найденное ограничение: F32-26

**P1 / Medium / native reproduction.** `DagRunner` сохраняет отмену сразу, но
`sleep` выполняет один полный `delay(ms)` и проверяет её только после действия.
В connected-stop с 10-секундным sleep результат пришёл примерно через 10 секунд
после stop; в network probes ожидание достигало примерно 70 секунд. Это измерение
stop → terminal API, не чистой сетевой задержки; точные samples — в evidence.
Следующее действие не выполнялось, но обещать немедленную остановку нельзя.

Affected: [DagRunner.kt](../../../android/app/src/main/kotlin/com/sphereplatform/agent/commands/DagRunner.kt),
ветка sleep и границы проверки cancellation. **Fix ещё не внесён:** требуется
прерываемое ожидание без изменения безопасного поведения root side effects;
regression должен отменять долгий sleep и проверять bounded latency, отсутствие
следующего эффекта и сохранность terminal receipt. Не снимать SQL fence по таймеру.

## Что остаётся открытым

- Быстрая кооперативная остановка sleep, physical root interruption и reboot/replay
  на 1.2.8; этот прогон не повторял reboot или прерывание OTA.
- Pilot DB login — owner/superuser с обходом RLS. Native успех не заменяет отдельные
  non-owner/NOBYPASSRLS tests и runtime-role deployment acceptance.
- Backend здесь перезапущен штатно; OS-kill, отказ PostgreSQL/Redis, batch/nested
  recovery имеют отдельные tests, но не воспроизведены всей новой native связкой.
- Decoder queue/error recovery, сквозной preview profile, общий command/video
  budget и Redis pressure/recovery остаются P0 перед нагрузкой 32. Последующий
  [AUD-139](REDIS-MEMORY.md) исправил container memory mismatch без restart;
  slow-client/eviction и масштабная приёмка остаются открытыми.
- Native concurrent fleet OTA, VPN end-to-end, независимый резервный ingress,
  latency/FPS/PSS под нагрузкой и успешные восемь часов не подтверждены.

Backup/старые образы сохранены приватно. Автоматического downgrade БД или возврата
старых writers нет: новые stop/lease intents требуют reconciliation. Следующий
этап — оставшиеся Fleet32 P0 fixes и новый ограниченный runtime-прогон, затем ramp
4/8/16/32; эта canary сама по себе разрешением на массовую нагрузку не является.
