Pilot сейчас использует owner/superuser DB login; его успешная canary сама по себе

Исходные версии backend/frontend и raw crash buffers сохранены приватно в

## Последовательность и критерии

1. Зафиксировать source revision, собрать образы из Git archive и pilot APK с
   подписанным discovery. Сверить package, version, signing certificate и checksum.
2. Сохранить backup нового PostgreSQL и проверить восстановление в изолированной
   БД; сохранить прежние образы, OTA-каталог и Compose override.
3. Доставить APK адресно через действующий OTA-канал сначала на одно устройство.
   Не менять общий Android release до проверки; ADB нужен для наблюдения, а не
   установки или ручного запуска приложения после OTA.
4. При отсутствии активной работы остановить старые backend workers, применить
   миграции и заменить только backend/frontend нового pilot. Смешанной версии
   writers быть не должно. Старый `sphere-platform`/`sphere-tunnel` не изменять.
5. Проверить task/pipeline receipts, durable stop, потерю/восстановление связи,
   отсутствие следующего действия после подтверждённой отмены и отсутствие новых
   crashes. Обновить второе устройство и сверить тот же контракт.
6. Опубликовать результат с точными версиями/хешами и только после приёмки обновить
   локальный LATEST artifact и обычный OTA-канал.

При неоднозначном результате изменяющий запрос не повторять вслепую: сверять API,
SQL и APK journal. Ошибка canary останавливает расширение. Возврат к старым writers
после создания новых stop/lease intents требует reconciliation; наличие старого
образа не означает безопасный автоматический rollback данных.
