# AUD-128: отказ stop-связи больше не завершает задачу в SQL

**20 сентября 2026 · High · исправлена часть F32-01 на уровне исходного кода.**
Исторический срез `6815879`; на pilot он не устанавливался. Последующий
[AUD-129](DURABLE-CANCELLATION.md) заменяет временный HTTP503 контракт сохранённой
отменой с HTTP202 и ожиданием terminal receipt. Ниже сохранены исходные evidence
и границы AUD-128, а не описание текущего исходного кода.
[Общий preflight 32](FLEET32-PREFLIGHT.md) · [Evidence](evidence/stop-delivery-regression.json).

## Дефект и доказательство

В [TaskService.force_stop_task](../../../backend/services/task_service.py) результат
`send_command_live=False` игнорировался; отсутствие publisher также считалось
нормальным. После этого снималась Redis-блокировка и сохранялся CANCELLED.
Настоящий `POST /api/v1/tasks/{id}/stop` возвращал `200 / stopped`, хотя в Redis
не было подписчика на канал устройства. Пользователь мог считать выполнение
остановленным, а поздний настоящий результат игнорировался из-за terminal status.

На исходном `d43d7e5` **восемь новых проверок упали**: реальный endpoint с нулём
подписчиков; False/None/неверный тип результата; отсутствующий publisher; ошибка
и зависшая отправка; последующий настоящий результат. Это PostgreSQL/Redis в
выделенном loopback окружении. Исключение/зависание задавались double, Redis
no-subscriber case проходил через настоящий `PubSubPublisher`. Import/fixture
errors отсутствовали; внешние APK/сервисы не затрагивались.

## Минимальное исправление

- При отсутствии publisher, результате не `True`, ошибке либо timeout API
  возвращает **503: остановка не подтверждена; задача остаётся активной**.
- Публикация ограничена двумя секундами и выполняется один раз. Нет автоматического
  повторения изменяющей команды при неопределённом результате.
- Ни статус, ни finished_at/result, ни device lock не меняются в этом пути.
- `CancelledError` запроса распространяется; он не превращается в успех и не
  запускает повторную публикацию. HTTP-ответ не раскрывает transport exception.

Тесты успешной публикации теперь возвращают явный `True`, соответствующий
контракту publisher, вместо неявной truthiness `AsyncMock`.

## Regression и ограничения

[Новые regressions](../../../tests/production/test_stop_delivery_failure.py):
9 cases; вместе с serialization/tenant/rollback/control-identity scenarios —
**26 passed**, Ruff и целевой mypy прошли. После отвергнутого stop настоящий
task completion всё ещё сохраняется и безопасно освобождает соответствующую
блокировку. Отмена запроса проверяется отдельно от transport timeout.

Согласованные границы этого атомарного fix:

1. Успешный Redis publish означает наличие подписчика, **не остановку Android**.
   Историческое поведение этой ветки пока сохранено; F32-01 не закрыт целиком.
2. Timeout может произойти после фактической публикации: повтор возможен только
   после проверки состояния; durable reconciliation ещё нужен.
3. QUEUED/ASSIGNED, pipeline child, scheduler/watchdog/batch stop writers требуют
   общего следующего контракта cancel intent → terminal device receipt.
4. Изменение не устанавливалось на pilot; native stop/rollback и frontend
   отображение pending/unknown будут приниматься вместе с полным контрактом.

Доказательства исходного Fleet32 среза сохранены как исторические: они не
переписываются задним числом под исправленное поведение.
