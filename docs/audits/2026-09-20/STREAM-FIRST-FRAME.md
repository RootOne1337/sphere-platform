# AUD-140 — восстановление первого кадра видеопотока

**23 сентября 2026 · F32-29 · P0 / High до Fleet32 · исправление в коде PR19; удалённая приёмка OPEN.**

[Fleet32 readiness](FLEET32-PREFLIGHT.md) · [Эксплуатационная готовность](../../operations/READINESS.md) · [Предыдущий аудит декодера](DECODER-RECOVERY.md)

## Влияние

WebSocket мог открыться и продолжать отвечать на ping, пока браузер не получил ни
одного декодируемого изображения. В таком случае экран оставался чёрным, а интерфейс
показывал «Подключение…». Это блокирует визуальный контроль удалённых устройств и
будущий поток наблюдений для внешнего потребителя данных, даже если карточка
устройства остаётся в сети.

## Первопричина и доказательство

`VideoStreamBridge.register_viewer()` отправляет `start_stream`, а WS-обработчик
затем один раз отправляет `viewer_connected`. Android обрабатывает эти команды
отдельными coroutine: `start_stream` только запускает activity захвата экрана;
энкодер появляется позднее, после выдачи MediaProjection. Если `viewer_connected`
приходит в это окно, `StreamingManagerImpl.onViewerConnected()` видит `encoder == null`
и не может запросить IDR. Это допустимая гонка инициализации, а не доказательство,
что она произошла в конкретном удалённом сеансе.

В активном интерфейсе `DeviceStream` запускал повторы `request_keyframe` только из
обратного вызова ошибки или восстановления декодера. При исправном декодере, который
не получил первый IDR, ошибки не возникало, обратный вызов не вызывался, а ping по
WebSocket не позволял watchdog заметить отсутствие изображения. Клиент не повторял запрос.

Регрессионный тест открывает WebSocket и намеренно не подаёт ни кадр, ни ошибку
декодера. **До изменения он падал:** после 1,1 секунды отправлялось только сообщение
авторизации, запроса IDR не было. Это доказывает дефект поведения браузера. Ранее
наблюдавшиеся удалённые SPS/PPS без IDR остаются отдельным runtime-симптомом:
тест не устанавливает, на каком участке реального удалённого тракта терялся IDR.

## Исправление и затронутые файлы

- [DeviceStream.tsx](../../../frontend/components/sphere/DeviceStream.tsx) начинает
  запрос ключевого кадра через 1,1 секунды после открытия socket. Следующие запросы
  идут с паузами 2, 5, 10 и максимум 20 секунд до первого нарисованного кадра.
- После первого кадра таймер останавливается. Ошибка декодера может запустить его
  снова; socket close, смена устройства и unmount очищают таймер.
- UI различает подключение WebSocket и ожидание изображения: отображает
  «Ожидание видеокадра…», пока не получен первый decode output.
- [reconnect.test.tsx](../../../frontend/__tests__/stream/reconnect.test.tsx)
  проверяет отсутствие IDR, расписание запросов, остановку после изображения и повторный
  запуск recovery после последующего сбоя декодера.

Формат WS-сообщений и видеопакета не менялся; обратная совместимость сохранена.
Повтор использует существующее WS-сообщение. Отдельная Android-гонка, при которой
одноразовый запрос терялся до готовности encoder, разобрана и исправлена в
[AUD-142 / F32-31](ANDROID-KEYFRAME-STARTUP.md).

- После исправления: тесты переподключения стрима **10/10**, весь frontend **265/265 в 30

- Android dev и enterprise flavors: **108 связанных JVM-тестов на каждый flavor**

  stream handler, bridge и clone-registration regressions: **31 passed**.

  ESLint-конфигурация, поэтому `next lint` открыл интерактивный мастер и завершился
  с кодом 1. Никакая конфигурация не создавалась.

## Остаточный риск и допуск

Исправления браузера и Android закрывают две подтверждённые точки потери команды,
но не доказывают, что Android-энкодер выдаёт IDR, что APK успешно отправляет двоичные
кадры, что backend/Redis их доставляет или что браузер поддерживает конкретный codec.
Нужна отдельная удалённая проверка одного устройства с безопасными счётчиками на
границах захват экрана → энкодер → WebSocket APK → backend/Redis → декодер браузера. Исходное
наблюдение SPS/PPS без IDR нельзя считать исправленным только по unit tests.

## Повторная проверка пилота — 2026-09-24

За свежие 30 минут public gateway записал 7 успешных `101`-upgrade для
`/ws/stream`, а backend — ровно 7 подключений и 7 отключений viewer. Длительность
сессий: 7,697–10,109 секунды; временные метки закрытия gateway укладываются в
2 миллисекунды. Владелец подтвердил, что запускал просмотр сразу для нескольких
устройств, проверял отсутствие картинки и затем выключил потоки. Это объясняет
наблюдаемую группу закрытий и не является доказательством тайм-аута Cloudflare.
`101` подтверждает WebSocket handshake через gateway, но ничего не говорит о
прохождении SPS/PPS/IDR или декодировании кадра. Логи `cloudflared` за тот же
интервал пусты; это также не доказывает отсутствие сетевых проблем.

Отдельно зафиксировано 480 событий `android_ws: invalid_token`, все с одной
идентичностью устройства. Они не совпадают по смыслу с семью viewer-сессиями.
Это самостоятельный сигнал отказа Android-аутентификации; версия APK этого
устройства в этих логах не подтверждается, поэтому связывать его с конкретной
установленной сборкой пока нельзя.

Во время проверки работающий pilot frontend имел revision `9924eb1`, который
предшествует fix `717c5a1`. Из чистого frontend checkout на `48c9480` локальный
pilot frontend был пересобран и заменён отдельно: новый container healthy,
`/login`, `/dashboard` и `/stream/<fixture>` ответили HTTP 200; скомпилированный
bundle содержит `request_keyframe`. Backend (`ff87b56dbbd7`) и Cloudflare
container не пересоздавались. После этого обновления реальный удалённый кадр ещё
не подтверждён, поэтому результат не считается end-to-end приёмкой.

Профильная регрессия `reconnect.test.tsx` прошла 10/10; production build и
type-check завершились успешно. Build вывел предупреждение Next.js о недостающем
`page_client-reference-manifest.js` при копировании trace для `/dashboard`.
Runtime healthcheck и три HTTP-маршрута прошли, за следующие пять минут в логах
frontend в пятиминутном окне проверки не было `Error`, `ENOENT` или HTTP 500.
Предупреждение сохраняется как отдельный packaging-риск и не считается
доказательством или исправлением проблем потока.

Новая версия frontend теперь установлена в локальный pilot. До подтверждения
реального кадра с удалённого устройства и совместного 32-device fault/soak
решение для Fleet32 остаётся **NO-GO**. F32-28 коллизии идентичности клонов,
WAN TLS/HTTP2 OTA и сбои Android захвата/энкодера этот UI fix не исправляет.
