# AUD-130: ограничение принятых pipeline и проверка SQL-ожиданий

**20 сентября 2026 · High / F32-05 · source fix; на pilot не установлен.**

[Fleet32 preflight](FLEET32-PREFLIGHT.md) · [Отмена AUD-129](DURABLE-CANCELLATION.md) · [Readiness](../../operations/READINESS.md)

## Дефект и причина

В [PipelineExecutor](../../../backend/services/orchestrator/pipeline_executor.py)
каждый опрос забирал ещё десять QUEUED runs, сохранял RUNNING и создавал coroutine.
Семафор ограничивал только вход в выполнение. Уже принятые задачи могли бесконечно
накапливаться в памяти, а SQL показывал работу, для которой ещё нет свободного
исполнителя. При потере worker очередь за семафором становилась осиротевшей RUNNING.

Исходный Fleet32 probe показал 32 RUNNING при десяти исполняемых runs. Новые
регрессии на `4b96ba2` подтвердили превышение при последовательных и конкурентных
опросах, нескольких workers, частичном освобождении слотов и остановке executor:
**9 failures / 1 pass** до изменения. Среди проверок — очередь 1000 runs.
Результаты и границы сохранены в [evidence](evidence/pipeline-admission.json).

## Исправление

- Число SQL claims равно свободным слотам: `10 - len(active_tasks)`.
  Остальные записи остаются QUEUED в PostgreSQL, без coroutine за семафором.
- Один lock защищает расчёт ёмкости, SQL claim/commit и регистрацию задач.
  Конкурентные poll одного executor не используют одни и те же свободные слоты.
- Между workers сохраняется `FOR UPDATE SKIP LOCKED`; порядок равных timestamps
  уточнён UUID. Завершение coroutine освобождает ровно один слот.
- При заполнении всех слотов cancellation reconciliation продолжает работать.
  Ошибка до commit не запускает работу и не расходует ёмкость.
- `stop()` закрывает admission. Незакоммиченный claim откатывается; уже отправленный
  commit учитывается в ожидании активных задач. Повторный запуск того же остановленного
  объекта запрещён. Лог сообщает оставшиеся runs, а не утверждает их завершение.

Это **десять принятых runs на один executor/process**. Четыре workers могут принять
сорок. Исправление не вводит общую квоту на кластер или устройство.

## Проверки

[Десять PostgreSQL regressions](../../../tests/production/test_pipeline_admission.py)
после исправления прошли. Проверяются 32/1000 queued, четыре конкурентных poll,
четыре executor с разными SQL sessions, повторное использование трёх слотов,
отказ commit, cancellation при полной ёмкости и stop до/после начала commit.

SQL настоящий; выполнение Android заменено управляемым ожиданием. Четыре executor
работают в одном тестовом event loop, а не в четырёх OS processes. Это проверка
claim/конкурентности, не измерение производительности 32 реальных эмуляторов.

Отдельно закреплены [три runtime SQL regressions](../../../tests/production/test_pipeline_wait_connections.py)
для F32-04: настоящий delay, ожидание Task и вложенного PipelineRun. Используется
пул **из одного соединения**, `idle_in_transaction_session_timeout=900ms`, проверка
`pg_stat_activity` до/после timeout и конкурентный контрольный SQL-запрос. Все три
pipeline завершаются успешно; `idle in transaction=0` в проверенных точках. Child
receipts в этих тестах задаёт fixture, а не APK. Освобождение транзакций реализовано
предыдущим AUD-129; здесь добавлено доказательство его runtime-поведения.

Проверки используют только выделенные loopback PostgreSQL/Redis. Сырые логи и
JUnit остаются приватными; публичная сводка содержит только счётчики и условия.

**Полный локальный backend-прогон: 1815 passed**, пять существующих deprecation
warnings; исключены только явно выделенные load profiles. Все 13 новых проверок
вошли в этот набор. Целевые Ruff (executor и новые tests) и mypy (executor) прошли.
Это локальный результат; CI нового исходного коммита проверяется отдельно.

## Остаточные риски и следующий шаг

1. **F32-02 остаётся OPEN:** у RUNNING нет lease/generation и durable step checkpoint.
   Потеря worker либо неизвестный результат commit требуют reconciliation;
   принятые записи нельзя слепо возвращать в QUEUED и повторять внешние действия.
2. Родитель `sub_pipeline` занимает слот во время ожидания child. Если все слоты
   заняты родителями, дочерняя работа может ждать до timeout. Нужен сохраняемый
   WAITING/checkpoint и безопасное освобождение слота, согласованные с recovery.
   Этот путь существовал и до исправления admission; увеличение лимита его не решает.
3. Pause/resume, глобальный timeout, общая/per-device квота и fencing позднего owner
   ещё требуют общей реализации восстановления. Одного ограничения очереди мало.
4. Проверки `stop()` относятся к executor API. Pipeline startup пока не регистрирует
   собственный shutdown hook; текущий 30-секундный drain не доказывает прекращение
   child task на Android и не обеспечивает crash recovery. Это не закрытие lifespan gate.
5. F32-04 проверен для трёх обычных ожиданий. Rollout, отказ SQL во время результата,
   сложные вложенные handlers и большой парк не приняты этими тестами.

Backend `85fb1ea`, frontend `03b161e`, APK `1.2.7/10207` этим изменением не обновлялись.
Для закрытия F32-05 нужны также общая политика admission, nested recovery и приёмка
развёрнутого backend. Длительный смешанный тест 32 устройств остаётся **NO-GO**.
