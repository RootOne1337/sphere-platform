## Причина и влияние

Три исходных hook запрашивали одну страницу `per_page=100`. Helper оставлял только
`items`: `total`, `page`, `per_page`, `pages` терялись. Оператор не мог открыть
101-й конвейер, запуск или расписание. Число строк первой страницы отображалось
как размер каталога. Доля завершённых запусков рассчитывалась по первой странице,
а область этого показателя не объяснялась.

Формы расписаний дополнительно строили выбор конвейера из списка главной страницы.
Переходы между страницами не должны менять уже сохранённую цель расписания или
делать её недоступной для редактирования остальных полей.

## Проверенный контракт сервера

| Источник | Endpoint | Поддерживаемые фильтры | Пагинация |
|---|---|---|---|
| Конвейеры | `GET /pipelines` | `is_active`, `tag` | `page`, `per_page`, максимум 200 |
| Запуски | `GET /pipelines/runs` | `pipeline_id`, `device_id`, `status`, `active_only` | `page`, `per_page`, максимум 200 |
| Расписания | `GET /schedules` | `is_active`, `target_type` | `page`, `per_page`, максимум 200 |

Источник контрактов: [Pipeline router](../../../backend/api/v1/pipelines/router.py),
[Schedule router](../../../backend/api/v1/schedules/router.py),
[Pipeline service](../../../backend/services/orchestrator/pipeline_service.py),
[Schedule service](../../../backend/services/scheduler/schedule_service.py).

`active_only` включает `queued`, `running`, `waiting`, **`paused`**. UI использует
этот же состав для счётчика активной очереди. Список `status` соответствует
[PipelineRunStatus](../../../backend/models/pipeline.py).

Эти endpoints не принимают свободный текстовый `search`/`query`. UI не отправляет
параметр, который сервер молча проигнорирует. Реализованы страницы и существующие
серверные фильтры активности/статуса; текстовый поиск явно ограничен загруженной
страницей. Глобальный текстовый поиск требует отдельного расширения API.

## Поведение после изменения

- У каждой вкладки собственные `page` и серверный фильтр. Переход на соседнюю
  вкладку сохраняет страницу; смена фильтра возвращает выбранную вкладку на page 1.
- Query key содержит ресурс, страницу, размер и фильтр. Axios получает `AbortSignal`;
  поздний ответ предыдущего фильтра не отображается в новой выборке.
- Ответ сохраняет весь envelope. Проверяются запрошенные `page`/`per_page`, `total`,
  `pages`, размер результата, уникальные IDs и необходимые для строк поля.
  Неверный ответ становится ошибкой чтения до появления действий строки.
- Числа во вкладках и «всего» берутся из `total` API с выбранным серверным фильтром.
  Нельзя считать отфильтрованную страницу размером всей организации.
- Счётчики статусов, активных расписаний и доля завершённых запусков обозначены
  как показатели загруженных страниц. Завершённый report не доказывает текущую
  работу Android. Backend-wide success rate здесь не имитируется.
- При ошибке обновления старые строки, действия, pagination и счётчики скрыты;
  есть отдельный retry. Error не превращается в подтверждённый пустой каталог.
- Если после изменения каталога запрошенная страница больше последней доступной,
  UI возвращается на доступную страницу. Выборки разных tabs не смешиваются.
- Обновление работает в foreground: активная вкладка запусков — 5 секунд,
  конвейеров/расписаний — 8 секунд. Остальные вкладки не имеют interval polling;
  React Query сохраняет стандартные focus/reconnect/read semantics.
- Поиск запусков сохраняет прежнее сопоставление по известному имени конвейера
  и дополнительно принимает ID запуска/конвейера/устройства и статус. Если имя
  не прочитано, показывается реальный pipeline ID. Весь каталог ради имён не скачивается.

Основные исходники: [page](../../../frontend/app/%28dashboard%29/orchestration/page.tsx),
[query hook](../../../frontend/src/features/orchestration/useCatalogPage.ts),
[envelope validation](../../../frontend/src/features/orchestration/listPayload.ts).

## Выбор конвейера в формах расписания

[PipelineCatalogPicker](../../../frontend/components/orchestration/PipelineCatalogPicker.tsx)
используется в Create/Edit. Он имеет собственную страницу и локальный поиск,
сохраняет выбранный ID при переходе на другую страницу или при скрытии результата
поиском. Уже существующая цель вне текущего ответа отображается отдельной
сохранённой option с ID. Выбор не подменяется первым доступным конвейером.

Ошибка каталога отключает неподтверждённый выбор и предлагает retry; текущий ID
не сбрасывается. Закрытая форма не инициирует чтение через picker. Отправку
сохранённого ID и валидность существующего расписания окончательно проверяет API;
наличие ID в поле не является свидетельством существования/активности конвейера.

Script picker и archive/rollback остаются отдельным [F27](../2026-10-01/WEB-FULL-CAPABILITY-AUDIT.md#f27).
Редактирование DAG конвейера остаётся [F28](../2026-10-01/WEB-FULL-CAPABILITY-AUDIT.md#f28).

## Оставшаяся приёмка

1. На установленной [Оркестрации](http://127.0.0.1:3015/orchestration) сверить build SHA.
2. Проверить геометрию таблиц/controls, keyboard/focus, небольшой viewport и тёмную/светлую тему.
3. Перейти между страницами каждого каталога; сопоставить total и серверный фильтр
   с API той же организации и роли. Не выполнять реальный запуск ради проверки навигации.
4. Открыть Edit расписания с конвейером вне первой страницы; проверить сохранённый
   ID, навигацию picker, затем закрыть без записи.
5. Подтвердить read errors и восстановление в разрешённой browser session.

API использует offset pagination, а каталоги меняются между чтениями. Переходы
по страницам не являются транзакционным экспортом всех записей за один момент:
вставка/удаление может сместить строки. Backend snapshot/cursor search, глобальные
аналитические агрегаты и экспорт требуют отдельного дизайна и tests. F13 исправляет
доступность страниц и достоверную область показателей; остальные findings не закрываются.
