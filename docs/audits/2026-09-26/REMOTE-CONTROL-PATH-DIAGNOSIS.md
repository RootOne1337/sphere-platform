## Что установлено

Текущий сбой затрагивает не только изображение. Удалённые APK проходят
WebSocket-авторизацию, но не поддерживают подтверждённый двусторонний канал:
нет свежего application heartbeat, короткая команда не получает результата,
подключения повторяются примерно раз в 47 секунд. Поэтому до восстановления
управляющего канала нельзя считать decoder или UI главной причиной инцидента.

**Точная причина разрыва пока не установлена.** Приоритетная гипотеза — участок
удалённый Android → сеть станции → публичный ingress. Возможны также зависание
APK/очереди отправки или различия установленной конфигурации. Успешные local
tests не исключают эти варианты. Смена close code и защита presence исправляют
реальные дефекты, но runtime показывает, что основную неисправность они не сняли.

## Почему Cloudflare нужно проверить первым

Cloudflare официально сообщает об ограничениях трафика российскими ISP,
включая передачу примерно первых 16 KB соединения: [service disruption](https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/).
Это внешний фактор риска для данной схемы. Он **не доказывает**, что конкретно
эти APK упираются в этот лимит: здесь не измерен порог TCP/TLS-байтов, а
наблюдаемые SPS/PPS-байты — другой уровень протокола. Нельзя приравнивать 5 KB
видеоданных в backend к 16 KB сетевого ограничения.

И локальная, и удалённая станция могут использовать один hostname и одного
провайдера, но проходить через разные сетевые маршруты. Поэтому работающий
локальный Android не снимает гипотезу неисправности удалённого пути. При этом
существование WebSocket-поддержки у Cloudflare не гарантирует прохождение
конкретного соединения из конкретной сети.

## Независимые подтверждённые дефекты

### P1 — транзакция синхронизации presence откатывается

`backend/tasks/sync_device_status.py` передаёт `live.status` в
`Device.last_status`. Redis и `DeviceLiveStatus` уже допускают `connecting`,
но `backend/models/device.py` и живой PostgreSQL enum содержат только
`online`, `offline`, `busy`, `error`, `maintenance`.

Backend пишет `InvalidTextRepresentationError` для `connecting`; обработчик
откатывает всю транзакцию. Безопасное воспроизведение на живой БД:

```sql
SELECT CAST('connecting' AS device_status_enum);
```

Результат: SQLSTATE `22P02`; записей в БД эта проверка не меняет. Один
неподтверждённый сокет может мешать сохранению статусов остальных устройств.
Это объясняет недостоверность persisted fallback, **не доказанную причину
разрыва WebSocket**. Исправление пока не внесено: сначала определить контракт
persisted статуса и сохранить regression с реальным PostgreSQL. Не добавлять
enum-миграцию автоматически, если transient `connecting` должен оставаться
только в Redis.

### P1 — версия в сборке не равна опубликованному OTA

Подробности в [аудите APK](ANDROID-PRESENCE-AND-APK-RELEASE.md): candidate
1.2.23 установлен только на локальный canary; `android/dev` и pilot alias
остаются на 1.2.9, `android-canary/dev` — на 1.2.19. Номер, показанный пользователю
на вручную установленном APK, не обновляет каталог. Нельзя заявлять доставку
новых исправлений удалённым Android без PackageManager/heartbeat/OTA receipt.

### P1 — отсутствует независимый проверенный резервный ingress

Проверенный discovery v24 на обоих локальных APK содержит единственный
Cloudflare management endpoint, без fallback. Повторное получение этого же
адреса через GitHub не создаёт независимый транспорт. При деградации единственного
канала обновление/диагностика через этот канал тоже могут не доходить.

## Следующая решающая проверка

1. Поднять независимый ingress к тому же **новому pilot**, проверить TLS,
   HTTP и авторизованный двусторонний WS. Старые проекты не использовать.
2. Перевести один удалённый canary с сохранением обратного маршрута. Получить
   доказательство нового Android ingress в gateway logs; одного успеха команды
   конфигурации недостаточно. Если команда недоступна, использовать проверенный
   подписанный bootstrap/recovery путь, а не повторять RPC без receipt.
3. Сначала проверить короткий command/result и несколько heartbeat-интервалов
   без видео. Затем открыть один stream и сопоставить APK encoder/queue,
   backend IDR ingress и реально декодированный кадр viewer.
4. На том же APK сравнить исходный маршрут. Если независимый путь работает, а
   исходный снова срывается, локализован транспорт. Если оба не работают —
   перейти к очереди/encoder/reader APK, сохранив свежие журналы canary.
5. Только после этого продвигать проверенный APK в нужный OTA channel и
   расширять rollout. Запросить и проверить terminal install receipts.

Не начинать очередной большой рефакторинг UI или decoder до этого сравнения.
Fleet32 остаётся **NO-GO**. Новый APK и смена туннеля в этой проходке не
публиковались; удалённая картинка не объявляется восстановленной.
