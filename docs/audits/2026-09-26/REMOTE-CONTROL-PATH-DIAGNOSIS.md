## Что установлено

Инцидент теперь разделён на два подтверждённых состояния. Удалённые
`auto-ph-022/023` передают видео через текущий Cloudflare ingress и отвечают на
команды; оператор подтвердил видимую картинку и клики. У другой удалённой группы
после авторизации нет подтверждённого heartbeat; адресный контрольный `PING` на
`019` не получил receipt. Это частичное восстановление, а не готовность всего
парка.

Статус `Connecting` в Fleet Matrix не означает, что WebSocket не установился:
backend сначала аутентифицирует сокет и записывает `connecting`, а переводит его
в `online` только после application-level `pong` (`backend/api/ws/android/router.py`,
`backend/websocket/heartbeat.py`). Поэтому у таких устройств есть
успешные HTTP 101/auth, но отсутствует подтверждённая двусторонняя готовность.
Для `auto-ph-019` Redis доставил безопасный `PING` активному backend subscriber,
но APK не прислал ни одного command receipt за 8 секунд. Тот же тест на
`auto-ph-023` вернул `received → running → completed` с `pong=true`.

**Почему часть удалённых Android не отвечает, пока не установлено.** У группы
`012–020` повторяются авторизации примерно раз в 60–64 секунды и закрытия
`1005` без close reason; нет `auth_ack_failed`, auth rejection или записанного
heartbeat-timeout события. У устройств без pong сервер также не знает версию APK.
Хотя оператор сообщает одинаковые условия удалённой станции, результаты
device-specific: часть устройств отвечает, часть нет; одинаковость установленных
APK не подтверждена. Это не доказывает сбой Cloudflare и не исключает локальный сбой Android-сервиса,
эмулятора или конкретного соединения. Для точной причины требуется свежая
клиентская диагностика с одного такого Android.

Cloudflare не является общим отказом: gateway зафиксировал Android WebSocket
трафик `022/023` через cloudflared; там же backend принял и переслал видеокадры.
Резервный LocalTunnel проверен как маршрут к правильной pilot-установке и
опубликован в signed discovery v25, но ни одного Android WebSocket через него
пока не зафиксировано. Следовательно, этот резерв ещё не проверен реальным APK.

Отдельно исправлена в исходниках ошибка синхронизации временного статуса
`connecting` с PostgreSQL enum; исправление прошло regression test и Ruff, но
не развёрнуто на pilot backend. Оно убирает ошибки и rollback в фоновой
синхронизации БД, но **не чинит отсутствующий pong или reconnect churn**.

## Дополнительная проверка presence-событий — source fix, ещё не развёрнут

Проверка полного WebSocket lifecycle выявила два дополнительных дефекта статуса:

1. При успешной авторизации backend уже записывал Redis `connecting`, но до
   любого ответа APK публиковал событие `device.online`. Локальный route-level
   regression сначала воспроизвёл это: подключение без единого `pong` всё равно
   вызывало `device.online` (1 failed до исправления). Это могло посылать ложный
   онлайн-сигнал подписчикам/webhook, хотя Fleet API ещё возвращал `connecting`.
2. Backend сериализует `FleetEvent` как `{event_type, ts}`, а frontend разбирал
   только `{type, timestamp}`. Regression с точным backend wire payload
   (`device.status_change`) завершался без invalidation (0 вызовов до исправления),
   то есть hook пропускал все серверные события.
3. После восстановления wire parsing оставался несовпадающий event name:
   backend фактически посылает `device.status_change`, а frontend слушал только
   `device.status_changed`. Оба дефекта исправлены: hook нормализует реальный
   backend payload и инвалидирует devices для серверного event name, сохраняя
   backward compatibility для прежнего `{type, timestamp}` формата.

Source fix: после успешной записи presence backend отправляет `device.status_change`
со статусом `connecting`; `device.online` публикуется только после первого `pong`,
который удалось сохранить для текущей WebSocket-сессии. Повторные pong не
дублируют онлайн-событие, устаревшая заменённая сессия не подтверждает online, а
неудачная запись Redis не публикуется как успешное состояние. Frontend принимает
точное серверное имя события и сохраняет совместимость со старым spelling.
Первый server heartbeat теперь отправляется сразу после соединения, а не после
ожидания полного 30-секундного интервала. Сохранившийся `connecting` имеет TTL
90 секунд вместо общего часового TTL offline-состояний; это ограничивает время
залипания после аварийного завершения worker без cleanup. Первый сохранённый pong
даёт INFO-диагностику с device/session, RTT и версией APK, если она передана.

После изменений тесты подтверждают: 1) backend-shaped JSON event payload
инвалидирует device query, 2) без pong публикуется только connecting,
3) первый сохранённый pong переводит состояние online ровно один раз,
4) потеря Redis записи допускает retry на следующем pong, 5) stale session и
неуспешная запись не порождают ложный online, 6) Fleet UI инвалидирует query по
фактическому `device.status_change`, 7) connecting TTL ограничен. Это улучшает
точность и скорость presence-диагностики, но **не доказывает, что Android из
группы `012–020` начнёт отвечать на heartbeat** и не объясняет чёрный экран.
Изменение остаётся source/PR-only до отдельного rollout и повторного live-среза;
pilot не перезапускался, APK не менялся.

## Cloudflare и альтернативные маршруты: вывод после live-среза

Документация Cloudflare содержит сведения о некоторых проблемах доступа через
российских ISP: [service disruption](https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/).
Это внешний фактор риска, но не доказательство причины наблюдаемой группы.
Новая корреляция показывает, что удалённые `022/023` установили Android WSS
через cloudflared, передали бинарные кадры, отвечали на PING и отображались у
оператора. Следовательно, Cloudflare не является общим отказом для всех удалённых
устройств. Сетевой маршрут всё ещё может вести себя по-разному для других
устройств/сессий; порог TCP/TLS и устройство-специфические сбои не измерены.
Нельзя приравнивать 5 KB видеоданных в backend к описываемому Cloudflare
ограничению первых 16 KB сетевого соединения.

И локальная, и удалённая станция могут использовать один hostname и одного
провайдера, но проходить через разные сетевые маршруты. Поэтому работающий
локальный Android не снимает гипотезу неисправности другого удалённого пути.
Опубликованный независимый fallback пока не наблюдался в Android gateway logs,
поэтому сравнительный эксперимент Cloudflare vs LocalTunnel остаётся открытым.

## Независимые подтверждённые дефекты

### P1 — транзакция синхронизации presence откатывалась (исправление в исходниках)

`backend/tasks/sync_device_status.py` передаёт `live.status` в
`Device.last_status`. Redis и `DeviceLiveStatus` уже допускают `connecting`,
но `backend/models/device.py` и живой PostgreSQL enum содержат только
`online`, `offline`, `busy`, `error`, `maintenance`.

Backend пишет `InvalidTextRepresentationError` для `connecting`; обработчик
откатывает всю транзакцию. За двухчасовое окно логи содержали 427 таких
ошибочных записей для `013`, 45 для `012` и 8 для `015` (число log events, не
подсчёт уникальных транзакций или потерянных строк). Безопасное воспроизведение
на живой БД:

```sql
SELECT CAST('connecting' AS device_status_enum);
```

Результат: SQLSTATE `22P02`; записей в БД эта проверка не меняет. Один
неподтверждённый сокет мог мешать сохранению статусов остальных устройств.
Это объясняет шум ошибок и rollback в синхронизации durable-состояния,
**но не является причиной отсутствующего pong или разрыва WebSocket**. В текущем исходнике transient `connecting`
сохраняется как допустимый durable `offline`; Redis/Fleet API продолжает отдавать
реальный `connecting`. Новый regression до фикса падал (`connecting` попадал в
enum), после фикса все 6 тестов файла проходят; Ruff также проходит. Исправление
ещё не развёрнуто в pilot. Enum-миграция не добавлялась.

### P1 — версия в сборке не равна опубликованному OTA

Подробности в [аудите APK](ANDROID-PRESENCE-AND-APK-RELEASE.md): candidate
1.2.23 установлен только на локальный canary; `android/dev` и pilot alias
остаются на 1.2.9, `android-canary/dev` — на 1.2.19. Номер, показанный пользователю
на вручную установленном APK, не обновляет каталог. Нельзя заявлять доставку
новых исправлений удалённым Android без PackageManager/heartbeat/OTA receipt.

### P1 — независимый ingress настроен, но APK-переключение не доказано

Подписанный pilot discovery v25 опубликован с независимым LocalTunnel fallback,
проверенным через изолированный sidecar до того же нового public gateway.
Gateway не видел ни одного Android `/ws/android/{id}` соединения от sidecar;
наблюдаемые Android WebSocket upgrades всё ещё пришли от cloudflared. Поэтому
fallback-конфигурация существует, но факт получения v25, переключения хотя бы
одного APK и двусторонней работы резервного маршрута **не подтверждён**. Ошибку
runner при адресной canary-команде нельзя интерпретировать как доставку или
недоставку `UPDATE_CONFIG`; слепо повторять изменяющую команду не следует.

1. Для одного устройства из `012–020`, пока оно в `connecting`, получить APK
   logcat/crash/service state через доступный диагностический канал и сопоставить

   Не считать отсутствие server-side close reason доказательством Cloudflare.

   доставить/подтвердить discovery v25, сохранив исходный endpoint. Переключение
   засчитывать только после gateway evidence от LocalTunnel sidecar, свежего
   heartbeat и command receipt; не повторять неизвестную по результату
   `UPDATE_CONFIG` вслепую.

### Что показал живой транспорт

В 12:08 UTC API содержал 16 устройств: 11 `online`, 5 `offline`; после старта
backend 14 разных устройств прислали подтверждённый первый pong, и все эти
идентификаторы присутствовали в API inventory. В последнюю минуту backend
зафиксировал 11 соединений, 11 первых pong и 11 закрытий; все 11 закрытий имели
server-side code `1005`. За весь интервал после rollout было 229 закрытий: 215
`1005`, 14 замен сессии `4009`; heartbeat-timeout и receive-loop ошибок не было.
Это доказывает продолжающийся reconnect churn, а не массовое отсутствие первичного
доступа. `1005` означает, что сервер не получил close status; сам по себе он не
указывает, кто закрыл TCP/WebSocket и почему, и не доказывает Cloudflare как
причину. В этой выборке не открывали видеопросмотр, поэтому она не подтверждает
ни доставку кадров, ни FPS.

без версии. Исправление ниже ещё не установлено на этих клиентах.

### Доказанный дефект Android reconnect policy

Перед исправлением две новые lifecycle-регрессии падали на текущей реализации:
закрытие без status code `1005` возвращало reconnect на primary вместо следующего
сохранённого маршрута; server close `4008/heartbeat_timeout` очищал token cache,
хотя backend использует `4008` для пропущенного heartbeat, то есть транспортного
сбоя, а не отказа учётных данных. Дополнительный сценарий моделирует наиболее
вероятное Android-представление потери TCP через `onFailure(IOException)`:
короткие авторизованные сессии ранее сбрасывали retry debt на каждом `auth_ok`,
поэтому последовательность быстрых обрывов не могла накопить circuit-breaker
threshold.

В source reconnect-счётчики теперь сбрасываются после 60 секунд непрерывной
авторизованной сессии. Короткое соединение/неожиданное закрытие идёт через
экспоненциальный jitter, поворот на следующий сохранённый route и существующий
circuit breaker. `4008` больше не очищает token cache; настоящий credential
rejection по `4001/4003/4004` по-прежнему запускает обновление токена. После
изменения проходят все 665 Android unit tests, целевые WebSocket suites и
`lintDevDebug`; `assembleDevDebug`, `assembleDevRelease` и `assembleEnterpriseDebug`
успешны. Source version увеличена до `1.2.25-dev` / `10225`. APK теперь пишет
компактные `ws_lifecycle` события для `onFailure`, `onClosed` и handshake
timeout: attempt, слот/число маршрутов, фазу, длительности, HTTP-статус, тип
исключения и close code. Структурированная запись не содержит URL, device ID,
token, текста исключения или close reason; два новых regression tests проверяют
обе callback-ветки и редактирование чувствительных значений. Первичная обычная
сборка не включала подтверждённый pilot discovery; после неё выполнен отдельный
candidate pipeline с подписанным discovery manifest v25 и локальной
pilot-подписью. OTA не публиковался, APK на устройства не устанавливался. Lint
завершился без ошибок, но
содержит 65 предупреждений (36 `GradleDependency`, 12 `UnusedResources` и 17
прочих); ни одно из них не относится к изменённым WebSocket-файлам. Это отдельный
технический долг, не основание считать reconnect-fix lint-clean во всём APK.

### Что это исправление пока не доказывает

1. Серверный `1005` не сопоставлен с конкретным callback удалённого OkHttp-клиента;
   нужны client-side события для canary и корреляция времени соединения.
2. Переменные pilot `PILOT_REMOTE_PRIMARY` и `PILOT_REMOTE_FALLBACK` сейчас
   содержат один и тот же URL. Поэтому перебор этих двух записей сам по себе не
   создаёт независимый туннель. Отдельный LocalTunnel ingress проверялся
   sidecar-ом, но Android traffic от него не подтверждён.
3. `4009` показывает вытеснение прежней сессии, но без безопасной корреляции
   идентичности процесса это не доказывает дублированный LDPlayer clone.
4. Этот APK source fix ещё нельзя считать live recovery fix: удалённые устройства
   продолжают работать на прежних версиях. Canary должен подтвердить минимум
   60 секунд стабильной сессии, отсутствие reconnect-storm, свежий heartbeat и
   командный receipt; video/FPS проверяются отдельно.

До такой canary-валидации Fleet32 остаётся **NO-GO**. Pilot debug APK не
является production-signed OTA artifact и не должен раскатываться на весь парк.

### Контролируемое восстановление control channel — 26 сентября

Первый эксперимент с `svc wifi disable` признан **недействительным**: вместе
с Wi-Fi пропал управляемый shell LDPlayer, и скрипт не смог выполнить обратную
команду. Сервер увидел canary `offline` и одно закрытие `1005`; для возврата
потребовалась точечная перезагрузка `LDPlayer-1` через host management. Это не
считается reconnect APK без перезапуска. После неё Wi-Fi снова был включён,
Android загрузился, процесс APK работал; в `14:21:12Z` API увидел устройство
`online`, свежий heartbeat и первый pong.

Повторный fault injection ограничивал исходящий трафик только Android UID APK
`10074` правилами owner-match в IPv4 и IPv6 `OUTPUT`; Wi-Fi и ADB shell оставались
доступны. До теста canary была `online` (heartbeat age 20 s), активного stream
viewer не было. Правила действовали 30 s; API зафиксировал `offline` при heartbeat
age 51 s. После удаления правил Android и LDPlayer не перезапускались: через
20.1 s два последовательных API-среза снова подтвердили `online` и свежий
heartbeat (последний age 5 s). Backend увидел один `1005`, один новый connect и
первый pong. Wi-Fi остался включён, `sys.boot_completed=1`, ADB отвечал.

Сохранившийся файл журнала APK содержит два redacted lifecycle callback для этой
попытки: authenticated `SocketTimeoutException` на slot 0 (session age 434.8 s),
затем pre-auth `IOException`/`EOFException` на slot 1. Это подтверждает локальную
диагностику client-side сбоя и failover-попытки; два route slot не доказывают
разные ingress, а успешный маршрут по slot 1 не подтверждён. Последняя
периодическая серверная загрузка (14:21:36Z) предшествовала этому fault test.
Однако on-demand путь проверен отдельно: в `14:30:58Z` запрос
`POST /api/v1/devices/{id}/logcat` с `mode=sphere` вернул HTTP 200, 380 строк /
65,466 символов, включая оба этих redacted callback. Это подтвердило доступный
control-channel запрос журналов через API/Redis к APK и обратно; проверен прямой
API-вызов, не визуальное отображение в браузере.

### Найденная потеря transport-диагностики при периодической выгрузке

После сетевого fault test периодический worker действительно выполнил новую
выгрузку: в `14:36:37Z` появилась 12-я секция журналов. Но в ней было 0
`ws_lifecycle` записей, хотя локальный файл APK их сохранял и on-demand запрос
вернул их ранее. Серверная секция содержала 174 строки / 32,953 байта; локальный
каталог логов — 4,983,118 байт. От последней локальной lifecycle-записи до конца
файлов накопилось 84,001 байт, тогда как `LogUploadWorker` запрашивает только
`readRecentLogs(32 KiB)`. Значит, обычный шум вытеснил редкое, но критичное для
разбора reconnect событие из файла, который уходит периодически. Это подтверждённый
дефект доставки диагностики (P2): live/on-demand путь работал, периодическая
выгрузка работала, но её ограниченный хвост не сохранил проверяемую причину.
Приватные сырые строки и ID не копировались в отчёт.

**P2 исправлен в `872c965`**: `FileLoggingTree` теперь сначала сохраняет
структурированные `ws_lifecycle` строки в отдельный sidecar `ws_lifecycle.log`
размером не более 64 KiB, удерживая последние записи; periodic worker добавляет
до 32 KiB этого приоритетного журнала после обычных секций. Unit tests проверяют,
что lifecycle-события переживают шумный обычный хвост, а sidecar остаётся
ограниченным и сохраняет последние записи. Затронутые файлы:
`android/app/src/main/kotlin/com/sphereplatform/agent/logging/FileLoggingTree.kt`,
`android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt`,
`android/app/src/test/kotlin/com/sphereplatform/agent/logging/FileLoggingTreeTest.kt`
и `android/app/src/test/kotlin/com/sphereplatform/agent/workers/LogUploadWorkerTest.kt`.

Повторная серверная проверка после изменения подтвердила восстановление доставки:
секция в `15:21:41Z` содержит обе lifecycle-записи app-only теста (два уникальных
события, без дублирования внутри секции). Предыдущая секция `14:36:37Z` после того
же outage содержала ноль таких записей. Это подтверждает периодический upload на
одной локальной canary; не доказывает доставку при длительном офлайне или
переключение ingress.

**P3 — совпадение двух источников** сначала было воспроизведено unit-тестом:
одна и та же строка присутствовала в 32-KiB обычном хвосте и priority sidecar,
поэтому собранный body содержал её дважды. На сервере этот эффект не был доказан:
серверная секция после outage содержала две уникальные записи, а не четыре.
Исправление в `d9e5c63` исключает из приоритетной секции строки, уже присутствующие
в обычном хвосте, сохраняя sidecar-only события. Regression до изменения падал
(две строки вместо одной), после изменения проходит с ровно одной строкой.

not duplicated when present in the regular tail`: до fix она ожидала 1 запись,
но получила 2. Версия APK поднята в `android/version.properties`.
