## ACCESS-01. Контекст расследования теряется на входе

При открытии защищённого пути без сессии `AuthInitializer` отправляет на `/login` без исходного маршрута и query. Оба успешных входа в `LoginPage`, включая MFA, заменяют URL на `/dashboard`. В фикстуре начальный путь `/tasks/fixture-task?tab=logs` привёл к `/login`, затем после ответа вошёл в `/dashboard`. Защищённое содержимое до входа не монтировалось. Отдельно проверен такой же результат после MFA. Для роли `api_user` RBAC не даёт `monitoring:read`, поэтому фиксированный переход дополнительно ведёт на экран недоступного раздела. [Guard](../../../frontend/app/providers.tsx#L24) · [Вход и MFA](../../../frontend/app/%28auth%29/login/page.tsx#L39) · [Маршруты](../../../frontend/src/features/access/routeAccess.ts#L1) · [RBAC](../../../backend/core/rbac.py) · [Jest](evidence/access-workflows.test.cjs).

Доработка. Сохранять разрешённый внутренний маршрут и поддерживаемые параметры на время входа. После верификации capability открыть прежний объект либо предложить доступное рабочее пространство с причиной. Принимать только известные маршруты текущего origin и параметры конкретного экрана. Для внешнего или неразрешённого адреса использовать доступную страницу. Вход по общему адресу может использовать роль и последнюю открытую доступную область.

Приёмка: пользователь открывает ссылку на задачу, журнал за выбранную дату и экран потока после истечения сессии. Вход паролем и MFA возвращает к разрешённому месту. У роли без мониторинга открывается доступная страница. Просроченная или отменённая попытка не меняет текущую сессию. События диагностики включают `request_id`, стадию `password|mfa|refresh`, итог и код причины. В журналы не попадают исходные параметры URL, пароль, одноразовый код и challenge.

## ACCESS-02. Временный пароль не имеет отдельного жизненного цикла

Форма создания пользователя подписывает обязательное поле «Временный пароль» и предлагает передать его человеку. API хеширует пароль и создаёт активную запись. Модель `User` хранит `password_hash`, роль, активность и MFA без срока bootstrap-учётных данных и признака обязательной смены. Обычный login проверяет тот же хеш при каждом входе. В штатных настройках доступны профиль, MFA и API-ключи; действия смены пароля нет. Следствие: оператор и новый пользователь могут считать, что переданный пароль перестанет действовать после первого входа или по сроку, а этот контракт отсутствует. Проверка выполнена по всей цепочке исходников, без выдачи настоящих учётных данных. [Форма](../../../frontend/src/features/users/UserDialogs.tsx#L65) · [Создание](../../../backend/api/v1/users/router.py#L80) · [Модель](../../../backend/models/user.py#L14) · [Вход](../../../backend/services/auth_service.py#L37) · [Настройки](../../../frontend/app/%28dashboard%29/settings/page.tsx#L169).

Доработка. Пока сервер применяет обычный пароль, интерфейс должен ясно описывать его срок и способ смены. Для расширения ввести приглашение с одноразовой активацией, сроком, статусом доставки, отзывом, повторной выдачей и установкой собственного пароля. Жизненный цикл приглашения хранить отдельно от роли и текущей активности пользователя. Для ручного создания отразить, какие действия может выполнить оператор, а какие делает получатель.

Приёмка: первое использование, повтор токена, истечение, отмена, сбой доставки, активация с новой ролью и аудит от создания до завершения. Журнал связывает ID приглашения, организацию, субъекта, итог и время. Частые повторные попытки идут в агрегат. Токен приглашения, исходный пароль и URL активации не сохраняются в диагностике.

## ACCESS-03. Область каталога администратора платформы не видна в строках

`GET /users` ограничивает запрос `org_id` для администратора и владельца организации, а для `super_admin` убирает этот фильтр. Web рисует одинаковый заголовок «Участники организации» и показывает email, ID пользователя, роль, активность, MFA и последний вход. `org_id` есть в данных, но отображается только внутри диалога действия. Реальная таблица с синтетическим ответом из двух организаций показала обе строки под общим заголовком и не вывела ни одного `org_id`. Создание относится к организации текущего субъекта. [API списка и создания](../../../backend/api/v1/users/router.py#L43) · [Тип ответа](../../../frontend/lib/hooks/useUsers.ts#L4) · [Таблица](../../../frontend/app/%28dashboard%29/users/page.tsx#L60) · [Подтверждение](../../../frontend/src/features/users/UserDialogs.tsx#L119) · [Jest](evidence/access-workflows.test.cjs).

Доработка. В каталоге платформы показывать организацию и предусмотреть серверный фильтр по организации, статусу, роли и имени. В области одной организации оставить явное название этой области. В карточке пользователя связать идентичность, разрешённые сессии, последнее наблюдение, изменения роли, приглашение и действия восстановления. Форма создания показывает организацию назначения до отправки. Возврат или повтор после неопределённого исхода использует перечитывание выбранного пользователя.

Приёмка: на фикстуре двух организаций администратор видит принадлежность строки до действия, а область обычного администратора остаётся своей. Смена роли и отключение показывают ID операции и результат; аудит содержит старую и новую роль, область назначения и ID запроса. Для чтения каталога достаточно счётчика ошибок и задержек, без записи на каждое автообновление.

## ACCESS-04. Временный отказ восстановления сессии выглядит как требование войти

`refreshSession` различает временные ошибки и подтверждённое прекращение сессии. При `503` функция сохраняет текущую границу и возвращает ошибку. При открытии новой вкладки `useInitAuth` поглощает ошибку и возвращает один `ready=true`. Если access token ещё не восстановлен, guard отправляет на тот же `/login`, что при отсутствии сессии. Фикстура с `503` увидела один запрос `/auth/refresh`, переход на `/login` и сохранённый `explicitlySignedOut=false`. Приватный контент остаётся закрыт. Оператор теряет причину перехода и может вводить пароль, когда сбой относится к доступности backend. [Refresh](../../../frontend/lib/store.ts#L87) · [Инициализация](../../../frontend/lib/store.ts#L124) · [Guard](../../../frontend/app/providers.tsx#L24) · [Jest](evidence/access-workflows.test.cjs).

Доработка. Отобразить «Не удалось проверить сессию» с возможностью повторить чтение и сохранить разрешённый внутренний маршрут. Отдельно обработать подтверждённое завершение сессии и ручной выход. Приёмка: один `503`, затем успех после явного повтора, `401`, явный выход и поздний ответ старой сессии. Проверить отсутствие приватных запросов до подтверждения. В метриках различать `refresh_unavailable` и `session_rejected`, к отдельному отказу приложить `request_id` без credential headers.
