# Журналы Android и PC Agent

Исходный срез `b8273839c0787ce865892c47577aa1b764117cc0`. Сопоставлены генерация, хранение, отправка и поиск. Объёмы ниже — расчёт по коду при заданной частоте, а не измеренный размер тома или файла. Службы, устройства и пилот не запускались. Ограничение Windows-журнала и реакция Android на `507` проверены локально отдельными прогонами.

Правки `Retry-After` и ротации PC Agent описывают локальный кандидат. Базовые исходники по ссылкам остаются опорой для наблюдений до правок. [Статус публикации](LOGGING.md#статус-изменений).

### Повторная передача, которая вытесняет полезную историю

На исходном срезе `POST /logs/upload` добавлял блок `Uploaded at` и полученное тело при каждом успешном запросе. Ни APK, ни этот серверный handler не вели cursor, устойчивый batch ID или список принятых событий. Пока тот же хвост доступен, новое содержимое не требуется для его повторной передачи. При потере ответа после записи тот же body может попасть в хранилище ещё раз. Раздельные имена WorkManager coalesce только запуски внутри каждой группы. [Создание body и retry](../../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt) · [Локальная дедупликация](../../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt#L271-L288).

Модель для 96 принятых upload в сутки. Планировщик Android может сдвигать и пропускать запуски, дополнительные crash, OTA и retry в таблицу не входят.

| Условие | Трафик/записи за 30 суток до серверного ограничения |
| --- | ---: |
| 32 KiB file tail повторяется у одного агента | 90 MiB этого компонента |
| 480 KiB на каждый upload одного агента | 1,318 GiB, или 45 MiB/сутки |
| 100 таких агентов | 131,84 GiB |
| 1 000 таких агентов | 1 318,36 GiB |

На исходном срезе 50 MiB относилось к текущему суточному файлу, а следующий upload удалял весь файл, если он уже превысил порог. Очистка старше 30 суток запускалась только при загрузке данного устройства. Поэтому завершивший работу агент мог оставлять старые файлы неопределённо долго. Проверка воспроизводится через `git show b8273839:backend/api/v1/logs/router.py`, исходные строки 59–60, 77–85 и 126–136. Изменения глобальной квоты и уборки в рабочей ветке ведутся отдельно. Квота ограничивает дисковое потребление, но сама по себе не уменьшает повторный трафик, не присваивает устройству cursor и не гарантирует доставку критических событий.

Отдельная проверка совместимости квоты: до исправления APK относил `507` к 5xx, мог отправить тот же body на следующий сохранённый маршрут и затем вернуться к backoff WorkManager от 15 с. В новой реализации `507` сразу завершает попытку с retry и записывает общий для periodic, immediate и crash работ срок в приватные настройки. Ключ — выданный устройству ID после проверки регистрации, общий для сохранённых management-маршрутов. При повторном старте в пределах срока Worker пропускает сбор logcat, refresh токена для upload и HTTP. Между запуском работ сохраняется обычное расписание WorkManager, поэтому локальное пробуждение раньше срока возможно. APK принимает число секунд или HTTP-date в формате RFC 1123, применяет диапазон 60–3 600 с и 900 с по умолчанию. В пределах одной загрузки ОС использует монотонный таймер, после перезагрузки сверяет ограниченный срок по системным часам. Без `2xx` файл crash остаётся. [Серверная квитанция кандидата](evidence/logging-backend-after.json) · [Проверки Android](#проверки-перед-приёмкой).

### Подтверждённые пробелы локальной диагностики

- В `CrashHandler` проверка 256 KiB выполняется по длине файла **до** `appendText`. Новый stack trace формируется без ограничения `StringWriter` и может сразу превысить этот порог. При чтении ранее большого файла `readText().takeLast(...)` сначала загружает весь файл. `LogUploadWorker` читает последние 128 KiB, а общий лимит 480 KiB сохраняет конец сформированного body, где расположен crash. JVM-фикстура с crash-файлом больше 140 KiB и переполненным logcat подтверждает, что новый маркер дошёл до HTTP body, старый не вошёл, а успешный ответ удалил весь неизменившийся файл. Это потеря ранней части на этапе чтения crash-файла. Частота и размер реальных исключений не измерялись. [Запись](../../../android/app/src/main/kotlin/com/sphereplatform/agent/logging/CrashHandler.kt#L50-L78) · [Чтение и удаление](../../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt#L258-L288) · [Фикстура](../../../android/app/src/test/kotlin/com/sphereplatform/agent/workers/LogUploadWorkerTest.kt).
- `dropped_entries_total` увеличивается при вытеснении записи из очереди. Ошибка дисковой записи сообщает в stderr и не меняет этот счётчик. В результате `0` в health-блоке исключает только вытеснение в очереди текущего процесса. При полном диске это не подтверждает сохранение записей. [Writer](../../../android/app/src/main/kotlin/com/sphereplatform/agent/logging/FileLoggingTree.kt#L78-L92) · [Счётчик](../../../android/app/src/main/kotlin/com/sphereplatform/agent/logging/FileLoggingTree.kt#L112-L123).

## Поиск в Web и происхождение данных

- `/logs/{device_id}` ищет по подстроке в пределах общего бюджета чтения 2 MiB, по умолчанию в трёх последних суточных файлах, с ответом до 512 KiB. При body по 480 KiB такой бюджет покрывает приблизительно 4,27 последних полных upload по объёму. Он может представлять меньше уникальных событий. Интерфейс `/logs` запрашивает до 1 000 строк, фильтр уровня применяется к полученной выборке, автообновление при включении срабатывает каждые 5 секунд. Поля `truncated`, `reasons` и `files_scanned` помогают отличить частичный ответ. Точный `date` поддерживается API, экран в этом срезе его не передаёт. [Бюджеты reader](../../../backend/services/device_log_reader.py#L14-L25) · [Семантика поиска](../../../backend/services/device_log_reader.py#L123-L169) · [Запрос и фильтр Web](../../../frontend/app/%28dashboard%29/logs/page.tsx#L179-L238).
- Кнопка Logcat в инспекторе по умолчанию отправляет разовую команду `REQUEST_LOGS` к APK и показывает его файловый хвост. Архив и эта команда могут видеть разные строки. Live-запрос требует доступности агента, поддерживает 500 строк в UI и не публикует ответ в архив. [Компонент](../../../frontend/src/features/devices/LogcatViewer.tsx#L17-L42) · [Преобразование запроса](../../../backend/api/v1/devices/router.py#L846-L875) · [Команды APK](../../../android/app/src/main/kotlin/com/sphereplatform/agent/commands/CommandDispatcher.kt#L760-L775).
- PC Agent отправляет телеметрию, топологию и результаты команд по WebSocket станции. В проверенном `pc-agent/` отсутствует uploader локальных журналов. Приёмник Android `/logs/upload` разрешает идентификатор активного `Device`; журналы Windows/Linux станции сейчас следует искать в её собственном sink. ## Windows и Linux PC Agent

До изменения `install.bat` перенаправлял stdout и stderr в отдельные файлы, ставил `AppRotateFiles=1` и `AppRotateSeconds=86400`, а размер, online rotation и удаление архивов не настраивал. NSSM проверяет ротацию при старте сервиса, возраст определяется временем последней записи. Поэтому активный `agent_stderr.log` рос между рестартами, а постоянно обновляемый файл мог не выполнить условие возраста и при рестарте. Ротация оставляла переименованные архивы. Loguru по умолчанию выводит в stderr на уровне DEBUG, а синхронизация ADB и reconnect могут повторять сообщения при длительном отказе. Например, гипотетический средний поток 500 байт/с за 30 суток образует 1,21 GiB. `SpherePCAgent` и его каталог логов на проверенной Windows-машине отсутствовали. Исторический скрипт читается через `git show b8273839:pc-agent/install.bat`. [NSSM](https://nssm.cc/usage#rotation) · [Loguru](https://loguru.readthedocs.io/en/stable/resources/troubleshooting.html) · [ADB цикл](../../../pc-agent/agent/main.py#L21-L30) · [Reconnect](../../../pc-agent/agent/client.py#L40-L79).

Для новых NSSM-установок добавлена служебная точка входа. Один `agent-service.log` и четыре фиксированных архива по 5 MiB ограничивают новый набор до 25 MiB при одном владельце файлов. Запись содержит UTC, severity, источник, текст, предел 16 KiB полезной строки плюс перевод строки. Bootstrap сохраняет старт и безопасный тип и позиции исключения без копирования значения ошибки конфигурации. NSSM больше не перенаправляет stderr в отдельный растущий файл. Службы с прежней конфигурацией и старые архивы требуют отдельной миграции. Ошибки до старта Python, нативный crash, принудительное завершение и недоступный каталог проверяются через состояние службы и журнал Windows. В этом проходе установщик не исполнялся. [Прежний установщик](../../../pc-agent/install.bat) · [Проверки PC Agent](#проверки-перед-приёмкой).

Команда `python -m agent.main` и Docker entry point остаются с обычным stderr. Dockerfile не выбирает драйвер/ротацию standalone-контейнера. У Docker по умолчанию `json-file` без лимита при отсутствии настройки запуска или daemon policy. В репозитории не найден service unit для Linux PC Agent. У будущего systemd unit нужно проверять политику журналирования ОС, per-service rate limit, хранение при reboot и выгрузку в центр. [Dockerfile](../../../pc-agent/Dockerfile) · [Docker logging](https://docs.docker.com/engine/logging/drivers/json-file/) · [systemd journal limits](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html).

## Проверки перед приёмкой

| Поверхность | Критерий |
| --- | --- |
| Android upload | Временная потеря HTTP-ответа, два параллельных инициатора и перезапуск агента сохраняют один идентификатор принятого блока. Архив принимает только новые события или явно помеченные снимки. Счётчики показывают фактические байты, повтор, отбрасывание и ошибку записи. |
| Crash и WS lifecycle | Oversize и недоступный диск дают контролируемые сигналы потери. Сохранённый заголовок crash и события reconnect коррелируют по device, времени и сессии. Очистка происходит после подтверждения конкретного блока. |
| Архив и поиск | Тест offline-агента и заполнения общей квоты показывает, что срок хранения применяется и без следующей загрузки устройства. Выборка по device, диапазону времени, severity и ID операции сообщает предел и наличие более старых результатов. |
| PC Windows / Linux | Проверить установщик и перезапуск в изолированной Windows VM, рост файла без рестарта, rollover после рестарта, новые breadcrumbs и сохранение старых архивов при миграции. Для standalone Docker и будущего Linux service подтвердить лимиты фактического драйвера, поиск после reboot и отсутствие дублей. |
| Файлы и host/relay | Для [новых возможностей](DEVICE-EXTENSIONS.md) по ID операции находятся запрос оператора, допуск, выдача агенту, подтверждение финализации, повтор и отмена. Логи не содержат байты файлов, приватные пути, секреты или полный поток ввода. При нагрузке передача не вытесняет ошибки и не увеличивает объём журналов пропорционально каждому chunk. |

Локально прошёл 41 тест в трёх PC Agent-файлах, включая две новые проверки ротации UTF-8 и breadcrumbs при некорректной конфигурации. Отдельная изолированная фикстура проверила INFO и WARN нормального запуска. Ruff для новых Python-файлов прошёл. Первый локальный `:app:testEnterpriseDebugUnitTest` по четырём Android-классам прошёл 19 тестов. Повтор Gradle с финальной фикстурой скомпилировал актуальный APK-код, затем не разрешил метаданные `androidx.work:work-testing:2.9.0` в offline. Те же четыре класса отдельно скомпилированы Kotlin 1.9.23 и запущены JUnit/Robolectric с актуальным `classes.jar` варианта `EnterpriseDebug` и локально закэшированным runtime classpath. Прошли все 20 тестов, включая три конкурентных запуска с одним HTTP `507`, новый device ID после перепривязки, смену часов и загрузки ОС в модели, а также удаление прочитанного crash-файла после `2xx`. Установленный APK, реальные перезагрузки Android и запуск NSSM остаются открыты для проверки. [Исходная проверка Android](../2026-11-11/evidence/android-jvm.md).
