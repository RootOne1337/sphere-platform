# Каталог релизов, внешний вид и навигация

Проверка 14.11.2026 по рабочему дереву от `2a4ba6fc7c5d865cd4803201e52b01d6e0acebcd`. Использованы текущие React-компоненты, синтетические ответы API, Blob и событие `storage` в Jest/jsdom. Управление рабочим каталогом и скачивание реального APK в проверку не входили. Продуктовый код не менялся.

| ID | Приоритет | Проверенное следствие |
|---|---|---|
| SETREL-01 | P2 | Пока удаление релиза не подтверждено, повторное нажатие отправляет ещё один DELETE. После потерянного ответа строка остаётся до успешного чтения каталога. |
| SETREL-02 | P2 | Браузеру передаётся APK, чьи байты не совпадают с SHA-256, указанным сервером. |
| SETREL-03 | P3 | Изменение акцента в давно открытой вкладке перезаписывает более свежие настройки текста и материала из другой вкладки. |

## SETREL-01. Удаление релиза не блокируется до ответа и не сверяется при потере квитанции

Кнопка `Delete` блокируется только на время GET каталога. Обработчик после подтверждения сразу вызывает `api.delete`, перечитывает список при успешном ответе и открывает `alert` при любой ошибке. После серверного удаления повторный `DELETE` того же ID возвращает `404`. Без повторного чтения потерянный `204` и последующий `404` выглядят как две ошибки, а строка остаётся доступной до ручного либо успешного фонового обновления. [Обработчик](../../../frontend/app/%28dashboard%29/updates/page.tsx#L81) · [Кнопка](../../../frontend/app/%28dashboard%29/updates/page.tsx#L194) · [API удаления](../../../backend/api/v1/updates/router.py#L578).

В Jest первый `DELETE /updates/fixture-release` оставался в ожидании. После удаления записи в синтетическом каталоге кнопка оставалась доступной. Повторное подтверждение отправило второй запрос с тем же ID. Второй запрос вернул `404`, первый завершился клиентским тайм-аутом. Оба сообщения были показаны, строка `v1.2.55-dev` оставалась на странице и до ручного обновления был выполнен только первоначальный GET. Клик «Обновить релизы» подтвердил пустой список. Реальный commit и HTTP-тайм-аут здесь смоделированы входами. [Фикстура](evidence/settings-release-closure.test.cjs#L18).

Критерий приёмки. Один активный запрос на ID релиза, подтверждение `204`, явное состояние неизвестного исхода при потере ответа и сверка каталога перед повторным удалением. При известной ошибке сообщать её причину в контексте операции. Для расследования сохранить ID релиза, время, состояние квитанции и ID HTTP-запроса, если он предоставлен.

## SETREL-02. Ручное скачивание игнорирует SHA-256 из квитанции

Публикация managed-артефакта проверяет хэш на диске. `GET /updates/downloads/latest` заново выбирает релиз для канала, проверяет размер и передаёт каталоговый `X-Sphere-APK-SHA256` и `X-Sphere-Version-Code`. Клиент проверяет тип Blob, размер и MIME, затем создаёт object URL и сообщает, что APK передан браузеру. Полученные байты с SHA-256 не сравниваются. В Jest ответ правильного MIME и размера с намеренно отличающимися байтами и корректным по формату SHA-256 привёл к созданию ссылки скачивания и сообщению об успешной передаче. Это подтверждает отсутствие проверки на границе скачивания. Повреждение реального артефакта или установка на Android не проверялись. [Проверка публикации](../../../backend/api/v1/updates/router.py#L536) · [Выбор и заголовки скачивания](../../../backend/api/v1/updates/router.py#L472) · [Проверки браузера](../../../frontend/src/features/updates/AgentDownloadPanel.tsx#L46) · [Синтетический Blob](evidence/settings-release-closure.test.cjs#L65).

Критерий приёмки. Успешная передача файла происходит после проверки целостности относительно SHA-256 релиза, выбранного на момент запроса. Несовпадение даёт отдельное состояние отказа с каналом, кодом версии и идентификатором запроса. Смена версии между чтением списка и нажатием допустима для действия «Скачать последний APK» и должна сообщаться по фактически полученной квитанции.

## SETREL-03. Изменение одного параметра внешнего вида затирает правки другой вкладки

`AppearanceDrawer` обещает хранение в текущем браузере. Применение акцента вызывает `setAccentColor`. Persist сериализует под одним ключом `sphere-ui-preferences` одновременно акцент, размер текста, плотность, материал и остальные поля из текущего Zustand store. Открытая вкладка не перечитывает эти предпочтения при событии `storage`. В Jest начальное состояние вкладки было `fontSize=base`, `surfaceStyle=glass`. Синтетическая запись другой вкладки сохранила `lg` и `solid` и отправила `storage`. Старая вкладка осталась в прежнем состоянии. Нажатие «Акцент темы» записало `accentColor=theme`, но одновременно вернуло `fontSize=base`, `surfaceStyle=glass` в хранилище. [Акцент](../../../frontend/src/features/preferences/AppearanceDrawer.tsx#L66) · [Хранилище](../../../frontend/src/shared/store/useUIStore.ts#L44) · [Фикстура](evidence/settings-release-closure.test.cjs#L45).

Критерий приёмки. Две вкладки последовательно меняют разные параметры. После повторного открытия браузера сохранены обе правки. Ручной сброс остаётся целевой операцией, заменяющей весь набор. Проверить как изменение отдельных полей, так и применение сочетания палитры, акцента и материала. Предпочтения внешнего вида остаются локальными и не требуют отправки персональных данных для диагностики.
