## LOGWEB-04. Ошибка старой OTA-команды отображается рядом с новой командой без привязки

После неудачной установки можно создать новое разрешение для того же APK, если устройство всё ещё сообщает более старую версию. `POST /updates/recovery` присваивает новый `command_id`, записывает новое разрешение и сохраняет предыдущие поля `meta`, включая последний результат. `GET /updates/recovery/{device_id}` возвращает одновременно `active` и `last_result`. `installEvidence` сравнивает SHA-256 и код версии, но не сравнивает ID команды. При совпадении APK функция возвращает `failed`, а текст ошибки показывает только код причины. ID старой команды остаётся внутри раскрываемой истории. [Выдача нового разрешения](../../../backend/api/v1/updates/router.py#L244) · [Состояние и история](../../../backend/api/v1/updates/router.py#L296) · [Проверка результата](../../../frontend/src/features/updates/recovery.ts#L81) · [Диалог OTA](../../../frontend/src/features/updates/RecoveryDialog.tsx#L130).

В фикстуре устройство сообщало версию `10222`, для релиза `10240` команда `22222222-2222-4222-8222-222222222222` вернула `install_failed`, а новое разрешение `33333333-3333-4333-8333-333333333333` было активно. React показал «Ожидается результат Android», ID новой команды и alert «Android сообщил ошибку: install_failed» без ID старой команды. Действие «Повторить доставку» в этом состоянии относится к новой команде. Ошибку можно сопоставить со старой командой после открытия истории. Фикстура проверяет чтение, новых OTA-команд она не отправляла. [Jest](evidence/logging-web-followup.test.cjs#L20).

Критерий приёмки. При повторной попытке того же APK состояние и результат текущей команды связаны по её ID. Предыдущий результат остаётся в истории с отдельным ID и временем. Подтверждение установки по версии и heartbeat сохраняет привязку к соответствующей квитанции.

## LOGWEB-05. После терминального результата карточка скрывает ещё доступный журнал выполнения

Android `CommandJournal` при восстановлении после смерти процесса может вернуть терминальный `failed` с `execution_outcome_unknown_after_restart` без тела результата. Backend сохраняет полученный словарь, добавляя признаки результата и ошибку. Для активной задачи без ожидающей отмены такой receipt переводит строку в `failed`. `GET /tasks/{id}/logs` берёт только итоговые `node_logs`. Отдельный `/live-logs` читает журнал Redis, проверяя принадлежность задачи без фильтра по её статусу. Redis хранит до 200 записей с TTL 600 секунд от последнего сообщения прогресса. [Android-журнал](../../../android/app/src/main/kotlin/com/sphereplatform/agent/commands/CommandJournal.kt#L146) · [WS-приём результата](../../../backend/api/ws/android/router.py#L395) · [Сохранение](../../../backend/services/task_service.py#L477) · [TTL](../../../backend/api/ws/android/router.py#L240) · [Итоговые отчёты](../../../backend/api/v1/tasks/router.py#L209) · [Live API](../../../backend/api/v1/tasks/router.py#L257).

Карточка опрашивает и показывает live-журнал только при `queued`, `assigned` или `running`. В фикстуре она сначала показала `fixture-node-before-disconnect`, затем после `failed` без `node_logs` показала «Отчёты шагов не получены», хотя React Query всё ещё содержал ту же запись. Новый вход в терминальную карточку не отправил ни одного `/live-logs`. Оператор теряет доступ из карточки к последнему наблюдавшемуся шагу даже в пределах TTL. Прогресс остаётся наблюдением, а факт завершения этого шага из него не следует. Этот случай отличается от BE-24, где Redis-ключ уже отсутствует во время выполнения. [Условие опроса](../../../frontend/app/%28dashboard%29/tasks/%5Bid%5D/page.tsx#L96) · [Отчёты и live-секция](../../../frontend/app/%28dashboard%29/tasks/%5Bid%5D/page.tsx#L283) · [Проверка перехода](evidence/logging-web-followup.test.cjs#L50) · [BE-24](../2026-11-11/BACKEND-DATA.md#be-24).

Критерий приёмки. При терминальном результате можно открыть ещё сохранённые наблюдения прогресса с их временем и границей хранения. Они отделены от подтверждённых итоговых отчётов, а состояние пустого или недоступного источника указано отдельно. Контрольный сценарий начинается с наблюдавшегося шага, заканчивается receipt без `node_logs` и повторным входом в карточку до истечения TTL.

## LOGWEB-06. Перегрузка чтения и недоступность источника неразличимы в журнале Web

`GET /logs/{device_id}` возвращает `503` для двух разных причин. `LogReadBusy` даёт `detail="Log read capacity is busy"` и `Retry-After: 1`, `LogReadUnavailable` даёт `detail="Log source is unavailable"`. `RequestIdMiddleware` добавляет `X-Request-ID` для сопоставления с серверными логами. `errorMessage` страницы использует только `error.message` и не читает `response.data.detail` или заголовки. Страница оставляет ручную кнопку повтора. [Различимые ответы API](../../../backend/api/v1/logs/router.py#L177) · [HTTP ID](../../../backend/middleware/request_id.py#L27) · [Обработка ошибки](../../../frontend/app/%28dashboard%29/logs/page.tsx#L118) · [Повтор](../../../frontend/app/%28dashboard%29/logs/page.tsx#L328).

Для обеих форм HTTP-ответа Jest показал одинаковый alert «Логи не загружены: Request failed with status code 503». Подробность API и ID (`fixture-busy`, `fixture-unavailable`) не отображались. После первого сообщения есть смысл повторить чтение с указанной задержкой. Во втором случае сначала требуется диагностика источника. Различие остаётся видно в DevTools. [Проверка ошибки UI](evidence/logging-web-followup.test.cjs#L90).

Критерий приёмки. Web показывает проверенное различие временной занятости и недоступности источника. Можно передать оператору поддержки безопасный ID запроса, когда он предоставлен. Последний успешный результат помечается временем и не становится подтверждением нового чтения.
