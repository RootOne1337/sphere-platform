## EGWEB-01 · P2. «Обработано» скрывает ошибку автоматизации

Одно поле `processed` означает два разных действия. `EventReactor` выставляет его после обхода триггеров, даже когда запуск вернул отказ и обработчик записал только `event_trigger.fire_failed`. В вебе кнопка «Отметить обработанным» выставляет тот же флаг напрямую, без запуска триггеров. В карточке и счётчике необработанных этих случаев не различить. При отсутствии сопоставимого результата оператор не может понять, обработал ли событие человек и создался ли запуск. [Реактор](../../../backend/services/event_reactor.py#L147) · [Ошибка триггера](../../../backend/services/event_reactor.py#L398) · [Ручная отметка](../../../backend/api/v1/device_events/router.py#L112) · [Отрисовка флага](../../../frontend/app/%28dashboard%29/events/page.tsx#L414).

В пробе активный триггер `fixture.*` ссылался на выключенный pipeline. Обработчик записал ошибку, сохранил `processed=true`, а число `PipelineRun` и успешных срабатываний осталось `0`. Для отдельного события, созданного штатным HTTP handler, ручная отметка ответила `204` и выставила такой же флаг, тоже без запуска. Это отдельный дефект представления исхода. [OPWEB-03](OPERATOR-WORKFLOWS.md#opweb-03) описывает охват выборок и ошибку формы, [OPWEB-04](OPERATOR-WORKFLOWS.md#opweb-04) — доступность сценария в селекторе, а [BE-05](../2026-11-11/BACKEND-DATA.md#be-05) — лимит запусков.

Доработка. Развести прочтение оператором и реакцию автоматизации. Событие показывает `acknowledged_by/at` отдельно от результата каждого правила: совпало, пропущено, поставлено в очередь, завершилось ошибкой или результат ещё неизвестен. Для созданного запуска сохранить `pipeline_run_id`. Старым событиям с одним флагом не приписывать историю, которой нет. Оператор с правом чтения получает цепочку по `event_id`, без дублирования одной записи на каждый опрос. При повторе учитывать счётчик и сводку.

Приёмка. Три события одного типа проходят через активный, выключенный и временно недоступный pipeline. Ручная отметка четвёртого события меняет только состояние операторского просмотра. После reload в вебе доступны автор, время, причина и ссылка на результат автоматизации. Ошибка запуска и терминальный отказ пайплайна различаются по стадиям.

## EGWEB-02 · P2. Удаление группы не показывает блокирующие расписания

Диалог удаления говорит проверить назначения после удаления. Запрос не выполняет предварительный просмотр зависимостей. У `Schedule.group_id` есть внешний ключ на группу без `SET NULL` или каскадного удаления. Сервис удаляет группу, handler делает commit без перевода отказа внешнего ключа в предметный ответ. В пробе удаление группы с расписанием вызвало `IntegrityError`, откат сохранил и группу, и расписание. Группа без зависимости удалилась. Схема миграции PostgreSQL содержит тот же FK. Реальный HTTP `500` в этой пробе не запускался. [Диалог](../../../frontend/src/features/groups/GroupDeleteDialog.tsx#L25) · [Обработчик](../../../backend/api/v1/groups/router.py#L82) · [Сервис](../../../backend/services/group_service.py#L209) · [FK в миграции](../../../alembic/versions/20260224_tz12_orchestrator.py#L172).

Доработка. Дать предварительную сводку непосредственных участников, дочерних групп и расписаний. Для блокирующих расписаний показать ссылки и путь переноса. Подтверждение операции сверяет актуальную ревизию и повторно проверяет зависимости на сервере, возвращая предметный конфликт. Архивирование группы и переназначение расписания оформить как явные отдельные решения. Для журналов достаточно `operation_id`, ID группы, причины отказа, количества блокирующих ссылок и итоговой ревизии. Сам список доступен в readback с правами организации.

Приёмка. Группа с одним и с несколькими расписаниями сообщает точные зависимости и сохраняется при гонке добавления расписания после предпросмотра. После подтверждённого переноса удаление доступно. Для дочерних групп до подтверждения показана политика обработки родителя. Повтор после потери ответа не требует угадывать, удалена ли группа.
