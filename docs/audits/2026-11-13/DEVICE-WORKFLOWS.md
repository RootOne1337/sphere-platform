## DEVWEB-01. Колонка «Доступ» не отражает активность VPN и подставляет отрицательный ADB

Чтобы увидеть столбец в чистом профиле, открыть `/devices → Столбцы → Доступ`: настройка `network` выключена по умолчанию и сохраняется в браузере. Включение столбца не отправляет отдельный запрос. `FleetMatrix` читает из строки `adb_connected` и `vpn_assigned`. Для отсутствующего `vpn_assigned` показывает `VPN —` с подсказкой `VPN not assigned`. `GET /devices` сериализует `DeviceResponse`, где `vpn_assigned` отсутствует. Запрос не читает каталог VPN-пиров. Вместо этого он добавляет актуальный флаг `vpn_active` и метаданные свежести наблюдения. Колонка игнорирует эти поля. В режиме карточек таблица «Доступ» вообще не рендерится. [Колонка](../../../frontend/src/features/devices/FleetMatrix.tsx#L207) · [Настройка](../../../frontend/src/features/devices/fleetTablePreferences.ts#L19) · [Ответ устройства](../../../backend/schemas/devices.py#L127) · [Обогащение списка](../../../backend/api/v1/devices/router.py#L230).

`adb_connected` в `DeviceResponse` и `DeviceLiveStatus` получает `false` по умолчанию. Проверенный перечень полей, которые агент может обновить через `merge_agent_status`, не содержит `adb_connected`. В исходниках backend, Android и PC Agent найдено чтение поля и сброс в `false`. Штатный путь, который пишет подтверждённое `true`, не найден. Поэтому UI превращает отсутствие положительного сигнала в `ADB not linked`, а карточка показывает «Не подключён». Отдельный Android APK может штатно обслуживать WebSocket, видео и команды без ADB. [Поля статуса](../../../backend/schemas/device_status.py#L16) · [Допустимые обновления](../../../backend/services/device_status_cache.py#L121) · [Сброс](../../../backend/services/device_status_cache.py#L226) · [Обзор карточки](../../../frontend/src/features/devices/DeviceInspectorDetail.tsx#L121).

В пробе действующие обработчики списка и детали вернули для одного синтетического устройства `vpn_active=true`, `vpn_observation_state=fresh`, `adb_connected=false` и без `vpn_assigned`. После включения столбца реальная ячейка показала `VPN —` и `ADB —`, а инспектор одновременно показал «VPN, активность по APK → Активен» и «ADB → Не подключён». Это воспроизводит расхождение представлений. Фикстура не измеряет живой туннель, трафик или ADB. [Ответы обработчиков](evidence/devices-contract-result.json) · [Проверка компонентов](evidence/devices-observations.test.cjs).

| Сигнал | Кто его даёт | Что означает |
|---|---|---|
| Подключение APK | Presence по WebSocket и heartbeat | Живой агент в рамках свежести наблюдения |
| VPN на Android | `vpn_active`, `vpn_observation_state`, `vpn_observed_at` из явного отчёта текущей сессии | Состояние управляемого Android VPN, актуальное до 120 секунд. При потере подтверждения значение `null` |
| Сведения Android VPN | `GET /vpn/runtime`, экран `/vpn → Подключения` | Подробный отчёт, фаза сервиса и свежесть |

| ADB | Поле `adb_connected` пока имеет только отрицательный источник по умолчанию в проверенном пути | Фактическая привязка ADB не подтверждается |

Свежий отчёт APK и router handshake отвечают на разные вопросы. Трасса трафика и IP выхода требуют отдельного измерения. При исправлении ячейка должна показывать доступные сигналы с источником и различать отрицательное измерение и неизвестное состояние. [Свежесть APK](../../../backend/schemas/device_status.py#L37) · [VPN runtime API](../../../backend/api/v1/vpn/runtime_router.py#L20) · [Router peers](../../../backend/api/v1/vpn/router.py#L295).

## DEVWEB-02. Карточка показывает «в сети», когда реестр сообщает offline или unknown

Условие — PostgreSQL хранит прежний `last_status=online`, а presence-записи уже нет либо Redis-клиент отсутствует. Реестр при отсутствующем ключе возвращает `offline`, при недоступном источнике возвращает `unknown` и `presence_available=false`. Одиночный GET в обоих случаях оставляет persisted `online` без heartbeat. Если клиент Redis присутствует и его GET выбрасывает исключение, карточка идёт по другой ветке, показывает отказ API и блокирует живые команды. [List fallback](../../../backend/api/v1/devices/router.py#L170) · [Detail fallback](../../../backend/api/v1/devices/router.py#L405) · [Проекция PostgreSQL](../../../backend/services/device_service.py#L45) · [Чтение Redis](../../../backend/services/device_status_cache.py#L93).

`DeviceInspectorDetail` вычисляет `isReachable` по свежести HTTP-ответа и `status=online/busy`, без проверки heartbeat. Следовательно, свежий ответ о сохранённом статусе делает доступными терминал, shell, Logcat, снятие кадра, профиль Android и reboot. Два вызова реальных handlers с cache-фикстурами дали соответственно `unknown/online` и `offline/online`, в детали `last_heartbeat=null`. В jsdom карточка показала «Последний heartbeat APK → Не сообщено» одновременно с активными кнопками «Терминал» и «Перезагрузка». Команды не отправлялись. Серверный исход команд и частота такого окна в реальном парке отдельно не проверялись. [Условие доступности](../../../frontend/src/features/devices/DeviceInspectorDetail.tsx#L41) · [Кнопки](../../../frontend/src/features/devices/DeviceInspectorDetail.tsx#L104) · [Результат](evidence/devices-contract-result.json) · [Наблюдение](evidence/devices-observations.test.cjs).

## DEVWEB-03. «Снять привязку» игрового сервера сохраняет прежнее значение

В `/devices → меню строки → Игровой сервер` выбрать «Снять привязку» и сохранить. Форма переводит выбранную опцию в пустое состояние и посылает `PUT /devices/{id}` с `server_name:null`. `DeviceService.update_device` меняет поле при `server_name is not None`. Ветка для пустой строки умеет очищать значение, но UI отправляет `null`. Ответ содержит прежний сервер, UI закрывает диалог и сообщает «Игровой сервер обновлён» без сверки значения. При прямом вызове service с синтетической записью `RED` значение осталось `RED` на `null`, а на `""` стало `null`. [Опция формы](../../../frontend/app/%28dashboard%29/devices/page.tsx#L812) · [Отправка и уведомление](../../../frontend/app/%28dashboard%29/devices/page.tsx#L316) · [Запись сервиса](../../../backend/services/device_service.py#L306) · [Результат](evidence/devices-contract-result.json).

## DEVWEB-04. Назначение группы стирает прежние назначения

В реестре одно действие доступно из меню строки и для выбранных строк. Диалог показывает только группу назначения и количество устройств. После «Назначить» выполняется `POST /groups/{id}/devices/move`; сервис заменяет `device.groups` целиком. В синтетическом вызове `move_devices_to_group` запись с членствами A+B получила только C, ответ `moved=1`. Риск касается как единичной, так и массовой операции. Локации используют другой путь и прямо подписаны «аддитивно». Для оператора существенно предупредить, какие прежние связи исчезнут. [Диалог](../../../frontend/app/%28dashboard%29/devices/page.tsx#L707) · [Mutation](../../../frontend/lib/hooks/useGroups.ts#L93) · [Замена членства](../../../backend/services/group_service.py#L217) · [Подтверждение](evidence/devices-contract-result.json).

## DEVWEB-05. Счётчики групп и локаций расходятся с реестром

Карточки групп показывают «N онлайн», локации «N online». Оба агрегата считают точное сохранённое значение `Device.last_status == ONLINE`, а реестр включает в живую категорию «В сети» также `busy`. На переходах persisted состояние отстаёт от presence. Соединения групп и локаций считают членов без `Device.is_active`; штатное удаление устройства из реестра выполняет soft delete и не снимает членства. Например, при единственном выведенном устройстве карточка группы может показывать `1 устройство`, а ссылка «Устройства» откроет пустой активный реестр. Это следствие исходных условий SQL и жизненного цикла, продакшен-счётчики не снимались. ## DEVWEB-06. Столбец «Android ID» не заполняется из действующего DeviceResponse

Опциональный столбец выводит только `row.original.android_id`. Действующий ответ содержит `serial`, поле `android_id` отсутствует. В пробе сервис сериализовал `serial=fixture-serial` без `android_id`. При таком ответе столбец остаётся «Не сообщён». Карточка при этом выводит отдельный «Серийный идентификатор». Происхождение поля имеет значение, поскольку серийный идентификатор может быть fingerprint или другим значением и его нельзя подписывать как Android ID. ### Границы Discovery

В форме стоит показывать, **откуда** выполняется операция: выбранный PC Agent/relay, его организация и область видимости. `localhost` здесь относится к той машине, где выполняется подключение. Локальная сеть относится к сети выбранного relay. Успешная заявка на обнаружение должна различать «relay недоступен», «операция не поддерживается», «отработало без кандидатов» и «кандидаты найдены». Приёмка на отдельном стенде включает localhost выбранной станции, одну разрешённую сеть, отказ транспорта и ручное подтверждение регистрации найденного устройства. Для глобальной работы продуктовый путь — исходящий enrollment агента или заранее разрешённый endpoint через управляемый relay/VPN, с проверкой идентичности устройства. Открытый интернет не нужен для первого выпуска Discovery. [Связь Discovery с PC Agent](../2026-11-11/INTEGRATIONS.md) · [Будущая роль relay](DEVICE-EXTENSIONS.md#агент-станции-и-relay).

### Журнал действий и состояния устройств

Хранить смену состояния с источником и временем измерения, отдельно от последнего чтения UI. Для назначения группы и VPN, reboot и Discovery связывать intent, результат по каждому устройству и readback через ID операции. Для терминала, Logcat, снимка и shell записывать субъект, устройство, время, разрешение, результат и размер, со строгим доступом к ограниченным диагностическим артефактам. Повторные heartbeat и polling не требуют записи на каждое чтение. Приёмка включает просроченный heartbeat, неверный peer, частичный результат и потерю ответа после commit.
