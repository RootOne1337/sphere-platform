## OPWEB-01. «Активен» в вебхуках обозначает включённую запись

Реестр делает CRUD `/n8n/webhooks`. Модель выдаёт `is_active`, `last_triggered_at`, `failure_count`. Карточка окрашивает «Активен» по `is_active`, выводит дату создания и игнорирует историю попыток. В фикстуре запись с `is_active=true`, `failure_count=7`, `last_triggered_at=null` отрисовывается с зелёным «Активен» и без данных о доставке. `dispatch_event()` имеет реализацию, но поиск вызовов в `backend` показывает только определение. У callback конкретной задачи есть собственный путь, ранее воспроизведённый в BE-20. Запись endpoint с событием `task.completed` не подключает этот callback. [Страница](../../../frontend/app/(dashboard)/webhooks/page.tsx#L125) · [Маршруты](../../../backend/api/v1/n8n/router.py#L23) · [Схема](../../../backend/schemas/webhook.py#L41) · [Диспетчер](../../../backend/services/n8n_webhook_service.py#L100) · [INT-06](../2026-11-11/INTEGRATIONS.md#int-06-webhook-registry-и-callback-задачи-не-образуют-один-контракт-доставки) · [BE-20](../2026-11-11/BACKEND-DATA.md#be-20-callback-сообщает-о-завершении-до-сохранения-результата).

Оператор не может отличить настройку без попыток от интеграции с отказами. Закрытие карточки требует producer → commit/outbox → подписка → попытка → квитанция и состояния «Включён», «Ещё не отправлялось», «Доставлено», «Ошибка», «Повтор запланирован». Тестовая отправка должна помечаться отдельно и показывать ограниченную диагностику. Проверить rollback до отправки, повтор с тем же ID, отключение подписки и фильтрацию по организации. Публикация внешних уведомлений и Telegram описаны в [AI и интеграциях](AI-AND-INTEGRATIONS.md#telegram-и-внешние-уведомления).

## OPWEB-02. Ошибки logcat выпадают из фильтра, а заголовок выглядит как сообщение о сбое

APK запускает `logcat -v threadtime`, помещает строки в пакет диагностики и всегда печатает заголовок `=== RECENT SPHERE CRASH ===`. Если файл исключения отсутствует, следующая строка — `No persisted uncaught crash record`. Для формата `11-13 09:00:00.000 321 321 E SphereAgent: …` веб распознаёт только формы с `E/` и выставляет резервный уровень `I`. При одинаковом уровне ошибки строка файлового формата остаётся в фильтре «Ошибки», строка logcat исчезает. На пользовательском устройстве конкретное событие и его причина остаются непроверенными. [Сборщик Android](../../../android/app/src/main/kotlin/com/sphereplatform/agent/logging/LogcatCollector.kt#L39) · [Пакет диагностики](../../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt#L166) · [Парсер](../../../frontend/app/(dashboard)/logs/page.tsx#L61) · [Фильтр](../../../frontend/app/(dashboard)/logs/page.tsx#L236).

Приёмка: `threadtime`, файловый журнал, заголовки секций, настоящий crash payload и отсутствие crash payload отображаются различимо. «Критические» включает `F` из поддерживаемых форматов. Выбранное устройство, время сбора и границы хвоста остаются видимыми. У аварийной записи есть время, источник и разворачиваемый оригинал. Серверную причину ложной квитанции очистки отслеживать отдельно. [WEB-13](../2026-11-11/WEB.md#web-13--журнал-подтверждает-очистку-хотя-лог-остался-на-сервере).

## OPWEB-03. Список и сводка событий описывают разные выборки

Поиск, уровень и «обработано» передаются только списку `/device-events`. `useEventStats()` вызывается без фильтра, а API статистики умеет ограничить результат только по `device_id`. «Обновить» повторяет запрос списка. В браузере поиск показал «0 записей» одновременно с карточкой «Всего 41», а на ручное обновление ушёл запрос списка с поиском. Фильтры `device_id`, `event_type`, `account_id` поддерживаются списком API, в форме страницы отсутствуют. В деталях связи полезно использовать для переходов к устройству, аккаунту, заданию и запуску, соблюдая их права чтения. Действие «отметить обработанным» требует `event:write`. Обработчик ошибки объявляет «Состояние сохранено» даже при потерянном HTTP-ответе, когда факт изменения не установлен. [Страница](../../../frontend/app/(dashboard)/events/page.tsx#L129) · [Хуки](../../../frontend/lib/hooks/useDeviceEvents.ts#L76) · [API событий](../../../backend/api/v1/device_events/router.py#L38).

Приёмка: сводка явно маркирована «Организация» с собственным временем либо агрегирует тот же фильтр. «Обновить» даёт понятный результат для обоих запросов. Ссылки сохраняют фильтр устройства и время. Неопределённый исход записи проверяется повторным чтением; запрещённое действие имеет объяснение до отправки запроса.

## OPWEB-04. Выбор сценария для триггера теряет диагностику и часть каталога

`usePipelineOptions` запрашивает `/pipelines?per_page=200` один раз на загрузку, проецирует только `items` и теряет ошибки и количество страниц. После `503` в браузере показано «Нет доступных сценариев». На каталоге из 201 записи сценарий, оказавшийся на второй странице, недоступен из формы. Неактивные сценарии видны как `INACTIVE`, но доступны для выбора; когда триггер сработает, `PipelineService.run` откажет неактивному сценарию. Основной экран уже явно маркирует поиск по текущей странице, так что это отдельное ограничение селектора. [Загрузка и форма](../../../frontend/app/(dashboard)/event-triggers/page.tsx#L62) · [Выбор](../../../frontend/app/(dashboard)/event-triggers/page.tsx#L521) · [Пагинация API](../../../backend/api/v1/pipelines/router.py#L83) · [Проверка запуска](../../../backend/services/orchestrator/pipeline_service.py#L199).

Приёмка: загрузка, пустой каталог и ошибка показаны отдельно, есть повтор запроса; сценарий №201 доступен через серверный поиск; неактивное старое назначение видно в режиме редактирования и требует замены для активации. Дальше добавить безопасную проверку glob на примерах, предпросмотр целевых устройств и историю «совпало / пропущено по лимиту / запущено / ошибка» со ссылкой на запуск. [Реактор](../../../backend/services/event_reactor.py#L325).

## OPWEB-05. Веб создаёт API-ключ без выбора области и срока

В `/settings` список показывает разрешения и срок, но форма POST отправляет `{name}`. Схема принимает `permissions` и `expires_at`, по умолчанию это `[]` и `null`. Роут валидирует делегируемые права. Оператор не может выпустить из UI ключ для конкретной интеграции с заданным минимальным набором прав и сроком, хотя API эти поля принимает. Приёмка: показать доступные для делегирования права, предпросмотр области и срока, явные серверные ошибки и квитанцию выдачи. Сохранить одноразовый показ, возможность отзыва и различие между секретом интеграции и токеном подключения. [Форма](../../../frontend/app/(dashboard)/settings/page.tsx#L80) · [Схема](../../../backend/schemas/auth.py#L74) · [Роут](../../../backend/api/v1/auth/router.py#L359).

## OPWEB-06. Визуальный переход от событий к триггерам ломает иерархию

События используют общий `PageHeading`, триггеры — `Event Triggers` моноширинным uppercase и буквальные `bg-black/50`, `#151515`, `#222` рядом с семантическими токенами. На одном маршруте системные подписи по-русски, на соседнем присутствуют `Event Triggers` и `INACTIVE`. В одной и той же светлой теме браузер подтвердил тёмную шапку таблицы триггеров со слабым контрастом, примерно 2,46:1 на белой подложке. Приёмка: общий заголовок, сетка, панель действий, тематические токены и язык. Моноширинный текст сохраняется для идентификаторов и шаблонов. Для таблиц сверить фокус, положение действий при 390 px и 1440 px, светлый/тёмный пресет, крупный текст и reduced motion. ## OPWEB-07. Переходы в поток и запись маршрута расходятся по статусу и правам

В списке `/stream` просмотр допускается по каталожному `online|busy`. При `offline` эта точка входа блокирует просмотр и не даёт ссылки на прямую страницу устройства. `/stream/[id]` и просмотр в инспекторе могут отдельно проверить доступность потока. На `/stream/[id]` действие «Записать маршрут» видно роли с `stream:read`, а в карточке устройства оно требует `stream:control`. При открытии Studio с этой ролью live-подключение и запись корректно ограничены. Библиотека остаётся отдельным действием. Расхождение касается доступности перехода и надписи кнопки. [Список](../../../frontend/app/%28dashboard%29/stream/page.tsx#L355) · [Прямой просмотр](../../../frontend/app/%28dashboard%29/stream/%5Bid%5D/page.tsx#L24) · [Инспектор](../../../frontend/src/features/devices/DeviceInspectorDetail.tsx#L87) · [Studio](../../../frontend/src/features/stream/TeachingWorkbench.tsx#L181).

Приёмка: тестовое устройство со stale heartbeat получает явный статус и понятный переход к проверке транспорта с соблюдением прав чтения. Действия «Открыть библиотеку» и «Записать маршрут» названы и проверяются отдельно; `stream:read` может открыть разрешённый просмотр, `stream:control` нужен для записи. Глубокие сценарии реконструкции остаются в [предыдущей матрице](../2026-11-11/WEB-CONTROLS.md), локальные изменения Route Studio не считаются выпущенной версией.

### Поиск и корреляция

У операций должен быть доступный оператору ID и однозначное имя действия. Для событий и вебхуков показывать результат по цепочке и время последней подтверждённой попытки. Для логов показывать UTC-дату, источник, предел выборки и причину усечения. Приёмка воспроизводит событие из четвёртого дневного файла, тайм-аут первичной авторизации WS и поиск запроса снимка экрана по идентификатору.
