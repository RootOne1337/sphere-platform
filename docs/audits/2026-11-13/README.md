## Оценка

В вебе уже есть рабочие элементы, которые стоит переиспользовать: детальная карточка устройства, редактор и версии DAG, серверная проверка, диагностика подключения, адресное OTA с квитанциями, журнал с фильтрами и экспортом. Главный риск возникает при переходах между этими частями. Разные страницы показывают разную доступность одного устройства. Пакетный запуск возвращает ID, который экран задач игнорирует. Назначение группы может снять прежние членства. Подтверждение формы бывает убедительнее подтверждения результата.

Для единичных операций есть хорошая основа. Для ежедневной работы с десятками и сотнями устройств проблемы существенно мешают: приходится вручную сверять цели, перепроверять состояние и восстанавливать контекст. До enterprise-приёмки этих сценариев нужно довести достоверность статусов, пакетные квитанции, сохранность привязок и согласованность доступа. Этот проход включает статическую проверку, браузерные и jsdom-фикстуры и отдельные вызовы реальных обработчиков с синтетическими зависимостями. Реальный парк, нагрузка, публичные подключения, физические устройства и полный прогон всех действий по ролям остались открытыми. [Предыдущая производственная приёмка](../2026-11-11/CLOSURE.md).

## Сквозные правила интерфейса

- **Устройство.** На всех экранах одинаковая идентичность и понятные источники: присутствие агента, достижимость ADB, назначенный профиль, работа туннеля, транспорт видео. Для просроченных и неподдерживаемых метрик нужен видимый статус. [Реестр и карточка](DEVICE-WORKFLOWS.md).
- **Действие.** Оператор заранее видит роль, цели и версию. После отправки можно различить принятие заявки, исполнение и результат с подтверждением от источника. При потере ответа открывается проверка результата по ID операции. [Автоматизация](AUTOMATION-WORKFLOWS.md).
- **Навигация.** Из события, пакета, VPN и журнала доступны ссылки на связанные объекты с сохранением фильтра и времени. Единый словарь для «скрипта», «пайплайна», «пакета» и «задания» помогает понять, что именно редактируется или запускается.
- **Дизайн.** Утвердить один образец страницы для реестра, наблюдения и конструктора. Включить состояния загрузки, пустой выборки, ошибки, просроченных данных, отсутствия права, ожидания и частичного результата. Проверять узкое окно, клавиатуру и темы на одних данных. Плотность интерфейса выбирается оператором, критическое действие остаётся доступным на обеих плотностях. [Пример сравнения](OPERATOR-WORKFLOWS.md#opweb-06).
- **Расширяемость.** Схемы приложения и рабочего пространства версионируются, настройки видны в UI, роль и область проверяет сервер. AI, файловые операции и relay используют согласованный контракт разрешений и журнал, с отдельным подтверждением чувствительных действий. [AI](AI-AND-INTEGRATIONS.md) · [Устройства](DEVICE-EXTENSIONS.md).
- **Диагностика.** Для каждого действия указывать подтверждающий источник, ID поиска, время события и исход. Отдельно проверять потерянный ACK, отсутствие данных, повтор и отказ записи. У каждого потока журналов есть измеряемый бюджет, TTL, метрика отказов и способ поиска. [Аудит журналов](LOGGING.md).

## Основания для приёмки

Сначала пройти 4 сквозных цепочки на стенде одной ревизии: «реестр → устройство → доступ», «скрипт → пакет → отмена/результат», «приложение → аккаунт → сценарий → сессия», «событие → триггер/вебхук → квитанция». Для каждой цепочки сохранить роль, ID и версию, ввод, отметки времени, сетевой/серверный ответ, UI после обновления и наблюдаемый результат. Затем пройти матрицу отдельных кнопок с теми же ролями и ошибками. Проверку новых возможностей вести по их критериям после стабилизации основных цепочек.

Точечные проверки доступны в [evidence](evidence). Существующие регрессии автоматизации и устройств проверяют разные наборы поведения. Синтетическая выборка на 100 целей проверяет навигацию и охват, а производительность и отправка на 100 устройств требуют отдельного измерения. Файлы Route Studio в рабочем дереве имели локальные изменения, глубокая приёмка реконструкции по этому срезу не проводилась.
