## Файлы в карточке устройства

Развить [проект Android File Manager](../../design/ANDROID-FILE-MANAGER.md). Первый экран — вкладка «Файлы» в полной карточке. Показывать только доступные корни, размер, дату, состояние операции, действия загрузить и скачать. Рабочая папка агента подходит для первой версии; для пользовательских папок Android нужен выбор на устройстве через Storage Access Framework. Android 11+ ограничивает выбор ряда системных каталогов и корней. Доступ к произвольной файловой системе оставлять за пределами первой поставки. [Правила Android](https://developer.android.com/training/data-storage/shared/documents-files#document-tree-access-restrictions).

Первые передачи использовать через HTTPS с временным хранилищем и отдельной очередью. Сервер проверяет разрешение, привязку операции к устройству и доступному корню. Операция хранит ожидаемый объём, состояние, срок жизни и результат проверки целостности. Файл появляется в каталоге после успешной финализации на агенте. UI показывает отдельно доставку в хранилище и подтверждение устройства. При скачивании интерфейс различает доступность файла у агента, готовность загрузки и наблюдаемый результат браузера. Для восстановления после обрыва кандидат для upload — tus, для download — потоковый HTTP с поддержкой диапазонов. Поддержка resume должна зависеть от неизменности исходного файла и текущих прав. [Проект транспорта](../../design/ANDROID-FILE-MANAGER.md#сначала-надёжный-резервный-путь) · [Спецификация tus](https://tus.io/protocols/resumable-upload).

Критерии первой приёмки — два направления с одинаковым SHA-256, обрыв и продолжение, смена страницы, истечение доступа, перезапуск агента, недостаток места, одновременная запись в одну папку, отзыв доступа, отмена с подтверждённой очисткой. Отдельно проверить действия оператора в другой организации, ссылки и junctions на хостах, SAF-провайдер с ограниченными операциями, большие имена и конфликт файлов. Браузерная матрица охватывает согласованный размер файла и допустимое потребление памяти. При одновременной передаче измерять очередь управления, FPS и время подтверждения ввода. Прямую передачу оценивать после устойчивого HTTPS-пути, если измерения показывают значимый выигрыш в задержке, трафике или расходах на хранение.

## Агент станции и relay

| Этап | Объём | Что требуется для приёмки |
| --- | --- | --- |
| 1. Windows/Linux host agent | Отдельный системный сервис для регистрации конкретного хоста, версии, heartbeat и базовой инвентаризации. Windows и одна согласованная Linux-конфигурация с systemd. LDPlayer и ADB остаются адаптером там, где доступны. Тип хоста, версия протокола и опубликованные capabilities определяют действия в UI. | Подписанные артефакты, воспроизводимая поставка, запуск после загрузки, отзыв идентичности, безопасное обновление и откат, различимый статус offline/unknown. Проверить восстановление связи и сопоставление рабочей станции при переустановке. |
| 2. Файлы хоста | Тот же пользовательский UX и сервис передачи, адаптеры Windows/Linux для разрешённых рабочих папок. Первоначально просмотр, загрузка и скачивание. | Набор файловых проверок из Android-этапа, с матрицей регистрозависимости, ACL, блокировки открытого файла, исчерпания квоты и несовместимости rename у провайдера. |
| 3. Рабочий стол | Начать с просмотра рабочей сессии пользователя и явной границы её доступа. Предусмотреть отдельное право на управление вводом. Выбирать между собственным desktop adapter и отдельным MeshCentral-провайдером по результатам изолированного сравнения. | Windows проверяет вход пользователя, lock/logoff, смену сессии, монитора и DPI. Wayland проверяет конкретный compositor/portal, согласие и его отзыв. Headless Linux остаётся доступным для базового управления хостом независимо от рабочего стола. [Microsoft](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services) · [XDG Desktop Portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html) |

Управляющий канал используется для авторизованного открытия сессии. Бинарный трафик рабочего стола или файлов получает отдельную политику маршрутизации и лимиты. Для файлов первым остаётся временное HTTPS-хранилище, для интерактивного рабочего стола подходит relay ограниченной сессии. Разрешение на сессию имеет срок, конкретного оператора, хост и допустимое действие. После потери канала ввод завершается, а новая сессия проверяет допуск заново. При сравнении измерить работу за NAT и ограничивающим прокси, отказ relay, расход канала, p95 времени первого кадра и подтверждения ввода. Принятие решения о прямом канале опирается на эти результаты. [Семантика TURN](https://www.rfc-editor.org/rfc/rfc8656).

На Windows служба и интерактивный компонент имеют разные жизненные циклы. Windows services не взаимодействуют с пользовательским рабочим столом напрямую. На Wayland штатный Remote Desktop portal управляет разрешениями и сессией, а захват экрана связан с PipeWire. Поэтому общий хостовый протокол может переиспользовать учётную запись устройства, статус и модель операций. Возможность экрана и ввода объявляет конкретный адаптер с учётом ОС и текущего сеанса. [Windows services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services) · [Wayland session lifecycle](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html#session-lifecycle).
