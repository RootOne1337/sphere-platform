# Серверные журналы, хранение и связь событий

Исходный срез `b8273839c0787ce865892c47577aa1b764117cc0`. Проверка охватила stdout контейнеров, приём Android-журналов, PostgreSQL audit/events/task results, временный Redis progress и исходящие callbacks. Изменение в этом проходе касается файлового хранилища Android-журналов. Для воспроизведения использованы временные каталоги, фиктивные данные и локальные тесты. [Проба](evidence/logging-backend-probe.py) · [до](evidence/logging-backend-before.json) · [после](evidence/logging-backend-after.json) · [pytest](evidence/logging-backend-pytest.txt) · [метрики](evidence/logging-backend-metrics.txt).

Изменения квот, очистки и ограничения OTA-повторов ниже относятся к локальному кандидату. Приложены наблюдения до и после. Для повтора тестов кандидата нужна его рабочая ревизия. [Статус публикации](LOGGING.md#статус-изменений).

## Файловые журналы Android

**LBL-01. Суточный предел удалял уже принятые журналы и не ограничивал объём фермы.** Исходный writer сравнивал существующий текущий файл с 50 MiB до append. На последующем upload он удалял файл целиком, если тот уже превысил порог. Очистка по возрасту проходила только для устройства, которое сейчас загрузило данные, поэтому журнал отключённого или снятого с эксплуатации устройства не очищался через 30 дней. Docker logging driver не управляет этим отдельным именованным volume. На временном пороге 200 B три upload вернули `204`, размеры составили `174 → 348 → 174`, первые два тела исчезли, а файл другого устройства старше 30 дней сохранился. [Историческая логика](../../../backend/api/v1/logs/router.py) · [постоянный volume](../../../docker-compose.full.yml#L47) · [результат до изменения](evidence/logging-backend-before.json).

После локального изменения действует 8 MiB на устройство за UTC-дату и 8 GiB на managed volume, оба параметра настраиваются через `DEVICE_LOG_DAILY_MAX_BYTES` и `DEVICE_LOG_STORAGE_MAX_BYTES`. Append считает прогнозируемый объём, сериализуется с другими writer-процессами, TTL sweep и DELETE через один lockfile и возвращает `507` при превышении. Уже принятый суточный файл сохраняется. Удаление по TTL ограничено 128 файлами в минуту при поступлении uploads. Оно охватывает журналы других устройств и не удаляет произвольные соседние файлы. При исчерпании каталога в 50 000 элементов или ошибке диска API возвращает `503` вместо записи без проверенного объёма. Short write откатывается до прежнего размера под тем же lock. Остаётся неизвестный результат при аварийном завершении после записи и до HTTP ответа. [Настройки](../../../backend/core/config.py) · [регрессии кандидата](evidence/logging-backend-pytest.txt) · [API](../../../backend/api/v1/logs/router.py) · [результат после изменения](evidence/logging-backend-after.json).

Лимит считает логические байты содержимого управляемых файлов и включает серверные разделители. Нужен отдельный резерв диска под метаданные ФС, PostgreSQL, Docker и бэкапы. Ручная очистка удаляет текущий файл, поэтому может заново открыть суточный бюджет для этого устройства. Существующий объём выше лимита не удаляется принудительно, новые записи ожидают освобождения места. В первой версии изменения том без uploads не запускал TTL sweep. Фоновая очистка добавлена в следующем проходе. Межпроцессная гарантия относится к workers с одной настройкой и общей ФС, на которой действует OS file lock. Смешанный запуск со старым backend и нагрузку на сетевой ФС не проверяли.

Следующий проход добавил фоновый sweep при запущенном backend. Работа по-прежнему ограничена общей отметкой, общей блокировкой, 128 удалениями за проход и 50 000 просматриваемыми элементами. В `/metrics` появились размер и свободное место на файловой системе архива и отметка времени последней завершённой проверки. Проверки на временном каталоге и Prometheus подтверждают очистку без uploads и различимость отсутствующего или застывшего источника. [Протокол кандидата](evidence/LOGGING-INFRA.md).

**LBL-02. Upload пересылает пересекающиеся снимки журнала.** Штатный Android worker планируется каждые 15 минут, формирует файл/приоритетный WS tail, до 300 строк logcat и снимок последнего crash, ограничивает тело 480 KiB. Курсор последней принятой строки или стабильный ID снимка отсутствует. Подавление относится только к пересечению двух файловых секций внутри одного тела. Если сервер записал тело, а HTTP ответ потерялся, следующая попытка может сохранить перекрывающиеся данные. При `507` исходная APK применяет общий путь 5xx и может попробовать запасной маршрут. Локально проверенный кандидат APK учитывает `Retry-After`. [Поведение агента](LOGGING-AGENTS.md). Подтверждённый crash-файл удаляется только после 2xx, но при заполнении квоты crash-диагностика может задержаться. Нужны delta cursor, дедупликация по стабильному идентификатору, ограниченный retry с `Retry-After` и резерв для диагностических событий высокого приоритета. [Расписание](../../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt#L67) · [снимок](../../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt#L159) · [ответы и повторы](../../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt#L196).

## Оценка объёма

| Сценарий для 100 устройств | В день | За 30 дней без общего cap |
| --- | ---: | ---: |
| 96 периодических upload по 64 KiB | 600 MiB | 17.6 GiB |
| 96 периодических upload по 480 KiB | 4.39 GiB | 131.8 GiB |
| Старый файловый порог 50 MiB плюс один upload до 512 KiB на устройство | примерно 4.93 GiB одновременно удержанных суточных файлов | примерно 148 GiB |
| Новый 8 MiB/device/day при одном стабильном журнале | до 800 MiB записей, пока volume принимает данные | 8 GiB в volume |

Это расчёт верхних профилей, а не наблюдение суточного трафика. WorkManager может запускаться реже, а срочная диагностика, повторы и смена маршрута добавляют запросы. Лимит 8 GiB при 100 постоянно активных устройствах и 30 днях соответствует около 2.73 MiB на устройство в день. При равномерных 96 upload это около 29 KiB на один upload, чтобы удержать 30 дней без отказов. При заполнении рано срабатывает общий бюджет, поэтому срок 30 дней описывает возраст удаления, а не гарантированную глубину истории. Серверный cap ограничивает сохранённые байты, входящий трафик и объём отклонённых тел требуют отдельных метрик.

Для SQL-объёма без замера нельзя переводить счётчики строк в реальный диск. Как расчёт чувствительности, 100 устройств × 1 записанное событие/мин дают 144 000 событий/сутки. При 1 KiB логического payload это около 141 MiB/сутки и 4.12 GiB за 30 дней до индексов, TOAST, WAL и backup. Terminal task результаты в 2 400 задач/сутки × 64 KiB дают 150 MiB/сутки или 4.39 GiB/30d без overhead. Такие модели требуют фактических p50/p95 по источникам, частоты, показаний `pg_total_relation_size` и write amplification на отдельной БД. Audit retention следует определять отдельной операторской политикой с подтверждаемым архивом. Для временного progress достаточно измерить rate, ошибки, ключи по TTL и фактический объём Redis.

На локальном пилоте read-only запрос измерил около 16,4 МиБ суммарно у четырёх таблиц `audit_logs`, `device_events`, `tasks`, `pipeline_runs` с индексами и TOAST. Это отдельный срез установленного экземпляра. Он не показал многогигабайтного накопления в этих таблицах и не измеряет суточный рост. [Снимок по таблицам](evidence/LOGGING-INFRA.md).

## Приёмка и наблюдаемость

- Принятый journal upload фиксирует `request_id`/`upload_id`, UTC time, исход, количество байтов и безопасный код отказа. Для оператора нужны точки `received`, `committed`, `duplicate`, `rejected`, `dropped`. Org/device IDs допустимы в защищённом структурированном журнале, а серии метрик используют только bounded reason и source. Не печатать credential headers, сырой payload или полный receiver URL.
- Из штатного API, фонового задания и терминального отчёта проследить `request_id → org_id → batch/task/pipeline_run → command_id → event_id/delivery_id`. Хранить `observed_at` и `recorded_at`, причину, этап, очередь, номер попытки и вид подтверждения. Событие физического завершения подтверждается отдельно от HTTP приёма и Redis publication.
- Установить бюджет по типу данных и метрики accepted bytes, rejected bytes, expired bytes/files, duplicate/suppressed/dropped lines, upload latency и lock busy, свободное место, SQL relation growth и delivery queue age. Реализованные `sphere_device_log_upload_bytes_total` и `sphere_device_log_retention_events_total{outcome}` показывают принятые байты и `expired|daily_quota|volume_quota`. Проверено наличие всех трёх нулевых baseline в multiprocess exposition. Потерянные Android entries пока известны только из `dropped_entries_total` в снимке агента.
- На отдельном стенде проверить 10 и 100 устройств с холодным запуском, поздним ACK, отключёнными устройствами, двумя backend workers, одновременным DELETE, падением места и burst crash logs. Проверить объём и время `p95` без записи в действующий volume. Данные с потерянным ответом не должны дублировать принятое событие, а отказ квоты не должен стирать ранее принятые записи. Отдельно проверить задержку TTL без upload и совместимость старых APK с новым статусом. [Регрессии кандидата](evidence/logging-backend-pytest.txt) · [диагностические клиенты](../../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt#L196).

## Повторы предупреждения OTA

В исходном хвосте backend одна пара устройство/команда заняла 994 из 1000 строк. Для события `android_ws.ota_recovery_receipt_unrecognized` каждый worker теперь использует 60-секундное окно. Первая строка для пары сохраняется, максимум восемь разных пар дают подробную строку за окно. Повторы и превышение этого предела считаются, а следующая квитанция после окончания окна выводит одну сводку с `suppressed_count` и `detail_count`. При прекращении потока сводка ждёт следующего события, а счётчик обновляется сразу. `sphere_android_ota_unrecognized_receipts_total` имеет два фиксированных значения `outcome`, `warning` и `suppressed`. Идентификаторы не попадают в метрики, ID команды в подробной строке проходит нормализацию UUID. [Хвост пилота](evidence/LOGGING-INFRA.md) · [Экспорт счётчиков кандидата](evidence/logging-ota-warning-metrics.txt) · [Место исходного предупреждения](../../../backend/api/ws/android/router.py#L317).

В тесте тысяча повторов одной квитанции выполнила тысячу прежних проверок replay и grant, вывела одно предупреждение и прибавила 999 к `suppressed`. Непризнанный результат не получил ACK и не прошёл в Redis task result. После окончания окна следующий повтор создал сводку и одну новую подробную строку. Та же квитанция получила прежний `result_ack`, когда проверка обнаружила сохранённую запись. Отдельный контроль 100 разных ключей оставил в памяти восемь пар. Доставка APK, ACK, повтор и запись в БД используют прежние ветки. Свежий процесс экспортировал оба нулевых значения `outcome` и зарегистрировал первое подавленное предупреждение в режиме Prometheus multiprocess. [Тесты](../../../tests/test_agent_discovery/test_ota_clone_recovery.py) · [Результат прогона](evidence/logging-ota-warning-pytest.txt) · [Проверка экспорта](evidence/logging-ota-warning-metrics.txt).
