## AUTO-06

**Условие.** При работающем фарме оператор выбирает другой сценарий в «Настройках пайплайна», пока задача старого сценария ещё выполняется. Второй путь — отмена уже принятой задачи фарма в очереди до отправки устройству.

**Причина.** Производитель создаёт Task с текущим `farming_script_id` и ссылкой на аккаунт, а аккаунт сразу переводит в `in_use`. При следующем учёте оркестратор ищет результаты только по *текущему* `farming_script_id` и только в состояниях `COMPLETED`, `FAILED`, `TIMEOUT`. Поэтому задача прежнего скрипта и `CANCELLED` не попадают в обработку. Кандидаты следующего фарма фильтруются по `free`. Сводка активных задач на экране настроек также строится по текущему скрипту. [Настройки и сохранение](../../../backend/api/v1/pipeline_settings/router.py#L81) · [Создание задачи](../../../backend/services/orchestrator/orchestration_engine.py#L312) · [Учёт результата](../../../backend/services/orchestrator/orchestration_engine.py#L430) · [Отмена в очереди](../../../backend/services/task_service.py#L607) · [Сводка](../../../backend/api/v1/pipeline_settings/router.py#L208).

**Доказательство.** Проба создала задачу со старым скриптом, сохранила новый ID через сервис настроек, приняла успешный результат с целевым уровнем через `TaskService` и выполнила учёт. После commit задача `completed`, `orchestration_processed_at` пуст, аккаунт `in_use`. Положительный контроль: возврат старого ID позволил тому же worker-методу учесть результат и перевести аккаунт в `free`. Отдельная задача была отменена штатным `cancel_task` в очереди при неизменном скрипте. После учёта она `cancelled` и аккаунт остался `in_use`. [Наблюдения](evidence/AUTOMATION-CLOSURE.md).

**Влияние.** Аккаунт выпадает из кандидатов для следующего фарма, хотя работа завершилась или гарантированно не отправлялась устройству. На экране настроек смена скрипта может убрать старую задачу из текущих счётчиков, оставив причину занятости на разных экранах.

**Изменение и приёмка.** Закрепить при admission тип работы, ревизию конфигурации, Task ID и принадлежность назначения или сессии. Учёт должен закрывать работу по этому снимку при любом подтверждённом terminal outcome, включая отмену до dispatch. При `cancel_requested` без terminal outcome сохранять назначение до подтверждения. Проверить смену скрипта во время работы, отключение новых запусков с завершением старых, отмену до отправки, поздний результат после запроса остановки, перезапуск worker и повторный учёт. Для регистрации проверить тот же контракт отдельно. Общий worker под runtime-ролью требует самостоятельной проверки с учётом BE-25.

## AUTO-07

**Условие.** Пайплайн назначил аккаунт устройству A и сохранил сессию. Пока выполнение находится между шагами, оператор штатно освобождает аккаунт и назначает его устройству B. Затем пайплайн A выполняет свой `release_account`.

**Причина.** Шаг назначения создаёт сессию с `pipeline_run_id` и кладёт ID аккаунта и сессии в контекст. Ручной release меняет аккаунт и увеличивает счётчик, не закрывая эту сессию. Pipeline release ставит блокировку на строку собственного запуска, выбирает аккаунт по ID и организации и очищает текущее назначение без сравнения с устройством или поколением назначения. Старую сессию шаг закрывает отдельно по ID из контекста. Защита поколения pipeline не распространяется на новое назначение аккаунта. [Контекст сессии](../../../backend/services/orchestrator/step_handlers.py#L797) · [Ручной release](../../../backend/services/game_account_service.py#L405) · [Проверка поколения запуска](../../../backend/services/orchestrator/pipeline_ownership.py#L46) · [Release в пайплайне](../../../backend/services/orchestrator/step_handlers.py#L853).

**Доказательство.** Реальный `OwnedPipelineRunner` выполнил `assign_account → delay → release_account`. Фикстура синхронизировала только паузу, чтобы ручное переназначение произошло между двумя шагами. Перед продолжением аккаунт был `in_use` на B и `total_sessions=1`. После продолжения пайплайн завершился как `completed`, закрыл сессию A, очистил назначение B, перевёл аккаунт в `free` и увеличил `total_sessions` до 2. Проба выполняет обычные сервисные операции внутри одной синтетической организации. [Наблюдения](evidence/AUTOMATION-CLOSURE.md).

**Влияние.** Карточка аккаунта может потерять действующее назначение, а старый запуск показывает успех. История сессий и суммарный счётчик расходятся. Аккаунт вновь становится кандидатом на назначение при отсутствии доказательства, что использование на B завершилось.

**Изменение и приёмка.** Дать ручному и автоматическому назначению единое поколение владения аккаунтом и сессией. При освобождении атомарно проверять поколение, устройство и сессию перед изменением текущей записи. Для устаревшего шага нужен явный исход с сохранением нового назначения и отдельной сверкой старой сессии. Приёмка включает повтор release, ручной перевод A→B, возврат на A с новым поколением, перезапуск между шагами и обычное завершение без ручного вмешательства. После двух одновременных запросов историю и счётчики сверять по ID, а не только по конечному статусу.

## Связи в вебе и ограничение журналов

Из «Настроек пайплайна» нужен переход к задачам, принятым с соответствующей ревизией, из запуска — к конкретной задаче и связанной сессии, из карточки аккаунта — к текущему поколению назначения и его источнику. В таблице сессий отличать управленческую привязку от подтверждённого использования на устройстве. При обработке старых записей без идентификатора поколения показывать отсутствие подтверждения и связь с исходной задачей там, где она сохранилась.

Записывать структурированные переходы при принятии задачи, изменении назначения, учёте terminal outcome и конфликте поколения. Коррелировать org, actor, config revision, pipeline run, task, account, device и session. Сохранять фиксированные коды причины, источник и время commit. Логин, сырые параметры и текст результатов устройств не нужны для этой корреляции. Текущий успешный `assign_account` уже записывает логин, а успешный release опускает ID сессии и запуска. Для метрик достаточно счётчиков с фиксированными `operation`, `outcome` и `reason`, количества неучтённых terminal задач и возраста старейшей записи. Повторяющиеся опросы записывать агрегатами. [События шагов](../../../backend/services/orchestrator/step_handlers.py#L810) · [Общий стандарт журналов](LOGGING.md).
