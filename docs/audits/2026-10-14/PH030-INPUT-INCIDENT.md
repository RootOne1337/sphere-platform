## Сохранённые факты

- В сеансе, открытом 02:58:25, управление закрылось с `discrete_result_unknown`.
  Видео оставалось `direct_webrtc`, один peer, примерно 54–56 FPS, RTT 1–2 мс.
- В 03:02:35.947 браузер того же устройства зафиксировал
  `native_input_rejected_or_unknown`. Обе активные вкладки получили ошибку ввода.
- APK затем сообщил один `input_failures_total` и один `unknown_releases_total`,
  состояние `cleanup_unknown`. Новые native peers завершались на `peer_setup_failed`
  без ответа SDP; браузеры накопили повторные `signaling_deadline` и остались на серверном пути.
- В высоком профиле сохранён предел кодека 12 Мбит/с, но фактическая цель до сбоя
  была 2 Мбит/с. После перехода на серверную очередь цель снижалась до 235 Кбит/с.
- Старый срез не сохраняет точный отказ root injector. Он не позволяет утверждать,
  что первопричиной был именно таймаут, CANCEL или изменение геометрии.
  Нет оснований объявлять это сетевой задержкой: перед остановкой peer был connected.

Исходные отчёты сохранены локально как ограниченные приватные JSON/log snapshots.
Адреса сети, секреты, траектории, текст и содержимое кадров в этот аудит не включаются.

## Исправления кандидата

1. Back/Home/Recents/Menu и конечные клавиши редактирования передаются `key_event`
   через тот же авторизованный `sphere-control-v2` peer. Android выполняет DOWN/UP
   в существующем root pipe, с отдельным точным ACK. HTTP handoff не требуется.
2. Общий arrival-order actor отменяет ранее удерживаемый жест перед клавишей.
   Поздние MOVE/UP прерванного участника не захватывают ввод заново.
3. Привилегированная очистка CANCEL использует упорядоченное ASYNC-принятие
   Android input queue. Физическое касание могло уже заменить старый stream,
   поэтому cleanup не требует наличия прежнего target window. В кандидате70 обычные
   действия сохраняли WAIT_FOR_RESULT. Версия72 переводит весь live pointer/key ввод
   на упорядоченный ASYNC API; это подтверждение приёма, а не обработки приложением.
   Строгий исполнитель DAG остаётся отдельным. Cleanup не подтверждает выполнение
   прерванного клика.
4. После точного native RELEASE новый участник открывается на том же живом
   v2 media peer и capture. Серверный socket и здоровое видео не перезапускаются
   только ради восстановления ввода. Неизвестные действия не воспроизводятся.
5. Недоступный native injector отказывает в OPEN, сохраняя возможность прямого
   просмотра. Изолированная ошибка SDP callback закрывает свой peer.
6. Геометрия берётся с реального display. DisplayListener перестраивает захват
   при повороте, включая 180°, с новым capture epoch. Существующий VirtualDisplay
   изменяется через resize/setSurface; повторное потребление MediaProjection token
   на Android 14+ не требуется. Это проверенная граница кода, а не доказанная
   первопричина данного инцидента.
7. Native telemetry сохраняет ограниченный код ошибки adapter/ACK и его возраст.
   В диагностике отсутствуют клавиши, координаты и тексты исключений.
8. WebRTC получает предел и стартовый битрейт реального источника вместе с RTP
   encoding limit. Пресет LAN задаёт запрос до 24 Мбит/с / 60 FPS, с реальным
   ограничением кодека и адаптацией сети. Это H.264, не lossless-обещание.

## Приёмка

Локально перед сборкой: TypeScript; 643 frontend stream tests;
182 backend admission/telemetry/history/heartbeat tests. Android tests, сборка,
подпись, установка и живые прогоны остаются отдельными проверяемыми этапами.

Нужен реальный прогон двух и десяти клиентов: системные кнопки, пересекающиеся
короткие клики/жесты, один закрытый участник, физический ввод, смена ориентации,
сохранение video/control peer, нулевые server input commands. Отдельно нужна
проверка настоящего телефона и hotspot: desktop viewport не заменяет её.

Полная Unicode/IME-клавиатура и опциональный звук не считаются выполненными
этой правкой. См. [клавиатура](DIRECT-KEYBOARD-PLAN.md) и [звук](DIRECT-AUDIO-PLAN.md).
