# Документация Sphere: источники и проверка

Этот документ описывает, как читать и поддерживать документацию репозитория.
Начните с [каталога](README.md); изменения продукта сопровождайте проверкой
влияния по [рабочему процессу](operations/DOCUMENTATION-WORKFLOW.md).

## Статусы и доказательства

Различайте исходный код, собранный артефакт, установленную версию и приёмку
сценария. Для наблюдений указывайте время, окружение, версии, объём и ограничения;
отрицательные и неизвестные результаты сохраняйте наряду с успешными. Установка,
зелёный тест или доступная страница сами по себе не подтверждают работу на всём
парке, безопасность, производительность или готовность к production.

[STATUS-REGISTRY.json](operations/STATUS-REGISTRY.json) связывает зафиксированные
требования и наблюдение с конкретными evidence и хешами. Дата `lastObservedUtc`
относится к описанному наблюдению, а не автоматически к настоящему моменту.
Датированные документы в `audits/` — история исследования и приёмки, а не
руководства текущей версии. Не переписывайте замороженные receipts для отражения
новой поставки: добавьте новое подтверждение и обновите соответствующий реестр.
Проектные документы описывают намерения; наличие спецификации не доказывает
реализацию. При расхождении проверьте исходники, тесты и применимый receipt.

## Машинные проверки

Из корня репозитория:

```powershell
python -m scripts.check_documentation_status
python -m unittest discover -s tests -p test_documentation_status.py
python -m unittest discover -s tests -p test_documentation_routes.py
python -m unittest discover -s tests -p test_documentation_api_headings.py
python -m unittest discover -s tests -p test_documentation_config_fields.py
python -m unittest discover -s tests -p test_documentation_impact.py
```

Проверка сверяет структуру реестра, закрытия и хеши связанных receipts,
классификацию учтённых Git Markdown и некоторые локальные inline-ссылки документов
ролей `CURRENT_ENTRYPOINT`, `OPERATING_GUIDE` и `PROJECT_POLICY`. Это не проверка
YAML issue forms и документов других ролей. Тест маршрутов сверяет имена
страниц App Router с таблицей Web UI; он не проверяет кнопки, поведение страниц или права. Проверка HTTP-заголовков
ручного справочника сверяет только перечисленные в них методы и пути с сохранённой
OpenAPI-схемой: она не проверяет текст, запросы, авторизацию или runtime.
Проверка конфигурации считывает имена полей Settings из синтаксического дерева
без загрузки env и проверяет их упоминание в справочнике; значения и правильность
применения она не подтверждает. [Инвентарь](operations/DOCUMENT-INVENTORY.json) — классификация,
а не подтверждение содержания каждого файла. Сканер не проверяет смысл текста,
фрагменты ссылок, внешние сайты, выполнение инструкций или состояние устройств.
После добавления или удаления Markdown подготовьте файл к учёту Git и обновите
инвентарь командой:

```powershell
python -m scripts.check_documentation_status --write-inventory
python -m scripts.check_documentation_status
```

Корневой `openapi.json` — старый снимок, не обслуживаемый генератором; для
текущих HTTP-контрактов используйте только `docs/openapi.json`.

HTTP-схема и каталог генерируются из приложения в среде с закреплёнными backend
зависимостями; CI проверяет расхождения:

```powershell
python -m scripts.export_api_docs --check
# После намеренного изменения HTTP-контракта:
python -m scripts.export_api_docs
```

Проверки и сборка не заменяют ревью пользовательских действий, авторизации,
ошибок, сценариев устройств и соответствия развёрнутой версии. Подробный порядок,
включая анализ затронутых документов, см. в [рабочем процессе](operations/DOCUMENTATION-WORKFLOW.md).

## Принципы организации

Один основной документ должен отвечать на конкретный вопрос; другие материалы
ссылаются на него вместо копирования изменчивых цифр, команд и статусов. Входные
страницы помогают найти актуальный материал, а длинные журналы остаются в
датированных аудиторских записях. Для новой функции обновляйте руководство в той
же работе, что и код, указывайте условия и ограничения, а затем запускайте
соответствующие проверки. Факты из сторонних источников проверяйте по их
оригинальным материалам и контексту конкретного проекта.
