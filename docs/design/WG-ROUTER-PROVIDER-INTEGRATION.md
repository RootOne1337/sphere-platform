# WG Router: границы интеграции со Sphere

Проверено 23 октября 2026 года. Рабочий Android-тест ограничен PH030.
После отдельного разрешения пользователя создан один AWG peer на существующем
`awg1`; прежний WG peer не используется и не удалён из-за ограничения API key.
Новых серверов и массовой ротации нет. Для единственного тестового peer
привязка `awg1` изменена с upstream 105 на 100; соседние серверы не менялись.
Текущее рабочее подключение использует частный LAN-шлюз на ПК.

## Что подтверждено

API выдаёт WireGuard-конфигурацию отдельного клиента. В Sphere она сохраняется
в зашифрованном каталоге; ключ API и приватный ключ клиента не предназначены
для браузера, журналов команд, Git, документации или GitHub Actions.
Независимый userspace probe с этим клиентом получил HTTPS-ответ по IP за
304 мс и HTTPS-ответ по имени с DNS за 381 мс. Это проверка пути с рабочего
ПК, а не доказательство работы Android, игры или непрерывной доступности.

Созданная конфигурация — обычный WireGuard v1, IPv4. Это не проверка AWG 3.1.
В Android для неё используется явная политика блокировки IPv6 приложений.
Один клиентский ключ нельзя одновременно использовать на разных устройствах
во время сравнительного теста; старый профиль и новый клиент имеют разные ключи.

## Что показал исходный код сервиса

Исследован репозиторий `RootOne1337/wg-tunnel-router`, commit
`525fe60a0666e959e84fce1f4e84d6dae32465f0`. Это проверенная версия исходников;
совпадение с реально развёрнутым сервером отдельно не аттестовано.

| Операция | Семантика и ограничение |
| --- | --- |
| `GET /api/v1/servers` | Пакетный снимок серверов и peers, в исследованном коде с кешем 3 с. Не использовать как мгновенное подтверждение изменения. |
| `GET /api/v1/servers/{id}` | `WGService.get_server()` вызывает `ensure_route_exists()`: чтение может восстановить маршрут. Router `GET .../peers` также вызывает этот метод. Для строго наблюдательного мониторинга использовать список серверов, пока API не разделяет чтение и repair. |
| `POST /api/v1/servers/{id}/peers` | Создание peer. Контракт idempotency key не найден. При неизвестном результате сначала сверить имя через список peers; повторный POST автоматически не отправлять. |
| `GET .../peers/{name}/config` | Секретный текст конфигурации, даже если предыдущий ответ создания уже содержал config. Не сохранять сырой HTTP-ответ в обычную телеметрию. |
| Изменение tunnel / server rotate | Меняется выход всего WG-сервера, а не одного peer. Нельзя выдавать эту операцию за индивидуальную ротацию PH030. |

В исследованном `wg_service.py` выбор маршрута выполняется по подсети WG-сервера
и одной привязке к upstream tunnel. Поэтому 100 peers на одном `wg1` не означают
100 независимых внешних IP. Точное распределение подтверждается наблюдением
выходного адреса и привязкой tunnel, а не числом созданных клиентов.

Сервер содержит собственные механизмы auto-heal upstream-туннелей и peers.
Sphere не должен запускать второй независимый цикл агрессивных переподключений.
Возраст handshake и суммарные байтовые счётчики не доказывают исправность DNS,
HTTPS или UDP игры. Изменение внешнего IP upstream также не требует нового
Android-конфига, если WireGuard endpoint и ключи клиента не изменились.

## Контракт будущего адаптера

1. Секрет подключения хранить только на backend; выдавать Android запечатанную
   ревизию профиля через существующий delivery. Клиентскому вебу доступны
   метаданные, доступные операции и редактируемая политика трафика.
2. Разделять ресурсы provider/server/peer/upstream. Перед ротацией вычислять
   всех затронутых арендаторов и устройства. Общая ротация требует отдельного
   полномочия и не подменяет ротацию одного устройства.
3. Выделять уникальное имя peer и сохранять намерение до POST. После timeout
   устанавливать `outcome_unknown`, сверять результат по имени и не создавать
   новый peer с другим именем вместо проверки первого.
4. Не считать HTTP 200 успехом без `success`, проверяемой формы `data` и
   фактического readback. Удаление — только собственного точно связанного peer.
5. Сохранять предыдущую рабочую ревизию, проверять сетевой путь до назначения,
   применять сначала на одном устройстве. Ошибка оставляет guard закрытым;
   автоматический откат не должен означать выход приложения через исходный IP.
6. Отдельно измерять provider endpoint, handshake, фактический egress, DNS,
   HTTPS и стабильность Sphere. Обычный трафик Sphere не использовать для
   оценки пропускной способности или доступности VPN.

Это проект контракта адаптера. Постоянный автоматический provisioner,
production executor, аренды, массовая ротация и пользовательский UI подключения
WG Router этим документом не объявляются реализованными.

### Проверенные ограничения выданного API key

22 октября создание собственного WG peer было разрешено, а его последующее
адресное удаление вернуло HTTP 403 / `FORBIDDEN_DELETE` (`your key cannot delete
resources`). Создавать peer и гарантировать его последующее удаление — разные
полномочия. Адаптер должен показывать их отдельно и не обещать автоматическую
уборку по одному факту успешного POST. Отказ не обходится другим endpoint.

Первый проход остановился после неуспешного удаления своего WG peer:
[историческая поставка](../audits/2026-10-22/VPN-APK86-ALLAPPS-PH030-CANARY.md).
Затем пользователь отдельно разрешил один дополнительный AWG peer. Создан
ровно один клиент с тем же тестовым именем в пространстве AWG. Неоднозначность
пакетного readback устранена чтением списка peers без повторного POST.
Запрет удаления сохранён; обход через другой endpoint не предпринимался.

## AWG и фактическая доступность

Развёрнутый OpenAPI описывает `AWGParams` как параметры AWG2.0: J/S/H.
Номер формата OpenAPI `3.1.0` не является версией протокола. Номер native
библиотеки Android `v3.1.20260814` также не доказывает AWG3.1 на сервере.
SSH и серверная аттестация нового движка отсутствуют; пользователь согласовал
испытание AWG2.0. Полноценная совместимость с новыми механизмами 3.1 не принята.

Проверка upstream 105 сообщала `healthy`, хотя независимый HTTPS probe с тем
же AWG peer не проходил. После ограниченного переключения только `awg1`
на upstream 100 host probe получил HTTPS по IP и имени. Android напрямую
продолжал терять прикладной трафик; LAN-шлюз через существующий сетевой путь
ПК дал рабочий HTTPS и видимый VPN-IP в Chrome. Причина различия прямого пути
не установлена. Нельзя заменять проверку приложения статусом provider health.

Серверные и Android-параметры приведены к одинаковым S1..S4=32, Jc=6,
Jmin=100, Jmax=400; скалярные H сохранены. После PUT параметров выдача config
может содержать старые значения. Адаптеру нужен отдельный контракт эффективной
ревизии: проверять серверный readback, запечатанную клиентскую ревизию и
доступность, не выдавать повторный GET config за актуальное состояние движка.

Клиентский A/B с официальной I1-сигнатурой не улучшил путь и отменён.
Параметры AWG2 и LAN Endpoint в ревизии 9 — текущий canary, а не универсальный
рецепт обхода ограничений. [Результат и границы](../audits/2026-10-23/PH030-AWG2-LAN-GATEWAY-CANARY.md),
[эксплуатация шлюза](../operations/VPN-LAN-GATEWAY-CANARY.md).
