# Sphere Web UI — концепции редизайна

**Исследование:** 28 сентября 2026 · **Обновлено:** 29 сентября 2026 · **Статус:** направление AdminCN/Fleet Console выбрано и интегрировано в основной frontend в PR #19 · **Публичный rollout:** не выполнялся

Этот документ и сопровождающий HTML — материалы для выбора визуального направления. Макеты работают отдельно от приложения, не вызывают backend и показывают помеченный демонстрационный срез. Ни одна концепция пока не считается утверждённой.

## Что изучено

В текущей ветке есть 30 файлов маршрутов и 21 раздел в защищённой части приложения: устройства, видео, события, задачи, сценарии, пайплайны, VPN, OTA, логи, мониторинг, группы, локации и администрирование. Данные и действия распределены по существующим страницам, React Query hooks и backend API; редизайн должен переиспользовать эти контракты, а не подменять их макетными числами.

Проверенный исходный стек ветки — Next.js 15.5.26, React 19, Tailwind CSS 3.4.17, TanStack Query 5.64 и Recharts 3.7. Это уже рабочая основа; смена major-версий не нужна для визуального результата и до отдельного технического обоснования не предлагается.

Исследование публичных реальных продуктов дало следующие практики:

- Linear сообщает о согласовании заголовков, навигации и элементов управления между разделами, уплотнении навигации и снижении её визуального веса; для списков важны быстрый поиск, контекстные действия и клавиатурная навигация. Источники: [обновление интерфейса Linear в марте 2026](https://linear.app/changelog/2026-03-12-ui-refresh), [поиск Linear](https://linear.app/docs/search), [массовый выбор и действия](https://linear.app/docs/select-issues).
- Grafana рекомендует строить панели вокруг конкретных вопросов, держать временной диапазон и источник данных видимыми, связывать сводный уровень с детальным и не обновлять данные чаще, чем они меняются. Источники: [обзор dashboard-модели](https://grafana.com/docs/grafana/latest/fundamentals/dashboards-overview/), [практики dashboard-дизайна](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/best-practices/).
- Railway собирает метрики, логи и данные конкретного окружения в одном observability-разделе; это полезный принцип навигации, но в Sphere показываются только источники и эндпоинты, уже имеющиеся в проекте. Источники: [Observability](https://docs.railway.com/observability), [Log Explorer](https://docs.railway.com/observability/logs).
- Sentry Issue Views сохраняют запрос, сортировку, проект, окружение и диапазон времени — хороший ориентир для повторяемых фильтров Fleet Matrix и событий. Источник: [Issue Views](https://sentry.io/changelog/new-nav-issue-views-ga/).
- Tailwind Plus показывает варианты таблиц с сортировкой, закреплённой шапкой, массовым выбором, плотным режимом и отдельной адаптацией колонок для мобильных экранов. Это паттерны, а не причина менять стек. Источник: [таблицы Tailwind Plus](https://tailwindcss.com/plus/ui-blocks/application-ui/lists/tables).
- Untitled UI ставит React Aria в основу доступной интерактивности; для Sphere это аргумент проверять клавиатуру, фокус и семантику действий независимо от выбранной библиотеки компонентов. Источник: [Untitled UI React](https://www.untitledui.com/react).

## Контракт данных и ограничения макетов

Для примеров использованы реальные типы записей проекта: идентификатор и имя устройства, Android/версия агента, статус (`online`, `busy`, `connecting`, `offline`, `error`), heartbeat, группа/локация, сведения ADB/VPN/экрана, события, API health и команды инспектора. В одном из обсуждавшихся пользовательских срезов были названы 23 устройства: 14 online, 2 busy, 3 connecting, 4 offline. Этот срез включён только как пример для сравнения композиции; он не читается из live API и может уже быть устаревшим.

Существующие контракты не дают права придумывать FPS, ping, uptime, потоковые bitrate, географическую карту, состояние хоста, здоровье очереди или возраст декодированного кадра. Там, где реальное API не возвращает значение, итоговый UI должен показывать «нет данных» или не показывать поле. Цветной статус WebSocket не равен подтверждению видеокадра. Любое изменяющее действие в будущей реализации обязано сохранить существующие API, RBAC, подтверждение опасного действия, обработку ошибки и обновление списка.

## Концепция 1 — Signal Desk

**Образ:** рабочее место оператора парка. Тёмный нейтральный фон, тонкие разделители, зелёный/янтарный/красный только для состояний. Шрифт интерфейса — Inter; моноширинный — только для идентификаторов, версий и временных отметок. Иерархия: текущая проблема → затронутые устройства → подробности выбранного устройства.

**Главный экран.** Компактная строка состояния парка заменяет ряд одинаковых KPI-карточек. Основную ширину занимает таблица «Требуют внимания» с фильтрами по статусу, группе и локации. Рядом остаётся инспектор выделенного устройства. Лента последних device events расположена под таблицей и сохраняет ссылку на полный журнал. Верхняя команда поиска доступна на любом маршруте.

**Реестр.** Плотная сортируемая таблица со статусом, последним heartbeat, версией APK и доступными полями. Панель массовых действий появляется только при выборе строк. Инспектор справа не сбрасывает фильтр и выделение при переходах между устройствами.

**Компоненты и взаимодействие.** Компактный status-count strip, фильтр-чипы, таблица с закреплённой шапкой, явные пустое/ошибочное/загружающееся состояния, правый drawer, context menu и command palette. Зелёный статус heartbeat визуально отделён от свежести кадров.

**Сильная сторона:** самый короткий путь от нестабильного статуса к диагностике. **Риск:** постоянная правая панель уменьшает ширину таблицы на 1366 px; в этом breakpoint инспектор должен превращаться в выдвижной overlay.

## Концепция 2 — Fleet Ledger

**Образ:** точный реестр инфраструктуры, рассчитанный на длительную работу и большие таблицы. Светлая каменно-белая поверхность, тёмные чернильные подписи, синий как основной интерактивный цвет, янтарный/красный только для предупреждений. Интерфейсный шрифт — Inter или системный; данные — табличные цифры и моноширинные ID. Минимум карточек, ровные строки, предсказуемые колонки.

**Главный экран.** Верхняя панель показывает активное пространство/организацию, глобальный поиск и состояние синхронизации. Центральная часть — широкая status-first таблица; над ней один сегментированный статусный ряд, фильтры и сохранённые представления, если их хранение будет согласовано с текущей моделью. Справа — отдельный компактный блок источников событий и системных проверок.

**Реестр.** Табличная страница — основной сценарий: группировка по имеющимся `group_id`, `group_ids` и `location_ids`, сортировка по heartbeat, версиям, имени и статусу, настройка колонок, массовый выбор. На узком экране вторичные колонки скрываются, а строка раскрывается в подробности; отдельная карта не добавляется, поскольку текущая модель не гарантирует координаты.

**Компоненты и взаимодействие.** Светлая/тёмная тема с одинаковой контрастностью, line-height для длинных имён, закреплённые заголовки таблиц, ячейки без выдуманных значений, понятная история фильтров и явная панель выбранных записей.

**Сильная сторона:** лучшая сканируемость и пригодность к длительной работе с большим количеством строк. **Риск:** без выразительного контекста может выглядеть слишком похоже на обычную админку; визуальный характер задают типографика, метки состояния и детальная панель, а не иллюстративные графики.

## Концепция 3 — Incident Stream

**Образ:** центр расследования с приоритетом на переходы состояния. Чернильно-синяя поверхность, ровные плоскости, голубой — транспорт и навигация, янтарный — stale/ожидание, красный — ошибки. Компактный гротеск и разреженный monospace только там, где сравнивают значения.

**Главный экран.** Узкая верхняя полоса состава парка, центральная хронология реальных device events и переходов статуса, слева — списки по online/busy/connecting/offline/error, справа — выбранное событие и переход к инспектору устройства. Если event feed недоступен, экран явно показывает состояние ошибки вместо пустой имитационной ленты.

**Реестр.** Таблица остаётся полноценным отдельным маршрутом. В каждой строке рядом со статусом показываются heartbeat и последние реально пришедшие события; выбор строки открывает правую инспекционную панель. Фильтр по событию или статусу сужает список, не создавая фиктивный «incident» объект.

**Компоненты и взаимодействие.** Timeline с уровнем важности, выбранное событие с payload-полями, breadcrumb/ссылки в журнал, панели с источником и временем обновления, drawer с быстрыми действиями по существующим контрактам. Любой «свежий кадр» обозначается только если backend/APK действительно присылает timestamp кадра.

**Сильная сторона:** быстрее всего раскрывает нестабильность и причинно-временную последовательность. **Риск:** если device-events недостаточно полны, основной экран будет беден; нужен честный fallback к таблице устройств.

## Сравнение и выбранное направление

| Критерий | Signal Desk | Fleet Ledger | Incident Stream |
|---|---|---|---|
| Главная единица работы | Выбранное устройство | Строка каталога | Переход состояния / событие |
| Самое сильное место | Быстрый triage с инспектором | Массовая работа с инвентарём | Диагностика обрывов по времени |
| Плотность | Высокая | Самая высокая | Средняя/высокая |
| Подходит для 20–100 устройств | Да | Да, лучше всего | Да, если события полны |
| Основной компромисс | Узкая рабочая область | Меньше «операторского» контекста | Зависимость от качества event feed |

Три варианта не смешиваются как переключаемые режимы основного продукта. Для основного приложения выбрана спокойная AdminCN/Fleet Console композиция: общая навигационная оболочка, понятный Dashboard и рабочая таблица устройств. Из Signal Desk используются только полезные triage-паттерны — связка события с устройством и инспектор. Плотность таблицы и контраст статусов взяты из Fleet Ledger. Отдельный «инцидентный» режим не вводится, пока event feed не подтверждает такую модель.

Это доказывает только визуальную композицию и работу локальных контролов прототипа. Не проверены API, RBAC, реальные данные, команды или права пользователя. На отдельной изолированной вкладке запрос `/devices` перенаправил на `/login`; там refresh вернул `401`, поскольку вкладка не имеет сессии пользователя. Встроенный браузер Codex также не удалось подключить: UI-bridge завершился системной ошибкой создания kernel assets. Исходную live-вкладку `/devices` и её сессию не изменяли.

## Интеграция в основной Sphere frontend — 29 сентября 2026

Изменения основной оболочки, Dashboard, реестра, login/MFA и общих компонентов находятся в [PR #19](https://github.com/RootOne1337/sphere-platform/pull/19), ветка `codex/enterprise-audit-20260905`. Это уже изменения штатного Next.js приложения, а не HTML-галереи из `previews/2026-09-28/`. Действующие 22 маршрута, API-клиент, React Query hooks, auth, права и mutations сохранены; AdminCN/Studio Admin исходники и assets в приложение не копировались. По каждому feature route продолжается отдельная UI/functional QA, поэтому текущий срез не заявляет, что все страницы глубоко переделаны.
