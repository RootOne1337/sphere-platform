# VPN всех приложений с сохранением прямого управления Sphere

22 октября 2026 · реализован кандидат APK86 / profile v2 / guard plan 5;
**в установленном APK85 этого режима нет, физическая приёмка не завершена**.

Пользователь ожидает два независимых выбора: какие приложения используют выход
и сохранять ли блокировку при недоступном VPN. Сейчас принят только конечный
pilot выбранных приложений. На PH030 профиль назначен `com.br.top`; остальные
приложения работают напрямую. Нельзя переименовать этот режим в «весь эмулятор».

## Два режима политики

| Политика | Покрытие | Состояние |
| --- | --- | --- |
| `selected_apps` | Явные package IDs, разрешённые после проверки UID/shared UID | Текущий контракт v1, максимум 64 package IDs |
| `all_apps_except_control` | Приложения основного Android user 0, кроме точного UID Sphere, включая устанавливаемые позже приложения | Исходники APK86, backend и веб реализованы; capability остаётся выключенной до физической приёмки |

Второй режим относится к приложениям Android, не к Windows-хосту, другим
эмуляторам, другим Android users или произвольному FORWARD-трафику. DNS системного
resolver должен следовать VPN-политике обслуживаемого приложения; исключать весь
системный UID resolver из анализа утечек нельзя. Служебный трафик самого Android
и DHCP требует отдельного явно описанного решения, прежде чем обещать защиту
буквально всех пакетов устройства.

В профиле v1 `selected_apps` требует список включённых package IDs;
в профиле v2 `all_apps_except_control` запрещает этот
список и пользовательские числовые исключения UID. Неизвестные поля, сочетания
версий и downgrade режима отклоняются. APK85 продолжает отклонять новый mode.
Зашифрованная команда широкого режима тоже использует wire schema 2; это
не позволяет старому APK переинтерпретировать запрос как v1.
Предварительная проверка, шифрование и capability должны различать синтаксическую
совместимость и проверенную возможность исполнения.

## Маршрутизация и защита

Android предоставляет `addAllowedApplication` и `addDisallowedApplication`; эти
списки нельзя смешивать в одном Builder. Для нового режима Builder исключает
собственный проверенный package, а не набор адресов управляющего сервера.
Список приложений действует в пределах Android user/profile. Основание:
[VpnService.Builder](https://developer.android.com/reference/android/net/VpnService.Builder),
[Android VPN](https://developer.android.com/develop/connectivity/vpn).

Это ещё не kill switch. После смерти сервиса Android закрывает TUN; без отдельной
защиты обычный маршрут может снова стать доступен. Поэтому новый режим требует
диапазонов application UID с исключением UID Sphere, а не моментального снимка
установленных package IDs. Снимок оставляет дыру для следующей установки.
Первый кандидат ограничен Android API 26–32 и основным user 0. Guard plan 5
хранит два точных диапазона от 10000 до 99999 с исключением owner UID Sphere;
в диапазон входят будущие app UID и isolated processes. Для owner UID 10000
остаётся один диапазон. Нельзя записать произвольные границы, другой user или
подменить plan 4 диапазонами. Android 13+ пока отклоняется до проверки SDK sandbox.
Это не слепое правило «все UID кроме одного».
Последнее может заблокировать DHCP, resolver и восстановление самой сети.

Перед изменениями агент сверяет package/signing identity, Android user, собственный
UID и shared UID. Несовпадение не разрешает применять политику частично. Root,
shell и диагностические инструменты не должны становиться скрытым универсальным
исключением для приложения. Все исключения отражаются в effective policy.

Guard получил plan 5 с точными диапазонами, таблицами, hooks,
interface name/index и фазой. Старые plan 3/4 очищаются по собственному точному
формату; их нельзя переинтерпретировать как диапазоны нового режима. Блокировка
обеих IP-семей подтверждается до открытия TUN. UDP транспорта защищён от самого
VPN; Sphere control/media/OTA работают через underlying network. Изменение сети
должно обновлять транспорт без освобождения защиты приложений.

Нельзя исправлять проблемы маркировки глобальным `iptables -F`, заменой main
routes, отключением всех фильтров или переписыванием Android fwmark. У Android
свои UID/mark правила и локальные lookup:
[AOSP RouteController](https://android.googlesource.com/platform/system/netd/+/refs/tags/android-11.0.0_r48/server/RouteController.cpp).

## Пауза, отключение и перезагрузка

| Действие / событие | Требуемый результат |
| --- | --- |
| Исчез интернет у peer | Нет автоматического перехода на прямой выход; health не равен handshake |
| Pause | TUN закрыт, защита сохранена, приложения заблокированы |
| Смерть `:vpn` / revoke consent | Защита сохранена, состояние требует согласования, Sphere доступен |
| Stop с включённой защитой | Остановить туннель, сохранить запрет прямого выхода |
| Явное «Разрешить прямой интернет» | Отдельная журналируемая операция, закрытие TUN и точное снятие owned guard |
| Перезагрузка Android / потеря kernel rules | Отдельная приёмка защиты до запуска приложений; текущий runtime guard её не доказывает |

В текущем APK85 явный `disconnect` **снимает** guard и возвращает обычный выход.
Для нового режима UI и команды должны разделять остановку туннеля и снятие защиты.
Успех crash/pause внутри одной загрузки нельзя выдавать за защиту после reboot:
kernel rules исчезают, а запуск APK из boot job может оставить временное окно.
Штатный Android always-on/lockdown тоже нельзя включать вслепую: текущий provider
отклоняет lockdown из-за требования прямого control bypass. Вариант с device-owner
политиками и разрешённым control требует отдельного provisioning и проверки.

## Сервер, интерфейс и автоматизация

Одна операция объединяет UI, script node, trigger и pipeline: actor/org/device,
expected profile revision, effective scope, operation ID, deadline, ACK/final
outcome и lease. Два apply/rotate не конкурируют за один guard. Неопределённый
результат означает status reconciliation, без нового физического запроса.

В вебе до применения показываются область действия, исключённый Sphere, IPv6
policy и поведение stop/kill switch. Для нового режима не рисуется произвольное
число «всех приложений», если инвентаризация не завершена. На телефоне область
действия также видна. Handshake, HTTP/DNS проверка и фактический egress IP — разные
состояния, каждое со своей временной меткой и источником. Неизвестное не равно нулю.
APK86 передаёт `trafficMode` в runtime snapshot; отчёты APK85 без этого поля
читаются как неизвестная область, а не как подтверждение широкого режима.

## Условия включения capability

1. Native journal/guard и backend schema принимают оба режима без ослабления v1.
2. Во всех lifecycle-фазах UID Sphere исключён; оба клиента direct media/control
   и OTA остаются доступны при разрыве VPN и смене сети.
3. Реальные HTTPS, UDP и DNS проходят от имени приложения, проверен внешний IP.
4. При pause, native crash, revoke и потере peer нет IPv4/IPv6/DNS выхода через
   физическую сеть. Проверяются физические пакеты, а не только таблицы.
5. Приложение, установленное после apply, покрывается без окна прямого выхода;
   проверены shared UID, isolated process и поддерживаемые users/profiles.
6. Поведение reboot/потери правил принято отдельно либо явно исключено из обещаний
   с запретом запускать защищённые задания до восстановления guard.
7. Lease/journal и lost-response recovery проходят конкуренцию UI/script/pipeline,
   ротацию, повтор command ID и неизвестный исход.

До этих проверок нельзя включать `execution_available` для нового режима или
выдавать selected-app опыт за production-защиту всего эмулятора. Текущие факты:
[APK85](../audits/2026-10-22/VPN-APK85-MAIN-CANARY.md),
[состояние PH030](../audits/2026-10-22/PH030-WG85-PATH-INVESTIGATION.md).
