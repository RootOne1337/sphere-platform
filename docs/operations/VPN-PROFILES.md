## Пользовательский путь

На `/vpn` каталог показывает имя, описание, протокол/версию, число выбранных
приложений, текущую revision и архив. Поиск — по буквальному фрагменту имени,
включая `%` и `_`; история постраничная. Импорт принимает `.conf`, выбранные package ID
и явную IPv6 policy. Список выбранных приложений не может содержать Sphere.
Подпись «Политика: Sphere вне VPN» описывает намерение профиля, а не измеренный маршрут.

Сохранение создаёт зашифрованную запись, не подключает устройство. Изменение — новая
неизменяемая revision с новым файлом: старый секрет не выгружается обратно в браузер.
Архивирование требует подтверждения и ожидаемую revision; история сохраняется.
Архив не разрывает уже работающую сеть. Применение, аренда выхода, ротация, восстановление
и fail-closed защита выбранных UID этим каталогом не выполняются.

В мобильном окне заголовок и кнопки закреплены, прокручиваются только поля.
Права `vpn:read` разрешают просмотр, `vpn:write` — импорт/версию/архив. React-компоненты
переоткрываются при смене actor scope, отменяют свои запросы и не кладут `.conf`
в общий query/store cache. Закрытие/abort запроса не означает отмену серверной записи.
Это не гарантия стирания копий строк из памяти JS/Python или browser devtools.

## HTTP и результаты

### Массовый импорт — новый исходный контракт, 22 октября

Веб принимает до 100 `.conf` одним выбором: до 64 КиБ на файл и 3 МиБ исходных
файлов вместе. Смешанные WG/AWG определяются по структуре; версия AWG задаётся
явно для пакета, список приложений общий. IPv6 проверяется для каждого профиля.
ZIP и списки HTTP/SOCKS-прокси этим импортом не поддерживаются.

`POST /api/v1/vpn/profiles/batch/preflight` принимает `items` из обычных
`VPNProfileImportRequest`, проверяет все файлы и возвращает только ID/вердикты/
коды ошибок/номера строк. Не сохраняет и не проверяет доступность VPN-сервера.
`POST /batch` сохраняет до 100 элементов одной транзакцией. Тело обоих запросов
ограничено 4 МиБ при потоковом чтении, даже без `Content-Length`. Ошибки JSON/
схемы не отражают исходные данные. Один некорректный файл или конфликт UUID
отменяет все новые записи и audit этой транзакции. Порядок получения блокировок
стабилен; порядок квитанций соответствует входу. Новых DB-таблиц/grants не требуется.

Каждый элемент имеет отдельный стабильный `request_id`. Это не фоновое задание
с отдельной batch identity: повторный набор уже известных элементов является
допустимым replay, новый элемент — отдельным намерением. Fingerprint каждого
запроса сохраняется только внутри ciphertext. Закрытие браузера не отменяет
запись. При timeout/непроверяемой квитанции UI удаляет исходные конфиги из своих
refs, блокирует повторный импорт и предлагает проверку прежних ID.

`POST /batch/status` принимает `request_ids` (1–100 уникальных UUID) и возвращает
по каждому квитанцию либо `null`. Последнее означает только «не наблюдается в
этом SQL snapshot»; завершившийся позже commit ещё возможен. Чтение использует
метаданные, не ciphertext; чужие ID также дают `null`. Можно закрыть окно
явной кнопкой; ID показаны для восстановления. Новый импорт автоматически
не запускается. Ключи не возвращаются в DOM/ответах/общем query cache.

Разные имена файлов не гарантируют разные выходные IP или разные клиентские
ключи. Импорт ничего не назначает эмуляторам. Аренды/распределение реализуются
отдельно по [плану управления парком](../design/VPN-FLEET-CONTROL.md).
Эта секция описывает новые исходники; installed baseline в начале документа
остаётся прежним до отдельной квитанции обновления.

### Операции отдельного профиля

Базовый путь `/api/v1/vpn/profiles`. Точные схемы находятся в
[OpenAPI](../openapi.json) и [каталоге HTTP](../api-endpoints.md).

| Метод/путь | Контракт |
| --- | --- |
| `GET /` | Метаданные текущих версий; `page` 1–10000, `page_size` 1–100, `search` до 120 символов, `include_archived` |
| `POST /` | `request_id`, имя до 120, описание до 1000, вложенный `profile` с конфигом/политикой; не применяет VPN |
| `GET /imports/{request_id}` | Только квитанция сохранения внутри текущей организации; не возвращает конфиг |
| `GET /{profile_id}` | Метаданные текущей версии, без ciphertext/ключей |
| `GET /{profile_id}/revisions` | Постраничная неизменяемая история метаданных |
| `POST /{profile_id}/revisions` | Те же поля импорта и обязательный `expected_revision`; новый request UUID |
| `POST /{profile_id}/archive` | `expected_revision`; архив без удаления истории/сетевых действий |

Идемпотентность scoped по организации и UUID. Fingerprint включает нормализованный
запрос, целевой профиль, ожидаемую revision и точный текст конфигурации; хранится
только внутри ciphertext. Повтор того же намерения/UUID возвращает исходную квитанцию
даже после дальнейшего изменения head. UUID с другим намерением отвечает 409.
Это не разрешение автоматически повторять физическое применение туннеля.

Успешный POST возвращает `profile_id`, `revision_id`, `revision`, `request_id`,
`persisted=true`, `apply_allowed=false`, `execution_confirmed=false`.
Конфликт head/архив/UUID — 409. Отсутствие owned профиля — 404. Ошибка формата —
422 без исходного секрета; слишком большой HTTP body — 413 (96 КиБ), конфиг ограничен
64 КиБ. Отсутствие/повреждение key ring — 503 `vpn_profile_secrets_unavailable`.

При потере ответа клиент считает исход неизвестным, очищает выбранный файл/сырой
конфиг, блокирует второй POST и предлагает GET по прежнему UUID. **404 означает
только, что запись не наблюдается в SQL snapshot:** первый запрос ещё может завершиться.
Нельзя автоматически создавать новый UUID. До закрытия окна оператор сохраняет UUID;
восстановления незавершённого UI-процесса после reload пока нет. Продолжить проверку
можно через import-status API с тем же tenant scope. Долговременный журнал VPN-операций
будет отдельной сущностью.

## Шифрование и ключи

Нужен отдельный secret `VPN_PROFILE_ENCRYPTION_KEYS`: от 1 до 8 Fernet keys через
запятую, новый первым. Первый шифрует, все разрешены для чтения. Ключи создаются и
доставляются штатным secret store, не в чате, документах, Git или выводе команд.
Поле в `.env.example` пустое; API не генерирует запасной эфемерный ключ и не сохраняет
plaintext. Нельзя повторно использовать JWT, `ACCOUNT_CREDENTIAL_KEYS` или router API key.

Полный конфиг и fingerprint защищены аутентифицированным ciphertext. Его identity
связывает организацию, профиль, revision/UUID, создателя, provider/protocol/schema,
policy, имя/описание, endpoint/features. Внутреннее расшифрование отвергает перенос
зашифрованного блока в другую запись. Это symmetric encryption с key ring, не KMS
envelope encryption. Ротация key ring требует штатного обновления API-процесса;
новый профиль или revision после rollout не требуют его перезапуска.

Старые ключи нельзя удалять, пока существуют зашифрованные ими revisions. История
append-only, поэтому массовое перешифрование не добавлено как обычный UPDATE endpoint.
Для ухода от старого ключа нужен отдельный проверенный forward migration/maintenance
процесс; восстановление БД без соответствующего secret store недостаточно.

Метаданные имени/описания, endpoint и package IDs видны пользователям с `vpn:read`
и находятся в БД открыто; не вставлять туда приватные ключи/пароли. Публичные SQL
проекции list/get/history/import-status не выбирают ciphertext. AuditLog записывает
действие, actor, org, профиль/revision/request ID, не `.conf` или его fingerprint.
HTTP decrypt/export/QR endpoint отсутствует. Чтение plaintext будущим provider потребует
собственной авторизации и аудита; его ещё нет.

При сетевом доступе обязателен TLS. На входных endpoints нельзя включать request-body
logging, APM body capture или HTTP debug с конфигом. Успешный импорт не делает
непроверенный `.conf` надёжным: preflight — только ограниченный импортный контракт,
движок должен отдельно подтвердить совместимость.

## БД, конкурентность и rollout

Миграция `20261021_vpn_profiles` следует за `20261006_script_catalog_metadata`.
Она создаёт `vpn_profiles` и `vpn_profile_revisions`, индексы/constraints и tenant RLS.
Историческую миграцию RLS не меняет. Lock timeout 3 с, statement timeout 15 с;
при конфликте миграция должна завершиться отказом, а не ждать без ограничения.
Downgrade с удалением истории намеренно запрещён, восстановление — backup/forward fix.

Runtime-пользователь каталога PostgreSQL должен быть nonowner, без superuser/BYPASSRLS;
tenant context задаётся транзакционно. Restrictive org boundary защищает обе таблицы.
Для revisions разрешены SELECT/INSERT, запрещены UPDATE/DELETE даже при дополнительной
permissive policy. Composite FK связывает org/profile, уникальность — request UUID
в организации и номер revision в профиле. Администратор/владелец таблицы может обходить
обычный RLS; это не защита от администратора БД.

Каталог теперь имеет собственный pool и secret `VPN_PROFILE_POSTGRES_URL`.
Пустое значение отключает HTTP каталога с 503; fallback на `POSTGRES_URL` запрещён.
Нужен `postgresql+asyncpg` URL с отдельным именем пользователя, паролем и той же
парой host/port/database, что у основного API. Query-параметры URL не принимаются.
Это не меняет старые миграционные credentials, стрим и фоновые задачи всего проекта.
Новый pool создаётся лениво: максимум два соединения на API worker, без overflow;
pool timeout 3 с, statement timeout 10 с, lock timeout 3 с. Вместе с основным pool
число подключений надо учитывать при расчёте лимита PostgreSQL.

На каждом запросе после JWT/RBAC и установки tenant context проверяются фактическая
роль соединения, RLS обеих таблиц и audit log, tenant и необходимые grants. Superuser,
BYPASSRLS/CREATEROLE, владелец с неактивным RLS, отсутствующая миграция или права не
дают работать каталогу. Проверка не кешируется как вечный признак «безопасной роли».
503 имеет ограниченный код `vpn_catalog_database_unavailable` либо
`vpn_catalog_database_policy_unavailable`; DSN, SQL и driver error не возвращаются.
Отдельный pool закрывается shutdown hook, SQL parameters не логируются.

Для выделенной роли без членства в административных/owner ролях нужны CONNECT на
этой БД и USAGE на public, а из таблиц только:

| Объект | Права |
| --- | --- |
| `vpn_profiles` | SELECT, INSERT, UPDATE |
| `vpn_profile_revisions` | SELECT, INSERT |
| `audit_logs` | INSERT и SELECT только колонок `id`, `created_at` для ORM RETURNING |

Не выдавать TRUNCATE, DELETE, DDL или чтение остальных audit payload/пользователей/
устройств. RLS должен оставаться активным; пароль поставляется через secret store.
Права и пароль не создаются API автоматически. Отдельный PostgreSQL тест прошёл
полный HTTP import/replay/list/append/archive именно с этими минимальными grants;
тот же endpoint отверг owner connection до первой записи. Это проверка временной
БД. При live rollout отдельно проверен вход под новой ролью; прежняя роль всего API
по-прежнему привилегированная и этим изменением не исправлена. Основание поведения owner/BYPASSRLS —
[документация PostgreSQL](https://www.postgresql.org/docs/15/ddl-rowsecurity.html).

Создание head/revision/audit происходит атомарно. Append использует row lock,
`expected_revision` и условное обновление head. Savepoint убирает спекулятивную запись
при конкурентном повторе UUID. Конкурентные архив и append не могут оба успешно
изменить одну ожидаемую revision. Число строк и страница читаются одним SQL snapshot,
в том числе для пустой/вышедшей за диапазон страницы.

Проверенный порядок rollout: backup и key-store recovery check → выделенная catalog роль →
миграция штатным release-процессом → API с ключами → read/write smoke на синтетическом
профиле → веб. Если миграция или crypto не готовы, не показывать это как пустой каталог
или рабочий VPN. Перед локальной установкой копия реальной БД восстановлена в своём
временном PG, там прошли миграция, минимальные grants и HTTP lifecycle; числа строк
прежних devices/users/organizations/scripts/script_versions/tasks сохранились.
После этого применена миграция и обновлены только API/UI. Секреты и резервная копия
остаются в приватной области; off-host disaster recovery не подтверждён.

Для локального пакета добавлен явный `package_local_backend --vpn-catalog`: он
допускает только неизменённую `20261021_vpn_profiles` после точного предыдущего head,
без изменения зависимостей или action contract. Копирует весь проверяемый packaged
source, включая Alembic, и запускает прежние изолированные runtime/metrics probes.
Обычный schema-free installer по-прежнему отвергает этот переход. Упаковка не
мигрирует рабочую БД, не добавляет ключи и не устанавливает API.

`install_vpn_catalog` подготовлен отдельно от schema-free installer. Он связывает
допущенный API-образ, точный переход схемы, SHA резервной копии, успешный restore
receipt и SHA миграционного worker. План проверяет полный Compose delta; разрешены
образ/удаление build recipe и только два новых catalog secrets. Применение ограничено
новой ролью `sphere_vpn_catalog` и указанной миграцией; ранее существовавшая такая
роль требует ручной сверки, а не смены её пароля. Неизвестный результат не повторяется.
При отказе нового API допускается возврат прежнего образа; добавленные таблицы не
удаляются. Worker проверен на восстановленной копии и затем применён локально.
Если запас памяти исчезает между миграцией и заменой API, `--resume-migration`
принимает только успешную receipt с исходным API container/image, backup/restore
hash и тем же worker. Схема и роль второй раз не создаются. После live HTTP smoke
и browser review каталога установка зафиксирована отдельной квитанцией выше.

## Нативный AmneziaWG-кандидат

[Lock](../../android/awg-native.lock.json) закрепляет официальный
[v3.1.20260814](https://github.com/amnezia-vpn/amneziawg-android/releases/tag/v3.1.20260814)
и commit `5c16489e2cd9ed3a0a7a27c7445bba5238132f86`. В выпуске обнаружен APK, а не AAR;
готовые Maven-координаты не предполагаются. Сборщик использует закреплённые Go/NDK,
проверяет source SHA, ограничивает GOMAXPROCS и сначала выполняет host resource guard.

```powershell
python scripts/build_awg_native.py --ndk-root '<NDK 26.3.11579264>' --go '<Go 1.25.4>' --android-clock --harden-jni --output '.local-pilot/awg-native-build'
```

Получены x86_64, arm64-v8a, armeabi-v7a: проверены ELF machine/class,
шесть JNI exports и 16-КиБ LOAD alignment. `--android-clock` применяет BOOTTIME
через изолированный Go overlay, без изменения установленного GOROOT. SHA исходных
ASM проверяются по lock. `--harden-jni` применяет закреплённый patch к отдельной
копии JNI backend: сериализация handle map, корректное закрытие при ошибке,
отключение filesystem UAPI. Изменённые/лишние исходники останавливают сборку.
Manifest остаётся diagnostic-only; эти флаги не разрешают production rollout.

`python -m scripts.sync_awg_sdk` проверяет 15 vendored Java sources и лицензию.
`:awg-sdk` сверяет их при preBuild. Для debug JNI нужен `SPHERE_AWG_NATIVE_DIR`
с этим manifest и точным набором трёх ABI; отдельный `:awg-smoke` допускает
`-PsphereProbeAbi=x86_64` для уменьшения диагностического APK. Release AAR всегда
без native `.so`, диагностические probe-модули не имеют release variant.

На Android 9 x86_64 пройдены изолированные root-TUN опыты: PH011 native AWG/HTTP
echo, PH030 native WireGuard/DNS по профилю владельца, crash/fail-closed и отдельный
контрольный UID Sphere. Это не установленный VPN service. Подробности, отрицательные
наблюдения и границы — в [квитанции](../audits/2026-10-21/VPN-ANDROID-PROVIDER-CANDIDATE.json)
и [архитектуре 1.2](../design/VPN-EGRESS-ARCHITECTURE.md).

Root-команды могут вызывать toast superuser. Не отключать глобальную защиту или
уведомления root-менеджера ради маскировки опроса. Штатная телеметрия должна читать
JNI counters и события; повторять `su` каждую секунду для статуса не нужно.
`UNKNOWN` нельзя интерпретировать как отключённый/безопасный VPN. После сбоя
сначала сверяются journal/UID/owned chains/routes, затем выполняется адресное
восстановление. Не удалять приложение с оставшимися UID rules: UID может быть
переиспользован системой.

Исходный APK84 добавляет service `:vpn` в то же приложение за debug-canary gate;
Android consent, private IPC и sealed device commands описаны в
[архитектуре 1.3](../design/VPN-EGRESS-ARCHITECTURE.md). Постоянный root polling не
используется. Новый `/vpn/runtime` читает отдельный отчёт текущего WS-соединения,
не смешивает его с peer assignment и не возвращает plaintext профиля. Состояние
старше 15 секунд в вебе считается устаревшим, даже если heartbeat продолжает идти.
Эти исходники пока не являются установленным main-APK или приёмкой media/control.

## Рабочее пространство и доставка профиля

Новая страница открывает подключения Android. Библиотека профилей, назначения на
маршрутизаторе и схема политики вынесены в самостоятельные вкладки. Ни назначенный
адрес, ни heartbeat, ни отдельный handshake не заменяют приёмку внешнего доступа
приложения. Неизвестные счётчики показаны прочерком; устаревший отчёт не получает
зелёный статус. Диагностика разделяет параметры соединения и идентификаторы.
В исходном веб-компоненте добавлена средняя RX/TX-скорость между двумя native
замерами с интервалом 1–15 секунд. Пара должна принадлежать одной сессии туннеля,
revision профиля, процессу VPN и управляющему WebSocket. Одинаковый повторный
отчёт не обновляет время измерения. Reset счётчика, смена identity, пауза,
ошибка API, смена страницы/фильтра/аккаунта начинают измерение заново; stale
данные скрывают скорость. Значения относятся ко всему туннелю, не к каждому
приложению, и не являются мгновенными показаниями или долговременной историей.
Изменение исходника само по себе не означает его установку: ревизии runtime
зафиксированы отдельно в текущей квитанции поставки.
Скриншоты исходных компонентов на двух темах и ширинах — в
[визуальном отчёте](../audits/2026-10-21/VPN-WORKSPACE-REDESIGN.md).

Legacy `/vpn/assign` всё ещё может возвращать plaintext config/QR для прежних
клиентов. Веб-хук назначения теперь проверяет device binding и возвращает только
`device_id`, `peer_id`, `assigned_ip`: config, QR, headers и Axios request не попадают
в React Query mutation data. Ошибка сохраняет только HTTP status для консервативной
обработки исхода; автоматического повтора назначения нет. Это не меняет старый HTTP
контракт и не делает его end-to-end encrypted. Три отдельные проверки подтверждают
ограниченный состав кэша, отказ при другом device ID и очистку error body.

Внутренний `profile_delivery.py` подготавливает encrypted envelope под одноразовый
Android recipient: RSA-OAEP SHA-256/MGF1-SHA1 и AES-256-GCM с operation UUID в AAD.
Tenant проверяется до decrypt; ограничены формат/размер RSA-ключа, срок получателя,
провайдер и политика сохранённой версии. Открытый профиль не возвращается вызывающему
коду. Перед вызовом будущий operation journal обязан связать recipient с текущей
аутентифицированной WS-сессией устройства и точной операцией. Сам по себе envelope
не является квитанцией применения. HTTP, очередь, retries и server lease этим helper
не реализованы.

Для будущего ограничения одновременных сессий вычисляется tenant-scoped identity из
WireGuard public key, а не private key. Разные X25519 clamping-представления одного
ключа дают одну identity. Пока нет транзакционного active lease и подтверждённого
освобождения, этот helper не разрешает массовое назначение одного клиентского профиля:
одинаковый WG-ключ на нескольких устройствах вызывает переключение endpoint у peer.

Остаются реальный `VpnService`/consent/revoke/socket protection, DNS/IPv6/boot,
долговременный server operation journal, delivery и приёмка полного WS/media/input.
`VPN_CONNECT`/`VPN_RECONNECT` и глобальный kill switch основного нового Android-кода
пока заблокированы. Существующие установленные Sphere APK/API/веб этим этапом не менялись.
