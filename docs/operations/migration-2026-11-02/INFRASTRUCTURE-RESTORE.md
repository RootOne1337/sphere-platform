# Восстановление инфраструктуры Sphere после переустановки Windows

Снимок обследования: 2 ноября 2026. Это инструкция для **локального pilot**,
не подтверждение готовности production. Переустановка допустима только после
проверки независимых копий и пробного восстановления. Git хранит код, но не
содержимое Docker volumes, приватные конфигурации, ключи, базы или локальные
образы. Не публикуйте закрытый архив, вывод `docker inspect`/`compose config`,
переменные окружения и дампы в GitHub: они могут содержать секреты и данные.

## До удаления Windows

1. Сохраните и проверьте исходный checkout вместе с незакоммиченными и ignored
   файлами в отдельной закрытой копии. Зафиксируйте commit и manifest с SHA-256;
   GitHub сам по себе не заменяет копию рабочего дерева. Сохраните исходный
   `.local-pilot`, включая install baseline/candidate, agent config, tunnel,
   secrets и bind-данные, в шифрованном хранилище с отдельной копией ключа.
   Конфиги могут содержать реальные пароли даже внутри JSON/YAML.
2. Получите логические дампы **обеих** баз `sphereplatform` и `n8n`, роли и
   права отдельно, а также все нужные volumes и bind mounts. Сверьте manifest,
   размер и хэш каждого файла. Дамп `sphereplatform` не включает базу `n8n`.
   Сохраните исходные ключи шифрования учётных данных, VPN-профилей и n8n,
   JWT, PostgreSQL/Redis/MinIO, agent identity, сертификаты и ключи туннелей.
   Старые ключи нужны для чтения старых зашифрованных данных; их замена —
   отдельная миграция, а не шаг восстановления.
3. Экспортируйте точные локальные Docker images с привязкой ID к контейнеру,
   в том числе reviewed backend/UI и Tuna, и проверьте возможность `docker load`
   на отдельном Docker Engine. Архивы образов также могут содержать секреты.
   Для исторического `sphere-tunnel` восстановите отсутствующий старый путь
   из отдельной копии или документируйте его соответствие текущим файлам;
   одного имени образа и labels недостаточно.
4. Вне Git сохраните DNS/provider account, настройки и учётные данные Tuna,
   Cloudflare/Serveo, доступ к VPS, router и его независимый backup AWG/WG,
   маршруты, firewall, client identities и сертификаты. Обычный Windows VPN
   может иметь отдельные профили и ключи вне проекта; экспортируйте их средствами
   соответствующего клиента. Наличие контейнера не подтверждает работу маршрута.
5. Проведите отдельную пробу: извлечь архивы, проверить SHA-256, восстановить
   базы и объекты в изолированное окружение и прочитать контрольные записи.
   Сверьте размер, владельцев, права и контрольные суммы объектов; проверьте
   расшифровку тестовой n8n credential без вывода значения. Храните как минимум
   две независимые копии и отдельно средство расшифровки. До успешной пробы
   исходный диск и данные сохраняются нетронутыми.

## Новая пустая установка из Git

Это отдельный сценарий: он создаёт **новые** базы, ключи и идентичность; данные,
учётные записи, устройства, VPN, туннели и текущий reviewed UI сам по себе не
восстановит. После clone выберите точный commit, проверьте чистоту checkout и
установите Docker Desktop и Compose версии не ниже 2.24.4: эта версия нужна для
`!override` ([документация Docker](https://docs.docker.com/reference/compose-file/merge/)).
Для `New` нужны Git, Docker и Windows PowerShell; устанавливать Node.js или
Python на Windows не требуется, зависимости собираются внутри Docker. Для
`Restore` дополнительно нужен Python 3.12 или новее как `python` в PATH.
Простой запуск в PowerShell из каталога репозитория:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migration\new-install.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migration\new-install.ps1 -Mode New
```

Первая команда лишь показывает план; вторая собирает исходники и создаёт новый
изолированный локальный проект с отдельной базой, ключами и первым
администратором. Самостоятельная регистрация в UI не заменяет создание этого
администратора. Скрипт печатает адрес и путь к приватному `admin.env`, а не
пароль; сохраните `admin.env`, `install.env` и `agent-config` в закрытом месте.
VPN и внешние туннели здесь не настроены. Запуск требует свободных loopback
портов и ресурсов; время зависит от сборки и сети. При ошибке проект и файлы
оставляются для диагностики, ничего автоматически не удаляется. Сценарий
проверяется отдельно; итог проверки и границы следует сверить перед переустановкой.

Ручной альтернативный порядок ниже рассчитан на
новую машину, не на старый действующий проект. Выберите незанятые loopback порты
и уникальное имя проекта. Запуск создаст volumes, контейнеры и образы.

1. В корне чистого checkout убедитесь, что `.env.local` отсутствует; выполните
   `python scripts/generate_secrets.py --output .env.local`. Откройте файл только
   локально: генератор не заполняет все `CHANGE_ME` (в частности MinIO и WG).
   Задайте отдельные случайные `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` и
   предназначенные для нового окружения значения WG. Опциональные отдельные
   Fernet-ключи учётных данных и VPN включают соответствующие возможности;
   порядок и формат описаны в `.env.example`. Ограничьте доступ к файлу и
   сохраните его в шифрованной копии. Не подставляйте новые ключи к старым данным.
2. Добавьте в этот приватный `.env.local` уникальные значения `PILOT_IMAGE_PREFIX`
   и `PILOT_REVISION`, а также `PILOT_AGENT_URL` и `PILOT_BROWSER_URL`; для
   чисто локальной проверки можно использовать `http://127.0.0.1:28080`.
   Укажите `PILOT_GATEWAY_PORT=28080`, `PILOT_N8N_PORT=25678`,
   `PILOT_S3_PORT=29000`, `PILOT_S3_CONSOLE_PORT=29001` после проверки, что
   они свободны. Loopback URL не доступен с других устройств. Создайте пустую
   директорию `.local-pilot/agent-config`; для реальных устройств потребуется
   корректная отдельная конфигурация и достижимый адрес.
3. В PowerShell из корня проекта выполните явно выбранные файлы:

   ```powershell
   $dc = @('--env-file', '.env.local', '-p', 'sphere-fresh', '-f', 'docker-compose.yml', '-f', 'docker-compose.full.yml', '-f', 'docker-compose.local-pilot.yml')
   docker compose @dc config --quiet
   docker compose @dc build backend frontend
   docker compose @dc up -d postgres redis minio
   docker compose @dc run --rm --no-deps backend alembic -c alembic/alembic.ini upgrade head
   docker compose @dc up -d backend frontend nginx n8n
   ```

   Дождитесь healthy PostgreSQL до миграции; при ошибке остановитесь и разберите
   её. Команда миграции предназначена только для **новой пустой** БД, никогда
   не направляйте её на старые данные без отдельной проверки. Доступность и
   создание первоначального администратора и enrollment потребуют следовать
   процедуре текущего commit; не создавайте ключи для старых устройств вслепую.
   На старом хосте выполнена изолированная проба source build: миграции,
   создание первого администратора и enrollment, readiness и API-вход прошли.
   Это сборка рабочего дерева; запуск именно чистого клона на новой Windows не
   проверен. Итоговый launcher повторно прошёл полный New с повторным
   использованием ранее собранных из этого дерева образов, включая API-вход.

   Дополнительная проверка 2 ноября: чистый shallow clone опубликованной ветки
   на commit `e52eae8f88039f0ee98ecfb34f3f5abcd0848223` до запуска не имел
   `.local-pilot`, `.env` или `.env.local`. `New` с явно выбранными ранее
   собранными локальными backend/frontend images завершился успешно: созданы
   новая БД, admin и enrollment, сервисы healthy, API-вход admin проверен самим
   запускателем. Затем `manage-install Stop` остановил только этот новый проект,
   сохранив тома. Это проверка опубликованного launcher и конфигурации, а не
   новая сборка images из чистого clone и не проверка переноса на новый Windows.

## Подключение снимка к отдельной установке

Режим Restore создаёт **новый** проект и тома, проверяет manifest и хэши,
импортирует `sphereplatform`, `n8n`, роли и volumes, использует сохранённые
пароли и ключи, затем запускает backend, frontend и nginx без миграций и без
нового администратора. Входить нужно с прежней учётной записью:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migration\new-install.ps1 -Mode Restore -Snapshot 'D:\private-backup\data-snapshot'
```

Путь должен содержать `manifest.json` и упомянутые им файлы, включая закрытый
`container-configs-sensitive.json`. Скрипт не использует и не перезаписывает
ранее созданный проект. Не запускайте импорт из недоверенного снимка: дамп и
контейнерные данные являются исполняемым или конфиденциальным материалом.
Сохраните исходный снимок отдельно. Docker volumes создаются только с новыми
именами; после ошибки частичная копия остаётся для диагностики.
Импорт ролей проверен для снимка 2 ноября, в котором globals содержат `sphere`
и `sphere_vpn_catalog`. Другой снимок может содержать конфликтующую роль
`postgres`; тогда импорт остановится и требует отдельного разбирательства.

Backend и хранилища подключены к внутренним Docker-сетям; только nginx также
подключён к отдельной bridge-сети для локального порта. n8n, VPN router,
туннели и устройства не запускаются. Это изолированная рабочая копия: фоновые
задачи backend могут изменять восстановленную БД и Redis. Внешние VPN и
интеграции требуют отдельного согласованного подключения. Если профильная БД
располагалась на другом узле или в другой базе, этот способ останавливается:
такая БД требует отдельного проверенного backup.

На старом хосте 2 ноября итоговый Restore прошёл от начала до конца с повторным
использованием ранее собранных из рабочего дерева образов: дампы обеих БД и
тома восстановлены в новый проект, backend и nginx healthy, readiness и login
page ответили 200; 19 из 19 зашифрованных VPN revisions расшифрованы без
вывода содержимого. Чистый clone на новой машине и устройства ещё не проверены.
После миграции сохраняйте исходный снимок до независимой приёмки данных и
внешних интеграций.

## Повторный запуск и внешнее переключение

Путь к приватной папке печатается в конце `New` или `Restore`; сохраните его.
В корне того же checkout используйте этот путь вместо примера:

```powershell
$install = '.local-pilot/new-installs/<имя-вашего-проекта>'
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migration\manage-install.ps1 -InstallDirectory $install
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migration\manage-install.ps1 -InstallDirectory $install -Action Start
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migration\manage-install.ps1 -InstallDirectory $install -Action Stop
```

Команды управляют только уже созданными контейнерами этого проекта; `Stop` не
удаляет тома, образы или секреты. `Start` не пересоздаёт контейнеры и откажет,
если bootstrap прервался и контейнер или нужный том отсутствует: не повторяйте
`New` в надежде, что он автоматически подхватит данные. Сначала разберите
сообщение и приватные логи или создайте новую изолированную пробу из сохранённого
снимка. Запуск изолированного Restore не включает n8n и туннели. Если вручную
добавить n8n или другие контейнеры в этот проект, `manage-install.ps1` откажет
из-за изменившегося состава: для внешнего cutover нужна отдельная проверенная
операционная конфигурация. На этом хосте
Status → Stop → Start проверены на New, а вход прежним локальным admin после
перезапуска подтверждён; проверочные стенды затем остановлены с сохранением данных.

Для фактического перехода устройств на восстановленный хост одной команды нет:
имена домена, облачный аккаунт, tunnel credentials, DNS, подписанная конфигурация
и доступ к внешнему VPN-router не входят в Git и зависят от приватной копии.
Пока старый хост работает, не запускайте второй коннектор с той же идентичностью
и не переключайте DNS. Проверьте и запишите следующие операции для выбранного
конкретного провайдера, затем выполняйте их в согласованное окно:

1. Проверьте восстановленную БД, вход старого администратора, MinIO, n8n
   credentials, VPN-профили и соответствие всех сохранённых ключей. Восстановите
   приватный agent-config, подписывающий ключ и старый опубликованный URL;
   сверяйте документы [discovery](../DISCOVERY-PUBLISHER.md) и
   [Android bootstrap](../../architecture/ANDROID-BOOTSTRAP-DISCOVERY.md).
   Одновременная запись старым и новым backend не объединяется автоматически.
2. Подготовьте отдельную проверенную копию приватного `private-overlay.yml`:
   для изолированной пробы обе application/data сети имеют `internal: true`.
   Для нужных исходящих сервисов настройте доступ намеренно, сохраняя loopback
   публикации и сетевую изоляцию БД. Укажите реальный внешний URL в приватном
   `install.env`, `agent-config` и разрешённых browser origins; сверьте TLS,
   DNS, внешний WG router, AWG-параметры и доступ к прежним устройствам.
   `manage-install.ps1 Start` не применяет изменения Compose: изменение сетей
   и env требует отдельного запланированного пересоздания нужных контейнеров.
3. Верните выбранный провайдер: для Tuna — его отдельный приватный compose и
   `/run/secrets/tuna.yml`, актуальную Docker network восстановленного проекта и
   правильный upstream; для Cloudflared Windows — его служебную конфигурацию,
   credentials и маршрут в панели провайдера; для Serveo — SSH identity и
   согласованный hostname. Старый `sphere-tunnel` ссылается на другой checkout.
   Не подменяйте named tunnel временным Cloudflare quick URL. Обе копии
   коннектора и маршруты должны быть согласованы до переключения.
4. Перед запуском n8n проверьте расшифровку credentials и отключите или
   согласуйте расписания/webhooks: восстановленные задания могут сразу
   выполняться. Только после переключения проверьте авторизованный доступ по
   HTTPS, WebSocket и регистрацию одного тестового устройства, фактический VPN
   handshake, DNS/маршрут и остановку при потере сети. Сохраните план отката к
   старому endpoint и независимую неизменную копию данных.

Эти шаги описывают оставшуюся работу, а не проверенную автоматическую процедуру
публичного cutover: на новой Windows, с реальными DNS/tunnel и устройствами она
ещё не выполнялась. Пользуйтесь точными инструкциями соответствующего
провайдера после проверки сохранённых конфигураций; не вставляйте секреты в лог.

## Порядок после установки Windows

1. Установите Git, WSL 2 и Docker Desktop/Compose с совместимыми версиями;
   проверьте свободное место, архитектуру, доступ к зашифрованным архивам и
   резервному ключу. Запустите из восстановленного checkout:

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\migration\restore-preflight.ps1
   ```

   Скрипт только читает версии, состояния и HTTP-коды loopback. Отсутствующие
   контейнеры до восстановления ожидаемы. Нулевой код не означает, что резервная
   копия есть, корректна или что сервисы работают.
2. Проверьте manifest и хэши всех файлов до распаковки. Восстановите исходный
   путь checkout или аккуратно перепривяжите все абсолютные bind paths в
   приватных конфигурациях. Не выполняйте сохранённые `baseline.json`/candidate
   как готовую автоматическую команду: они могут содержать старые абсолютные
   пути, адреса сетей и секреты. Сначала локально проверьте монтирования, сети,
   переменные и точные image ID. Избегайте автоматического `docker compose up`
   с неявным `docker-compose.override.yml` — в нём dev-переопределения.
3. Загрузите проверенные image archives на новом Engine, сопоставьте ID с
   inventory: `docker image load -i <путь-к-проверенному-архиву.tar>`.
   Эта команда добавляет образы и может изменить существующие теги; используйте
   отдельный новый Engine и проверьте ID после загрузки. Создайте отдельный
   изолированный проект и **новые пустые** volumes;
   при совпадении имён с существующими данными остановитесь. Восстанавливайте
   каждый архив только в соответствующий новый том по manifest. Не используйте
   `down -v`, `volume prune`, перезапись существующих томов или автоматические
   миграции. Сырые файлы PostgreSQL допустимы лишь при доказанной согласованности
   и совместимости версии; предпочтителен логический restore.
4. Сначала поднимите только совместимый PostgreSQL в изолированной сети,
   восстановите роли/права и **обе** базы из проверенных дампов в новые пустые
   базы средствами, соответствующими формату дампа (`pg_restore` для custom,
   `psql` для SQL). Сверьте базы, расширения, ownership, Alembic revision и
   контрольные данные. Не применяйте миграции вслепую. Верните Redis, MinIO,
   n8n и их исходные ключи/тома; проверьте объекты и расшифровку n8n credential.
   Точный набор и команды зависят от manifest созданной копии; не угадывайте.
5. Восстановите backend, pilot frontend и nginx; затем review UI/gateway,
   соединяя external network с фактической сетью backend. Для pilot порядок
   Compose файлов — `docker-compose.yml`, `docker-compose.full.yml`,
   `docker-compose.local-pilot.yml`; public-gateway добавляет
   `docker-compose.remote-pilot.yml`. Review описан в `docker-compose.review.yml`,
   мониторинг — `infrastructure/monitoring/docker-compose.observability.yml`.
   Это схемы, а не достаточная инструкция для побайтного восстановления
   изменённых установщиком контейнеров. Используйте сохранённые образы и
   приватный config, проверенный на новом хосте, без rebuild/pull изменяемых тегов.
6. Проверьте `/api/v1/health/readyz` на 18080 и 3015 и `/login` на 3015;
   проверьте авторизацию, БД, OTA, n8n, MinIO и нужные пользовательские данные.
   Поднимите мониторинг, сверив сети, секрет и приватный bind-конфиг Prometheus.
   Health HTTP не подтверждает сохранность или полноту данных.
7. Только после локальной проверки включайте нужный удалённый gateway и один
   согласованный туннель, проверяя DNS, TLS, upstream и авторизацию снаружи.
   Quick Cloudflare выдаёт меняющийся URL; это не фиксированная точка входа.
   Верните VPN router/клиенты отдельно и сверьте фактические peers, handshake,
   маршруты, DNS и kill switch. `GET /api/v1/vpn/health` — статический ответ,
   не проверка туннеля: см. [VPN incident](../../runbooks/02-vpn-incident.md).
   Не пересоздавайте peers и не запускайте массовое управление устройствами до
   согласования фактического состояния router и БД.

Завершение требует успешного пробного чтения всех необходимых данных и ручной
проверки устройств/внешних интеграций. До этого архив — кандидат на резервную
копию, а не доказанное восстановление.
