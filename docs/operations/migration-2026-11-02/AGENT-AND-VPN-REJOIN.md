# Подключение существующих Android-агентов и VPN после переноса

## Что можно обещать

Старые устройства **могут** переподключиться без повторного enrollment, если восстановлены совместимые состояние сервера и устройства, исходные ключи, доступный им адрес и сеть. Это не гарантировано одним наличием дампа PostgreSQL: устройство могло обновить токен после снятия дампа, токен мог истечь, адрес или сертификат мог измениться, а Android/emulator storage — не сохраниться. VPN-профили тоже требуют ключей расшифровки и работающего внешнего VPN-сервера/маршрутизатора. Подтверждение возможно только после изолированного восстановления и поштучной безопасной проверки. Новый пустой install создаёт новую организацию/учётные данные: существующие агенты не становятся его устройствами автоматически.

**Снимок схемы 2 ноября 2026:** прочитанная без изменения таблица `alembic_version` живой базы `sphereplatform` содержит `20261021_vpn_profiles`; единственная `head` текущего checkout — `20261021_vpn_profiles` (`alembic -c alembic/alembic.ini heads`). Это совпадение только обозначений на момент проверки, не подтверждение отсутствия дрейфа схемы, соответствия запущенного image исходникам или пригодности любого другого дампа. Повторить проверку на восстанавливаемом дампе и версии кода до upgrade; миграции применять только к отдельной проверенной копии.

## Идентичность Android и условие согласованности

- `backend/models/device.py` хранит `devices.id`, `org_id`, `is_active`, `meta.fingerprint`, `meta.instance_binding`, `meta.instance_binding_version`, `refresh_token_hash`, `refresh_previous_token_hash`, `refresh_rotation_key_hash`, `refresh_token_expires_at`; хранятся хеши, не сам клиентский refresh-токен. Вместе требуются организации, устройства, ключи enrollment, связи групп/локаций и данные авторизации в той же БД.
- Android `AuthTokenStore.kt` держит в Android `EncryptedSharedPreferences` `device_id`, `access_token`, `refresh_token`, `refresh_rotation_id`, сроки и `server_url`, `primary_server_url`, `fallback_server_url`, instance binding. Сохранить соответствующее состояние каждого устройства/эмулятора и его Android Keystore: перенос каталога приложения на другую установку/образ сам по себе не гарантирует доступ к зашифрованным значениям. Не копировать и не публиковать токены. Не удалять приложение, данные, эмулятор или экземпляр при диагностике.
- `/api/v1/devices/refresh` ротирует токен; клиент сохраняет ID намерения, сервер допускает ограниченное восстановление ответа только при совпадении прежнего токена и того же намерения. После дальнейшей ротации старый снимок БД может не содержать текущий клиентский хеш. При HTTP 401 клиентский код может очистить отвергнутые credentials для повторного enrollment. Поэтому сначала изолировать восстановленную копию от **реальных** агентов; согласовать момент финального снимка и переключения, проверить свежесть и историю ротаций. Одного совпадения JWT-ключа недостаточно.
- WebSocket `/ws/android/{device_id}` аутентифицирует первое сообщение и сопоставляет device ID, организацию и активную запись; статус, который виден в каталоге, не доказывает видеопоток и управление. Доступный из Android `SERVER_PUBLIC_URL`, прежние основной и резервный URL, DNS/TLS, gateway, маршруты, WebSocket upgrade и связь с сервером должны совпадать с реально допустимыми настройками устройства. Для emulator `localhost` означает сам эмулятор; `127.0.0.1` Windows не является универсальным адресом для Android или удалённого компьютера.
- При re-enrollment сервер сопоставляет fingerprint и binding внутри организации; изменившийся/дублированный binding может создать отдельную карточку или отклонить несовместимую версию. Для эмулятора `InstanceBindingReader.kt` использует стабильный VM serial, для физического Android — Android ID; неоднозначный serial эмулятора отклоняется. Сохранить VM identity и mapping LDPlayer, а не размножать копии с одинаковой идентичностью. Серийный номер, ключ и fingerprint в этот документ не выводятся.
- Для контролируемого повторного enrollment требуется действующий enrollment API key с правом `device:register` и привязкой к прежней организации, согласованная доставка конфигурации и проверка fingerprint/binding. Это отдельная операция, способная обновить данные устройства/токены; сначала решить, какую карточку она должна сохранить. В пустой БД появятся новые ID и не восстановятся связи со старыми задачами, группами или записями только за счёт имени устройства.

## Что хранить вместе

| Компонент | Требуемое состояние и имена конфигурации |
|---|---|
| Identity и API | Согласованный дамп PostgreSQL, организации, пользователи, устройства, API keys и роли; исходные `JWT_SECRET_KEY`, `JWT_ALGORITHM`, а также настройки времени жизни JWT и время системы. Права функций `sphere_auth.*` и row-level security необходимо восстановить, а не обходить superuser. |
| VPN-профили приложений | Строки `vpn_profiles`, `vpn_profile_revisions`, их ciphertext и привязки к org/profile/revision/user; полный действовавший упорядоченный набор `VPN_PROFILE_ENCRYPTION_KEYS` (старые ключи нужны для прежних ревизий), `VPN_PROFILE_POSTGRES_URL` и роль/права каталога. Исходный `VPN_KEY_ENCRYPTION_KEY` нужен для использующего его legacy peer flow, если он использовался. |
| Внешняя VPN-инфраструктура | Сервер/peer WireGuard или AmneziaWG, его приватные и публичные ключи и PSK, реальные `.conf`/настройки, адреса, DNS, маршруты, firewall, allowlist приложений и назначенные адреса; при применении `WG_ROUTER_URL`, `WG_ROUTER_API_KEY`, `WG_SERVER_PUBLIC_KEY`, `WG_SERVER_ENDPOINT`, `VPN_SERVER_HOSTNAME`, `VPN_POOL_SUBNET`, `AWG_*`. Сохранять секреты отдельно, не вставлять значения в Git. Профиль в БД не заменяет VPN-сервер, установленный клиент или проверку handshake. |
| Игровые учётные данные | Строки аккаунтов **и** полный применимый список `ACCOUNT_CREDENTIAL_KEYS`; ciphertext привязан к org и account ID. Отсутствие ключа не исправляется повторным созданием другого ключа. |
| n8n и объекты | Дамп n8n и его volume, тот же `N8N_ENCRYPTION_KEY` для сохранённых credentials; связанные объекты MinIO и `SCREENSHOT_STORAGE_*`, настройки доступа. Проверять доступ не раскрывая payload и не запуская workflows. |
| Устройства, группы, цвета, сценарии | PostgreSQL хранит устройства, привязки, `device_groups.color`, `locations.color`, сценарии/версии и связанные записи. Цвет темы интерфейса, настройки таблиц и несохранённые черновики Studio живут в browser localStorage и не восстанавливаются из БД автоматически. |
| Записи маршрутов | `frontend/src/features/stream/teachingLibrary.ts` использует browser origin-private file system `sphere-teaching-<scope>`; `TeachingReview.tsx` предлагает штатный экспорт в выбранную пользователем папку. До очистки браузера сохранить и проверить **каждый важный пакет** и связанные файлы; смена origin/профиля сама по себе не переносит OPFS. Результаты `.local-pilot/reconstruction-jobs` и реконструкционные links/capabilities — отдельные чувствительные локальные файлы; их наличие и восстановимость нужно сверять независимо. Одни БД и Git не сохраняют браузерные видео и локальные карты. |

Проверка имён фактически переданных переменных живому backend 2 ноября без вывода значений: `JWT_SECRET_KEY`, `VPN_PROFILE_ENCRYPTION_KEYS`, `VPN_PROFILE_POSTGRES_URL`, `WG_ROUTER_URL`, `SERVER_PUBLIC_URL` непустые; `ACCOUNT_CREDENTIAL_KEYS`, `VPN_KEY_ENCRYPTION_KEY`, `WG_ROUTER_API_KEY`, `SCREENSHOT_STORAGE_ENDPOINT` пусты или отсутствуют. Это не проверка содержимого записей, актуальности ключей, безопасности, доступности объектов или состояния других контейнеров. Не генерируйте замену старым ключам в надежде расшифровать старые данные.

## Порядок восстановления и контроль

1. До переустановки сохранить проверенные копии данных и оригинальной защищённой конфигурации, резерв внешних VPN/доменов/Keystore, VM и маршрутов/черновиков браузера. Зафиксировать сроки отдельных снимков и риск ротации; один `pg_dump` консистентен внутри своей БД, но отдельные БД и live копии volumes не образуют единый момент времени. Бэкапы должны быть вне стираемого диска и защищены.
2. Развернуть **изолированный** восстановительный стенд без доступа к настоящим агентам, webhook-адресатам и работающему VPN. Поднять отдельные совместимые PostgreSQL/Redis и object storage, восстановить данные, старые нужные ключи и `N8N_ENCRYPTION_KEY`, затем корректные роли, права и функции; сверить ревизию БД с кодом и миграции, структуру и данные. Проверять без вывода секретов. Наличие дампа не является доказательством пригодного restore.
3. Прочитать каталог устройств/связи и цвета, скрипты и версии, VPN-каталог и настройки, маршруты/файлы, выборочно проверить расшифровку и целостность без передачи значений; проверить n8n в отключённом от внешнего мира режиме. Сверять сохранённые идентификаторы, не только визуальные имена и количество.
4. Приступать к переключению лишь после согласованного актуального финального снимка, подготовки исходных ключей, прежнего reachable endpoint или проверенного механизма миграции адресов, DNS/TLS и недублирования экземпляров. Не допускать одновременной работы старой и восстановленной системы с одними агентами и credentials; не обещать, что snapshot переживёт все ротации. Резерв и план возврата сохраняются.
5. На одном выбранном устройстве проверить существующий ID/org и безопасный heartbeat/WS, затем отдельно при разрешении оператора — видео и ввод. При отказе 401 или изменении identity остановиться, исследовать причины и лишь затем планировать re-enrollment. Проверить VPN клиента и handshake отдельно, сохраняя канал управления; далее расширять проверку на остальные устройства. Не выполнять массовый запуск заданий, OTA или изменение VPN во время первой проверки.

## Границы существующих инструментов

`scripts/migration/restore_data.py` поддерживает `--compose-volumes` для имён/labels проекта Compose и `--preserve-roles` для восстановления globals и исходных владельцев/ACL в изолированной PostgreSQL. Это исправляет прежнее расхождение имён и пропуск owners/privileges, но само по себе не доказывает end-to-end подключение приложения. Режим Restore в `new-install.ps1` создаёт изолированный проект, импортирует часть исходных секретов, делает обе Compose-сети internal, не запускает n8n и не выполняет миграции/seed. Он допускает исходный `VPN_PROFILE_POSTGRES_URL` только если тот указывает на восстановленную базу `postgres/sphereplatform`, и выбирает `AGENT_CONFIG_ENV=restore` без готовой среды enrollment. По сообщению исполнителя восстановительного стенда, 19 из 19 VPN-ревизий расшифрованы без вывода данных; это ещё не проверка VPN handshake, а enrollment этим запуском не подтверждён. Фактические политики RLS, все зависимости и полный end-to-end приём на изолированной копии должны проверяться отдельно. Backend всё равно запускает orchestration/watchdogs, поэтому может изменять данные и Redis внутри стенда; это рабочая копия, а не неизменный эталон. Live копии разных компонентов не становятся атомарными от того, что restore прошёл успешно. `new-install.ps1` в режиме создания новой БД создаёт новый identity и ключи; его нельзя смешивать с прежним состоянием без предусмотренного и проверенного restore workflow.


## Выполненная проверка

Исходники Android и backend изучены статически. Тесты `tests/test_account_cipher.py` и `tests/vpn/test_profile_catalog.py` в `.venv-audit` с тестовым JWT: **29 passed**, одна warning. Дополнительные 47 integration cases по device refresh, clone registration, account credentials и VPN catalog **skipped**: требуется отдельный PostgreSQL/Redis с `SPHERE_RUN_INTEGRATION=1`; против живой БД они не запускались. Затем выполнены изолированное восстановление и вход прежним паролем, сверены идентичности/метаданные устройств, цвет группы, 61 сценарий со всеми версиями/DAG и 10 VPN-профилей: [API observation](RESTORE-API-OBSERVATION.json). 19/19 encrypted VPN revisions расшифрованы. Подключение Android, импорт маршрутов в действующую установку и VPN handshake не выполнялись.
