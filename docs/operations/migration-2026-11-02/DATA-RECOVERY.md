# Pilot data recovery evidence — 2026-11-02

The staging snapshot is `.local-pilot/migration-20261102/data-20261102-live/` on C:. It is **not an independent backup** and will be lost if this disk or Windows installation is erased. It contains passwords, encryption keys, database data and private container configuration: keep it private and transfer it to an encrypted, independently stored destination. Do not commit it or publish it. SHA-256 detects accidental changes but does not authenticate the manifest.

`scripts/migration/backup_data.py` creates three PostgreSQL custom dumps (`sphereplatform`, `n8n`, and `postgres`), a globals-only SQL dump, archives of pilot MinIO, n8n, Redis, OTA, device logs, identity, SSH identity and certificate volumes, and sensitive container inspection metadata. The latter includes the running n8n encryption key; that key must accompany the n8n database when restoring credentials. PostgreSQL dumps are transactionally consistent individually, but taken separately: they are not a shared cross-database snapshot. The volumes were archived while services were running; they are not application-consistent or synchronized with the database dumps. In particular, Redis memory may contain newer data than its on-disk files, and MinIO and n8n cannot be assumed synchronized with PostgreSQL.

To create a new snapshot, first create a private parent directory and ensure adequate free disk space, then run `python scripts/migration/backup_data.py <new-directory>`. The destination must not exist. The script checks a 12 GiB free-space threshold before starting, but cannot predict the size of a growing source: monitor free space throughout. It writes the manifest only on successful completion; `.partial` files or a directory without a manifest indicate an incomplete capture. Archive metadata may include private keys and credentials. Do not run this into a public repository or shared unencrypted storage.

Run `python scripts/migration/backup_verify.py <snapshot-directory>` to check hashes, read all volume archive contents, and restore the two application databases into a disposable PostgreSQL 15 container with no networking or published ports. This restores without ownership or privileges and does not test global roles, application login, n8n credential decryption, Redis recovery, or S3 object-level MinIO recovery. It also compares table row counts to the current live databases, which can legitimately change between snapshot and comparison. The script removes its disposable database container after the test.

On this host the completed snapshot contained 14 artifacts (approximately 114 MB). Hashes and archive reads passed. The isolated restore produced 31 public tables in `sphereplatform` and 22 in `n8n`; comparing row counts to the live instance found one differing `sphereplatform` table (two distinct count entries) and no differing n8n entries. Live MinIO contained 13 underlying files compared with 11 in the archive; the two added live paths were internal `.minio.sys` files. No service was stopped; the result is point-in-time evidence, not a final cutover snapshot.

The separate `selected-local` store contains seven selected trees: `agent-config`, `updates`, `remote`, `apk`, `motor-ph011-20261023`, and both `host-repair-20261006T150602` and `host-repair-20261011T121248Z-ec3fe5cb`. It includes the two historical `4-debug.keystore` files and GGUF files under `motor-ph011-20261023/{qwen-small,qwen-2b}`; their presence does not establish which signing key is used in production. Its manifest maps each original relative path to a content-addressed blob. `python scripts/migration/backup_verify_selected.py <selected-local>` read and verified 5,738 unique blobs for 5,991 paths, with no copy errors. It does not cover all local route recordings, SQLite databases, other bind mounts, external VPN credentials, images or inactive Docker volumes. Preserve those separately; do not assume Git contains ignored data.

To reconstruct the selected files, run `python scripts/migration/restore_selected.py <selected-local> <new-private-directory>`. This reads and verifies every blob before creating the destination, then restores the original paths beneath it. It refuses an existing destination; file permissions and Windows ACLs from the source are not preserved. A small synthetic restore and existing-destination refusal were tested.

The separate `routes-essential` store contains reconstruction-job input trees and small metadata files. The capture includes all 14 `input/video.h264` files, totalling 474,357,845 bytes, and 526 file paths overall; all 456 unique blobs were read back and SHA-256 verified. It excluded 4,486 other files totalling 7,259,294,186 bytes, including prepared images and databases, fragments and geometry outputs. These are often derived, but their complete reproducibility has not been verified. Keep them on the secondary drive if their history matters. `python scripts/migration/backup_routes_essential.py <new-private-directory>` can create this profile directly on a destination drive; use `backup_verify_selected.py` to verify and `restore_selected.py` to reconstruct it. The source files can change while the services are active, so this is not a synchronized application snapshot.

The separate `routes-sqlite` store contains all 20 SQLite candidates found under `reconstruction-jobs`, copied with the SQLite backup API; each passed `quick_check` and a later hash/size readback. Their combined backup size is 651,063,296 bytes. `python scripts/migration/restore_routes_sqlite.py <routes-sqlite> <new-private-directory>` checks the manifest hashes before reconstructing paths. These databases are separate point-in-time snapshots. A broader earlier attempt to copy SQLite from all of `.local-pilot` was interrupted after a busy database stalled. Its 186 incomplete files were removed only after all 62 corresponding source paths were identified and confirmed to exist; the mapping and deletion receipt are in `local-inventory`. They were not verified backups, and the other source databases remain outside this snapshot.

For a smaller file collection, `python scripts/migration/backup_selected_files.py <new-private-directory> --profile essential` selects agent configuration, remote files, the two historical host-repair directories, the release manifest and the latest APK for each platform/flavor. Each selected APK is checked against its release SHA-256. The captured profile contains 452 paths and 142,744,590 bytes of unique blobs. Older APKs are intentionally omitted even though the saved release manifest can refer to them; the full `selected-local` collection is optional. A new destination outside the repository can be used on an independent SSD. On this host the scripts reserve 12 GiB on the source drive and 1 GiB on a different destination drive; monitor space during long operations.

`python scripts/migration/backup_verify_minio.py <data-snapshot>` restores the archived MinIO filesystem into a temporary volume and a container with no network or published ports, then compares the S3 listing and SHA-256 of common objects to the live endpoint. On this host the live and restored API each listed **zero buckets and zero objects**; no object content hash was exercised. The temporary container and volume were removed. This test requires `boto3`, the original running local MinIO endpoint, and the captured credentials.

For a later isolated import, install Docker and have local `postgres:15-alpine` and `alpine:latest` images available. Create a private UTF-8 file containing a new PostgreSQL password and keep it safe; the importer does not print or save the password. For example:

```powershell
python scripts/migration/restore_data.py <data-snapshot> --project migration-recovery-20261102 --database sphereplatform --database n8n --volume minio_data --volume n8n_data --pg-password-file <private-password-file>
```

All selected hashes and archives are validated before volume creation. The `migration-` prefix is required, and the command refuses any already existing target volume. It creates named volumes such as `migration-recovery-20261102-postgres` and `migration-recovery-20261102-minio-data`; it exposes no ports and removes the temporary database container afterwards. On failure, created volumes are retained for inspection and must be treated as incomplete. A rehearsal importing n8n and MinIO succeeded; repeating it refused to overwrite the existing target. This is an isolated data import, not a turnkey application restore: ownership and grants are intentionally omitted, the globals SQL is not applied automatically, and n8n requires its original encryption key from the sensitive container metadata. Restore appropriate roles and privileges and configure a separate application deployment before use. Do not point a fresh live stack at these volumes until the database, credentials, and services have been verified.

For a Compose-compatible isolated target, add `--compose-volumes --preserve-roles` to the command. This uses `<project>_<volume>` names with Compose project and volume labels, verifies and applies the captured globals, then restores each application database with its ownership and privileges. Both application databases and the MinIO volume were successfully imported this way. The integrated installer subsequently started an isolated source-built application with the original keys; old-password login and catalog/script comparisons passed, documented in [RESTORE-API-OBSERVATION.json](RESTORE-API-OBSERVATION.json). The password file sets the new PostgreSQL bootstrap superuser password, while the captured globals restore the original application roles and their password hashes. The original n8n encryption key must still be supplied separately before starting n8n; the isolated application rehearsal intentionally did not start n8n.

Before reinstall: copy to independent encrypted storage, verify hashes there, perform an isolated restore including required roles, credentials, n8n decryption and MinIO objects, and obtain a final coordinated application-consistent backup after writes have been stopped or safely quiesced. Keep source data until the restored application and its data have been checked. Never restore the live volume archives directly over the existing production volumes.
