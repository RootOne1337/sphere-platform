# Интеграция n8n: состояние исходников и ограничения

Этот документ описывает проверенные исходники репозитория, а не приёмку
развёрнутой интеграции. **Текущие узлы `n8n-nodes` нельзя считать совместимыми
с текущими backend-маршрутами без доработки и отдельной проверки.** Не включайте
автоматизацию, влияющую на устройства, исходя только из наличия узлов или webhook.
Реальные n8n, backend и устройства при этой сверке не запускались.

## Учётные данные и транспорт

Пакет объявляет три узла и тип учётных данных `Sphere Platform API`. Форма
требует `Server URL` (по умолчанию `http://backend:8000`), `API Key` и
`Organization ID`. Общий HTTP-клиент добавляет к URL `/api/v1` и отправляет
`X-API-Key` и `X-Org-ID`. Это описание клиента, а не подтверждённый способ входа:
исследованные endpoints устройств, задач и реестра webhook используют
`get_current_user` с пользовательским Bearer access token; для устройств
требуется также `device:read`, создания задачи — `script:execute`, чтения обычной
задачи — `script:read`. Заголовки узлов сами по себе не удовлетворяют этой
зависимости при обычной авторизации. `X-Org-ID` не заменяет организацию из
проверенного пользователя. Не включайте обход авторизации ради интеграции.

URL и имя ключа в форме являются настройками клиента; не публикуйте ключи,
Bearer-токены, webhook URL или секреты в workflow и логах. URL документации
`docs.sphere.local` указан в метаданных пакета, но доступность этого адреса не
проверялась. Совместимость установленной версии n8n, сетевой адрес и сборка
пакета не проверялись.

## Device Pool

В форме есть Get All Devices, Get by Tags, Get Online Only и Get by Group,
лимит и два режима выдачи: отдельный item на устройство или один item с массивом
и count. Пустые tags/group для соответствующей операции вызывают ошибку узла;
пустой результат в режиме отдельных items даёт пустой output.

Узел делает один `GET /devices` с параметром `limit`, без обхода страниц;
backend принимает `per_page` и по умолчанию возвращает первую страницу из 50.
Передаваемый узлом `tags` не входит в параметры этого обработчика; поиск по
тегам таким способом не подтверждён. Group ID соответствует `group_id`, но
зависит от права и принадлежности организации. Пункт Online передаёт `status=online`
для сохранённого DB-статуса, а не `live_status=online` из presence. Поэтому
названия Get All, Limit и Online не подтверждают полный или актуальный список.

## Execute Script

Узел последовательно обрабатывает входные items, передаёт `device_id`,
`script_id`, priority и необязательный `webhook_url` в `POST /tasks`. Он не
прикрепляет ожидаемый ID текущей версии: смена опубликованной версии между
выбором и запуском не ограждена этой формой. Права и доступность сценария и
устройства проверяет backend. Ошибка HTTP оборачивается в `NodeApiError`;
отсутствующие device/script ID вызывают ошибку операции.

При выключенном ожидании узел сразу выдаёт `queued` после ответа о создании;
это не подтверждает запуск на устройстве. При ожидании он опрашивает
`GET /tasks/{id}` с интервалом около двух секунд, по умолчанию до 120 секунд.
Только `completed` идёт в success, только `failed` — в failed; другие состояния,
включая отмену и серверный timeout, узел продолжает опрашивать до собственного
timeout. В failed он читает поле `error`, хотя обычный подробный ответ API
использует `error_message`, поэтому возможно общее `Unknown error`. Собственный
timeout и потеря ответа не отменяют задачу и не доказывают её исход: перед
повторным запуском необходимо найти созданную задачу и проверить её состояние.

Ввод `webhook_url` сохраняется задачей; отдельный task callback вызывается из
обработчика результата через `WebhookService`. На этом пути secret не передан,
поэтому не следует ожидать подпись `X-Sphere-Signature`. Само сохранение URL,
создание задачи и наличие примера suspend/resume не доказывают доставку,
успешное возобновление workflow или результат на устройстве.

## Event Trigger и реестр вебхуков

Узел показывает выбор типов событий, фильтр тегов и включённую по умолчанию
проверку HMAC. Его `create` отправляет `POST /webhooks`, а `delete` —
`DELETE /webhooks/{id}`. Реестр текущего backend находится под `/n8n/webhooks`;
схема создания требует `name`, `url` и непустой `events`, а узел `name` не
передаёт. Создание узлом нельзя считать подтверждённой регистрацией. `checkExists`
проверяет только локальный `webhookId`; удаление подавляет ошибки и удаляет ID
из локального состояния, поэтому не доказывает удаление серверной записи.

После успешного создания через соответствующий серверный API секрет выдаётся
один раз, а список возвращает только активные записи. Узел при создании
сохраняет ID, но не сохраняет секрет из ответа в настройку проверки. В исследованном
backend найдено определение `dispatch_event` реестра, но не найден его вызов из
других компонентов; регистрация и активный статус не доказывают доставку события.

Если серверный сервис реестра вызывается, он подписывает точные байты JSON
ключом из UTF-8 байтов hex-строки SHA-256 исходного секрета. Узел проверяет HMAC
непосредственно строкой из поля Webhook Secret и заново сериализует разобранный
body через `JSON.stringify`; это не общий контракт проверки исходных байтов и
не совместимо с введением выданного исходного секрета напрямую. При включённой
проверке отсутствие или несовпадение подписи даёт 401. Отключение проверки не
решает остальные несовместимости и не является подтверждением безопасной доставки.
Типы событий в выпадающем списке и фильтр тегов описывают запрос узла, а не
доказательство, что каждый тип реально публикуется.
