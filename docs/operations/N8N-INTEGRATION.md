# Интеграция n8n и доставка вебхуков

Узел Event Trigger зарегистрировал подписку и выполнил workflow на
изолированном n8n 1.32.0. Проверены доставка результата тестовой задачи,
подпись и история в Sphere. Device Pool, Execute Script и рабочий парк
имеют отдельные условия приёмки.

## Учётные данные и транспорт

Пакет объявляет три узла и учётные данные `Sphere Platform API`. Укажите
`Server URL` и действующий пользовательский `Access Token` для маршрутов
с Bearer-аутентификацией. Организация берётся из проверенной сессии.
Поля API Key и Organization ID сохранены для прежних вызовов, которые их
поддерживают. Каталог подписок и история требуют `webhook:read`, изменение
подписки и повтор доставки требуют `webhook:write`. Для устройств
требуется `device:read`, для создания задач `script:execute`, для чтения
задач `script:read`. Для регистрации или отключения из n8n нужен действующий
токен. Входящие подписанные события проверяются секретом узла.

URL и имя ключа в форме являются настройками клиента; не публикуйте ключи,
Bearer-токены, webhook URL или секреты в workflow и логах. URL документации
`docs.sphere.local` указан в метаданных пакета. Рабочий экземпляр n8n и
его сетевые настройки проверяются отдельно от стендового n8n 1.32.0.

## Device Pool

В форме есть Get All Devices, Get by Tags, Get Online Only и Get by Group,
лимит и два режима выдачи: отдельный item на устройство или один item с массивом
и count. Пустые tags/group для соответствующей операции вызывают ошибку узла;
пустой результат в режиме отдельных items даёт пустой output.

Узел делает один `GET /devices` с параметром `limit`, без обхода страниц;
backend принимает `per_page` и по умолчанию возвращает первую страницу из 50.
Передаваемый узлом `tags` не входит в параметры этого обработчика; поиск по
тегам таким способом не подтверждён. Group ID соответствует `group_id`, но
зависит от права и принадлежности организации. Пункт Online передаёт `status=online`
для сохранённого DB-статуса, а не `live_status=online` из presence. Поэтому
названия Get All, Limit и Online не подтверждают полный или актуальный список.

## Execute Script

Узел последовательно обрабатывает входные items, передаёт `device_id`,
`script_id`, priority и необязательный `webhook_url` в `POST /tasks`. Он не
прикрепляет ожидаемый ID текущей версии: смена опубликованной версии между
выбором и запуском не ограждена этой формой. Права и доступность сценария и
устройства проверяет backend. Ошибка HTTP оборачивается в `NodeApiError`;
отсутствующие device/script ID вызывают ошибку операции.

При выключенном ожидании узел сразу выдаёт `queued` после ответа о создании;
это не подтверждает запуск на устройстве. При ожидании он опрашивает
`GET /tasks/{id}` с интервалом около двух секунд, по умолчанию до 120 секунд.
Только `completed` идёт в success, только `failed` — в failed; другие состояния,
включая отмену и серверный timeout, узел продолжает опрашивать до собственного
timeout. В failed он читает поле `error`, хотя обычный подробный ответ API
использует `error_message`, поэтому возможно общее `Unknown error`. Собственный
timeout и потеря ответа не отменяют задачу и не доказывают её исход: перед
повторным запуском необходимо найти созданную задачу и проверить её состояние.

Ввод `webhook_url` сохраняется задачей. Callback ставится в PostgreSQL в
транзакции результата и сохраняет прежнее тело с `event_type: task.completed`,
полями задачи и `success`. Callback остаётся без подписи. Его HTTP-итог
доступен в истории, а возобновление workflow проверяется на стороне n8n.

## Event Trigger и реестр вебхуков

В узле выберите `task.completed`, `task.failed` или оба типа, при необходимости
укажите фильтр тегов. Для проверки подписи заполните Webhook Secret перед
активацией. Узел передаст секрет при создании через `POST /n8n/webhooks`
и при повторной проверке читает сохранённый ID подписки.
Подписка может быть активна в каталоге при выключенной
публикации или недопущенном origin. Настройки описаны в
[руководстве запуска](STARTUP.md#outbox-вебхуков).

Подписка получает JSON с `event`, `data`, `timestamp` и `delivery_id`.
`X-Sphere-Delivery` совпадает с ID в подписанном теле. `X-Sphere-Signature`
имеет вид `sha256=<hex>`. Ключ HMAC-SHA256 — UTF-8 байты hex-строки SHA-256
исходного секрета. Получатель проверяет исходные байты HTTP-запроса.
Узел n8n отклоняет несовпадение подписи и расхождение ID.
[Обработка исходного тела в n8n 1.32.0](https://github.com/n8n-io/n8n/blob/n8n%401.32.0/packages/nodes-base/nodes/Webhook/Webhook.node.ts).

## История, повторы и пределы

История показывает ID, источник, результат, HTTP-статус, причину и
время попыток. Для ожидающей записи показано время следующей попытки,
для отправляемой — срок аренды воркера. URL, тело запроса, подпись и
текст ответа получателя в историю API не входят.

При сетевом сбое, HTTP 429 и 5xx очередь повторяет отправку. Базовые паузы
составляют 5, 30 и 120 секунд, `Retry-After` для 429 ограничен 120 секундами.
Другие HTTP-отказы завершают текущую серию. Для подходящей завершённой
ошибки оператор может запустить одну дополнительную серию с тем же ID и
телом. В каждой серии до четырёх попыток. При потере ответа или остановке
воркера получатель мог уже обработать запрос. Дедуплицируйте действие по
ID в своей базе в одной транзакции с эффектом. HTTP 2xx подтверждает
приём HTTP, а результат n8n нужно проверить по выполнению workflow.

На организацию допускается до 32 активных подписок, 2000 ожидающих и
отправляемых записей, 10 000 записей истории и 64 МиБ сохранённых тел.
Предел одного тела 256 КиБ. При переполнении причины видны в истории.
Доставленные тела очищаются. Через 30 дней завершённая запись становится
доступна для фоновой очистки. При достижении лимита старейшие завершённые
записи могут удаляться раньше.
