## Реестр страниц и действий

| Страница | Действия в исходниках интерфейса | Права и ограничения |
| --- | --- | --- |
| `/scripts` | Поиск, фильтр активных/архивных, просмотр исходника и истории, создание, запуск, управление версиями | `script:read` для чтения, `script:write` для изменений, `script:execute` для запуска; архив и отсутствие опубликованной версии блокируют запуск из каталога. [Каталог](SCRIPT-CATALOG.md) |
| `/scripts/builder` | Редактор графа, параметры, проверка и сохранение, импорт/экспорт, лаборатория устройства | Маршрут требует `script:write`. Проверка структуры не подтверждает исполнение на Android. Запись, запуск и управление устройством имеют отдельные права и условия. [Studio](SCRIPT-STUDIO.md) |
| `/tasks` | Поиск, статус и сортировка истории, активная очередь и pipeline, открытие задания, история пакетов, результаты по волнам, повтор, запуск на всех online устройствах | Чтение задач — `script:read`, повтор и broadcast — `script:execute`; окончательную проверку выполняет API. Broadcast имеет область всей организации, не только видимые строки. |
| `/tasks/{id}` | Контекст и результат, отчёты шагов и журнал, отмена, остановка или повтор | Доступ зависит от организации и прав; варианты действий определяются статусом и свежим чтением. Принятие команды не означает завершение действия на устройстве. |
| `/orchestration` | Каталоги pipelines, запусков и расписаний, просмотр/правка определения, запуск, пауза/продолжение/отмена run, работа с расписаниями | Отдельные права `pipeline:read/write/execute` и `schedule:read/write`; доступность кнопки не заменяет серверную авторизацию. |
| `/pipeline-settings` | Чтение настроек и статуса, изменение полей и отдельных переключателей | API требует `pipeline:read` для чтения и `pipeline:write` для изменения. Включение функции не доказывает выполнение конкретного сценария. |

Матрица [RBAC](../../backend/core/rbac.py) разрешает `script:read`,
`pipeline:read` и `schedule:read` ролям `viewer`, `script_runner`,
`device_manager`, `org_admin`, `org_owner`, `super_admin`. Для
`script:execute` и `pipeline:execute` нужны те же роли, кроме `viewer`;
для `script:write`, `pipeline:write` и `schedule:write` — `device_manager`
или одна из трёх административных ролей. Это матрица исходников, а не проверка
прав конкретного пользователя: организацию, сессию и разрешение проверяет сервер.
Открытая страница или доступная кнопка не гарантируют право на действие.

## История и управление заданием

История `/tasks` запрашивается постранично, по 25 строк; поиск, фильтр статуса
и сортировка передаются серверу. Отдельно запрашиваются активные задачи и активные
pipeline. Показатель успешности считает `completed / (completed + failed + timeout)`;
очередь, активные и отменённые задания не включаются в этот знаменатель. При
ошибке загрузки пустой каталог и статистика не подтверждены.

В карточке задания при успешном свежем чтении:

- `queued` или `assigned` — **Отменить задание** (`DELETE /tasks/{id}`);
- `running` — **Остановить задание** (`POST /tasks/{id}/stop`);
- `completed`, `failed`, `cancelled`, `timeout` — **Повторить выполнение**,
  если известна исходная версия. Создаётся новое независимое задание с прежней
  версией и входами, а не перезапуск старой записи. API может вернуть 409,
  например при активном исходном задании, неизвестной версии или дубликате.

Эти три действия в карточке отправляются сразу, без отдельного диалога
подтверждения. На время чтения или отправки любого из них управление временно
недоступно; ошибка обновления задания оставляет прежний снимок и блокирует
команды до успешного чтения. Кнопка **Повторить загрузку задания** повторяет
только чтение. При начальной ошибке 401, 403 и 404 показываются разные сообщения;
другие ошибки загрузки не доказывают отсутствие задания. Сервер проверяет право
на действие, даже если кнопка видна.

Успешный повтор показывает квитанцию и, если ответ содержит ID, ссылку
**Открыть новое задание**. Новая запись сохраняет исходные версию, параметры,
приоритет и таймаут, но не наследует привязку к пакету и его результаты. Сам
факт создания не подтверждает выполнение на устройстве: откройте новую запись и
проверяйте её состояние. После успешной отправки кнопка повтора в старой карточке
может снова стать доступна; это не приглашение создавать ещё одно выполнение.

Принятая отмена может ожидать terminal result устройства; при ожидающей отмене
или таймауте дальнейшее управление блокируется. Отправка, 200/202 и живой прогресс
не равны подтверждённому финальному результату. На странице списка кнопка повтора
видна шире, чем на странице результата; API всё равно проверяет статус и версию.
После потери ответа сначала сверяйте историю и ID созданных задач: неизвестный
исход не является разрешением немедленно повторять физическое действие.

Страница результата периодически перечитывает задачу и отчёты шагов; для активной
работы отдельно доступны прогресс и журнал. Если обновление не удалось, старый
снимок может оставаться на экране с предупреждением; он не подтверждает новое
состояние. Отчёты, снимки и терминальный результат зависят от фактически
полученных данных и доступности хранилища.

Для активного задания страница показывает текущий прогресс и журнал; после
завершения — полученные отчёты шагов и доступный итоговый JSON. Показатель
успешных отчётов относится только к полученным отчётам и не подтверждает полноту
выполнения. При ошибке загрузки отчётов кнопка **Повторить загрузку отчётов**
повторяет чтение; пока обновление не удалось, прежний отчёт или данные из снимка
результата не подтверждают полноту. Прочерк в итоговых числах означает, что
значение не сообщено.

В завершённой карточке **Показать наблюдения** открывает ссылку
`/tasks/<id>?tab=logs`. Из Redis читается до 200 сообщений прогресса,
которые хранятся 10 минут от последнего сообщения. Экран отображает до 100
последних наблюдений, объединяя подряд идущие повторы одного узла, и время
последнего чтения. Для завершённого задания доступно ручное обновление.
Пустой источник и его недоступность отображаются отдельно. Последний
наблюдавшийся шаг сам по себе не подтверждает его успешное выполнение.

В истории активная очередь и активные pipeline загружаются отдельными запросами;
списки этих виджетов ограничены первыми десятью записями каждый. Снимки шагов
открываются по запросу; ошибка получения снимка не доказывает, что его не было.
Если запрос управления завершился потерей ответа или timeout, общий текст ошибки
страницы не доказывает, что команда не принята. Сначала перечитайте задание и
сверьте новые записи, прежде чем повторить действие, даже если кнопка снова активна.

## Пакетные запуски

Откройте **Задания → Пакетные запуски**. Каждая запись ведёт в пакет по
`/tasks?batch_id=<id>`. Пакет показывает сохранённую версию сценария, число
целей и допущенных волн, ближайшее время следующей волны и распределение целей
по состояниям. Фильтры ищут устройство или ID во всём пакете и сужают таблицу
по волне и состоянию. Ссылка появляется, когда дочернее задание записано в БД.
Из его карточки кнопка **К пакету** возвращает к тому же запуску.

Отказ до создания задачи отображается отдельно с кодом ответа. Статус
**Ожидает допуска** означает, что план содержит цель и очередь ещё не создала
задание. Для старых пакетов без сохранённого плана доступны фактические задания
этого пакета. Полнота списка целей в таком случае неизвестна.

Подтверждение **Остановить пакет** прекращает допуск следующих волн, отменяет
задачи в очереди и запрашивает остановку назначенных задач. Уже выполняющиеся
задачи могут завершиться. Итог каждой цели виден в таблице. До конечной
квитанции назначенной задачи отображается ожидание результата.

## Broadcast на все online устройства

Кнопка **Запустить на парке** открывает поиск сценария, выбор версии из каталога,
размера волны, задержки и приоритета. Запрос передаёт ожидаемый ID текущей
версии. Если версия сменилась, сервер отклоняет запуск. При приёме сервер
выбирает активные устройства организации со свежим `online` в Redis. Занятые
устройства исключены. Показанное в диалоге число может измениться до обработки
запроса. Если Redis недоступен, API отвечает `503`.

`POST /batches/broadcast` требует `script:execute`. Ответ `202` содержит
ID принятого пакета и число выбранных целей. Открывшийся пакет показывает,
какие задания созданы и что подтвердили устройства. При неизвестном результате
запроса откройте историю пакетов и проверьте, была ли создана запись.

Размер волны в форме 1–100, задержка 0–60000 мс. Нулевая задержка сохраняется.
Сервер по умолчанию добавляет случайный разброс до 1000 мс между волнами.
Приоритет 1 выше 10 при выборе из очереди одного устройства.

## Pipeline и расписания

На `/orchestration` вкладки разделяют определения, запуски и расписания. Серверный
фильтр применяется к каталогу, текстовый поиск — только к текущей странице.
Статистика запусков и активных расписаний рассчитывается по загруженной странице;
она не является общим счётчиком всего парка. Ошибка загрузки каталога не означает,
что записей нет. На странице запрашивается до 100 записей каждого каталога;
доля завершённых — число `completed` среди всех запусков загруженной страницы,
включая ещё активные и отменённые, а не доля среди только завершившихся.

Запуск pipeline предлагает выбрать устройства и JSON входов: одно устройство
использует отдельный run endpoint, несколько — batch endpoint. Оба запроса
проверяют версию и время изменения определения из диалога. При конфликте
откройте обновлённое определение и подтвердите запуск заново. Квитанция
показывает точный ID и версию, а ссылка открывает список запусков с фильтром
по этому ID. Фактическое выполнение видно по состояниям отдельных запусков.
Для активного run доступны пауза
и отмена; для paused — продолжение и отмена. При отмене может потребоваться
дождаться завершения дочерней работы. Настройка и условная запись определения
описаны отдельно в [Pipeline definitions](PIPELINE-DEFINITIONS.md).

**Важная особенность формы «Новый Pipeline»:** если открыть выбор устройств
через «Создать и запустить» и выбрать устройства, последующая кнопка «Создать
Pipeline» скрывает выбор, но не очищает его. После создания интерфейс может
отправить запуск на ранее выбранные устройства и через эту кнопку. Закрытие
диалога через «Отмена» само по себе тоже не сбрасывает выбор. Для создания без
запуска сначала откройте выбор устройств и явно снимите все отметки. Создание и
запуск — отдельные запросы: ошибка второго не отменяет уже созданный pipeline.
При потере ответа проверьте определения и runs до повторной отправки.

Для нового определения форма требует непустое имя и хотя бы один шаг с ID и
именем; параметры шага разбираются как JSON при отправке. Эти условия не
подтверждают корректность определения или успешность выполнения. Диалог запуска
требует устройства и разбирает входные параметры как JSON при отправке; ошибка
JSON не является подтверждённым запуском. В paused run интерфейс блокирует
продолжение при ожидающей отмене, фазе `unknown` или непустом поле lease; при
неизвестном результате сначала выясните исход шага. Сервер дополнительно
проверяет состояние операции.

Кнопки паузы и отмены также показаны для `queued`, однако сервер принимает
паузу только для `running` или `waiting` без запроса отмены. Ошибка паузы не
доказывает, что run остановлен: перечитайте его статус. Отмена и пауза не имеют
отдельного подтверждения в этой таблице. При потере ответа проверьте run и его
дочернюю работу до повторного действия.

Схема определения допускает от 1 до 100 шагов с уникальными ID, существующими
ссылками переходов и параметрами-объектами; timeout шага — 1000–3600000 мс,
`retries` шага — 0–10. Разбор JSON в форме не заменяет серверную проверку.
В исследованном recovery коде подтверждён повтор шага по его `retries` для
результата `failure`; при неподтверждённом эффекте требуется разбор, а не
автоматический повтор. Поле общего `max_retries` сохраняется, но его применение
для перезапуска pipeline в просмотренном backend не найдено. Не рассчитывайте
на заданное число повторов всего pipeline без отдельного подтверждения.

Вкладка расписаний предоставляет создание, редактирование, включение/выключение,
принудительное срабатывание, историю и удаление/деактивацию. В форме создания
выбираются сценарий или pipeline, устройства, cron, интервал или одноразовое
время, часовой пояс CRON и политика конфликта. **Форма отправляет новое
расписание активным**. Одноразовое время редактируется в UTC. Если значение
осталось прежним, форма передаёт исходное значение с его смещением и точностью. Для CRON
сервер проверяет пять полей и IANA-зону. API удаления деактивирует расписание
и сохраняет историю. Ранее созданная работа остаётся в своём жизненном цикле.

Следующий слот CRON показан в UTC и в выбранной зоне со смещением.
Весной отсутствующее местное время пропускается. Осенью повторяющееся
местное время используется один раз, при первом наступлении. Интервалы
измеряются в секундах. Одноразовый слот хранится как абсолютный момент.
Уже сохранённый при обновлении слот обрабатывается в прежнее время.

После паузы воркер обрабатывает один ожидающий слот. Если периодическое
расписание остаётся активным, остальные уже наступившие слоты сводятся
к одной записи пропуска, а следующее время переходит за момент обработки.
При закрытом окне или исчерпанном лимите сохраняется причина пропуска
ожидающего слота и расписание завершается.

`fire-now` ставит активное расписание на ближайший опрос воркера. Выключенная
запись, закрытое окно активности и исчерпанный лимит дают HTTP 409. Успех
запроса означает, что команда принята. В истории плановое время взято из
`next_fire_at`, фактическое отражает обработку воркером. Пропуск сообщает
причину, а созданный запуск ведёт к пакету. Для видимых записей API читает
исходы дочерних задач и пайплайнов, включая завершение без успеха.

Веб хранит идентификатор неподтверждённого ручного запроса в текущей вкладке,
если браузер разрешает `sessionStorage`.
В течение 24 часов повтор с тем же заголовком `Idempotency-Key` возвращает
время первоначального слота даже после его обработки и выключения одноразового
расписания. Новый ключ означает новый запрос. При истечении срока интерфейс
предлагает сверить историю перед новой попыткой. Если правка времени или
выключение расписания вытеснили принятый слот до обработки, в истории
появляется пропуск с причиной. По одному слоту сохраняется одна запись.

Веб передаёт значение `updated_at` просмотренного расписания как
`expected_updated_at` при правке, переключении, выключении и первом ручном
запросе. Конфликт возвращает HTTP 409. Для правки нужно открыть обновлённую
запись и сверить изменения. Повтор уже принятого ручного запроса сохраняет
силу после изменения версии. Клиенты прежнего API могут опустить проверку
версии и сохранить свой порядок вызовов.

При создании нужно выбрать хотя бы одно устройство: пустой выбор в этой форме
не обозначает весь парк. Диалог истории расписания загружает записи отдельно;
ошибка загрузки не означает отсутствие запусков. Удаление после подтверждения
деактивирует запись и убирает следующее время срабатывания, но не доказывает
остановку уже запущенной работы. После неизвестного исхода создания, изменения,
переключения или `fire-now` перечитайте расписание и историю до повтора команды.

Снятие всех выбранных устройств при редактировании отправляет пустой список.
Прежняя группа или теги продолжают определять цели, если были заданы. Без целей
воркер запишет пропуск. Для интервала форма и схема принимают целое число от
60 до 86400 секунд. Архивные сценарии и выключенные пайплайны дают пропуск
без расхода лимита запусков.

## Прежние настройки оркестрации

`/pipeline-settings` отображает настройки организации и счётчики статуса;
кнопка обновления перечитывает оба источника. И `GET /pipeline-settings`, и
`GET /pipeline-settings/status` вызывают `get_or_create` и commit: это не
гарантированно read-only операции для организации без записи настроек.
Учитывайте это при аудитах.

Карточки активных регистраций и фарм-сессий считают прежние задачи со статусом
`queued`, `assigned` или `running`. Новые задачи учитываются по роли
«регистрация» или «фарм», исторические записи без роли учитываются по ID
сценария. Сводка исключает задачи, аккаунты и устройства профилей организации.
Она показывает состояние записей в БД. Для прежней автоматизации требуются
общий переключатель `orchestration_enabled`, переключатель операции и её сценарий.

Поля формы сохраняются частичным PATCH. Отдельные переключатели orchestration,
scheduler, registration и farming отправляют собственные изменения сразу,
без ожидания общей кнопки сохранения. При ошибке обновления старый снимок и
локальные правки могут оставаться видимыми, но запись блокируется до успешного
чтения. Если редактируемое поле изменилось на сервере, интерфейс предлагает
принять серверные значения или оставить свои правки. Эта клиентская проверка
конфликта не является доказательством серверного compare-and-swap для PATCH.

Переключатели генерации ника, обнаружения блокировок и автозамены относятся к
локальной форме и сохраняются общей кнопкой вместе с другими изменёнными
полями. Пустые значения сценария регистрации, сценария фарма и примечания
отправляются как `null`. Селекторы сценариев запрашивают первую страницу до
200 записей; отсутствие варианта или пустой список при ошибке не доказывают,
что сценария нет. Возможность записи в форме зависит также от состояния
загрузки и локального конфликта, но не является проверкой права `pipeline:write`.
После timeout или потери ответа перечитайте серверное состояние и сопоставьте
правки: оставшийся черновик и доступная кнопка сохранения не доказывают, что
предыдущий запрос не применился.

В серверной схеме ограничены: параллельные регистрации 1–100, их timeout
60–7200 секунд; параллельный фарм 1–500, длительность сессии 300–86400 секунд;
целевой уровень 1–100 и пауза между сессиями 0–1440 минут. Шаблон ника имеет
длину 3–100 символов. Сервер проверяет PATCH; видимые поля и их числовые границы
не подтверждают допустимость или применение всех значений.

## Автоматизация по приложениям

В `/pipeline-settings` откройте «Автоматизация по приложениям» и выберите профиль организации. У регистрации и фарма отдельные переключатели, сценарии и лимиты. Поиск сценариев постраничный. Сценарий должен быть активным и иметь опубликованную версию. При допуске новой задачи сервер фиксирует текущую версию сценария. Снятие сценария в форме одновременно выключает соответствующий режим.

Запуск требует Android-пакет профиля и устройства, привязанного к серверу этого профиля. Для подбора аккаунта должны совпадать ключ приложения и имя сервера из каталога. Переключатели профилей действуют независимо от общего переключателя прежней автоматизации. Для встроенной Black Russia остаются прежние настройки организации. Изменение профиля подтверждается повторным чтением и относится к будущим запускам. Сохранённый переключатель сам по себе не подтверждает запуск задачи. [Привязка устройства](DEVICE-CATALOG.md#приложение-и-сервер-устройства).

Для чтения политики нужно `pipeline:read`, для записи — `pipeline:write`, для выбора профиля и сценария — `account:read` и `script:read` соответственно. При конфликте версий перечитайте настройки и примените нужные изменения к новой версии. Перед сменой Android-пакета выключите регистрацию и фарм этого профиля.

Оркестратор добавляет допущенные задания в очередь PostgreSQL. Диспетчер
отправляет их после подтверждения присутствия устройства. Пара «профиль, сервер»
определяет пул аккаунтов. Сам сценарий задаёт, какое приложение открыть и к
какому серверу подключиться. Результат уже принятой задачи обрабатывается по
её сохранённой роли и назначению аккаунта, даже после смены сценария или
выключения операции. [Протокол проверки профилей](../audits/2026-11-14/APPLICATION-AUTOMATION-ISOLATION.md).

### Результат регистрации и фарма из Android-сценария

Сценарий может сохранить наблюдаемый уровень в контекст через `get_element_text`
с `save_to`, `lua` с `save_to` или `set_variable` с `from_node`. Проверку
блокировки можно сохранить из логического результата Lua или из отдельной
ветки сценария через `set_variable`. На достигнутом конечном узле `end` без
`on_success` укажите ключи контекста, которые должны попасть в результат.

```json
{
  "type": "end",
  "result_outputs": {
    "level": "observed_level",
    "ban_detected": "observed_ban"
  }
}
```

Поддерживаются целый уровень от 0 до 2147483647 и логический признак блокировки.
Строки из `set_variable` распознаются как десятичные цифры либо точные
`true` и `false`. Уровень передаётся при успешном выполнении. Признак
блокировки также передаётся из явно обработанной ветки ошибки, дошедшей до
конечного узла. Остальные данные контекста в этот результат не экспортируются.
Явное `ban_detected: true` помечает аккаунт как заблокированный даже при
успешном завершении графа регистрации. Уровень обновляет запись аккаунта в фарме.
У старых версий без `result_outputs` сохраняется прежний формат ответа.
