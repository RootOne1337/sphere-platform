## Серверный контракт

Источники правил: [router](../../backend/api/v1/users/router.py),
[RBAC](../../backend/core/rbac.py), [schemas](../../backend/schemas/auth.py).

- GET `/api/v1/users` разрешён org_admin, org_owner и super_admin. Сервер использует
  page/per_page; обычный администратор получает свою организацию, super_admin может
  получить пользователей других организаций.
- POST `/api/v1/users` создаёт пользователя в организации текущего администратора.
  Email проходит EmailStr, пароль — от8 до128 символов. Доступны семь серверных ролей.
- org_admin может назначать viewer/script_runner/device_manager/api_user, но не
  административную роль. org_owner — все роли кроме super_admin; super_admin — все.
- PUT `/api/v1/users/{UUID}/role` разрешён только org_owner/super_admin. Проверяются
  текущая и новая роли целевого пользователя. Последнего активного владельца нельзя
  понизить; сервер сериализует снятие прав владельца и отключение на организации.
- PATCH `/api/v1/users/{UUID}/deactivate` возвращает204. Нельзя отключить себя,
  неподконтрольную роль или последнего активного владельца. DELETE/reactivate и
  редактирование пароля через эту страницу отсутствуют: несуществующие API не изображаются.

UI ограничения помогают оператору; полномочия всегда проверяются сервером. Количество
владельцев на одной странице не используется как доказательство наличия второго владельца.

## Форма создания

Настоящий submit form работает с native required/email validation, проверкой длины
пароля в Unicode code points и допустимой роли. Пустые/ошибочные поля не отправляются.
422 связывается с email/password/role через `detail[].loc`, aria-invalid,
aria-describedby и фокус на первом поле. 409 duplicate email выделяет email; известный
403 «Cannot assign this role» — роль. Остальные отказы имеют отдельное общее сообщение.

Валидационные `input`, произвольные серверные payloads и пароль не отражаются в тексте
ошибки. Пароль хранится только в состоянии открытой формы; после подтверждения/закрытия
форма размонтируется. Автоматическое повторение mutation выключено даже если общий
QueryClient включает retries. Неопределённый сетевой результат требует чтения каталога
перед новой командой; это не доказательство, что сервер не исполнил запрос.

Успешный POST должен вернуть структурированный UserResponse с совпадающими email,
ролью и организацией, активным состоянием. Иначе форма остаётся открытой с сообщением
«результат не подтверждён». Она не создаёт новый предполагаемый ресурс по пустому ответу.

## Смена роли и отключение

Выбор другой роли открывает отдельное подтверждение: email, UUID, org UUID, исходная
и целевая роли. Таблица до подтверждения продолжает показывать прежнюю роль. Отключение
использует тот же адресный dialog вместо browser confirm. Собственное отключение
заблокировано; изменение собственных прав предупреждает о потере доступа.

Ошибка называет целевого пользователя и серверное ограничение. Last-owner400,
403/404/409/transport не изображаются успешными. PUT должен подтвердить тот же UUID,
org UUID и выбранную роль; PATCH — именно204. После подтверждения каталог перечитывается.
Собственная подтверждённая роль обновляет auth state и доступные действия.

На pending поля/Cancel заблокированы, Escape/outside click не сбрасывает команду;
single-flight ref закрывает повторный submit. При refetch исходный target сохраняется.
Если пользователь/роль/активность изменились или read failed, команда блокируется до
закрытия dialog и нового выбора. Это обнаружение изменения snapshot, не backend CAS/ETag.

## Владение состоянием и актуальность

Каталог использует org/user/session scope в query key, AbortSignal, page/per_page и
30-секундное согласование только в активной вкладке. Ответ страницы проверяется;
cached data при read error не предоставляет write controls. Новая сессия/роль
размонтирует старый editor/dialog. Позднее завершение старой команды не закрывает и
не помечает успешной форму нового оператора. Mutation success инвалидирует каталог.

Общая role-aware навигация всех разделов остаётся отдельным F39. Этот workflow не
является завершением всех permission UX, MFA onboarding или долговременной приёмки
безопасности учётных записей.

## Проверки и предел доказательства

[16 component regressions](../../frontend/__tests__/users/workflows.test.tsx) на source
4898577 дали16 assertion failures/0 runtime errors. После изменения проходят они и5
существующих hook cases:21 targeted. В hook fixtures заменены несуществующие роли
admin/operator и противоречивые ответы на реальные server roles/receipts; assertions
не удалены. Полный frontend:96 suites/777 tests, types и lint passed; прежние lint
warnings учитываются отдельно. Transport в этих тестах заменён; React Query и Radix
dialogs настоящие. JSDOM не доказывает размеры, scroll/focus geometry или smoothness
в настоящем браузере.

Installed SHA, server readback и CI записываются в отчёт текущей установки. Визуальная
приёмка Sphere остаётся OPEN_URL_POLICY_BLOCKED; обход browser URL denial не выполнялся.
Реальные пользовательские права/пароли для проверки не менялись. Серверные интеграционные
тесты используют синтетических пользователей и SQLite; PostgreSQL конкурентная
защита last-owner не объявляется принятой только по этим component/HTTP тестам.
