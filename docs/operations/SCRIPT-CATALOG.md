## Чтение каталога

Страница `/scripts` использует **`GET /api/v1/scripts/catalog`**.
Первый запрос списка получает метаданные текущих версий без тел DAG.
Сервис выбирает явные скалярные поля; чтение каталога не вычисляет хеш из JSONB,
не запускает backfill и не создаёт версий, заданий или команд Android.
Право чтения — `script:read`; запуск и запись проверяются отдельно.
Фильтрация организации применяется к строкам и общему количеству.

Параметры: `query`, `page >= 1`, `per_page=1..200`,
`state=active|archived|all`; значения по умолчанию — страница 1, размер 50, active.
Поиск серверный, по имени и описанию, с существующей семантикой `ILIKE` и `%`/`_`.
Порядок — `updated_at DESC, id ASC`; UI предлагает размеры 25/50/100.

Envelope содержит `catalog_schema: 1`, `items`, `total`, `page`, `per_page`, `pages`.
`total` относится ко всей выбранной серверной выборке; при `total=0` API даёт `pages=0`.
Пустая страница после конца сохраняет общее количество.
Строки страницы и count читаются одной SQL-командой из общего снимка.
Между запросами разных страниц offset-пагинация может сместиться после публикации.

Строка содержит ID сценария и организации, имя, описание, архивный признак,
даты создания/изменения, `current_version_id`, `node_count`, `current_version`.
Вложенная версия содержит только ID, `script_id`, номер, `dag_hash`, дату создания.
`dag`, история `versions`, notes, автор, код и параметры действий в эту схему не входят.
Опубликованная строка имеет lowercase SHA-256 из 64 hex-символов и count >= 0.
ID вложенной версии равен указателю и принадлежит этому сценарию и организации.
`node_count` считает все элементы сохранённого массива узлов, включая начало/конец.
Это размер источника, а не количество выполненных действий.
Без текущей версии указатель, объект версии и count одновременно равны `null`.
Неизвестное значение не заменяется нулём; ноль остаётся самостоятельным значением.

## Исходник, запуск и кэш интерфейса

**Посмотреть DAG** доступно только при известной опубликованной версии, включая архив.
Клик фиксирует выбранный ID и метаданные; исходник читается отдельным запросом
**`GET /api/v1/scripts/{script_id}/versions/{version_id}`**.
Ответ должен принадлежать выбранным сценарию и версии.
UI сравнивает номер, полный серверный хеш, дату версии и длину массива узлов
с зафиксированными метаданными; неподходящий ответ не показывается как подтверждённый DAG.
Проверка хеша здесь означает сравнение receipt с каталогом;
сервер версии вычисляет хеш своего сохранённого исходника существующим алгоритмом.
Отображение маскирует очевидные поля credentials; показанный текст отличается от
полного исходника, к которому относится хеш.
Новая публикация во время запроса не подменяет источник открытой панели.
Чтобы выбрать новую версию, закрыть панель и открыть её из обновлённой строки.
Без версии интерфейс явно сообщает об отсутствии опубликованного DAG.

Редактор по ID сценария по-прежнему читает актуальную серверную версию.
История, сравнение, архивирование и откат доступны через **История и управление**;
их порядок описан в [инструкции по версиям](SCRIPT-VERSIONS.md).
Запуск передаёт зафиксированный `expected_current_version_id`.
Серверная проверка состояния и условий допуска сохраняется; конфликт требует обновления.
Старая строка списка сама по себе не разрешает запуск или запись.

HTTP-ответ каталога имеет `Cache-Control: no-store`.
React Query использует отдельный ключ `['scripts', 'catalog', scope, params]`;
scope включает организацию, пользователя, роль и версию сессии.
Запрос получает AbortSignal; чужой или поздний ответ прежней сессии отклоняется.
Ручной refetch до подтверждённого пользователя и организации не отправляет GET.
Каталог имеет staleTime 30 секунд и gcTime 60 секунд для неиспользуемого кэша.
Кэш выбранного источника отделён от списка и включает scope, ID сценария,
receipt версии и count; source staleTime — Infinity, gcTime — 60 секунд.
Смена count требует нового подтверждения даже при прежних ID и хеше.
Это кэш текущего интерфейса, а не сохранение исходника в localStorage.

## Недоступность и совместимость

Если выбранной опубликованной строке не хватает корректной пары метаданных
или принадлежащей ей версии, API возвращает **503** с телом:

```json
{"detail":{"code":"script_catalog_metadata_unavailable"}}
```

UI показывает недоступность метаданных и предлагает ручной **Повторить**.
Ошибка чтения или несовместимая схема не изображается пустым успешным каталогом.
Нет автоматического перехода к старому полному списку или загрузке DAG для count.
На старом API новый маршрут может быть недоступен; требуется правильный порядок установки.
Проверка доступа, malformed receipt и сетевой отказ также имеют явный путь повторного чтения.

Старый **`GET /scripts`**, CRUD, detail и history сохраняют прежние ответы.
Существующее `include_dag=false` оставляет поле `dag: null` в version response.
Metadata-объект нового каталога не заменяет полный `ScriptVersion`.
Другие потребители legacy списка этим переключением страницы не мигрируются.

Локальные предпочтения сохраняются по организации и пользователю:
список/карточки, плотность, 25/50/100, описание, хеш, идентификаторы, дата создания.
Поиск, страница и state не сохраняются; DAG и версии в предпочтения не записываются.
При отказе записи localStorage настройки остаются в памяти, UI сообщает об этом.
Повреждённая или слишком длинная запись настроек возвращает defaults.

## Подготовка метаданных до переключения UI

1. Установить additive [миграцию](../../alembic/versions/20261006_script_catalog_metadata.py)
   и API/writers, заполняющие `dag_hash` + `node_count` из read-visible PostgreSQL DAG
   в одной транзакции с новой версией и текущим указателем.
   Миграция оставляет пару nullable для совместимости; сама она не выполняет backfill.
2. Проверить используемые writers. [Общий publisher](../../scripts/publish_script_source.py)
   создаёт новую версию с precondition; старые SQL-патчи DAG выведены из эксплуатации.
   In-place изменение источника существующей версии нарушает достоверность метаданных.
3. Для каждой включаемой организации выполнить tenant-explicit dry-run,
   затем apply и отдельный reconcile-проход по сохранённым источникам.
   Команды запускаются из корня установленного API с его конфигурацией БД;
   `ORG_UUID` заменить подтверждённым ID целевой организации.

```sh
python -m scripts.backfill_script_metadata --org-id ORG_UUID --max-versions 1000 --max-seconds 60
python -m scripts.backfill_script_metadata --org-id ORG_UUID --apply --max-versions 1000 --max-seconds 60
python -m scripts.backfill_script_metadata --org-id ORG_UUID --reconcile --max-versions 1000 --max-seconds 60
```

Обычный backfill читает только версии с отсутствующей парой; `--reconcile`
проверяет также заполненные пары. Без `--apply` оба режима только оценивают изменения.
После рассмотрения расхождений исправление производных полей выполняет
`--apply --reconcile`; содержимое DAG, ID/номер версии, указатели и даты сохраняются.
Maintenance читает один ограниченный источник за раз, с короткими транзакциями и tenant context.
По умолчанию предел одного источника — 8 MiB; это бюджет maintenance, не лимит каталога.

Сохранить JSON receipt: org, `scanned`, `would_update`, `updated`, `failed`, `failures`,
`after`, `stopped`, `readiness`. При budget-stop продолжить с `--after UUID`
из последнего receipt. При contested/query-stop курсор не пересекает непрочитанную строку.
Exit 2 может означать исчерпанный бюджет; сверить `stopped`, а не объявлять проход завершённым.
Ошибочные источники фиксируются по ID без вывода DAG; после исправления или пересмотра
бюджета повторить проход от начала, чтобы ранее пропущенный ID не остался за курсором.

Чистая готовность tenant требует нулевых `invalid_current_pointers`,
`current_metadata_missing`, `version_metadata_missing`, `catalog_ready=true`,
а также полного reconcile от начала с `stopped=complete`, `failed=0`, `would_update=0`.
При apply/reconcile с исправлениями подтвердить результат новым dry reconcile.
Поле `source_hashes_reconciled` в scalar readiness всегда false:
полнота пары сама по себе не является сертификатом равенства хеша исходнику.
Не подставлять count=0 и не очищать указатели ради успешного чтения каталога.
После чистых receipts проверить каталог tenant через API, затем переключить UI.
Зафиксировать реальную установку и результаты отдельно в документации доставки.

## Откат приложения и границы проверки

При откате **сначала вернуть UI**, использующий legacy список, **затем прежний API**.
Additive столбцы и backfill оставить: этот порядок **не включает Alembic downgrade**.
Старые writers могут снова создавать NULL-пару; перед повторным включением нового UI
заново проверить writers, completeness и reconcile для каждой организации.
Откат интерфейса не изменяет DAG, версии и уже созданные задания.
