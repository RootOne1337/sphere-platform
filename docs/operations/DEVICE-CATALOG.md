# Реестр устройств: пагинация и смысл live-статусов

**Срез:** 30 сентября 2026 г.<br />
**Область:** `GET /api/v1/devices` и страница Fleet Matrix.  
**Среда:** source PR #19; это описание контракта исходников, не подтверждение раскатки.

## Что получает браузер

Запрос поддерживает `page`, `per_page`, `search`, `group_id`, `location_id`, зарегистрированный тип `type`, прежний DB-фильтр `status` и новый `live_status` (`online`, `busy`, `connecting`, `offline`, `attention`). Fleet Matrix передаёт по умолчанию страницу из 100 строк и обновляет её каждые 30 секунд. Пользователь может выбрать 50, 100 или 200 строк. Выбор действий ограничен текущей страницей; при смене страницы или фильтра старое выделение сбрасывается.

Фильтры поиска, группы и локации применяются на сервере до пагинации. Поиск проверяет имя, serial, модель и полное UUID устройства. `total` — число записей после всех фильтров, включая `live_status`; `pages` рассчитан из этого `total`. `scope_total` — размер области до применения `live_status`.

`status_counts` относится ко всей области поиска/группы/локации и DB-фильтра `status`, до применения `live_status`, а не только к текущей странице. `online` включает `busy`; `busy` — подмножество `online`. `issues` включает `error`, `maintenance` и `unknown`. `as_of` отмечает UTC-время после чтения live-состояний, `presence_available` говорит, удалось ли использовать Redis-кэш присутствия.

## Откуда берётся состояние

Для всех записей области backend сначала читает небольшой DB-проекционный список `id + last_status`, затем выполняет один Redis `MGET`. Из Redis выбираются статусы с ещё действующим TTL. Если Redis доступен, но ключ присутствия отсутствует, запись считается `offline`; известные DB-состояния `error` и `maintenance` сохраняются как проблемы. Если Redis не сконфигурирован или запрос `MGET` завершается ошибкой соединения/таймаутом, состояние показывается `unknown`, а не выдаётся устаревший DB-статус за живой heartbeat. `presence_available` становится `true` только после успешного чтения presence; UI отражает это и сохраняет доступность каталога.

Frontend приводит wire-поле API `per_page` к внутреннему `page_size`, которое используют существующие страницы. Это нормализует контракт в одном месте и не требует массово переписывать потребителей `useDevices`.

### Совместимость с прежним runtime

Read-only проверка pilot API 30 сентября показала ответ из `items`, `total`, `page`, `per_page`, `pages`: старый backend image `40357ca` не передаёт `status_counts`, `presence_available` и `as_of`. Отсутствующий `presence_available` теперь отображается как «состояние не сообщено API», отдельно от явного `false` («недоступен»). Отсутствие метаданных не доказывает отказ Redis. Без `status_counts` UI подписывает счётчики как расчёт по загруженной странице; они не объявляются глобальным агрегатом. При отказе первого запроса KPI остаются неизвестными (`—`), а не нулевыми. Отметка `as_of`, когда она есть, включает дату и время UTC.

Это адаптация отображения, не обновление backend: старый runtime может не поддерживать новый `live_status` filter. Для приёмки фильтров и глобальных счётчиков нужен совместимый backend, сверка SHA и отдельный тест. Снимок из 19 строк / 14 online / 5 offline относится только к моменту чтения, не доказывает длительный uptime.

Таким образом, `GET /devices` фильтрует live-состояние, а исторический query-параметр `status` сохранён для совместимости и по-прежнему фильтрует DB `last_status`. Новый Fleet Matrix использует `live_status`; новые клиенты должны делать то же самое, если им нужна текущая доступность.

## Границы производительности

Ответ и ORM-гидратация для браузера ограничены размером страницы: не пересылаются и не сериализуются тысячи полных моделей при каждом обновлении. Однако точные глобальные счётчики и фильтр по live-статусу пока требуют пройти все ID активной области и прочитать их Redis-статусы одним `MGET`. Серверная работа поэтому остаётся **O(N)** по размеру области. Это устраняет большой HTTP payload, но само по себе не доказывает готовность к десяткам тысяч устройств.

Перед масштабом 1 000+ следует измерить время SQL, MGET и сериализации на 100/1 000/10 000 синтетических записях. Если бюджет не выдержан, следующий архитектурный этап — атомарные status-index/агрегаты с обработкой disconnect/TTL-expiration, сверкой и восстановлением индекса; нельзя подменять точные live-счётчики DB `last_status` или неаутентифицированным Redis `SCAN`. До появления таких измерений UI не объявляет fleet масштаб протестированным.

## Проверка и rollout

Покрытие этого изменения включает порядок страниц, пересечение live-фильтра с полным статусным агрегатом, точное совпадение total, model search, поведение при недоступном Redis, ограниченный размер запроса со стороны Fleet Matrix и случай `busy` в видеосетке. Предрелизный acceptance дополнительно должен проверить location/group filters, удаление последней записи страницы, гонку изменения статуса между обновлениями, 1 000 synthetic IDs, network bytes и API latency.

Первое изменение контракта не выполняло deployment. Последующая локальная
сборка `3012` и её SHA записаны в [CURRENT-STATE](CURRENT-STATE.md); backend,
public frontend и APK rollout ею не обновлялись. Сверяйте frontend/backend по
[runbook provenance](BUILD-PROVENANCE.md); `running` не означает `passed`.

## Карточка и диагностические действия — 30 сентября

Нажатие имени открывает modal inspector; «Полная карточка» ведёт на
`/devices/{id}` с тем же источником данных. `GET /devices/{id}` обновляется каждые
15 s. Команды доступны только после свежего успешного ответа для online/busy;
сохранённый snapshot при ошибке не открывает управление. Uptime показывается
только при настоящем `connected_since`; старый backend `40357ca` его не сообщает.

Вкладки задач/событий ограничены 6 записями выбранного ID; видео раскрывает
diagnostics APK; сохранённые логи — ручной хвост 100 строк, доступный и при offline.
Viewer и shell — отдельные явные действия. Снимок сохраняет свежий browser PNG;
неработающий workstation screenshot endpoint не вызывается. Перезагрузка имеет
подтверждение, результат принятия не равен восстановлению Android.
Shell — последовательные HTTP команды, не постоянная SSH-сессия или автономное
полётное задание. Ошибка/неполный ответ прерывают последующие команды; закрытие
панели отменяет ожидание без доказательства отмены уже отправленного действия.
Все источники, ограничения, регрессии и runtime receipt описаны в
[аудите инспектора](../audits/2026-09-30/WEB-DEVICE-INSPECTOR.md).
