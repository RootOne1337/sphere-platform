# LDPlayer запущен, но APK не выходит в сеть

**13 сентября 2026 · AUD-99 · проверено на двух LDPlayer 9 / Android 9.**

Запущенное окно эмулятора не доказывает работу его сети. В инциденте второй
экземпляр имел внутренний IP и работающий DHCP, но его процесс `VBoxNetNAT.exe`
отсутствовал. После восстановления только этой сети оба APK подключились и
одновременно выполнили команды. Обновление APK не требовалось.

[Подробное доказательство](../audits/2026-09-05/LDPLAYER-NAT-INCIDENT.md) ·
[Стенд](LOCAL-PILOT.md) · [PC-agent](../pc-agent.md)

## Проверка и восстановление одного экземпляра

Используйте **VBoxManage из установки LDPlayer**, а не другой VirtualBox.
Команды ниже предназначены для текущего Windows-стенда и индекса `1`; для другой
станции сначала определите её фактические paths и index через `ldconsole list2`.

```powershell
python -m scripts.ldplayer_network --index 1 --vboxmanage 'C:/Program Files/ldplayer9box/VBoxManage.exe'
python -m scripts.ldplayer_network --index 1 --vboxmanage 'C:/Program Files/ldplayer9box/VBoxManage.exe' --repair
```

Первый вызов только диагностирует. Exit 0 означает наличие NAT-процесса выбранной
сети, 2 — его отсутствие, 1 — ошибка/несоответствие конфигурации. Это **не** проверка
DNS, HTTPS, доступности backend или авторизации APK. Эти границы явно отражены в JSON.

Второй вызов восстанавливает уже существующую сеть, только если NAT отсутствует:

1. Проверяет `leidian{index}`: running, первый интерфейс NAT network,
   `LdNatNetwork{index}`, кабель подключён.
2. Берёт общую OS/thread-блокировку ремонта этой установки LDPlayer. Выбирает
   NAT/DHCP по точному аргументу сети и пути executable. Несколько
   кандидатов или неподтверждённый путь означают отказ от изменений.
3. Если NAT уже работает — ничего не перезапускает. При отсутствии NAT сверяет
   VM/process state повторно; изменившийся DHCP требует новой диагностики.
4. Проверяет, что другие запущенные VM не используют выбранную сеть, включая
   вторичные интерфейсы. Если остался DHCP выбранной сети, проверяет его PID, creation time, executable,
   полную командную строку и отсутствие NAT непосредственно перед остановкой.
   Это устраняет наблюдавшееся `DHCP server already running` при старте NAT.
5. Запускает `natnetwork start` для выбранной сети и проверяет появление её процесса.

Утилита не создаёт сети, не меняет адреса, port forwarding, firewall, Docker,
APK credentials или файлы эмулятора. Она не перезапускает саму VM. Сеть с другим
именем или bridge mode требует отдельного разбора. Нельзя применять её к специально
переустроенной топологии, где несколько VM используют одну и ту же выбранную сеть.

## Обязательная проверка результата

После ремонта смотрите фактическое подключение устройства к Sphere и выполните
безопасную команду, например `echo SPHERE_NETWORK_OK`. Проверяйте оба устройства
одновременно и разные ответы/IDs: один статус online не является доказательством
правильной маршрутизации. Не удаляйте данные приложения ради повтора регистрации.

При сохранении ошибки разделяйте границы: процесс NAT → DNS/HTTPS из Android →
signed discovery → enrollment/auth → WebSocket → результат команды. Журналы
получайте по [контракту диагностики APK](../audits/2026-09-05/DEVICE-DIAGNOSTICS-SOURCE.md).

## Автоматическое восстановление на станции

[Watchdog](../../scripts/ldplayer_watchdog.py) выполняет одну проверку за запуск.
Он устанавливается на **Windows-станции с LDPlayer**, под тем же пользователем,
который запускает эмуляторы. Сервер, Docker, GitHub, PC-agent и его токены для
ремонта локального NAT не требуются. APK внутри VM не может запускать процессы хоста.

Сохраните локальную конфигурацию, используя фактические абсолютные пути станции:

```json
{
  "indices": [0, 1],
  "vboxmanage": "C:/Program Files/ldplayer9box/VBoxManage.exe",
  "state_path": "C:/Sphere/station-network/status.json"
}
```

`indices` — явный список разрешённых экземпляров (1–256 уникальных индексов).
Новые экземпляры сами в него не добавляются. Путь состояния должен быть отдельным
JSON-файлом в доступном для записи каталоге, вне установки LDPlayer. Запускайте из
корня Sphere; Python 3.12+, только стандартная библиотека для этого инструмента.

```powershell
python -m scripts.ldplayer_watchdog --config C:/Sphere/station-network/config.json --check-config
./scripts/Install-LDPlayerWatchdog.ps1 -ConfigPath C:/Sphere/station-network/config.json -PythonExecutable C:/Sphere/python/python.exe -TaskName Sphere-LDPlayer-workstation01
```

Первая команда только проверяет конфигурацию, состояние и чтение host inventory.
Установщик повторяет проверку и создаёт задачу текущего пользователя: скрытое окно,
Limited, AtLogon и раз в минуту, IgnoreNew, максимум 5 минут на запуск. Пароль не
сохраняется. Чужая задача с тем же именем/другим действием не перезаписывается.
Исполнение — напрямую через `pythonw.exe` рядом с указанным Python, без PowerShell
wrapper. Дочерние команды используют `CREATE_NO_WINDOW`. Наша прежняя задача
мигрирует при совпадении action/config и SID пользователя.
[Проверка отсутствия консоли](../audits/2026-09-05/WINDOWS-BACKGROUND-WINDOWS.md).

Политика ремонта:

- Здоровая станция: один запрос CIM на все процессы и один `list runningvms`.
  Не создаётся постоянный Python-процесс; у остановленной VM сеть не запускается.
- Отсутствие NAT подтверждается двумя последовательными проверками с интервалом
  не менее 30 s. После паузы более 180 s, ошибки наблюдения или возврата NAT
  подтверждение начинается заново. При минутном расписании обычная задержка
  обнаружения и подтверждения составляет около 60–120 s, плюс время ремонта/APK.
- Максимум один ремонт за цикл; попытки одного экземпляра разделены 300 s.
  Cooldown записывается **до** host mutation и переживает аварийный выход процесса.
  При нескольких отказах сначала выбирается экземпляр с самой старой попыткой.
- Manual/automatic repair используют общую блокировку установки. Другая задача
  не выполняет второй ремонт одновременно. Перед действием состояние VM и
  идентичность процессов проверяются заново. Здоровый NAT не перезапускается при
  ошибке DNS/интернета/серверного подключения.
- Повреждённое состояние, чужая область конфигурации или невозможность сохранить
  cooldown требуют устранения ошибки оператором. Не удаляйте state для обхода защиты.

## Как увидеть отказ самого watchdog

Смотрите `checked_at` (Unix UTC), `status`, `instances` и последние 50 `events` в
файле состояния. `nat_present`/`nat_restored` означают только наличие host process.
Для регистрации результата в Sphere всё ещё нужна настоящая команда APK.
`repairing` обозначает незавершённую попытку, `cooldown` — выдержку после неё,
`deferred` — ожидание очереди, `stopped` — VM выключена. Состояние старше трёх минут
требует проверки расписания; старый `ok` не доказывает работу текущего наблюдения.

```powershell
Get-ScheduledTaskInfo -TaskName Sphere-LDPlayer-workstation01
Get-Content C:/Sphere/station-network/status.json
```

Exit codes: 0 — все разрешённые запущенные VM имеют NAT; 2 — degraded/error inventory;
1 — ошибка конфигурации/диска; 3 — другой цикл удерживает блокировку. Если файла
нет или он не обновляется, проверьте `LastTaskResult`, пути и запуск вручную.
Для отключения только этого watchdog: `Disable-ScheduledTask -TaskName Sphere-LDPlayer-workstation01`.

## Границы приёмки

Причина первоначального завершения NAT-процесса пока не установлена. Автоматическое
восстановление не исправляет сбой интернет-провайдера, DNS, зависший живой NAT или
общий отказ хоста. Задача требует входа пользователя; reboot/logoff recovery не
приняты. На удалённой станции нужно установить этот компонент отдельно. Отправка
его свежего состояния в backend/UI через PC-agent ещё не реализована.

Один ремонт за минутный цикл выбран для текущего пилота с двумя экземплярами.
Одновременный отказ десятков сетей будет восстанавливаться постепенно: перед
массовым rollout нужны измерения и отдельная настройка ограниченного batch repair.
Физические телефоны этот Windows-компонент не используют.
