# Хранение полученных Android-журналов

Обновлено 14 ноября 2026, Asia/Yekaterinburg. Область: файлы upload `/logs/upload`,
а не Docker stdout, Logcat, PostgreSQL, Windows-диск или все события платформы.

## Просмотр и удаление через Web

На `/logs` выберите устройство. Страница читает уже полученные сервером журналы;
она не запрашивает новый Logcat или снимок у Android. **Обновить** выполняет
запрос вручную, **Автообновление** включает интервал 5 секунд. Поиск выполняется
на сервере по ограниченному хвосту, фильтр уровня применяется к загруженным
строкам. UI запрашивает до 1000 строк. По умолчанию область охватывает до трёх
последних файлов. Для любой области действуют лимиты 2 МиБ сканирования и
512 КиБ ответа. Отсутствие совпадения относится к проверенной области.
Для GET требуется `device:read` и доступ к активному устройству организации.

Выбор источника ищет по каталогу и показывает страницы по 100 устройств. При
отсутствии выбранного ID первая запись первой успешно загруженной страницы может
быть выбрана автоматически. Поиск или ошибка каталога не переключают уже выбранный
источник; фильтр уровня действует только на полученные строки. Автообновление по
умолчанию выключено, а смена источника открывает отдельный viewer.

Поиск по тексту выполняется сервером без учёта регистра и возвращает только
совпадения в пределах бюджета чтения. Изменение уровня (`V`, `D`, `I`, `W`,
`E`, `A`) фильтрует уже загруженный ответ в браузере; серверный поиск при этом
не расширяется. Для нераспознанной строки UI использует уровень `I`, а `F`
отображает как `A`. Числа «показано» и «загружено» относятся к полученному
ответу, не ко всему архиву.

Ограничитель пропускает строки длиннее 16 КиБ целиком, а не отдаёт их обрезки;
панель сообщает причины неполного чтения, когда сервер возвращает метаданные.
При отсутствии этих метаданных полнота не установлена. Если каталог файлов
слишком велик для безопасного перечисления или источник недоступен, API может
вернуть ошибку вместо пустого результата. Смена фильтра или обновление не меняют
и не удаляют журнал.

**Архив по дате** загружает сохранённые UTC-даты устройства через
`GET /api/v1/logs/{device_id}/dates`. Кнопка **Обновить даты** перечитывает
список вручную. Выберите день или откройте ссылку
`/logs?device_id=<UUID>&date=YYYY-MM-DD`. Поиск использует выбранный день,
а проверенный ответ подтверждает дату в `read.date`. Если дневной файл
отсутствует, экран сообщает об этом отдельно от пустого поиска. **Последние
журналы** возвращают исходную область. В архиве автообновление приостановлено.
Этот просмотр ограничен бюджетами чтения. CSV на `/audit` выгружает события
аудита.

При `503` по коду `log_read_busy` экран сообщает о перегрузке и учитывает
`Retry-After` перед ручным повтором. `log_source_unavailable` означает,
что источник сейчас нельзя прочитать. При наличии безопасного `X-Request-ID`
его можно передать для поиска запроса в серверной диагностике. При сбое
автообновление останавливается. Если ранее прошёл тот же запрос, видны его
строки и время успешного чтения. При отказе в доступе этот снимок скрывается.

**Очистить логи** открывает подтверждение удаления всех сохранённых файлов этого
устройства на сервере, а не только показанных или совпавших с фильтром строк;
действие необратимо. API требует `device:delete` и проверяет принадлежность
устройства. Кнопка также недоступна при загрузке, ошибке или отсутствии успешного
среза. Веб очищает отображение после `204`, а при открытом архиве перечитывает
список дат. Удаление использует общую с записью блокировку и сообщает об ошибке
хранилища. Новые upload от агента после очистки могут снова создать файлы.

Кнопка и диалог очистки в текущем Web-коде не скрываются по проверке
`device:delete`: право проверяется сервером при запросе. Отказ выводится в
диалоге, сохранённые строки не считаются удалёнными. Пока запрос выполняется,
подтверждение и отмена отключены, автообновление приостановлено.

[HTTP-обработчик](../../backend/api/v1/logs/router.py) и

## Путь и жизненный цикл

Full, production и local-pilot Compose задают `SPHERE_LOGS_DIR=/var/lib/sphere/device-logs`
и один project-scoped named volume `device_logs` на этот путь. Production image
создаёт каталог с владельцем UID1001 заранее: Docker копирует его permissions при
инициализации нового пустого тома. Метрики `/tmp/sphere-metrics` остаются отдельным
bounded tmpfs; OTA-том не меняется. Внешний путь не принимает HTTP-параметры.

Restart/recreate контейнера сохраняет том. `docker compose down -v`, удаление тома
и потеря host storage уничтожают историю; named volume не заменяет backup/restore.
Запуск backend вне этих Compose без `SPHERE_LOGS_DIR` сохраняет прежний временный
fallback `/tmp/sphere_device_logs`; это не production storage policy.

## Перенос существующего временного каталога

Добавление пустого mount не переносит старые файлы автоматически. Сначала проверить
актуальные image/container IDs, путь и отсутствие перекрывающего mount; подготовить
и проверить новую конфигурацию/образ, rollback и соседние контейнеры.

1. Graceful stop только backend: дождаться остановки всех writer workers.
2. Скопировать каталог из **остановленного** контейнера в приватный staging;
   проверить число файлов, byte budget, отсутствие symlinks и SHA256 каждого файла.
3. Сохранить этот staging как rollback archive. Не публиковать device IDs/содержимое.
4. Создать отдельный project-scoped том. Переносить только в подтверждённо пустой
   том, ограниченным helper без сети; установить UID1001 и сравнить все hashes.
5. Только после проверки заменить backend с новым mount. Не удалять staging/том.
6. Проверить ready/build, сохранность исходных byte prefixes, права non-root writer,
   authenticated GET и новую upload активность. Контроль количества online отдельный.

Если ошибка возникла до recreate, запустить прежний контейнер: его filesystem
сохранён. После recreate rollback использует прежний image **с новым постоянным
mount/path**, чтобы не потерять поступившие после переключения строки. Возвращение
к `/tmp` без обратного переноса не является безопасным rollback.

## Установленный upload budget

Backend `76596c39`, 6 октября 2026, 01:37 UTC+5: body принимается инкрементально,
не через полный `Request.body()` cache. Declared oversize отвергается до receive;
unknown/false length — на первом превышающем chunk. Предел принятого body 512 KiB,
общий ASGI intake deadline 60 s, четыре операции intake + writer на HTTP worker.
Mkdir/stat/rotation/append/cleanup выполняются в отдельном fixed executor.
Отмена HTTP во время writer не освобождает admission до фактического окончания I/O.
4 workers допускают до 16 загрузок, не общий лимит 4 на весь сервер.
400/408/413/503 не означают сохранение полного batch; successful upload остаётся 204.
Retry-After при busy/storage error — 1 s; успешный ответ не является fsync guarantee.
APK 480 KiB batch limit совместим, обновление APK для этого контракта не требуется.

## Квоты и сроки хранения

При установленном backend этой версии `DEVICE_LOG_DAILY_MAX_BYTES` (8 МиБ по
умолчанию) ограничивает файл устройства за UTC-день. `DEVICE_LOG_ORG_MAX_BYTES`
(2 ГиБ) ограничивает все сохранённые файлы организации. `DEVICE_LOG_STORAGE_MAX_BYTES`
(8 ГиБ по умолчанию) ограничивает логические байты файлов в управляемых каталогах.
Границы проверяются перед добавлением записи, включая служебный разделитель.
При превышении возвращается `507` с `Retry-After: 900`, сохранённый дневной файл
остаётся доступен. Новый [Android worker](../../android/app/src/main/kotlin/com/sphereplatform/agent/workers/LogUploadWorker.kt)
после `507` сохраняет паузу для текущего устройства и откладывает работу до её
окончания. Установленные старые APK могут продолжать перебор маршрутов и повторы.
Сохранённый crash worker удаляет только после принятого `2xx` и проверки снимка.

Файл и каталог устройства сохраняют прежние имена. Первая запись на новой
версии добавляет пустую метку с хешем владельца. Старые каталоги без метки
сопоставляются с текущей организацией через реестр, включая выведенные
устройства. Неатрибутированные байты учитываются в общей квоте. TTL
применяется к дневным журналам. При тайм-ауте проверки API возвращает 503
и сохраняет прежние байты.

Общий файловый lock сериализует append, sweep и ручное удаление у процессов,
использующих один путь и поддерживаемые блокировки. Фоновая задача при запущенном
backend и входящие загрузки используют одну отметку времени успешной очистки.
Каждый проход обрабатывает до 128 дневных файлов и пустых каталогов в сумме.
Удаляются дневные файлы старше 30 суток по `mtime`, пустые каталоги и их
служебные метки. Интервал между проходами составляет не менее минуты.
Бюджет относится к байтам приложения, фактический
расход тома дополнительно включает файловые метаданные, блоки и другие данные.

Метрики `sphere_device_log_upload_bytes_total`,
`sphere_device_log_retention_events_total` и `sphere_device_log_storage_lock_busy_total`
показывают записанные байты, истечение TTL, отказы и тайм-ауты блокировки.
`sphere_device_log_retention_bytes_total` показывает логические байты по
причинам `expired`, `daily_quota`, `org_quota` и `volume_quota`. Истечение считает логический
размер файлов, чьи пути успешно удалены. Фактически освободившееся место
зависит от открытых файлов, жёстких ссылок и файловой системы. Отказ считает
размер отклонённой записи с разделителем, в том числе при повторной попытке.
`sphere_device_log_filesystem_*` показывает доступность, размер и свободное место
файловой системы настроенного каталога. `sphere_device_log_retention_last_success_timestamp_seconds`
отражает последнюю завершённую проверку хранения. Prometheus собирает
счётчики квот и предупреждает, если измеренное свободное место устойчиво
снижается и прогноз показывает исчерпание в ближайшие шесть часов.
[Модель прогноза Prometheus](https://prometheus.io/docs/prometheus/latest/querying/functions/#predict_linear).

При восстановлении сохраните имена, файлы меток и исходные `mtime`. Для
архивов без метки сохраните соответствующий реестр устройств. Применяйте
один лимит ко всем репликам общего тома и обновляйте writer-процессы
согласованно. Ограничения старых и новых writer различаются во время
смешанного запуска. Приёмка выполнена на изолированном томе с двумя
процессами и восстановленной копией.
