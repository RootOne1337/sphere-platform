# Как поддерживать документацию при изменениях

[Каталог документации](../README.md) · [Актуальность документов](../DOCUMENTATION.md) · [Участие](../../CONTRIBUTING.md)

## Один источник — несколько указателей

Сначала определите, что действительно изменилось: пользовательский сценарий,
контракт, настройки, эксплуатация или только внутренняя реализация. Исправьте
основное руководство или контракт соответствующей области; остальные страницы
должны вести к нему, а не повторять большие фрагменты. README обновляют при
изменении назначения, входа или основных возможностей проекта, а не ради каждого
отчёта. Датированные аудиты и подписанные квитанции сохраняют свой исторический
смысл: не переписывайте их как новую проверку.

## Подсказки по изменённым файлам

Из корня репозитория Python 3.10+ и Git без дополнительных пакетов:

```bash
# Ветка относительно общего предка origin/main и HEAD; только коммиты.
python -m scripts.documentation_impact --base origin/main

# Только staged-файлы; до коммита это удобно для проверки состава изменений.
python -m scripts.documentation_impact --staged

# Изменения tracked-файлов относительно HEAD и неигнорируемые untracked-файлы.
python -m scripts.documentation_impact --worktree

# Проверка конкретного сценария, без Git diff. Пути относительно корня.
python -m scripts.documentation_impact --path backend/api/v1/devices/router.py --path 'frontend/app/(dashboard)/devices/page.tsx'

# Машиночитаемый отчёт вместо текстового вывода.
python -m scripts.documentation_impact --base origin/main --json
```

`--base` сравнивает merge-base выбранной ревизии с `HEAD`: локальные незакоммиченные
изменения туда не входят; проверьте их отдельно с `--worktree`. В этом режиме Git
показывает оба пути переименования; untracked учитываются только в `--worktree`,
игнорируемые файлы не включаются. Укажите имеющуюся локально базовую ветку;
при ошибке ревизии команда завершается с кодом 2. Команда работает только на чтение,
не запускает сервисы, не записывает отчёт и не обновляет документацию.

Результат группируется по областям, содержит затронутые пути, **кандидаты для
проверки**, соответствующие команды и пути без правила. Все совпавшие правила
показываются одновременно. Проверяйте неназванные зависимости вручную; путь без
правила не означает отсутствие влияния. Правило может подсказать лишний документ;
менять все подсказанные файлы необязательно. Карта `RULES` в
[scripts/documentation_impact.py](../../scripts/documentation_impact.py) вручную
поддерживается по мере развития структуры проекта. Для новых важных областей
добавляйте правило с проверкой реального сценария в
[tests/test_documentation_impact.py](../../tests/test_documentation_impact.py).

### Автоматическая подсказка в PR

Workflow [Documentation advisory](../../.github/workflows/documentation-advisory.yml)
работает только на `pull_request` и показывает кандидатов в GitHub Actions job
summary. Он не пишет комментарии в PR, не запрашивает права записи и не обновляет
документацию. Для GitHub API нужны `pull-requests: read`, для checkout —
`contents: read`; токен не сохраняется в Git config. В job `advisory` выполняются
скрипт и карта правил из checkout базового commit; отдельный checkout PR-head
используется там только для проверки его SHA. Отдельный job `tests` запускает
проверку реестра и набор `test_documentation*.py` из PR-head с правом `contents: read`
и без сохранения checkout-учётных данных; он не является выполнением кода из
доверенной базы. Успех этих проверок не является проверкой всех документов по смыслу. Новые правила подсказчика
начнут применяться после попадания в базовую ветку. При первом включении, если
скрипта ещё нет в base commit, summary явно сообщает о неполном результате.

API страницы по 100 файлов сравниваются с количеством из PR metadata. Head, base
и количество проверяются до и после чтения; несовпадение, недоступность API,
неполный ответ и достижение лимита GitHub **3000 файлов** дают неполный результат,
а не заключение об отсутствии влияния. Старые и новые имена переименований
учитываются отдельно. Файловая карта неполна; проверка SHA до и после не является
атомарным снимком API. Пути считаются недоверенными, а их вывод ограничен по
объёму; ограничение показа не означает ограничение анализа полученного списка.

Для PR, превысившего лимит, используйте локальный `--base` выше: сначала убедитесь,
что доступны нужные base, head и их общий предок. При отсутствии общего предка
нужно отдельно получить достаточную Git-историю; простое сравнение двух деревьев
не эквивалентно PR diff от общего предка. Точное влияние по смыслу в любом случае
оценивает автор или reviewer. Сетевая ошибка и отсутствие подсказки не отменяют
ручной проверки.

## Завершение изменения

1. Сверьте изменившееся поведение с кодом и соответствующими проверками. Для UI
   отдельно рассмотрите доступность действия по роли, ошибки, ограничения и
   изменение состояния. Не приписывайте mock или CI результат устройству.
2. Исправьте актуальный контракт, пользовательское руководство или runbook;
   проверьте навигационные ссылки. Если влияние отсутствует, укажите причину в PR.
3. При изменении HTTP-схемы выполните генератор в окружении с закреплёнными
   `backend/requirements.txt`: `python -m scripts.export_api_docs`, затем
   `python -m scripts.export_api_docs --check`. Генератор не проверяет WebSocket,
   авторизацию, фактическую успешность вызовов или установленную версию.
   `python -m unittest discover -s tests -p test_documentation_api_headings.py`
   дополнительно сопоставляет HTTP-заголовки ручного справочника с сохранённой
   схемой, но не подтверждает содержание разделов.
4. После добавления или удаления Markdown обновите инвентарь командой
   `python -m scripts.check_documentation_status --write-inventory`, затем
   `python -m scripts.check_documentation_status`. Инвентарь использует
   `git ls-files`: новые документы должны быть добавлены в индекс до генерации.
   Команда с `--write-inventory` **изменяет файл инвентаря**. Эта проверка не
   аттестует смысл каждого утверждения, anchors, внешние ссылки или runtime.
   Для Markdown с ролями `CURRENT_ENTRYPOINT`, `OPERATING_GUIDE`,
   `PROJECT_POLICY` и `ADR` scanner также требует, чтобы
   существующая цель локальной inline-ссылки присутствовала в Git index;
   staged additions учитываются, staged deletions — нет. Ссылка на каталог
   проходит, если в индексе есть сам путь (например, submodule) или хотя бы один
   путь внутри него; содержимое submodule при этом не проверяется. Генерируемый
   локальный файл не является исключением: его наличие на диске не делает его
   доступным читателю GitHub. Для намеренно локального артефакта используйте
   описание/inline code вместо навигационной ссылки или опубликуйте его в Git.
   Scanner читает текст документов из рабочей копии, а состав целей — из индекса;
   поэтому успешная проверка сама по себе не подтверждает содержимое будущего
   коммита. Проверяйте staged diff. Изображения, reference-style ссылки и anchors
   этой ограниченной проверкой не охвачены. Формы issue в YAML и документы других
   ролей, включая `DATED_EVIDENCE`, в этот охват не входят; например, `CODE_OF_CONDUCT.md` пока относится к
   `SUPPORTING_DOCUMENT`. Роли определяются классификатором, а не названием файла.
5. Укажите в PR обновлённые документы, выполненные проверки и оставшиеся ограничения.
   Запишите новое evidence отдельно, только если есть фактическое наблюдение.

Подсказчик не анализирует смысл diff, не доказывает полноту карты, актуальность
или production readiness и не заменяет review. Статус успешного завершения
обозначает успешное построение подсказок, а не отсутствие документационного долга.
