# 🛠️ Участие в Sphere

[Главная](README.md) · [Разработка](docs/development.md) · [Открытые работы](ROADMAP.md) · [Помощь](SUPPORT.md)

Наша ближайшая цель — стабильная работа реальных Android перед тестом на 32
эмуляторах. Приоритет — воспроизводимые ошибки исполнения, связи и восстановления,
затем скорость и удобство. Зелёная сборка не заменяет проверку поведения.

## До изменения

1. Проверьте [реестр Fleet32](docs/audits/2026-09-20/FLEET32-PREFLIGHT.md) и открытые
   [issues](https://github.com/RootOne1337/sphere-platform/issues), чтобы не повторять работу.
2. Для бага сохраните минимальное воспроизведение: версии, условия, ожидаемый и
   фактический результат. Для функции опишите пользовательский сценарий и критерий приёмки.
3. Работайте в отдельной ветке или fork. Не используйте чужую инфраструктуру,
   рабочую базу и действующий парк устройств для разрушающих тестов.

## Локальная среда

[Developer guide](docs/development.md) содержит зависимости и команды проверок.
[Startup](docs/operations/STARTUP.md#first-install) описывает новую установку;
[Local pilot](docs/operations/LOCAL-PILOT.md) — уже подготовленный отдельный стенд.
Не смешивайте их Compose project, env, volumes и порты.

## Один дефект → одно проверяемое изменение

- Сначала failing regression или сохранённое доказательство; затем минимальный fix
  и повтор исходного сценария. Тест должен проверять наблюдаемое поведение.
- Для reconnect, concurrency, RLS, cancellation и idempotency нужны соответствующие
  runtime/SQL/transport проверки. Mock не доказывает поведение реального устройства.
- Отдельно опишите миграцию, grants, порядок backend/APK rollout, совместимость и
  rollback. Не меняйте формат сохранённых данных без плана перехода.
- Обновите контракт, runbook и статус проблемы. Не заменяйте прежнее evidence новым.
- Для чистого оформления достаточно проверки ссылок, форм и отображения. Не добавляйте
  тесты, которые просто повторяют текст документа.

## Коммиты и pull requests

Коммиты атомарные, в формате Conventional Commits, с описанием на русском:

```text
fix(android): сохранять результат задания до подтверждения сервера
docs(operations): уточнить порядок восстановления после отказа Redis
```

Одна логическая причина изменения на коммит. Не включайте случайные форматирования,
сборки APK, `.env`, `.local-pilot`, raw logs или чужие незавершённые правки.
Перед push просмотрите `git diff --cached` и список файлов.

Целевая ветка по умолчанию — `main`; ветку интеграции выбирают явно в рамках задачи.
Работа текущего аудита находится в draft [PR #19](https://github.com/RootOne1337/sphere-platform/pull/19).
Незавершённую работу отмечайте Draft. Не объединяйте несколько независимых задач
только ради уменьшения числа PR.

В [PR template](.github/pull_request_template.md) укажите **что и зачем изменилось**,
before/after, команды и результаты проверок, rollout и оставшиеся ограничения.
Если проверка не запускалась — так и напишите. Ссылка на AUD/F32 дополняет описание,
но не заменяет его. CI должен относиться к финальному commit.

## Проверка и review

Точный набор автоматических проверок задают [workflows](.github/workflows/).
Владелец review указан в [CODEOWNERS](.github/CODEOWNERS); этот файл сам по себе
не устанавливает branch protection, число approvals или обязательные checks.
Фиксированных сроков review и поддержки проект не обещает.

При runtime изменении результат приёмки записывается отдельно от CI:
**source commit → установленная версия → сценарий → результат → residual risk**.
[Правила актуальности документов](docs/DOCUMENTATION.md).

Участие предполагает соблюдение [кодекса поведения](CODE_OF_CONDUCT.md).
Уязвимости отправляйте через [приватный канал](SECURITY.md), а обычные вопросы —
через [Support](SUPPORT.md). Изменения распространяются на условиях [MIT](LICENSE).
